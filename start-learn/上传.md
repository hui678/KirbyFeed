幂等是怎么实现的
一句话：不用去重表，也不用唯一索引；它靠 Redis 里的一个状态位，在写任何数据之前先判断“这片是不是已经传过”，传过就直接返回。

一、代码路径
chunk_handler.go:148-229 的顺序是有意安排的：

Go



session, err := h.getSession(c, req.UploadID)   // ① 从 Redis 取会话
if session.AccountID != accountID { 403 }       // ② 归属校验
if idx < 0 || idx >= session.TotalChunks { 400 } // ③ 序号合法性

if session.UploadedBits[req.ChunkIndex] {        // ④ 幂等判断 ← 关键
    c.JSON(200, gin.H{"chunk_index": req.ChunkIndex})
    return                                        //    直接返回，不读文件、不校验、不落盘
}

// ⑤ 到这里才开始真正处理
hash := md5(chunkFile); 不一致 → 400
os.Create(tmpDir/{idx}); io.Copy(...)            // ⑥ 写临时文件
session.UploadedBits[idx] = true                 // ⑦ 翻位
saveSession(session)                             // ⑧ 回写 Redis
第 ④ 步就 return 了，后面的 MD5 计算、建文件、写字节、回写 Redis 全部跳过。这就是“短路”（short-circuit）。

二、为什么这样就算幂等
幂等的定义：同一请求执行 1 次和执行 N 次，系统最终状态相同。这里成立是因为三个事实叠加：

1. 状态位只有一个终态

UploadedBits[idx] 是 bool，只有 false → true 一次跃迁。重复执行 = true 结果不变——这是集合写入的天然幂等。

2. 写文件是覆盖式，不是追加式

L211 用的是 os.Create(chunkPath)，它在打开时会 truncate 成 0 字节。所以即使某个分片文件已经存在，重写也是“从零重新写一遍”，不会出现第 2 片接在第 1 片后面的错误拼接。

3. 内容被 MD5 钉死

第 ⑤ 步校验通过才落盘，意味着“bit 为 true” ⇒ “磁盘上这份字节的 MD5 等于前端声明的 chunk_hash”。所以重试传同一片、内容一致，覆盖写出来的文件与原来逐字节相同。

用数学语言说：设操作 f 为“把第 idx 片写成内容 X 并置位”，因为 f 的输入被 MD5 锁定、输出位置固定、写入是 truncate 覆盖，所以 f(f(x)) = f(x)。这就是幂等。

三、幂等其实有三层，不止这一处
层级	位置	防的是什么
会话层	init L91-105	同一用户重复 init 同一个文件 → 靠 (accountID, fileHash) 命中旧 upload_id，不新建会话，也不产生两份磁盘文件
分片层	upload L169-172	同一分片重复上传 → bitset 判断短路
合并层	complete L295-313	缺片时拒绝合并；合并成功后 IsComplete 仍为 true，但 session 已被删除，第二次调用会因 404 失败，不会重复生成第二份 mp4
其中会话层的幂等更强：fileHash 是内容指纹，它是真正的天然幂等键（idempotency key）。同一文件无论调用多少次 init，都映射到同一个 upload_id。

四、这套实现的边界（重要，别当成强幂等）
有 4 个地方并不完美，值得知道：

1. Check-Then-Act 不是原子操作

第 ④ 步的“读”和第 ⑦ 步的“写”之间没有锁。如果前端同时发两个相同 chunk_index 的请求（比如超时重试 + 原请求还没返回），两个都可能读到 false，然后都去写文件、都置位。

后果有多大？因为两个请求的内容被 MD5 保证相同、写入位置相同、都是 truncate 覆盖，所以最终字节仍然正确。这是“结果幂等”而非“执行幂等”——过程重了，状态没坏。

2. 短路省的不是网络

c.ShouldBind(&req)（L142）对 multipart 的表单绑定会触发 ParseMultipartForm，也就是整个请求体在那之前已经被读进来了（大文件会被 Gin 落到临时文件）。所以第 ④ 步的短路省下的是 MD5 计算 + 一次磁盘写 + 一次 Redis 写，不是带宽。

这点常被误解成“命中就不传字节了”——实际字节已经到了服务端。

3. 崩溃窗口是安全的

顺序是“先写文件成功 → 再置位 → 再存 Redis”。如果在写文件和写 Redis 之间进程崩了：

文件在，bit 是 false → 下次重传，覆盖写，没问题。
反过来（先置位后写文件）才会坏事：bit 说“已传”，磁盘却没有 → complete 时 chunk i missing。
代码选择了“宁可重传，不可假完成”的顺序，这是正确的取舍。

4. complete 之后的重复请求不是幂等，是失败

session 在 L363-364 被删掉，所以第二次 complete 返回 404 而不是返回同样的 URL。

这是幂等性的常见缺口：真正的幂等应该“第二次调用返回第一次的结果”。如果要修，得把 upload_id → 最终 play_url 的结果也缓存一段时间（比如 1 小时），让重复 complete 返回旧结果。

五、如果要升级成强幂等，怎么改
按代价从小到大：

结果缓存：complete 成功后写 chunk_result:{uploadID} → play_url（TTL 1h）。重复 complete 先查这个 key，命中就直接返回。补上第 4 点缺口。
分片去重键换成内容 hash：临时文件名从 {chunkIndex} 改成 {chunk_hash}。这样即使并发重复传，两次请求写的是同一个路径且内容天然相同，把“结果幂等”变成“路径幂等”。
原子置位：改用 Redis 的 SETBIT（位图命令）或 HSETNX，把“判断 + 置位”合成一个原子命令，消除 Check-Then-Act 竞态。代价是 session 从单个 JSON 拆成 Hash 结构。
合并前二次校验：complete 时按文件名/大小核对每片长度，防止“bit 说齐了但文件被外部清掉”。
一句话总结
幂等的实现 = Redis bitset 当状态机 + 判断后短路 + truncate 覆盖写 + MD5 锁内容。 它保证“同一分片重传 N 次，最终文件和状态与传 1 次相同”，属于结果幂等，但 complete 阶段的重复调用目前不幂等（返回 404）。

两个问题分开答
问题一：bit 10 已为 true，是不是说明数据坏了
大概率不是。 这个状态位只记录“第 10 片在某个时刻已成功上传并通过 MD5 校验”，并不表示“这次请求是重复的或异常的”。

正常的 4 种来源，都会让服务端看到 index=10 时 bit 已经是 true：

场景	说明
乱序并发	前端 MAX_CONCURRENT = 3，3 个分片同时在传，9/10/11 谁先到不确定
自动重试	前端 MAX_RETRIES = 3，第一次请求其实成功了但响应超时，客户端又发一次
续传	刷新页面后重新 init，命中旧会话，返回 uploaded_chunks 含 10；前端按 pending 构造 跳过它。但跳过前已经先发出去的请求仍可能到达
请求重复	浏览器/代理层的重发、用户快速双击
所以 if UploadedBits[10] { return 200 } 的语义是**"这片的活已经干完了，不用再干"**，不是"检测到异常"。

真正算“数据有问题”的只有两种
① bit 为 true，但磁盘上的临时文件没了

这是唯一会真正卡死的状态不一致。触发原因：手动清理了 .run/uploads/tmp、容器重建没挂 volume、磁盘写满被截断、进程在“写完文件、回写 Redis”之间被杀（这个顺序其实是安全的，因为 Redis 后写）。

此时：

客户端重传 10 → 被 L169 短路，直接返回 200，不会重建文件
调 complete → L341-L347 chunk 10 missing → 500
在 24h TTL 内，这个会话永远无法完成，且客户端无从知晓是哪一片坏了
这就是这套“bit 单一事实来源、从不与磁盘核对”设计的真实缺口。

② bit 为 true，但内容是错的

服务端只校验 chunk_hash（客户端自己声明的），从不校验最终合并文件的 MD5 是否等于 file_hash。所以一个 buggy 或恶意的客户端，只要自己算的 chunkHash 与它发的错误字节一致，服务端就会照收。file_hash 只用来做续传索引，没参与完整性验证。这类“数据有问题”服务端是完全无感知的。

排查手段：直接看 .run/uploads/tmp/{uploadID}/ 下是否存在 10、11… 文件，大小是否等于 5MB（最后一片除外）。要强制重置就删两个 Redis key：chunk_upload:{uploadID} 和 chunk_upload_hash:{uid}:{fileHash}。

问题二：11 及之后没传上去，是不是再也传不了了
不是。 这里的关键是：它不是水位线（watermark），是位图（bitset）。

数据结构是 UploadedBits []bool，长度 = total_chunks，每个下标独立一个 bool。

如果设计成 uploadedCount = 11（表示“0~10 都传完了”），那确实会出现你担心的“缺口永久卡住”。
但现在是逐片独立标记，所以 10=true, 11=false, 12=false 是完全合法的中间态，11、12 随时可以补传，顺序无所谓。
代码侧也支持这点：

// 前端：把所有 false 的位收集成待传列表，天然支持空洞

IsComplete() 才是唯一要求全 true 的地方，而它只在 complete 时检查。

真正会“传不了”的是这三种边界
边界	结果	能否恢复
超过 24h TTL	会话和 hash 索引都过期，upload 返回 404	能，重新 init 会创建新会话，但进度归零，全部重传
bit true 但文件丢失（问题一①）	complete 永久 500，重传被短路	24h 内不能，需手工删 Redis key
换了文件	file_hash 变了，命中不到旧会话	新会话，从头传（符合预期）
另外注意前端的一个行为：uploadOne 重试 3 次都失败后会抛错，整个 Promise reject，本次上传中止。但已成功的分片 bit 不会回滚，所以用户重新选同一个文件再传时，init 会返回已传列表，只会补传失败的那几片——这正是位图设计带来的好处。

一句话总结
bit 10 为 true ≠ 数据坏了，只说明第 10 片曾经传成功过（乱序、重试、续传都会造成）。
11 之后没传≠永远传不了，位图允许任意空洞，补传随时可以，顺序无关。

早退不会导致续传出错——因为 chunkIndex 不是游标
你的担心来自一个隐含假设：服务端有一个“当前传到第几片”的指针，早退时没推进它，所以下次还卡在原地。

但代码里没有这个指针。req.ChunkIndex 是客户端每次请求自带的“这片是第几片”，服务端从头到尾不会修改它。

一、两个东西要分清
名称	身份	谁维护	会变吗
req.ChunkIndex	这次请求的标识（第几片）	客户端在 form 里传	不改，也不该改
session.UploadedBits[idx]	服务端状态（这片传没传完）	服务端写 Redis	成功上传后置 true
早退分支里的 return 200 只有一个含义：目标状态已经是 true 了。它不需要“再改一次 chunkIndex”，就像你把开关从“开”拨到“开”，不需要发生任何变化。

真正的更新早在上一次成功请求的 L223 就完成了：

Go



session.UploadedBits[req.ChunkIndex] = true   // 上次请求已经写过
saveSession(session)
所以早退不是“跳过了更新”，而是“更新早已完成”。幂等的标准写法就是这样：先判断状态是否已达终态，已达就直接返回。

顺带看响应也很清楚——早退返回的是 {"chunk_index": req.ChunkIndex}，把入参原样回显。如果它是个游标，响应应该是“下一个要传的序号”。

二、续传为什么不会错
推进上传的是客户端的 pending 列表，不是服务端的任何变量：

JavaScript



// VideoView.vue L152-158
const pending = []
for (let i = 0; i < totalChunks; i++) {
    if (!uploadedSet.has(i)) pending.push(i)   // 从 gaps 重建待传列表
}
uploadedSet 来自 init 的响应，而 init 的响应由 UploadedChunks() 从 bitset 遍历得出。

完整推演（20 片，传到 10 失败，用户刷新后续传）：




① init  → hash key 命中 → uploaded_chunks = [0,1,...,10]
② 前端  → pending = [11,12,...,19]        ← 缺口由 bits 反推，不是"从 11 开始"的猜测
③ upload 11..19 → 每片各自独立请求，各自带自己的 chunk_index
④ bits[11..19] 逐个置 true
⑤ complete → IsComplete() 全 true → 合并
每一步都不依赖任何“游标推进”，所以中间有没有早退、重试几次、乱序到什么程度，都不影响结果。

三、唯一会真的续传出错的场景
就是上一轮说的那个：bitset 说 true，但磁盘文件丢了。




① bits[10] = true，但 .run/uploads/tmp/{uploadID}/10 不存在
② 续传时前端 pending 里没有 10（因为 uploaded_chunks 含 10）
③ 客户端根本不会重发 10
④ complete 遍历到 10 → os.Open 失败 → "chunk 10 missing" → 500
⑤ 反复重试 complete 都是 500，24h 内无解
这时“错误”的根因不是早退没更新，而是状态（Redis）和实际数据（磁盘）发生了分歧，而代码只信 Redis。

四、如果要补这个缺口
最小改法是在早退前加一次磁盘核对，不一致就清位并继续往下走：

Go



if session.UploadedBits[req.ChunkIndex] {
    chunkPath := filepath.Join(".run/uploads", "tmp", req.UploadID, strconv.Itoa(req.ChunkIndex))
    expected := session.ChunkSize
    if req.ChunkIndex == session.TotalChunks-1 {
        expected = session.FileSize - int64(req.ChunkIndex)*session.ChunkSize
    }
    if fi, err := os.Stat(chunkPath); err == nil && fi.Size() == expected {
        c.JSON(http.StatusOK, gin.H{"chunk_index": req.ChunkIndex})
        return
    }
    session.UploadedBits[req.ChunkIndex] = false   // 状态不可信，降级为"未传"
}
代价是每次早退多一次 os.Stat（微秒级），换来的是状态与文件不一致时能自愈。

一句话
chunkIndex 是请求的标签，不是服务端的进度条；早退时它不需要变，因为要变的是 bitset，而 bitset 在上一次请求里已经被置成 true 了。续传靠客户端按 bitset 的缺口重建待传列表，只要“bit 与磁盘一致”就不会错——会错的只有 bit 与磁盘不一致那一种情况。

D. 中间层重放
浏览器不会自动重试 POST，但中间设施会：

Nginx proxy_next_upstream error timeout：上游超时/断连时，把同一个 POST 转发给下一台后端 → handler 执行两次
负载均衡的失败重试
CDN/网关的重试策略
HTTP/2 连接迁移失败后的上层重发
这类在生产环境很常见，且客户端完全不知情。所以幂等必须做在服务端，不能指望“客户端不会重复发”。

complete 只在所有 pending 的 Promise 都 resolve 后才调用，所以单标签页内不会触发；但多标签页、或某片重试还在写、另一个标签页已点完全部传完时，就可能撞上。正确做法是先写 .part 临时文件再 os.Rename 原子替换，这样任何时刻读到的都是完整版本。

一句话总结
重复的同 chunkIndex 请求主要来自 “成功但响应丢了”的客户端重试（本项目的 3 次重试循环）、401 后原样重放、多标签页/刷新续传的快照竞态、代理层重试。当前设计对这些都能正确收敛，唯一真正的隐患是bit 与磁盘不一致，以及truncate 写入 + 无锁导致合并时可能读到半片。
