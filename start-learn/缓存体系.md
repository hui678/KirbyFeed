## 0. 这个模块在做什么

`FeedService` 负责所有"读视频列表"的请求，一共 5 个入口（路由见 `backend/internal/http/router.go` 第 173-184 行）：

| 接口 | 数据来源 | 用到的缓存手段 |
|---|---|---|
| `POST /feed/listLatest` | Redis ZSET 时间线 + MySQL 冷尾 | 时间线 ZSET、singleflight、三级实体缓存 |
| `POST /feed/listByFollowing` | MySQL（子查询关注关系） | Redis 读缓存 + **SETNX 互斥锁** |
| `POST /feed/listByPopularity` | Redis 分钟级热榜快照 + MySQL | ZUNIONSTORE 快照 |
| `POST /feed/listTags` | MySQL（tags JOIN video_tags 聚合） | 无缓存 |
| `POST /feed/listByTag` | MySQL 三表 JOIN（复合游标） | 无缓存 |

其中 `/feed/listByFollowing` 在 `protectedFeedGroup` 里，**必须登录**；其余挂在 `SoftJWTAuth` 下，匿名可访问。

这个模块的缓存设计可以拆成两条独立的线，不要混在一起理解：

- **线 A：实体缓存（按 ID 查单个视频）** → 三级缓存 `L1 → L2 → L3` + `singleflight`
- **线 B：列表缓存（整页结果）** → Redis 读缓存 + `SETNX` 分布式锁

## 1. 线 A：三级缓存 GetVideoByIDs

入口：`service.go` 第 36-146 行。输入一批 videoID，输出按原顺序排好的视频实体。

### 1.1 数据结构

```go
type FeedService struct {
	repo         *FeedRepository
	likeRepo     *video.LikeRepository
	rediscache   *rediscache.Client
	localcache   *cache.Cache        // L1：go-cache，进程内
	cacheTTL     time.Duration       // 列表缓存用，24h
	requestGroup singleflight.Group  // 进程内请求合并
}
```

构造在 `service.go` 第 32-34 行：

```go
localcache: cache.New(3*time.Second, 5*time.Second)
cacheTTL:   24 * time.Hour
```

`cache.New(defaultExpiration, cleanupInterval)`：
- 第 1 个参数 `3s` 是**默认过期时间**；
- 第 2 个参数 `5s` 是**后台清理 goroutine 的扫描间隔**，不是 TTL。

### 1.2 执行流程

```
videoIDs
   │
   ├─► L1 本地 go-cache ──命中──► 放入 videoMap，continue
   │        │未命中
   │        ▼
   ├─► L2 Redis MGet（50ms 超时，一次批量）
   │        ├─命中：反序列化 → 写回 L1（5s）→ 放入 videoMap
   │        ├─未命中：记入 missedL2
   │        └─Redis 报错：missedL2 = missedL1（整体降级）
   │        ▼
   └─► L3 MySQL：每个 miss 的 ID 起一个 goroutine
              └─ singleflight.Do(sf:entity:<id>)
                   ├─ leader：repo.GetByIDs → 异步回写 Redis（1h）→ 返回
                   └─ follower：阻塞等待，拿同一份返回值
              → 各自写 L1（5s）→ 放入 videoMap
   │
   ▼
buildOrderedResult(videoIDs, videoMap)   ← 按原顺序重排
```

逐层对应的代码：

**L1（第 44-62 行）**

```go
cacheKey := video.VideoEntityKey(f.rediscache, id)
if v, found := f.localcache.Get(cacheKey); found {
	if data, ok := v.(video.Video); ok {
		videoMap[id] = &data
		continue
	}
}
missedL1 = append(missedL1, id)
```

key 构造统一走 `video.VideoEntityKey()`（`video/video_cache.go`），它内部用的是 `rediscache.Key(...)`，所以本地 key 跟 Redis key **同名同前缀**（`v1:video:entity:123`）。这样 L1 和 L2 共用一套 key 构造逻辑，不用维护两份命名规则 —— 详情页读取也走同一个函数。

**L2（第 64-99 行）**

```go
cacheCtx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)
results, err := f.rediscache.MGet(cacheCtx, cacheKeys...)
cancel()
...
} else {
	missedL2 = missedL1
	log.Printf("L2 Redis MGet 失败，全部降级到 MySQL: %v", err)
}
```

三个要点：
1. `MGet` 一次拿多个 key，避免 N 次网络往返；
2. **50ms 硬超时**，Redis 抖动不能拖垮整个请求；
3. Redis 出错时不返回错误，而是把全部 miss 沉到 MySQL —— 这就是项目"Redis 是可选依赖"的降级原则。

`MGet` 返回的 `[]interface{}` 里，不存在的 key 对应 `nil`，代码先判 `res != nil` 再做 `res.(string)` 类型断言，断言失败（或 JSON 解析失败）也归入 `missedL2`。

**L3（第 105-144 行）**

```go
for _, id := range missedL2 {
	wg.Add(1)
	go func(videoID uint) {
		defer wg.Done()
		// 与详情页 GetDetail 共用同一个回源去重组
		v, err, _ := video.EntityLoadGroup.Do(video.EntitySingleflightKey(videoID), func() (interface{}, error) {
			videoList, err := f.repo.GetByIDs(ctx, []uint{videoID})
			if err != nil || len(videoList) == 0 {
				return nil, err
			}

			safeCopy := *videoList[0]
			cachekey := video.VideoEntityKey(f.rediscache, safeCopy.ID)
			if b, err := json.Marshal(safeCopy); err == nil {
				go func(k string, b []byte) {
					setCtx, setCancel := context.WithTimeout(context.Background(), singleRedisOpTimeout)
					defer setCancel()
					f.rediscache.SetBytes(setCtx, k, b, video.VideoEntityTTL)
				}(cachekey, b)
			}
			return videoList[0], err
		})
		...
	}(id)
}
```

- 每个 miss 的 ID 一个 goroutine，**不是一个批量查询**。一页 20 个冷 ID 会并发 20 次 `WHERE id = ?`。这是为了配合 singleflight 的"按 ID 合并"而做的取舍：并发度高时能合并掉重复请求，但冷启动时会产生 N 次单行查询。
- Redis 回写是**异步的**（`go func` + `context.Background()` + 50ms 超时），两个原因：一是不让写缓存的耗时进入响应路径；二是请求结束后 `ctx` 会被取消，不能复用。
- 最后 `buildOrderedResult`（第 561-569 行）按传入的 `videoIDs` 重排，因为缓存回填顺序不可控。

### 1.3 为什么 L1 只有 3 秒

L1 是 `patrickmn/go-cache`，**纯进程内存**。N 个 API 实例就有 N 份互不可见的副本。

而缓存失效只删 Redis 的 key（比如点赞后 `video/popularity_cache.go` 第 17 行）：

```go
InvalidateVideoEntity(context.Background(), cache, id)
```

**没有任何跨实例广播去清别人的本地缓存。** 所以 L1 的 TTL 就是"最坏情况下的脏数据窗口"：

- TTL 太长 → 实例 A 写的 L1，在实例 B 上感知不到 Redis 的 `DEL`，用户看到过期点赞数 / 已删除视频；
- TTL 太短 → 失去本地缓存的意义（本来就是为了吸收同实例上毫秒级的重复读）。

3 秒是折中：Feed 对这几秒的旧数据不敏感，但足以把同一热点视频的瞬时并发收敛成本地内存读。

> **代码与注释不一致的地方**
> 构造函数默认值是 3s，但两处写入都显式传了 5s：
> - 第 86 行：`f.localcache.Set(cacheKeys[i], v, 5*time.Second)`
> - 第 140 行：`f.localcache.Set(..., safeCopy, 5*time.Second)`
>
> `Set` 的显式 TTL 优先于 `cache.New` 的默认值，所以**实际生效的 L1 TTL 是 5 秒**，3 秒只对 `SetDefault` 生效（本模块没用到）。

## 2. singleflight：进程内只放 1 个去查库

### 2.1 机制

`golang.org/x/sync/singleflight` 的 `Do(key, fn)`：

- 若此刻没有同 key 的调用在执行 → 当前 goroutine 成为 leader，执行 `fn`；
- 若已有同 key 的调用在执行 → 当前 goroutine **阻塞等待**，不执行 `fn`，直接拿 leader 的返回值。

所以 100 个并发 miss 同一个 videoID：**DB 只被查 1 次**，其余 99 个共享结果。

### 2.2 为什么必须 safeCopy

```go
safeCopy := *videoList[0]                  // 闭包内：隔离 Redis/返回值
...
safeCopy := *(v.(*video.Video))            // 闭包外：隔离下发给各请求
```

singleflight 把**同一个指针**返回给所有等待者。如果直接把它塞进各自的 `videoMap`，任何一处修改都会污染其他请求的结果。拷贝一份再下发，是共享返回值场景的必需操作。

### 2.3 本模块里的 4 处用法

| 位置 | key 粒度 | 防的场景 |
|---|---|---|
| 第 112-133 行 | `sf:entity:<videoID>` | 同一视频被并发读 |
| 第 165-189 行 | `sf:fallback:global_timeline_rebuild` **全局唯一** | ZSET 为空时，所有用户、所有游标一起去重建 1000 条 |
| 第 214-217 行 | `sf:cold:listLatest:<limit>:<reqTime>` 参数化 | 冷尾单用户的分页并发 |
| 第 261-264 行 | `sf:stitch:listLatest:<remain>:<cursor>` 参数化 | 冷热边界拼接的并发 |

第 2 条是"全局静态锁"，第 3、4 条是"参数化锁"，区别在于：重建时间线是一个**全局唯一的重活**，必须无视用户差异合并；而冷数据查询天然按用户/游标分散，用参数化 key 才不会把不同请求错误地合并成一份结果。

## 3. 线 B：SETNX 分布式锁

### 3.1 调用现场（ListByFollowing，第 378-409 行）

```go
} else if rediscache.IsMiss(err) {          // 只有"key 明确不存在"才进锁逻辑
	lockKey := "lock:" + cacheKey
	token, locked, _ := f.rediscache.Lock(cacheCtx, lockKey, 500*time.Millisecond)
	if locked {
		defer func() { _ = f.rediscache.Unlock(context.Background(), lockKey, token) }()
		if b, err := f.rediscache.GetBytes(cacheCtx, cacheKey); err == nil {
			// 双重检查：拿锁期间别人可能已经回填
			...
			return cached, nil
		} else {
			resp, err := doListByFollowingFromDB()   // 只有持锁者回源
			...
			_ = f.rediscache.SetBytes(cacheCtx, cacheKey, b, f.cacheTTL)  // 1 天
			return resp, nil
		}
	} else {
		for i := 0; i < 5; i++ {                  // 没抢到锁：最多等 5×20ms
			time.Sleep(20 * time.Millisecond)
			if b, err := f.rediscache.GetBytes(cacheCtx, cacheKey); err == nil { ... }
		}
	}
}
// 抢锁失败且等待超时 → 兜底直接查库（第 413 行）
```

四个设计点：

1. **只在 `IsMiss` 时加锁**。`IsMiss` 等价于 `err == redis.Nil`（`middleware/redis/redis.go` 第 49-51 行）。如果 Redis 是连接错误而不是 key 不存在，说明缓存层本身就不可用，加锁也没意义，直接走后面的兜底查库。
2. **双重检查**。拿到锁之后立刻再读一次缓存 —— 从"发现 miss"到"拿到锁"之间，别人可能已经把缓存填好了。
3. **等待方不查库优先**。没抢到锁的请求轮询 5 次、每次 20ms，等 leader 回填；等不到才在函数末尾兜底查库。宁可多一次 DB 查询，也不让请求无限阻塞。
4. **缓存 24 小时**（`cacheTTL`），靠关注/取关时的主动失效来保证一致性（见第 5 节）。

### 3.2 Lock / Unlock 的实现（middleware/redis/redis.go 第 70-104 行）

```go
func (c *Client) Lock(ctx context.Context, key string, ttl time.Duration) (token string, ok bool, err error) {
	if c == nil || c.rdb == nil {
		return "", false, nil
	}
	token, err = randToken(16)
	...
	ok, err = c.rdb.SetNX(ctx, key, token, ttl).Result()
	return token, ok, err
}
```

`SetNX` 就是 Redis 的 `SET key value NX PX ttl`，一条命令原子完成"不存在才写 + 带过期"，不存在"先查再写"的竞态。

```lua
-- Unlock 的 Lua 脚本
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

**为什么要 token 比对，而不是直接 `DEL`？**

经典误删场景：
1. A 拿到锁，业务执行超过 500ms；
2. 锁自动过期，B 拿到锁；
3. A 执行完，直接 `DEL` → 把 **B 的锁** 删了。

token 让解锁变成"只删自己的锁"。`GET` 和 `DEL` 必须在同一个 Lua 脚本里，否则两步之间仍可能被插入。

**降级**：Redis 为 nil 时 `Lock` 返回 `("", false, nil)`，调用方 `locked=false`，最终走兜底查库。**锁不可用不会阻塞业务**。

### 3.3 同样的模式在视频详情

`backend/internal/video/video_service.go` 第 150-183 行，结构一致，差异是：

- 锁 TTL 2s；
- 没抢到锁的等待用 `select { case <-ctx.Done(): ... case <-time.After(20ms): }`，会响应请求取消；
- 抢锁失败且等不到缓存时，**直接往下落到查库**（第 186 行），不会返回错误。

### 3.4 已知实现缺陷

`ListByFollowing` 里 `cacheCtx` 的定义在第 369-370 行：

```go
cacheCtx, cancel := context.WithTimeout(ctx, 50*time.Millisecond)
defer cancel()
```

这个 **50ms 超时的 context 被复用到了多个耗时操作上**：

- 第 381 行 `Lock`（此时可能已经用掉了一部分 50ms）；
- 第 395 行 `SetBytes`（在 DB 查询之后执行，50ms 基本必然已超时）。

后果：leader 抢到锁、查完库后回写缓存会因 `context deadline exceeded` 失败，而错误被 `_ =` 丢弃。**缓存长期写不进去，锁实际退化为"串行查库"**。正确写法是为 `Lock` 和 `SetBytes` 各自新建独立超时的 context（参考第 417-422 行的兜底分支，那里就是新建的）。

## 4. singleflight 与 SETNX 的分工

| | singleflight | Redis SETNX |
|---|---|---|
| 作用域 | **单进程内**（内存结构体） | **跨进程 / 跨实例**（Redis 共享） |
| 成本 | 一次内存 map 操作，无网络 | 1~2 次 Redis 往返 |
| 失败者行为 | 阻塞等待 leader，**拿到同一份返回值** | 轮询缓存，等不到就**自己查库兜底** |
| 缓存写入 | 只有 leader 写 Redis，followers 各写自己的 L1 | 只有持锁者回源并写缓存 |
| 本项目用于 | 视频实体批量读（高频、廉价） | 关注流列表（查询重、响应体大、缓存 1 天） |

一句话：**singleflight 省的是"同一个 Go 进程里的 99 次重复劳动"，SETNX 省的是"N 个 Pod 之间的并发回源"。**

singleflight 无法跨进程（每个 Pod 各有一份 Group）；SETNX 每个请求都要走一次 Redis，对高频小 key 不划算。所以热路径用 singleflight，重查询用 SETNX。

## 5. 缓存一致性：写操作后怎么失效

| 数据 | 失效方式 | 代码 |
|---|---|---|
| `video:entity:<id>` | 点赞/热度变化、视频删除时 `DEL`（详情页共用同一份实体缓存） | `video/popularity_cache.go` 第 17 行 |
| `feed:listByFollowing:*:accountID=<id>:*` | 关注/取关后按 pattern 删除 | `social/service.go` 第 94-102 行 |

`DelByPattern` 用的是 `SCAN` 迭代 + 逐个 `DEL`（`middleware/redis/cache.go` 第 30-39 行），不是 `KEYS`，避免大 key 空间下阻塞 Redis。

注意：**L1 清不掉**。关注/取关后，别的实例的本地缓存仍可能在 3~5 秒内返回旧列表。这是 L1 短 TTL 存在的原因，也是它无法消除的代价。

## 6. 自测题：击穿 / 穿透 / 雪崩

### 缓存击穿（热点 key 过期瞬间，大量并发回源）

对应三处：

1. `service.go` 第 112-133 行：singleflight 合并实体回源；
2. `service.go` 第 381-398 行：SETNX 合并关注流回源；
3. `service.go` 第 165-189 行：ZSET 为空时用全局 singleflight key 合并重建。

外加 L1 短 TTL 本身也是一层：热点 key 在本地存活期间，压力根本到不了 Redis。

### 缓存穿透（查不存在的 key，每次都打 DB）

**本项目没有防护，这是已知短板。**

第 117-119 行：

```go
if err != nil || len(videoList) == 0 {
	return nil, err     // err 为 nil，且没有缓存"不存在"这个事实
}
```

第 135 行的 `err == nil && v != nil` 判断直接跳过 —— **既没有空值缓存，也没有布隆过滤器**。同一个不存在的 `videoID` 被反复请求，每次都会 `SELECT` 一次 MySQL。

最小修补方案：在 `len(videoList) == 0` 分支写一个短 TTL（30~60s）的占位值（如 `"null"`），L2 解码时识别到就跳过 DB 查询。

### 缓存雪崩（大批 key 同时失效 / 缓存层整体不可用）

分两种情况：

1. **同批 key 同时过期**
   实体缓存 TTL 1 小时，但是**读时按需写入**，过期时刻由各自首次访问时间决定，天然被打散；热榜快照 `hot:video:merge:1m:*` 只有 2 分钟，且 key 带分钟级 `as_of`，不同分钟互不影响。
   → 没有主动加随机抖动，但实际同时失效的概率不高。

2. **Redis 整体挂掉**（真正的雪崩入口）
   第 94-98 行把所有 L2 miss 一次性沉到 MySQL。此时唯一的缓冲是 L1 的 3~5 秒本地缓存 + singleflight 按 ID 去重，**没有熔断、没有限流兜底**。
   → 设计取舍：优先保证"可用"，而不是"保护 DB"。

## 7. 设计文档对照（易错点）

- **第 218 行「分布式锁防击穿」**：与第 378-409 行的实现吻合，"仅允许一个请求回源构建缓存，其余等待/返回兜底结果"两个分支代码里都有。
  但文档写的"Feed **匿名流**"对不上：`ListByFollowing` 要求 `viewerAccountID != 0`（第 363 行），且挂在 `protectedFeedGroup` 下，是**登录态**接口。匿名流 `ListLatest` 用的是 singleflight，不是 SETNX。
- **第 219 行「Feed 冷热分离时间线」**：对应 `ListLatest`。热数据走 Redis ZSET 分页（第 224-248 行）；冷数据（`reqTime <= watermark`）回源 MySQL（第 210-222 行）且**不回写 ZSET**，防止冷数据污染热点时间线；跨边界时再拼接一次（第 251-270 行）。

## 8. 值得记住的取舍与待修项

**设计上的取舍**

1. L1 用短 TTL 换"多实例最终一致"，而不是引入广播失效（成本高、复杂度高）。
2. Redis 一切异常都降级到 MySQL，可用性优先于 DB 保护。
3. 每个视频实体单查 + singleflight，而不是整页批量查：合并重复请求的能力换掉了一部分批量查询的效率。
4. 异步回写缓存，牺牲"写完立即可见"换取响应延迟。

**代码里能挑出来的问题**

| 问题 | 位置 | 影响 |
|---|---|---|
| `cacheCtx` 50ms 被复用到 `Lock`/`SetBytes` | service.go 第 369-395 行 | 关注流缓存实际写不进去，锁退化为串行查库 |
| L1 默认 3s 与写入 5s 不一致 | service.go 第 33、86、140 行 | 读代码时容易误判 TTL |
| 无空值缓存 / 布隆过滤器 | service.go 第 117-119 行 | 不存在 ID 的请求全部穿透到 MySQL |
| 冷启动按 ID 单个查询 | service.go 第 108-142 行 | 一页 20 个冷 ID 产生 20 条单行 SQL |
