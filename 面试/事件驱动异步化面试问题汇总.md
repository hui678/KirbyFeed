## 1. 三十秒总览（先背这一页）

### 1.1 一条数据流

```
POST /video/like
  └─ 同步：JWT → 参数校验 → 视频存在？ → 已点赞？（读后写，只做体验层快速失败）
       └─ 发两条消息，各自等 publisher confirm（3s 超时）
            ├─ like.like                 → like.events 队列              → LikeWorker
            └─ video.popularity.update   → video.popularity.events 队列  → PopularityWorker
       └─ 都 confirm 成功 → 200（此时 likes 表可能还没有行）
       └─ 哪条没发出去 → 同步补哪条（复用消费端同一个事务入口）

LikeWorker（MySQL，强一致）
  └─ 一个事务：INSERT IGNORE likes → RowsAffected=0 直接结束
                          └─ likes_count+1 → popularity+1

PopularityWorker（Redis，准实时）
  └─ 失效实体缓存 → Lua：SETNX 去重标记 → ZINCRBY 分钟桶 → EXPIRE 2h

失败路径（所有 Worker 共用 Consumer 骨架）
  进程内退避重试 ≤3 次（0.5~4s）→ TTL 重试队列 30s × 3 轮 → Nack(false,false) → 死信队列
```

### 1.2 关键参数

| 项 | 值 | 位置 |
|---|---|---|
| publisher confirm 超时 | 3s | `rabbitmq/publisher.go:15` |
| 消息持久化 | `DeliveryMode = Persistent` | `rabbitmq/publisher.go:85` |
| 进程内重试 | 3 次（共处理 4 次），退避 0.5~1 / 1~2 / 2~4s，上限 8s | `worker/retry.go:18`、`:119` |
| 重试队列 TTL | 30s，最多 3 轮（`MaxRetryCount`） | `rabbitmq/retry.go:17`；`rabbitmq/dlx.go:11` |
| 死信 | 每主队列专属 `<queue>.dlx`，精确绑定键 | `rabbitmq/dlx.go:32`；`rabbitmq/rabbitMQ.go:83` |
| 消费预取 | 业务队列 50；时间线 10 | `cmd/worker/main.go:64`；`worker/outboxworker.go:215` |
| 评论幂等键 | `comments.event_id` 唯一索引 | `video/comment_entity.go:18` |
| 点赞幂等键 | `(video_id, account_id)` 联合唯一索引 | `video/like_entity.go:7` |

| Redis 单操作超时 | 50ms | `video/video_cache.go:17` |
| Outbox 轮询 / 抢占超时 / 清理 | 1s / 60s / 已发送保留 24h | `worker/outboxworker.go:19`；`video/video_entity.go:62` |

### 1.3 三句话结论（被要求总结时用）

1. **同步路径只做「能不能做」的判断和「消息有没有交出去」的确认，200 的语义是「已持久化」，不是「副作用已完成」。**
2. **消息系统只给 at-least-once，幂等必须落在消费端的存储操作上**：点赞靠唯一索引 + 同事务计数，评论靠 `event_id`，热度靠 Lua 原子去重。
3. **可靠性不是一层，而是四层**：confirm（发出去）→ 事务（效果原子）→ 三级重试（扛故障）→ 死信（兜底可见）。少任何一层，前面的承诺都会在某一环断掉。

# 一、第一层：基础原理

## Q1. 为什么把点赞、评论的落库与热度更新拆成不同消息？哪些逻辑必须同步完成，哪些可以异步？

**一句话要点**
因为这两类副作用**失败域、幂等语义、存储介质、可容忍延迟**全都不一样：落库是 MySQL 里的状态变更（必须原子、不能多不能少），热度是 Redis 里的增量指标（可重放、丢一点只影响榜单精度）。拆开之后，Redis 挂了点赞照样能落库，MySQL 慢了也不会堵住热度队列。

**展开**

1. **先分清「同步」和「原子」是两个维度**。
   - 相对 HTTP 请求：连 `likes` 行都是异步的 —— 返回 200 时表里可能还没数据。
   - 相对彼此：`likes` 行、`likes_count`、`videos.popularity` 必须在**同一个事务**里。少了这一条，重试时行会被唯一索引挡住，计数永远补不回来（详见 Q7）。
2. **必须同步完成的只有四件事**：鉴权、参数校验、视频存在性、重复点赞的快速判重。它们都是「这次操作能不能做」的判断，成本低、失败可以直接告诉用户。
3. **必须同步等的只有一件事**：`publisher confirm`。它决定这次走异步还是走降级直写，不等就不知道消息到底交没交出去。
4. **可以异步的**：`likes` 行与计数的落库、Redis 分钟桶、通知、时间线。共同点是「用户不需要立刻看到结果」，且都能通过重试/重放收敛。
5. **拆开的收益是故障域隔离**：合并成一条消息交给一个 Worker 串行处理，Redis 故障会让整条消息失败，连带 MySQL 写入被重试反复冲击；MySQL 锁等待又会把热度事件堵在同一个队列里。拆成两个队列后，两边的重试、积压、降级互不影响。
6. **代价**：两条消息 = 两次 publish confirm（约两个 RTT）、两套队列/死信/重试拓扑、以及「点赞数 +1 了但热榜还没动」的秒级窗口。这个窗口是明确接受的。

**代码依据**
- 两条消息的发布：`video/like_service.go:63`、`:68`。
- 两条链路各自的写入入口：`video/like_repo.go:22`（MySQL 事务）、`video/popularity_cache.go:60`（Redis Lua）。
- 拓扑注册表：`rabbitmq/topics.go:22`、`:40`。

**可能的追问**
> 「热度不是也要更新 `videos.popularity` 吗？那它到底算 MySQL 还是 Redis？」
> 两条链路各写各的：`LikeWorker` 在 MySQL 事务里把 `videos.popularity` +1（用于详情页展示，强一致）；`PopularityWorker` 只写 Redis 分钟桶（用于热榜，准实时）。同名不同义，面试时要主动点破，否则会显得概念不清。

## Q2. API + Worker 双进程架构的边界是什么？为什么不把所有业务逻辑都写在 Gin Handler 中？

**一句话要点**
边界是**「请求生命周期」和「副作用生命周期」分离**：API 负责鉴权、校验、读和「把事件交出去」，Worker 负责可重试、可延迟、可能需要几分钟才能完成的副作用。塞进 Handler 的问题是：HTTP 连接会被重试绑住，故障无法隔离，两边也无法独立扩缩容。

**展开**

1. **API 进程做**：JWT、参数绑定、视频/账号存在性、点赞状态查询、publish + confirm、发布失败时的同步降级。
2. **Worker 进程做**：点赞/评论/关注落库、计数更新、Redis 热度、通知入库与 SSE 推送、死信消费。
3. **不写进 Handler 的四个理由**：
   - **时间尺度不同**：一条消息从失败到进死信最长约 100 秒（见 Q9），HTTP 请求不可能挂这么久；异步化后 API 的 RT 只含校验 + confirm。
   - **故障隔离**：Redis/MySQL 抖动只会让某个队列积压，不会让 API goroutine 堆积、连接池耗尽。
   - **独立扩缩容**：读流量大就扩 API，消息多就扩 Worker，两者的资源画像完全不同。
   - **优雅关闭**：API 可以快速摘流量；Worker 需要停止拉取、等在途消息处理完（`cmd/worker/main.go:216` 退出时留 10 秒）。
4. **Handler 也不该承载业务逻辑**：本项目里 Handler 只做绑定 + 调用 Service（`video/like_handler.go:18`），用例边界在 Service，副作用在 Worker。三层职责清晰，追问「为什么不全写 Handler」时可以直接指出来。
5. **代价与边界**：
   - 两个进程 = 两套连接池、两套配置、两套部署；业务代码共享，但不是同一运行时。
   - 跨进程后没有函数调用栈，**队列拓扑就是接口契约**。项目用 `Topic` 注册表消除「Worker 声明在 A 队列、发布端发到 B 交换机」的静默故障（`rabbitmq/topics.go:9` 的注释就是为此写的）。
   - 目前时间线消费者、通知消费者、Outbox poller 仍在 API 进程内（`http/router.go:226`、`:278`），理由见学习文档 §11：单次处理轻、要求低延迟、丢了可容忍。这是明确的取舍，不是遗漏。

**代码依据**
- Worker 装配：`cmd/worker/main.go:27`（只消费四类事件）、`:189`。
- API 内消费者：`http/router.go:226`、`:278`。
- 契约集中定义：`rabbitmq/topics.go:57`。

**可能的追问**
> 「两个进程共用数据库连接池吗？」
> 不共用。各自按配置建池，默认 `MaxOpenConns=64 / MaxIdleConns=16`（`config/loadconfig.go:35`）。Worker 目前每个队列单 goroutine 串行消费，实际只占 1 条连接；真正需要调池的是 API 和「扩了消费者的 Worker」。

## Q3. RabbitMQ 的 ACK、NACK、Reject 分别是什么？自动 ACK 与手动 ACK 有什么区别？

**一句话要点**
ACK 是「处理成功，可以删」；NACK 是「处理失败」，带 `requeue` 决定是回队列还是走死信；Reject 是 NACK 的单条版本。自动 ACK 在**投递时**就删消息，进程崩溃即丢；手动 ACK 在**处理完**才删，代价是必须幂等。

**展开**

| 动作 | 语义 | `requeue=true` | `requeue=false` |
|---|---|---|---|
| `Ack` | 成功 | — | 消息删除 |
| `Nack(multiple, requeue)` | 失败，可批量 | 回队列，可能立刻重投 | 有 DLX 则进死信，否则丢弃 |
| `Reject(requeue)` | 失败，单条 | 同上 | 同上 |

1. **自动 ACK（`autoAck=true`）**：broker 把消息发出去就认为完成。优点是简单；缺点是消费者崩溃时消息已经没了，而且**不受 prefetch 限制**，容易把内存打爆。只适合「丢了也无所谓」的场景。
2. **手动 ACK**：消息在处理完成前一直是 unacked，连接/Channel 断开后 broker 会重新投递。这才是 at-least-once 的来源，也是为什么消费端必须幂等。
3. **NACK 的坑**：`requeue=true` 会让消息几乎立刻回到队列，如果失败原因是「数据本身有毒」，就会形成热循环，把 CPU 和数据库打满。所以重试必须有上限和退避，而不是原地 requeue。
4. **本项目的用法**：
   - 消费统一用 `Consume(queue, "", false, ...)` 关掉自动 ACK（`worker/retry.go:46`）。
   - 成功 `Ack(false)`；失败先进程内退避重试；耗尽后投重试队列并 ACK；重试轮数用尽 `Nack(false, false)` 进死信（`worker/retry.go:84`、`:114`）。
   - 进程退出时 `Nack(false, true)` 把在途消息退回队列（`worker/retry.go:77`），宁可重投也不丢。
   - 坏消息（JSON 解析失败、字段缺失）直接返回 nil → ACK，因为重试一万次也解不开（`worker/likeworker.go:44`）。

**代码依据**
- 手动 ACK + prefetch：`worker/retry.go:46`；`cmd/worker/main.go:64`。
- 三级失败处理：`worker/retry.go:69`。
- 死信：`worker/retry.go:114`；`rabbitmq/dlx.go:32`。

**可能的追问**
> 「ACK 丢了会怎样？」
> 消息会被重投，但业务已经执行过 → 靠幂等吸收。ACK 丢失不影响正确性，只影响效率，这是「至少一次」的必然后果。

## Q4. 为什么需要唯一索引配合 `INSERT IGNORE`？它解决的是重复消息、重复请求，还是两者都能解决？

**一句话要点**
唯一索引把「是否已存在」的判断交给数据库，在插入的原子操作里完成；`INSERT IGNORE` 把冲突变成 `RowsAffected=0` 而不是错误。它能同时吸收**重复消息**和**重复的状态型请求**，但前提是两者映射到同一个业务唯一键。

**展开**

1. **为什么不用「先 SELECT 再 INSERT」**：检查和写入之间有窗口，两个并发请求/两次并发投递都能通过检查，然后一条插入成功、一条报错或重复插入。窗口无法靠应用层代码消除。
2. **为什么不用「捕获 1062」**：能去重，但拿到的是「出错了」而不是「这次到底写没写」。后续任何副作用（计数、发通知、推 SSE）都无法判断该不该执行。这是学习文档 §4 里那张表的第二行。
3. **`INSERT IGNORE + RowsAffected` 的好处**：一次 SQL 同时回答两个问题 ——「是否重复」和「本次是否真的写入」，而且天然并发安全。`RowsAffected==1` 才执行后续副作用。
4. **它能解决什么**：
   - 重复消息：`like.like` 投递两次，第二次 `RowsAffected=0`。
   - 重复请求：用户连点两次，第二次同样被唯一键挡住。
   - 两者能一起解决，是因为**幂等键是业务天然键**：一个人对一个视频只能有一条点赞记录。
5. **它不能解决什么**：
   - **两次合法但内容相同的动作**：同一个人在同一视频下发两条一样的评论。业务上没有天然唯一键，必须引入 `event_id`（`video/comment_entity.go:18`），由发布端在发布前生成，MQ 与降级共用。
   - **副作用不是插入**：`ZINCRBY`、发短信、推送 SSE，唯一索引管不到，必须单独设计幂等（Q7）。
   - **顺序问题**：唯一索引只保证「重复的 like」幂等，挡不住「重投的旧 like 排在 unlike 之后」（Q16）。
6. **`INSERT IGNORE` 的副作用**：它会把一部分错误降级成 warning（如数据截断），所以只适合字段简单、约束明确的表；严格场景应改为 `ON DUPLICATE KEY` 或先查 warning。本项目字段少、索引明确，风险可控。

**代码依据**
- 联合唯一索引：`video/like_entity.go:7`。
- 幂等插入 + RowsAffected：`video/like_repo.go:36`、`:44`。
- 评论的 `event_id` 唯一索引：`video/comment_entity.go:18`；写入：`video/comment_repo.go:45`。

**可能的追问**
> 「`event_id` 为什么用 `*string`？」
> AutoMigrate 加列时历史行是 `NULL`，MySQL 唯一索引允许多个 `NULL`。如果用 `string`，历史行会落成 `''`，建索引时直接冲突，服务起不来。

## Q5. 什么情况下应该使用消息队列，什么情况下直接调用函数或同步写库更合适？

**一句话要点**
判断标准不是「技术先不先进」，而是**副作用的失败代价 × 延迟容忍度 × 下游数量**：需要削峰、重试、多下游、故障隔离时用 MQ；需要 read-your-writes、只有一个下游且很快时，直接调用更简单、更可靠。

**展开**

1. **适合 MQ 的信号**：
   - 一个事件有多个下游（本项目 `like.like` 同时被 `LikeWorker` 和 `NotificationWorker` 消费）。
   - 副作用耗时不可控，且可以延迟（通知、热度、时间线）。
   - 需要缓冲尖峰（热点视频被集中点赞）。
   - 需要失败重试和隔离（Redis 挂不影响落库）。
2. **不适合 MQ 的信号**：
   - 用户必须立刻看到结果（点赞后详情页立刻显示计数）。这时应做「同步写 + 异步补」，而不是全异步。
   - 只有一个下游、耗时稳定在毫秒级、失败可以直接返回错误。
   - 团队还没有幂等、死信、积压监控的能力 —— 引入 MQ 会把「一个 bug」变成「一类需要长期运维的故障」。
3. **本项目的实际划分**：
   - 走 MQ：点赞/评论/关注的落库与计数、热度、通知、时间线。
   - 同步：账号、视频详情/列表、点赞状态查询、分片上传的位图操作。
   - **例外**：评论里的 `@mention` 通知仍然在 Service 里同步写 `notifications` 表（`video/comment_service.go:132`）。它是历史实现，失败只记日志，不影响评论成功。面试时要主动承认这是「通知链路有两条路径」的不对称，统一的做法是给 mention 也发事件。
4. **一个反例帮助说明**：把点赞拆成 MQ 后，接口 RT 变短了，但「点赞后立即刷新看不到」变成了产品问题。所以拆分前要确认：**读路径能不能接受最终一致**（本项目详情页计数走 MySQL，Worker 通常毫秒级追上；热榜允许秒级延迟）。
5. **口诀**：**能不异步就不异步；要异步，先把幂等和死信设计好再动手。**

**代码依据**
- 同步路径：`video/like_service.go:24`。
- 一对多消费：`http/router.go:239`（通知队列与业务队列绑定同一交换机）。
- mention 同步写：`video/comment_service.go:145`。

**可能的追问**
> 「那你们为什么不用 Go Channel 直接异步？」
> Channel 只在进程内，进程重启消息就没了，也无法多实例竞争消费；它适合「丢了无所谓」的后台任务，不适合「用户操作不能丢」的场景。RabbitMQ 提供了持久化、confirm、ACK、死信这些 Channel 没有的能力。

## Q6. 用户连续点击点赞 10 次，接口如何处理？点赞记录是使用状态更新，还是插入一条记录？

**一句话要点**
10 次点击是 10 个请求。顺序请求时第 1 个成功、后面被 `IsLiked` 挡住；并发请求时 10 个都可能通过判重，发出 10 条消息，但消费端唯一索引只让 1 条生效，计数只加 1。存储上是**关系行（插入/删除）**，不是 status 字段。

**展开**

1. **顺序 10 次**：第 1 次发布成功返回 200；如果第一条已经被 Worker 消费，第 2 次 `IsLiked` 会查到已点赞，返回 `user has liked this video`（如果还没被消费，则继续发消息，只是无害的重复）。当前 Handler 把所有错误映射成 500（`video/like_handler.go:39`），语义上应该是 409 或幂等 200 —— 这是已知的体验缺口。
2. **并发 10 次**：`IsLiked` 是「读后写」，10 个请求可能都读到「未点赞」→ 10 条消息 → 10 次 `INSERT IGNORE`。只有 1 次 `RowsAffected=1`，其余 9 次直接返回，计数不会多加。**结果正确，但做了 9 次无用功**。
3. **为什么用「行」而不是 `status` 字段**：
   - 行存在 = 已点赞，删除 = 未点赞。唯一索引 `(video_id, account_id)` 本身就是幂等键，不需要额外判重。
   - `status` 字段也能幂等（`UPDATE ... WHERE status=0`），但会失去「唯一索引即幂等键」的天然约束，且要额外处理「先有行还是先无行」，并不能简化任何东西。
   - 行模型还能直接支撑「我点赞过的视频」列表（`ListLikedVideos`）。
4. **代价**：消息被放大 10 倍，Worker 做 10 次事务（9 次是空事务）。防护手段：前端防抖/合并、接口改成幂等语义（`PUT /like {state: liked}` 或带 `Idempotency-Key`）、网关按用户+视频限频。
5. **一个容易忽略的语义**：点赞接口是「增量动作」而不是「设置状态」，所以**并发 like/unlike 的最终状态取决于到达顺序**，没有版本控制。要做到「以最后一次用户操作为准」，请求必须带客户端序号或时间戳，消费端按版本取舍（Q16）。

**代码依据**
- 同步判重：`video/like_service.go:42`。
- 幂等插入：`video/like_repo.go:36`。
- 联合唯一索引：`video/like_entity.go:7`。

**可能的追问**
> 「并发 10 次里 9 次返回什么？」
> 如果它们都在第一条消息被消费前执行完，9 次都会返回 200，但实际只落一条 —— 对用户是「都成功了」，符合幂等直觉。如果晚到的请求碰上已落库，会返回「已点赞」错误，当前是 500，应该改成 200/409。

## Q7. 消息重复投递时，`INSERT IGNORE` 如何保证业务幂等？如果消费者需要同时更新热度，单靠它是否足够？★

**一句话要点**
不够。`INSERT IGNORE` 只挡「插入」这一个动作，挡不住计数：插行成功、计数失败时重试会被唯一索引直接跳过，计数永久少 1。正确做法是**把插行和计数放进同一个事务**；而热度在 Redis，事务管不到，必须再叠一层 `event_id + Lua` 的原子去重。

**展开**

1. **单靠 `INSERT IGNORE` 的失败时间线**（这是学习文档 §5 的核心）：

   ```
   T1  插 likes 行成功
   T2  likes_count + 1 因为锁等待超时失败
   T3  消息重试 → 插行命中唯一索引 → RowsAffected=0 → return nil
   T4  likes_count 永远没有机会再 +1
   ```

   没有报错、没有告警，计数就是永久比实际少 1。**「最终一致」的系统里最不该出现的就是永久偏差。**
2. **修复**：`INSERT IGNORE`、`likes_count +1`、`popularity +1` 放进一个事务（`video/like_repo.go:26`）。要么全生效，要么全回滚。重试时如果行不存在，说明上次事务没提交，计数会重新执行；如果行存在，说明上次已全部提交，直接结束。
3. **评论同理**：插评论 + `videos.popularity + 1` 同事务，靠 `event_id` 唯一索引判断是否首次（`video/comment_repo.go:31`）。
4. **Redis 热度必须单独幂等**：
   - `ZINCRBY` 是累加，天生不幂等；「先处理再 ACK、崩溃后重投」会加两遍。
   - 用 `event_id` 做去重标记，且**必须用 Lua 把「SETNX 占位 + ZINCRBY + EXPIRE」做成一个原子操作**（`video/popularity_cache.go:36`）。如果拆成两条命令，中间崩溃会留下「已标记处理过、但没累加」的状态，之后所有重试都被挡住 → 热度永久丢失。
   - 去重标记 TTL 24h，必须大于「一条消息最长可能重投多久」（约 100 秒），否则标记先过期、重投又被当成新事件。
5. **`event_id` 必须在发布前生成，且 MQ 与降级共用**：publish 成功但 confirm 超时是**无法消除**的窗口 —— 消息其实在队列里，Worker 迟早会处理；服务层以为失败又直写 Redis，就会加两遍。所以 `popEventID` 在 publish 之前生成（`video/like_service.go:59`），消费端和降级路径传同一个（`video/like_service.go:69`、`:92`）。
6. **边界**：去重标记存 Redis，Redis 丢数据时去重能力和分钟桶一起丢。此时重投会重新累加，但桶也没了，等价于从零重建，误差被限制在一个窗口内，可以接受；不能接受的话就得把事件持久化（Outbox / 消息流）。

**代码依据**
- 事务 + RowsAffected：`video/like_repo.go:22`。
- 计数兜底：`video/like_repo.go:85`（`GREATEST(col + ?, 0)`）。
- Lua 去重：`video/popularity_cache.go:36`、`:76`。
- 发布前生成 eventID：`video/like_service.go:59`。

**可能的追问**
> 「为什么不给点赞也加一张 event_id 去重表？」
> 因为点赞有业务天然唯一键，唯一索引已经是最便宜、最可靠的去重；再加 event_id 表只会多一次写入和一次清理，收益为零。**幂等键要选业务本身已经保证唯一的东西**，没有才引入 event_id（评论就是这种情况）。

## Q8. 消费者完成数据库操作后、发送 ACK 前崩溃，消息会怎样？再次消费时如何避免重复修改数据？★

**一句话要点**
消息在 Channel/连接断开后会被 broker 重新投递（`redelivered=true`）。重复消费靠「存储层的幂等」吸收：MySQL 是唯一索引 + 同事务计数，Redis 是 `event_id` + Lua，通知是 `RowsAffected=1` 才推 SSE。

**展开**

1. **崩溃后的完整过程**：

   ```
   Consumer 处理消息 → 事务提交成功 → 进程崩溃（ACK 未发出）
     → TCP 断开 → broker 把 unacked 消息重新入队
     → 另一个消费者/重启后的自己再次收到同一条消息
   ```

   `Qos(50)` 意味着崩溃时最多有 50 条 unacked 消息被重投，所以幂等不是「以防万一」，而是常态。
2. **MySQL 侧**：重投时 `INSERT IGNORE` 命中唯一索引，`RowsAffected=0`，事务直接返回，计数不再执行。因为上次事务已提交，数据和这次「什么都不做」完全一致。
3. **反过来的崩溃点**：如果崩溃发生在事务提交**之前**，重投会完整重跑一次，等价于上次根本没执行 —— 事务保证了不会出现中间态。
4. **Redis 侧**：Lua 里 `SETNX` 返回 false 就跳过，不会重复 `ZINCRBY`。标记和执行在同一脚本里，不存在「标记了但没执行」的窗口。
5. **通知侧**：先 `INSERT IGNORE` 通知行，只有 `RowsAffected=1` 才 `hub.Push`。重投时行已存在 → 不再推 SSE，用户不会看到两条一样的「xxx 点赞了你的视频」（`worker/notificationworker.go:142`）。
6. **这个保证的边界**：
   - 幂等键必须**稳定**。如果每次重投都换一个 `event_id`，去重直接失效。
   - Redis 去重标记的 TTL 必须覆盖最长重投时间（24h vs 约 100s，余量充足）。
   - 如果 Redis 去重数据丢了而消息还在重投，会重复加一次；属于「Redis 整体故障」的边界，不是消息系统的锅。
   - SSE 是尽力而为：重投被去重时不会补推，用户可能错过实时提醒，但通知列表能查到 —— 仍然最终一致。

**代码依据**
- 事务幂等：`video/like_repo.go:44`。
- Lua 去重：`video/popularity_cache.go:37`。
- 通知去重后才推送：`worker/notificationworker.go:142`、`:149`。

**可能的追问**
> 「为什么不在数据库里存一个『消息已处理』表，处理前先查？」
> 那是「去重表」思路，需要额外的写入和清理，而且「查 + 写」仍有窗口，必须靠唯一索引收敛。能用业务唯一键表达幂等时，去重表是多余的（Q7 追问同理）。

## Q9. 你提到「三级重试」，具体是哪三级？每一级的触发条件、延迟、最大次数和最终处理方式是什么？★

**一句话要点**
进程内指数退避（瞬时抖动）→ TTL 重试队列延迟重投（持久一点的故障）→ 死信队列（注定失败）。每级解决**不同时长的故障**，所以不能合并成「一直重试」。

**展开**

| 级别 | 机制 | 触发条件 | 延迟 | 最大次数 | 最终去向 |
|---|---|---|---|---|---|
| 1 | 进程内退避 + jitter | `process` 返回 error | 0.5~1s / 1~2s / 2~4s | 再试 3 次（共处理 4 次） | 仍失败 → 第 2 级 |
| 2 | TTL 重试队列 | 第 1 级耗尽，且 `x-death.count < 3` | 固定 30s TTL | 3 轮 | 仍失败 → 第 3 级 |
| 3 | 死信队列 | 轮数用尽，或投递重试队列本身失败 | 无 | 1 次 | `DLQWorker` 记录 + ACK，人工处理 |

1. **第 1 级解决什么**：网络闪断、行锁等待、连接池瞬时耗尽。这些故障通常在秒级自愈，原地退避比走一圈 MQ 更快。
2. **jitter 为什么必须有**：`wait/2 + rand(wait/2)`。如果没有抖动，同一批失败消息会在同一秒集体重试，把刚恢复的 MySQL/Redis 再打出一个尖峰，形成「恢复 → 打挂 → 再恢复」的循环。
3. **第 2 级怎么计数**：不存业务状态，读 RabbitMQ 自己维护的 `x-death.count`（`rabbitmq/dlx.go:59`）。消息每次经过重试队列 TTL 死信回主交换机，count 自动 +1。
4. **重试队列怎么做到「延迟 30 秒自动重投」**：队列设 `x-message-ttl=30s` + `x-dead-letter-exchange=<主交换机>`，**故意不设** `x-dead-letter-routing-key`。RabbitMQ 的规则是「没指定就沿用原始 routing key」，于是 `like.like` 回来时仍然匹配主队列的 `like.*`，天然完成重投，不需要定时任务（`rabbitmq/retry.go:31` 的注释）。
5. **第 3 级为什么直接 `Nack(requeue=false)`**：走到这里的消息已经注定失败（坏数据、逻辑 bug、下游长期不可用）。继续 requeue 只会让它反复冲击数据库；进专属死信队列，至少「可见、可查、可重放」。
6. **总时长量级**：`(0.5~4s 退避) × 3 + 30s × 3 ≈ 100 秒`（不含处理耗时）。这个数字要能脱口而出，它解释了「为什么热点故障恢复后，热榜可能延迟一两分钟才追平」。
7. **三个例外**：
   - **坏消息**（JSON 解析失败、字段缺失）：直接返回 nil → ACK。重试一万次也解不开，只会占满轮次、制造无意义告警（`worker/likeworker.go:44`）。
   - **进程退出**：`Nack(false, true)` 退回队列，不计轮次、不消耗重试额度。
   - **投递重试队列失败**：直接进死信，因为没有第 2 级可用了。

**代码依据**
- 退避实现：`worker/retry.go:119`。
- 三级分派：`worker/retry.go:100`、`:114`。
- 重试拓扑：`rabbitmq/retry.go:35`。
- 死信拓扑：`rabbitmq/dlx.go:32`。

**可能的追问**
> 「为什么不直接重试 10 次？」
> 1 秒级故障重试 10 次也只是浪费 10 次；分钟级故障需要把消息放回队列、释放消费者；而「数据库主从切换」这类故障，原地重试还会占着 goroutine 和 unacked 配额，让整个队列停摆。

## Q10. 为什么不在 RabbitMQ 消费回调里直接 `time.Sleep` 进行重试？这种做法对消费者吞吐量有什么影响？

**一句话要点**
因为本项目每个队列只有**一个 goroutine 串行消费**，在回调里 sleep 等于让整个队列停摆：后面的消息全部排队，prefetch 进来的消息只能干等，进程还无法优雅退出。短退避可以留在进程内，但长延迟必须交给 TTL 队列。

**展开**

1. **吞吐影响**：假设一条消息要等 30 秒，单消费者在这 30 秒内处理能力是 0。QPS 从「1/处理耗时」掉到「1/等待时长」。积压随之线性增长。
2. **内存影响**：`Qos(50)` 允许 50 条 unacked 在客户端。sleep 期间它们都占着内存、不能被其它消费者接管，等于把并行的队列变成了串行的漏斗。
3. **可靠性影响**：sleep 期间如果连接断开或进程被杀，消息会重投，但你已经「等过」的时间白费了，还可能和重投的消息重复执行。
4. **可控性影响**：`time.Sleep` 不能响应 `ctx.Done()`。本项目用 `select { case <-timer.C: case <-ctx.Done(): }`（`worker/retry.go:128`），进程退出时能立刻 `Nack(requeue=true)` 把消息还回去。
5. **本项目的折中**：进程内退避只做**短等待**（≤4s），用于抹平瞬时抖动；真正的**长延迟**（30s）交给重试队列 —— 消费者发完消息立刻 ACK，腾出手处理别的消息。代价是消息离开本进程后**顺序不再受控**，所以业务必须幂等。
6. **如果要并发**：不能只加 goroutine，因为同一队列的多条消息并发处理会破坏顺序（Q16）。正确做法是按 key 路由到固定消费者，或接受乱序并用版本号收敛。

**代码依据**
- 可中断 sleep：`worker/retry.go:128`。
- 短退避常量：`worker/retry.go:19`。
- 长延迟外置：`rabbitmq/retry.go:17`。

**可能的追问**
> 「那你们进程内不也 sleep 了吗？」
> 是，但它是**有界且可中断**的：最长 4 秒、最多 3 次、退出时可立即放弃。这和「在回调里 sleep 30 秒做重试」是两回事。判断标准是：等待时长是否超过「可以接受阻塞整条队列」的量级。

## Q11. 如何设计死信队列和告警？消息进入死信队列后，是自动重放还是等待人工处理？

**一句话要点**
每个主队列配**专属死信队列 + 精确路由键**，死信只落到自己的队列；消费者记录 `event_id`/重试轮数/消息体后 ACK。默认**人工/工具重放**，因为自动重放一条有毒消息只会再次进死信，形成循环。

**展开**

1. **拓扑设计**：
   - 所有主队列共用 `dlx.events` 交换机，但每个主队列声明自己的 `x-dead-letter-routing-key = <queue>.dlx`（`rabbitmq/rabbitMQ.go:83`）。
   - 死信队列 `<queue>.dlx` 只用**精确键**绑定（`rabbitmq/dlx.go:47`）。
   - 为什么不能用 `#`：那等于把 topic 交换机当 fanout 用，一条 `like` 的死信会被复制到 comment、social、timeline 的所有死信队列，被不相干的消费者处理。
2. **消费死信**：`DLQWorker` 解析 `event_id`，打印队列、轮数、完整 body，然后 **ACK**（`worker/dlqworker.go:66`）。继续 requeue 只会反复冲击下游；死信队列是「隔离区」，不是「重试区」。
3. **告警设计**（生产应有，当前只打日志）：
   - **任何一条消息进入死信都应告警**，因为正常情况下它不该发生。指标用 counter（queue + event_type 维度），而不是只看日志。
   - 同时监控**死信深度**：如果消费者也挂了，深度会持续上涨。
   - 消息体里必须有 `event_id`，否则排查和重放都无从下手。
4. **自动 vs 人工**：
   - 默认人工。死信通常意味着代码 bug、坏数据或下游长期故障，自动重放会在根因未修复时再次失败，甚至放大故障。
   - 可以提供「按 event_id 单条重放」「按时间范围批量重放」的管理接口，带限速和审计。重放时 **event_id 必须保持不变**，否则消费端去重失效。
   - 只有当失败原因是「已确认恢复的临时故障」时，才适合自动重放。
5. **重放的安全性**：依赖消费端幂等。点赞重放是 `INSERT IGNORE` 空操作；热度重放被 24h 去重标记挡住；评论重放被 `event_id` 挡住；通知重放被通知表唯一索引挡住。**没有幂等的重放是灾难。**

**代码依据**
- 精确死信路由键：`rabbitmq/rabbitMQ.go:71`。
- 死信声明：`rabbitmq/dlx.go:32`。
- 死信消费：`worker/dlqworker.go:56`。
- 已知缺口：`worker/dlqworker.go:64` 的 TODO。

**可能的追问**
> 「死信队列会不会无限增长？」
> 会，如果没人处理。所以 DLQ 本身也要有保留策略和清理/归档，并且必须有深度告警；否则它只是把「消息丢失」变成了「磁盘写满」。

## Q12. 如果一个 Worker 同时处理大量消息，如何限制 Goroutine 数量、数据库连接数和单条消息的处理超时？

**一句话要点**
本项目用「**每队列单 goroutine + prefetch 50**」把并发天然限制在极低水位；真要提高并发，靠增加消费者/Channel 或 worker pool，而不是给每条消息开 goroutine。数据库连接由进程级连接池兜底，单条超时目前只有 Redis 和 publish 有，DB 没有 —— 这是已知缺口。

**展开**

1. **Goroutine 限制（现状）**：
   - 每个 Worker 一个 `Consumer.Run` 循环，串行调用 `process`（`worker/retry.go:50`）。
   - 一个 Worker 进程里同时运行的消费循环 = 4 个业务队列 + 4 个死信队列；API 进程里另有 3 个通知队列 + 1 个时间线消费者。
   - 所以「大量消息」不会产生大量 goroutine，只会产生积压。
2. **prefetch 的意义**：`Qos(50)` 限制**未 ACK 的消息数**。它既是内存上限，也是崩溃时重投量的上限。如果处理很慢，broker 最多再推 50 条，不会把客户端内存打爆。
3. **数据库连接数**：
   - 进程级池默认 `MaxOpenConns=64 / MaxIdleConns=16`（`config/loadconfig.go:35`）。
   - 当前串行消费每队列只占 1 条，远低于池上限；**扩消费者时**才会真正用到池，此时要同步评估 MySQL 的总连接数（API 实例数 × 64 + Worker 实例数 × 64 很容易打满）。
4. **单条消息超时（现状与缺口）**：
   - 有：Redis 单操作 50ms（`video/video_cache.go:17`）、publish confirm 3s、Outbox publish 10s。
   - 没有：DB 操作继承消费者 ctx，没有 per-message deadline。一条慢 SQL（锁等待）会卡住整个队列，直到连接层超时。
   - 正确做法：`msgCtx, cancel := context.WithTimeout(ctx, 3s)`，超时返回 error → 走重试。注意超时必须**映射成失败**，否则等于静默丢消息。
5. **扩并发的三种方式**（按代价排序）：
   - 多开消费者/Channel（竞争消费）：简单，但**放弃同队列顺序**。
   - worker pool + 按 key 路由：保留同 key 顺序，复杂度中等。
   - 拆队列（按业务/优先级）：最彻底，也最重。
6. **一个反直觉点**：消费端扩 10 倍不一定有用（Q17）。如果瓶颈是同一视频的行锁或 Redis 单线程，加消费者只会让锁竞争更激烈。

**代码依据**
- 串行消费：`worker/retry.go:50`。
- prefetch：`cmd/worker/main.go:64`；`worker/outboxworker.go:215`。
- 连接池：`config/loadconfig.go:35`；`db/db.go:36`。
- Redis 超时：`video/video_cache.go:17`。

**可能的追问**
> 「为什么时间线消费者用 Qos(10)？」
> 它每条消息是一次 Redis 写 + 裁剪，处理很快；10 是为了在 Redis 抖动时少压一些 unacked，减少重投量。prefetch 应该按「单条处理耗时 × 可接受内存」来定，而不是抄一个数字。

## Q13. 点赞落库成功，但热度消息丢失，最终如何修复热度？是否需要定期对账？

**一句话要点**
先分清丢的是哪一份：MySQL 的 `videos.popularity` 由落库事务保证，不会丢；丢的是 Redis 分钟桶，只影响热榜精度，且窗口滚过 60 分钟就自然消失，**不会累积成永久偏差**。修复路径是「死信重放 + 实体缓存失效」，是否对账取决于业务是否要求热榜精确。

**展开**

1. **什么情况才会丢**：热度消息 publish 失败且降级直写 Redis 也失败（例如 Redis 整体故障），或消息走到死信没人处理。正常路径下 confirm + 三级重试已经排除了绝大多数窗口。
2. **影响面**：

   | 数据 | 是否受影响 | 修复方式 |
   |---|---|---|
   | `likes` 行 | 不受影响 | 无需 |
   | `videos.likes_count` | 不受影响（同事务） | 无需 |
   | `videos.popularity` | 不受影响（同事务） | 无需 |
   | Redis 分钟桶 | 少 1 | 重放 / 等窗口滚过 |
   | 热榜分数 | 偏低，最多持续 60 分钟 | 同左 |
   | 实体缓存 | 可能短暂陈旧 | TTL / 主动失效 |
3. **修复手段**：
   - **死信按 `event_id` 重放**：最直接。热度去重是幂等的，重放安全。
   - **实体缓存**：`videos.popularity` 是权威值，详情页读 MySQL；缓存有 TTL，必要时主动删 key。
   - **热榜重算**：当前**做不到精确重算**，因为没有「热度事件流水」。MySQL 只有累计 `popularity`，无法还原「哪一分钟增加了多少」。这是设计边界，要主动说出来。
4. **要不要定期对账**：
   - **点赞/评论计数**：事务保证，不需要对账；最多做抽样校验作为兜底。
   - **热度**：`videos.popularity`（累计）和 Redis 分钟桶（60 分钟窗口）语义不同，**不能直接相等比较**，所以「对账」本身要先定义口径。可行的是「抽样比对最近一分钟的事件量与桶增量」，用于发现系统性丢失。
   - **更值得对账的是可靠性指标**：Outbox `pending/failed` 数量、死信深度、重试率。这些能提前暴露「正在丢」。
5. **如果业务要求热榜精确**：热度事件也必须持久化（Outbox 表 / Kafka / Redis Stream），消费端可重放、可从某个时间点重建。代价是写入放大和存储成本。本项目选择「允许窗口内漂移」，因为热榜本身就是近似指标。

**代码依据**
- 计数与热度同事务：`video/like_repo.go:48`、`:51`。
- 热度失败抛错：`worker/popularityworker.go:58`。
- 去重标记：`video/popularity_cache.go:37`。
- 窗口 TTL：`video/popularity_cache.go:15`。

**可能的追问**
> 「那你们现在有对账任务吗？」
> 没有自动对账任务。可靠性靠「confirm + 三级重试 + 死信可见」在链路内解决，而不是靠事后核对。如果要做，第一步是补齐死信告警和 Outbox `failed` 监控，第二步才是抽样比对 —— 没有告警的对账只是在延迟发现问题。

# 三、第三层：故障与反问

## Q14. 简历中说「MQ 不可用时不丢写」，但如果 API 已经将点赞记录写入 MySQL，发送 MQ 失败后进程立即崩溃，如何确保后续仍然有消息？★

**一句话要点**
先纠正前提：本项目**不是**「先写 MySQL 再发 MQ」，而是「先发消息、confirm 失败才同步写 MySQL」。所以不存在「库已提交、消息没发、进程崩溃」这个组合。承诺的准确边界是：**返回 200 时写入一定已持久化**；200 之前崩溃，客户端拿不到成功，会重试。

**展开**

1. **实际执行顺序**（`video/like_service.go:63`）：

   ```
   ① 校验（视频存在、未点赞）
   ② publish 落库事件 → 等 confirm（3s）
   ③ publish 热度事件 → 等 confirm（3s）
   ④ 两条都成功 → return nil → Handler 返回 200
      任一条失败 → 同步补那条（ApplyLike / UpdatePopularityCache）
   ```

2. **崩溃点枚举**：

   | 崩溃位置 | 消息 | 数据库 | 客户端 | 结果 |
   |---|---|---|---|---|
   | 发布前 | 无 | 无 | 无响应 → 重试 | 一致 |
   | 发布成功、未 confirm | 通常已在队列 | 无 | 超时 → 重试 | 消息会被消费，重试被幂等吸收 |
   | confirm 超时、降级前 | 已在队列 | 无 | 超时 → 重试 | 同上 |
   | 降级写库成功、未返回 | 可能在也可能不在 | 有 | 超时 → 重试 | 唯一索引吸收重复 |
   | 返回 200 后 | 至少一条路径已成功 | 有 | 成功 | 一致 |

3. **关键点**：**只要客户端收到 200，落库就一定已经发生**（confirm 成功意味着 broker 持久化；降级成功意味着 MySQL 已提交）。服务端不会「先说成功，再说消息丢了」。
4. **「不丢写」不等于「任何崩溃点都不丢」**。如果进程在降级写库之前崩溃，这次点赞确实没了 —— 但客户端也没收到成功，用户会重试，状态不会错。这是可接受的一致性边界。
5. **如果产品要求「服务端收下请求就必须最终落库」**（比如请求已经进入队列、用户不再重试），唯一正确解是 **Outbox**：业务行 + outbox 行同事务提交，后台 poller 投递。项目里「发布视频 → 时间线」就是这么做的（`worker/outboxworker.go:37`），而点赞没有用，是因为它在请求内等 confirm，已经用「同步确认 + 降级」覆盖了主要窗口，代价是多一个 RTT。
6. **一个体验缺口**：客户端可能没收到 200 但服务端已成功，用户重试会得到「已点赞」错误（当前 500）。正确做法是把「已点赞」处理成幂等成功，否则用户会以为失败。

**代码依据**
- 发布 + 降级：`video/like_service.go:63`、`:83`。
- confirm 语义：`rabbitmq/publisher.go:66`（注释明确写了「不代表消费者已处理」）。
- Outbox 对照：`worker/outboxworker.go:26`。

**可能的追问**
> 「那你们干脆全用 Outbox 不是更稳？」
> 更稳，但点赞是高频写，Outbox 会多一次 INSERT、多一张表的热点、多 1 秒轮询延迟；而点赞本身可以在请求内等 confirm。**Outbox 适合「不能等 MQ、且必须原子」的场景（视频发布），同步 confirm 适合「能等一个 RTT」的场景（点赞）。**

## Q15. 如果先写业务数据库，再直接发布 RabbitMQ 消息，而不是使用 Outbox，系统在哪个时间窗口会丢失消息？

**一句话要点**
窗口在「事务提交成功」到「消息被 broker 确认」之间：进程崩溃、网络分区、broker nack、confirm 超时都会让消息消失。更糟的是，数据库里已经有行，用户重试会被判重挡住，**事件永久无法补回**。

**展开**

1. **丢失窗口**：

   ```
   BEGIN → INSERT likes → UPDATE counts → COMMIT   ✅ 数据库已生效
                                            │
                                            ├─ 进程崩溃        → 消息从未发出
                                            ├─ 网络分区        → publish 失败
                                            ├─ broker nack     → 消息被拒
                                            └─ confirm 超时    → 结果未知
   ```

2. **后果比「少一条消息」严重**：
   - `likes` 行存在，但 `likes_count` / `popularity` 少 1（如果计数在消费端）→ 永久偏差。
   - 通知不发、热度不加。
   - 用户看到「已点赞」不会重试；即使重试，同步 `IsLiked` 也会返回「已点赞」，事件永远补不回来。
3. **为什么「重试」救不了**：写库在前的设计把「用户重试」这条自愈路径关掉了。这是它比「发布在前」更危险的地方 —— 失败是静默的、永久的。
4. **Outbox 如何消除窗口**：业务行和 outbox 行在**同一个事务**里提交，消息的「意图」和业务状态一起持久化。之后 poller 扫描 `pending` 投递，失败退避重试，崩溃由 `ReapStuck` 回收，重复由消费端幂等吸收。于是「业务已提交」⇔「消息一定能被投递（至少一次）」。
5. **Outbox 的代价**（要主动说）：
   - 秒级投递延迟（轮询 1s）。
   - outbox 表增长，需要 `PurgeSent`（保留 24h）。
   - 多一套状态机（pending/processing/sent/failed + 租约 + fencing token）。
   - 仍需消费端幂等：Outbox 只保证「不丢」，不保证「不重」。
6. **取舍结论**：写路径必须「不能等 MQ + 不能丢」→ Outbox；能接受一个 RTT 的同步 confirm → 直接发布 + 降级（本项目点赞/评论）。**两者都比「先写库再随手 publish」可靠。**

**代码依据**
- Outbox 同事务写入：`video/video_entity.go:79`；投递：`worker/outboxworker.go:37`。
- 抢占与令牌：`video/outbox_repo.go:59`、`:113`。
- 崩溃回收：`video/outbox_repo.go:140`。

**可能的追问**
> 「Outbox 会不会重复投递？」
> 会，而且一定会：confirm 丢失后 poller 重投。所以 Outbox 的准确语义是「至少一次」，消费端必须幂等。Outbox 解决的是「丢」，不是「重」。

## Q16. 如果同一用户对同一视频连续点赞、取消点赞、再次点赞，消息乱序后热度如何保证正确？★

**一句话要点**
要分两种语义：热度是**增量事件**（+1/-1 可交换），乱序不影响总和，只要每条恰好生效一次（`event_id` 去重）；点赞行是**状态变更**（插入/删除不可交换），乱序会留下错误状态。当前靠「单队列单消费者」保序，扩容时会破坏它，必须显式设计。

**展开**

1. **热度为什么不怕乱序**：

   ```
   like(+1) → unlike(-1) → like(+1)
   任何顺序求和都是 +1，前提是每个事件只生效一次
   ```

   `ZINCRBY` 是加法，交换律成立。真正要防的是**重复**，不是顺序，所以用 `event_id` + Lua 原子去重（`video/popularity_cache.go:36`）。
2. **点赞行为什么怕乱序**：

   ```
   正确顺序：like → unlike → like   ⇒ 最终已点赞
   乱序后：  like → like → unlike   ⇒ 最终未点赞（错误）
   ```

   唯一索引保证「同一个 like 重复插入」幂等，但它**不保证顺序**，也无法判断「这条 like 是不是旧消息」。
3. **当前为什么基本有序**：`like.like` 和 `like.unlike` 进同一个队列、一个消费者、一个 goroutine，FIFO 处理（`cmd/worker/main.go:189`）。同一用户的请求通常也按到达顺序发布。
4. **什么时候会乱**：
   - Worker 扩成多实例/多消费者（竞争消费，谁先拿到谁处理）。
   - 消息重投：一条 like 处理完但 ACK 丢失，用户随后 unlike，旧 like 被重投 → **重新插入点赞行**。
   - 多个 publisher/Channel 并发发布，broker 不保证跨 Channel 顺序。
5. **真实缺口（要主动承认）**：`LikeWorker` 目前**没有用 `EventID` 去重**，只用业务唯一键。所以「重投的旧 like 排在 unlike 之后」会复活点赞 —— 最终状态与用户最后一次操作相反（行与计数仍在同一事务里，彼此一致，只是一起错）。
6. **解法（按成本排序）**：
   - **按 key 路由**：`hash(user_id, video_id)` 固定到某个队列/消费者，同 key 严格有序。
   - **事件带版本**：客户端序号或 `occurred_at`，消费端记录 `last_event_version`，旧事件直接丢弃。
   - **状态型 API**：接口改成「设置目标状态」（like/unlike 幂等），而不是「增量动作」，重试和乱序都自然收敛。
   - **消费端 event_id 去重表**：挡住重投的旧事件，但仍需版本判断谁更新。
7. **统一话术**：不要笼统说「MQ 保证顺序」。准确说法是「**单队列 + 单消费者 + 单 Channel 时保序**；扩容或重投会破坏，业务必须能收敛」。

**代码依据**
- 同队列：`rabbitmq/likeMQ.go:21`、`:22`。
- 单消费者：`cmd/worker/main.go:189`。
- 消费端只用 user/video：`worker/likeworker.go:53`。
- 热度可交换 + 去重：`video/popularity_cache.go:40`。

**可能的追问**
> 「那通知的顺序呢？」
> 通知每个类型一个队列（like/comment/social），同队列单消费者保序；跨类型不保证。同一用户的「先关注后点赞」两条通知可能乱序到达，但通知本身是独立事实，乱序只影响展示顺序，不影响正确性。

## Q17. RabbitMQ 的消费者数量增加 10 倍，系统吞吐量一定会增加 10 倍吗？哪些资源会成为瓶颈？

**一句话要点**
不会。吞吐由最短的那块板决定：同一视频的**行锁**、MySQL 事务提交、Redis 单线程、publisher confirm 的串行锁、以及顺序约束，任何一个都可能让「加消费者」变成「加锁竞争」。

**展开**

1. **第一瓶颈通常是数据库行锁**：`UPDATE videos SET likes_count = GREATEST(likes_count+1, 0)` 会对同一行加排他锁。热门视频的所有点赞在 MySQL 层是**串行**的，消费者再多也只能排队（`video/like_repo.go:83`）。
2. **事务提交成本**：每个点赞一个事务、一次（或多次）redo fsync。QPS 上限受磁盘 IOPS 和 `innodb_flush_log_at_trx_commit` 约束。
3. **Redis**：单线程执行命令。`ZINCRBY` 本身很快，但同一分钟桶 key 的热点、Lua 脚本、网络 RTT 都会排队；集群模式下同一 key 落在一个分片。
4. **publisher confirm 的串行锁**：一个事件类型一个 publisher、一把 mutex，`发布 + 等确认` 串行（`rabbitmq/publisher.go:80`）。单实例单类型的发布吞吐 ≈ `1 / RTT`。扩 API 实例能线性提升，扩消费者不能。
5. **顺序约束**：增加消费者 = 竞争消费 = 放弃同 key 顺序（Q16）。点赞/取关这类状态变更不能随便放弃顺序。
6. **prefetch 与内存**：`Qos(50)` 是每个消费者的上限；10 倍消费者 = 10 倍 unacked 内存和 10 倍崩溃重投量。
7. **正确的扩容顺序**：先量「生产速率 vs 消费速率」和「单条消息各阶段耗时」→ 找出占比最大的阶段 → 再决定扩哪一层。如果 80% 时间在等行锁，扩消费者是负优化。

**代码依据**
- 行锁更新：`video/like_repo.go:83`。
- 发布串行：`rabbitmq/publisher.go:80`。
- 消费者数量：`cmd/worker/main.go:189`。
- prefetch：`cmd/worker/main.go:64`。

**可能的追问**
> 「那热门视频的点赞怎么优化？」
> 常见做法：计数改为 Redis 原子自增 + 异步批量回写 MySQL（把行锁从「每赞一次」降到「每批一次」），或者按视频分片计数再汇总。代价是计数不再是强一致，详情页需要用缓存值。这是「热点写」问题，不是 MQ 问题。

## Q18. 当队列积压达到百万条时，你如何决定扩容消费者、限流生产者还是降低非核心任务优先级？

**一句话要点**
先判断积压的**性质**：生产太快、消费太慢、还是 broker 自身故障。下游有余量且能放弃顺序 → 扩消费者；下游是瓶颈 → 限流生产、降级非核心；broker 有问题 → 先修 broker。队列按事件类型拆开，正是为了让这个决策可执行。

**展开**

1. **先看三个数**：
   - 生产速率 vs 消费速率（是否持续倒挂）。
   - 队列深度与 unacked 数（消费者是「没拿到」还是「拿到了处理不完」）。
   - 最老消息年龄（用户实际感知到的延迟）。
2. **分情况处理**：

   | 现象 | 判断 | 动作 |
   |---|---|---|
   | 生产突增，消费速率正常 | 尖峰流量 | 先扩消费者（若下游有余量），同时 API 限流非核心 |
   | 消费速率骤降，unacked 高 | 下游慢/锁 | 不要扩消费者，先查 MySQL/Redis 延迟，必要时降级 |
   | unacked 为 0，消息堆在 broker | 消费者挂了/连接断 | 修消费者、重连 |
   | broker 内存/磁盘告警、flow control | broker 自身 | 扩磁盘/内存、加节点，消费者扩容无效 |
3. **按优先级降级**（队列拆分让这件事可行）：
   - **核心**：点赞/评论/关注的落库 —— 尽量保。
   - **可延迟**：热度分钟桶、通知 —— 可以慢，甚至短时间丢弃（热度窗口会滚过）。
   - **可重建**：时间线 —— 可以从 MySQL 重建前 1000 条。
4. **限流生产**：API 对非核心接口返回 503（不是 500），让客户端退避；核心写接口保留配额。绝不能用「消费端直接 ACK 丢弃」来降积压 —— 那是静默丢数据。
5. **极端情况**：如果积压已经超过 SLA 且无法短期消化，宁可让低价值事件过期/进死信并告警，也不要让核心队列被拖垮。**丢弃必须是显式的、可统计的、可重建的**，不能是 `Ack` 掉。
6. **扩容的副作用**：消费者变多 → 顺序丢失（Q16）、DB 连接数上涨、死信/重试流量放大。扩之前先确认这些代价可接受。

**代码依据**
- 队列拆分：`rabbitmq/topics.go:22`（like/comment/social/popularity 各自独立）。
- 预取上限：`cmd/worker/main.go:64`。
- 重试拓扑：`rabbitmq/retry.go:35`。

**可能的追问**
> 「百万积压要多久才能消化？」
> 用「积压量 ÷（消费速率 − 生产速率）」估算。如果消费 200/s、生产 100/s，净消化 100/s，百万条需要约 2.8 小时 —— 这通常不可接受，所以真正的解法是**同时**扩消费、限生产、降级非核心，而不是单点扩容。

## Q19. 如果点赞接口 RT 下降了，但消息积压越来越严重，这个优化是否成功？你会用哪些指标判断？

**一句话要点**
不算成功。这只是把延迟从 API **转移**到了队列：用户点赞后详情页/热榜看不到，体验依然坏，而且积压最终会反噬（内存、重投、超时）。判断标准是「端到端时延有界」，不是「接口 RT 变短」。

**展开**

1. **为什么 RT 下降可能是假象**：
   - 同步路径从「写 MySQL + 写 Redis」变成「两次 publish confirm」，RT 自然下降。
   - 但如果消费能力没跟上，副作用完成时间被推后，**用户感知的总时延**（点赞 → 计数/热榜可见）反而变长。
   - 积压到一定程度会触发 broker flow control、消费者超时、重投放大，最终连 API 的 publish 也会变慢。
2. **必须同时看的指标**：

   | 维度 | 指标 | 判断 |
   |---|---|---|
   | 生产 | publish 速率、confirm p99、发布失败率 | API 是否真的更稳 |
   | 消费 | 消费速率（msg/s）、单条处理耗时 p99 | 是否能追上生产 |
   | 积压 | 队列深度、深度导数、**最老消息年龄** | 是否持续恶化 |
   | 失败 | 重试率、死信速率、DLQ 深度 | 是否在静默丢 |
   | 下游 | MySQL 事务耗时/锁等待、Redis 延迟、连接池等待 | 瓶颈在哪 |
   | 业务 | 点赞数与 MySQL 偏差、热榜延迟、通知延迟 | 用户是否真的感知更好 |
3. **成功标准**（建议直接背）：
   - 峰值下队列深度**有界**（不随时间线性增长）。
   - 最老消息年龄 < SLA（例如点赞 1s、热榜 5s）。
   - 死信速率 = 0，重试率在可解释范围内。
   - API p99 没有因为 publish confirm 而抬高。
4. **如果积压涨但 RT 降，说明什么**：消费端是瓶颈。优化方向不是继续压 API，而是：
   - 提升消费吞吐（批量事务、减少 RTT、按 key 并发）。
   - 削峰（前端防抖、合并点赞、限流）。
   - 拆分/降级非核心事件（热度、通知）。
5. **一个容易被忽略的点**：RT 下降可能来自「降级路径没被触发」或「测试流量太小」。要在**压测/峰值**下看 p99 和积压曲线，而不是看平均值。

**代码依据**
- 同步路径耗时构成：`video/like_service.go:24`（校验 + 两次 confirm）。
- 当前可观测性：只有日志和 pprof（`internal/observability/pprof.go`），**没有 Prometheus 指标**，这是要主动承认的缺口；生产化第一步就是补 counter/gauge。

**可能的追问**
> 「没有指标你怎么证明优化有效？」
> 用压测做对照实验：固定并发和数据规模，分别测「同步写」和「异步化」两版的 API p99、端到端可见延迟（点赞后轮询详情页直到计数变化）、队列深度曲线。没有监控数据时，至少要有可复现的压测方法和明确的对照口径，不能只说「感觉快了」。

## 五、如果只记三件事

1. **200 的语义是「已持久化」，不是「副作用已完成」**。说清这一点，所有「零丢失/零重复」的追问都会回到同一个框架：发出去（confirm）→ 原子生效（事务）→ 扛故障（重试）→ 兜底可见（死信）。
2. **幂等要落在存储操作上，不要落在应用判断上**。`SELECT` 后 `INSERT`、`IsLiked` 后发消息，都有窗口；唯一索引、条件更新、Lua 原子脚本才是最终防线。
3. **所有绝对化表述都要配边界**：「不丢写」= 返回 200 时已持久化；「不乱序」= 单队列单消费者；「最终一致」= 允许秒级/分钟级窗口，且死信有人看。能主动说出边界，比坚持结论更加分。

## 附：一分钟口述串联

> 我们把点赞拆成「同步校验 + 两条异步消息」：同步只做参数、视频存在、是否已点赞的校验，然后发落库事件和热度事件，各自等 3 秒 publisher confirm；都成功就返回 200，哪条失败就同步补哪条。
>
> 落库事件由 LikeWorker 消费，`INSERT IGNORE` 加联合唯一索引做幂等，插行、`likes_count +1`、`popularity +1` 在同一个事务里 —— 这是为了修掉「插行成功、计数失败、重试被唯一索引挡住导致永久少 1」的问题。
>
> 热度事件由 PopularityWorker 消费，只写 Redis 分钟桶，用 `event_id` 加 Lua 把去重、`ZINCRBY`、续期做成原子操作；`event_id` 在发布前生成，MQ 和降级路径共用，避免 confirm 超时导致加两遍。
>
> 失败处理是三级：进程内退避 3 次、TTL 重试队列 30 秒 3 轮、然后 `Nack(requeue=false)` 进专属死信队列。消息系统只保证至少一次，所以所有消费端都必须幂等；顺序只在「单队列单消费者」时成立，扩容时要按 key 路由或加版本号。
>
> 已知边界：Redis 故障期间热度精度会丢，但 60 分钟窗口会滚过、不累积；死信目前只打日志，生产要补告警和按 event_id 重放。
