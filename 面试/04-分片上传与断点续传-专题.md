## 一、先说结论：这个模块到底解决了什么

一个 200MB 的 mp4，用一次 HTTP POST 传完，有四个绕不过去的坑：

| 坑 | 后果 |
|---|---|
| 单连接单流 | 传到 90% 断网 → 全部重来 |
| 服务端无进度记忆 | 无法断点续传 |
| 中间层 body size 限制 | 大请求易被 Nginx/Gin 砍掉 |
| 单连接 TCP 拥塞控制 | 跑不满带宽 |

**分片本质**：把一个不可靠的大传输，拆成 N 个可独立重试的小传输。

但分片不是免费的——它把「无状态的文件上传」变成了「**有状态的分布式会话**」。一旦有状态，下面这些问题就全冒出来了：

1. 状态存哪儿？（Redis，为什么不是 MySQL 见 §7）
2. 并发传 3 片，同时更新状态，会不会互相覆盖？（会，这就是本模块原来的 P0 bug，见 §3）
3. 状态说「传完了」，但磁盘上的字节真的在吗？（不一定，见 §5）
4. 重试、刷新、多标签页，会不会重复合并出两份文件？（会，见 §6）

**本文的骨架就是这四个问题的答案。**

## 二、四个接口与数据布局

### 2.1 接口

| 接口 | 作用 | 幂等性 |
|---|---|---|
| `POST /video/chunk/init` | 建会话 / 按 `file_hash` 找回旧会话 | 同文件同账号 → 同一 `upload_id` |
| `POST /video/chunk/upload` | 传一片（multipart） | 重复传同一片 → 200 短路 |
| `POST /video/chunk/status` | 查位图，返回已传下标 | 只读 |
| `POST /video/chunk/complete` | 合并 + 校验 + 清理 | 重复调用 → 回放同一 URL（仅限本人） |

### 2.2 Redis key 布局

```
chunk_upload:{upload_id}          会话元数据 JSON        TTL 24h
chunk_upload_bits:{upload_id}     进度位图（bit i）      TTL 24h
chunk_upload_hash:{uid}:{hash}    (账号,文件MD5)→会话ID   TTL 24h
chunk_upload_result:{upload_id}   合并结果 URL+归属      TTL 1h
chunk_upload_lock:{upload_id}     合并互斥锁（token）    TTL 10min，心跳续期
```

**三个 TTL 必须一起续**：会话、位图、hash 索引是同一份状态的三个视角，任何一个先过期都会产生错位——位图还在但会话没了（upload 404），或会话还在但 hash 索引没了（同一文件被当成新上传建第二份会话）。所以 `touchSession` 用一次 `PExpireMany` 同时续三者（`chunk_handler.go:123-132`）。

**为什么进度要单独拆成一个 key？** 因为「元数据」和「进度」的写入模式完全不同：

- 元数据：init 时写一次，之后基本只读
- 进度：每传一片写一次，且是**并发写**

把它们放在同一个 JSON 里，就意味着每次更新进度都要「读整个 JSON → 改一位 → 写回整个 JSON」——这正是原来那个 P0 bug 的根源。拆开之后，进度可以用 `SETBIT` 单 bit 原子写，元数据根本不参与。

### 2.3 磁盘布局

```
.run/uploads/
├── tmp/{uploadID}/
│   ├── 0      1      2   ...       ← 已确认的完整分片
│   └── 3.{rand}.part                ← 正在写的分片（请求独占，rename 前）
└── videos/{uid}/{date}/{rand}.mp4   ← 合并后的成品
    └── {rand}.mp4.part              ← 合并中的半成品（崩溃后由 cleaner 回收）
```

分片临时名带**请求唯一后缀**（`3.a1b2c3d4.part`），不是固定的 `3.part`。`.part` 保证「读到的 `3` 永远是完整片」，唯一后缀保证「同一片的并发写者各写各的临时文件、不会互相覆盖或互删」。详见 §5.3。

## 三、P0：并发上传为什么会丢进度（以及怎么修）

### 3.1 原来的实现

```go
// 旧代码
session, _ := h.getSession(c, req.UploadID)   // ① 读整个 session JSON
...
session.UploadedBits[req.ChunkIndex] = true   // ② 在内存里改一位
h.saveSession(c, session)                     // ③ 把整个 JSON 写回 Redis
```

前端 `MAX_CONCURRENT = 3`，同一时刻有 3 个请求在跑。真实时序：

```
请求A(片5): GET session → 内存里 bits[5]=true  ─────────────┐ 写回 {bits:[..,5,..]}
请求B(片6): ───── GET session → 内存里 bits[6]=true ────────┼── 写回 {bits:[..,6,..]}  ← 覆盖了 A 的 5
请求C(片7): ──────────── GET session → bits[7]=true ────────┴── 写回 {bits:[..,7,..]}  ← 覆盖了 B 的 6
```

**这是教科书式的 read-modify-write 竞态**：三个请求读到的都是同一个旧值，各自基于旧值计算新值，最后写的人赢。结果是「3 片都传成功了，会话只记得最后一片」，complete 时 `missing=2`。

注意它**不是**「偶发的小概率问题」。并发度越高、网络抖动越多的场景（弱网、大文件），命中率越高。测试里因为 `uploadChunk` 是串行调用的，永远复现不出来——这也是这类 bug 最容易溜到生产的原因。

### 3.2 修法一（错误示范）：加锁

「加个分布式锁，读-改-写都在锁里」——能用，但代价是：

- 每片上传多 2 次 Redis 往返（加锁/解锁）
- 并发 3 片变成串行，上传吞吐直接掉到 1/3
- 锁的 TTL、误删、死锁全套问题都要处理

**为一个单 bit 的写引入锁，是把问题想重了。**

### 3.3 修法二（采用）：换成真实 Redis 位图

```go
// SetBitWithTTL：置位和续期必须在同一段脚本里完成
var setBitWithTTLScript = redis.NewScript(`
redis.call("SETBIT", KEYS[1], ARGV[1], ARGV[2])
redis.call("PEXPIRE", KEYS[1], ARGV[3])
return 1
`)
```

`SETBIT` 是 Redis 的**单命令原子操作**，作用在服务端的一个 bit 上。三个并发请求各写各的 offset，物理上互不干扰：

```
请求A: SETBIT key 5 1   ┐
请求B: SETBIT key 6 1   ├─ 三个不同的 bit，Redis 串行执行，全部生效
请求C: SETBIT key 7 1   ┘
```

对比：

| | 旧（JSON） | 新（位图） |
|---|---|---|
| 写粒度 | 整个 session（几百字节 JSON） | 1 个 bit |
| 并发安全 | ❌ 需外部锁 | ✅ 命令本身原子 |
| 读进度 | 一次 GET + JSON 反序列化 | `GETBIT` pipeline / `BITCOUNT` |
| 占用 | ~200B/会话 | `ceil(total/8)` 字节（40 片 = 5 字节） |

**关键认知**：并发问题优先想「能不能换一个本身就原子的数据结构和命令」，而不是「怎么给非原子操作加锁」。`SETBIT`、`HINCRBY`、`INCR`、`SETNX`、`Lua` 都是这个思路的工具。

顺带一个细节：`SETBIT` 之后必须 `PEXPIRE`，否则第一次置位创建的 key 永不过期（孤儿 key）。**pipeline 不是原子执行**，它只是批量发送：`SETBIT` 成功而 `PEXPIRE` 失败（连接中断、实例切换）仍会留下永不过期的 key。所以把两条命令放进 Lua 脚本，由 Redis 单线程一次性执行——要么都生效，要么都不生效。这也是本项目里「能用命令原子解决就别加锁」原则的延伸：**复合的原子性用 Lua，不用分布式锁**。

### 3.4 位图的配套方法

```go
func (h *ChunkUploadHandler) reconcileBits(...) ([]bool, error)  // GETBIT pipeline 读 N 位 + 逐片 os.Stat 对账
```

`GETBIT` 对不存在的 key 返回 0 而不是报错，所以「会话刚建、一片没传」时读出来是全 false，不需要特殊处理空 key。

> 判满不再单独用 `BITCOUNT`：位数对了不等于字节还在，必须先过一遍磁盘对账（见 §5.5）。

## 四、参数校验：别让客户端造出「永远完不成的会话」

init 之前，四个字段 `file_size / chunk_size / total_chunks / file_hash` 全是客户端自己报的。服务端**照单全收**会出什么事？

| 客户端瞎报 | 后果 |
|---|---|
| `total_chunks` 远小于实际 | 位图永远填不满？不——是前端只传这么多片，合并出来的是**半个文件** |
| `total_chunks` 远大于实际 | 位图永远填不满，会话 24h 内**不可能完成** |
| `chunk_size` 和 `file_size` 不自洽 | `ExpectedChunkSize` 算出负数/越界长度，合并时按错误下标读 |
| `file_hash` 不是 MD5 | 续传索引失效；合并后校验必然失败 |
| `filename` 带 `../` | 路径穿越风险（虽然最终文件名是 randHex，但仍应拒绝） |

修法是 `InitChunkUploadRequest.Validate()` 一次性卡死：

```go
total_chunks == ceil(file_size / chunk_size)   // 三者自洽
chunk_size ∈ (0, 5MB]                          // 与前端 CHUNK_SIZE 对齐，后端兜底
file_size  ∈ (0, 200MB]                        // 与单次上传接口一致
total_chunks ∈ (0, 4096]                       // 防止恶意分配超大位图
file_hash 是 32 位 hex
filename 不含 / \
```

还有一个容易漏的：**续传命中旧会话时也要校验**。用户换了分片大小重新选同一个文件，`(uid, fileHash)` 会命中旧会话，但旧会话的 `chunk_size` 和这次不一样——直接复用会导致前端按新大小切片、服务端按旧大小校验长度，全部 400。所以加了 `session.Matches(req)`，参数不一致就当陈旧会话重建。

## 五、幂等的三层，和「位图 ≠ 磁盘」的坑

### 5.1 三层幂等

| 层 | 位置 | 防什么 |
|---|---|---|
| 会话层 | `init` 的 `(accountID, fileHash)` → `upload_id` | 同一文件重复 init 不产生两份会话 |
| 分片层 | `upload` 的位图短路 | 同一片重复传不重复写 |
| 合并层 | `complete` 的结果缓存 + 合并锁 | 重复/并发 complete 不产生两份文件 |

### 5.2 分片层的短路不是「看一眼就返回」

原代码是 `if UploadedBits[idx] { return 200 }`。现在多了一步磁盘核对：

```go
uploaded, _ := h.cache.GetBit(ctx, bitsKey, idx)
if uploaded == 1 {
    if fi, err := os.Stat(chunkPath); err == nil && fi.Size() == expected {
        return 200          // 位图说传了，字节也真的在 → 短路
    }
    // 位图说传了，但文件没了（tmp 被清 / 容器重建 / 磁盘满）→ 清位重收
    h.cache.SetBitWithTTL(ctx, bitsKey, idx, 0, sessionTTL)
}
```

**为什么必须核对？** 因为位图和磁盘是两份独立的事实，而代码只信位图。一旦两者分歧：

- 客户端重传 → 被短路，不重建文件
- complete → `chunk i missing` → 500
- **24 小时 TTL 内这个会话永远完不成，且客户端无从知晓是哪一片坏了**

加了 `os.Stat` 之后，这个死锁**自愈**：下次重传时位被清掉，分片被重新写入。代价只是一次微秒级的 stat。

### 5.3 写分片必须原子替换

旧代码 `os.Create(chunkPath)` 是 **truncate 写**：打开瞬间文件被截成 0 字节，然后慢慢写 5MB。这中间存在一个窗口，另一个标签页触发的 complete 会读到「半片」，拼出损坏的 mp4。

第一次修法是「先写固定的 `{idx}.part`，写完 `os.Rename` 成 `{idx}`」。这解决了「读到半片」，但漏了**并发**：同一片被两个请求同时传（客户端重试与首次请求重叠、多标签页），两个写者共用同一个 `3.part`，会互相覆盖内容；Windows 上 `os.Rename` 不能覆盖已存在的目标，旧代码的兜底是「删目标再 rename」，于是两个写者还可能互相把对方刚 rename 好的文件删掉。

现在的做法是**请求独占临时名**：

```go
suffix, _ := randHex(8)
partPath := fmt.Sprintf("%s.%s.part", finalPath, suffix) // 3.a1b2c3d4.part
// ① 写自己的临时文件 → ② fsync → ③ 原子 rename 到 {idx}
if err := dst.Sync(); err != nil { ... }
if err := renameReplace(partPath, finalPath); err != nil { ... }
```

`renameReplace` 处理 Windows「目标已存在」的情况，但不是无脑删目标，而是有界重试：

```go
for attempt := 0; attempt < 5; attempt++ {
    if err = os.Rename(src, dst); err == nil { return nil }
    if _, statErr := os.Stat(src); statErr != nil { return err } // 自己的临时文件没了，重试无意义
    if _, statErr := os.Stat(dst); statErr == nil { _ = os.Remove(dst) }
}
```

几个要点：

- **临时名唯一**：并发写者各写各的文件，谁也不覆盖谁；最后 rename 成功的那份生效。
- **先 fsync 再 rename**：否则崩溃/断电后可能出现「文件名在、内容没落盘」。
- **删目标前先确认自己的源还在**：两个写者同时删目标时，只有一个能删成功，另一个不能因此判失败——它应该回去重试 rename，而不是把「目标已不存在」当成错误。
- **rename 仍可能失败**：极端情况下返回 500，客户端重试即可；位图只有在 rename 成功后才置位，所以不会留下「位是 1、文件是半片」。

回归测试 `TestConcurrentSameChunkUploadIsSafe`（8 个 goroutine 同时传同一片，断言全部 200、无 `.part` 残留、合并字节正确）与 `TestRenameReplaceKeepsDestinationWhenSourceMissing` 覆盖了这两点。

### 5.4 顺序很重要：先落盘，后置位

```
① 写 .part → ② rename → ③ SETBIT 置 1
```

如果反过来（先置位后写文件），进程在中间崩了，就会留下「位图说传了、磁盘却没有」——这正是 5.2 那个死锁状态。现在这个顺序下崩溃只会留下「文件在、位是 0」，最多让客户端重传一片。

**取舍原则：宁可重传一片，绝不可假完成。**

### 5.5 但这还不够：三个出口必须统一对账

5.2 的核对只在 `upload` 里生效，也就是说**只有「客户端主动重传这一片」才机会修正**。而最常见的场景恰恰用不上它：

> 用户刷新页面 → 重新选同一个文件 → `init` 命中同一会话，返回 `uploaded_chunks = [0,1,2,3]`（含坏片 3）
> → 前端跳过第 3 片 → 前端调 `status` 核对 → **status 说的是同一张不可信的位图** → gaps 为空
> → `complete` → 400 `chunk 3 missing` → 会话不会被删 → 重试还是 400
> → **卡死到 24h TTL 过期**

根因是「判断这一片到底在不在」这件事被散在了多处，而 `init` / `status` 直接拿位图当了答案。修法是**把它收敛成一个函数**，所有对外表达进度的出口都过它：

```go
// reconcileBits 是「位图」与「磁盘」这两份事实的唯一收敛点
func (h *ChunkUploadHandler) reconcileBits(ctx context.Context, s *ChunkUploadSession) ([]bool, error) {
    bits, err := h.cache.GetBits(ctx, h.bitsKey(s.UploadID), s.TotalChunks)
    ...
    for i, uploaded := range bits {
        if !uploaded { continue }
        fi, statErr := os.Stat(h.chunkPath(s.UploadID, i))
        if statErr == nil && fi.Size() == s.ExpectedChunkSize(i) { continue }
        bits[i] = false
        _ = h.cache.SetBitWithTTL(ctx, h.bitsKey(s.UploadID), int64(i), 0, sessionTTL) // 当场清位
    }
    return bits, nil
}
```

| 出口 | 改前 | 改后 |
|---|---|---|
| `init`（续传） | `chunkBits` 直接读位图 | `reconcileBits`，返回的分片一定磁盘上有 |
| `status` | 同上 | 同上 |
| `complete` 判满 | `BITCOUNT` | `reconcileBits` + `countBits` |

代价是每个出口多 N 次 `os.Stat`（几十片的 stat 是微秒级，比一次 Redis 往返还便宜）；换来的是**任何一个入口都能自愈**，不再依赖「客户端运气好重试到那一片」。

**配套的一环**：`complete` 失败时必须给出**完整**的缺失清单，客户端才能一轮补完。原来的 `mergeChunks` 是拼到第一片坏了就 `return`，只能报一个片号，客户端要一轮轮猜。现在先全量 `Stat` 一遍再动手：

```go
if len(missing) > 0 { return "", missing, nil }   // 不写半成品
```

响应统一带 `missing_chunks: [0, 3]`，前端据此把它从本地记账里删掉、立即补传、再重试合并——闭环完成。

### 5.6 TTL 管不了磁盘：必须有一个补偿清理任务

Redis 的 TTL 只保证 key 被回收，**不保证外部资源被回收**。本模块有三类残留在 Redis 之外：

| 残留 | 产生原因 | 谁来清 |
|---|---|---|
| `tmp/{upload_id}/` | 用户传一半放弃；会话过期 | `chunk_cleaner` |
| `videos/**/{rand}.mp4.part` | 合并中途进程崩溃 | `chunk_cleaner` |
| `videos/**/{rand}.mp4` | 合并成功但用户从未 publish | **没人清**（需要 assets 表，见 Q8） |

`chunk_cleaner` 每小时扫一次（`cmd/main.go` 在 Redis 可用时启动，启动时先跑一遍）：

- **tmp 目录**：只有「目录 mtime 超过 24h」**且**「Redis 里没有对应 session」才删。两个条件缺一不可——只看年龄会毁掉正在续传的活会话；只看 session 缺失会误删刚建好、还没写 session 的目录。
- **`.mp4.part`**：只看年龄（>24h）。这是合并的中间产物，不会有任何正常流程在读它。
- **成品 `.mp4` 一律不碰**：它可能已经被 publish 引用，磁盘状态无法判断「有没有主人」。

反过来的风险同样存在：清理太早会破坏正在进行的上传，清理太晚磁盘会满。所以清理任务要**保守**：Redis 读失败时直接跳过，宁可留着，也不在状态不明时删。

**边界**：cleaner 只清本实例磁盘；多实例共享存储时需要分布式协调或按实例分目录。用对象存储时，更彻底的做法是 `AbortMultipartUpload` + lifecycle 规则，而不是自建扫描任务。

## 六、complete：合并不是「复制粘贴」

### 6.1 完整流程

```
① 解析账号 → 查结果缓存 → 命中则校验 result.account_id 后回放（重复 complete 幂等）
② 读会话 → 校验 session.account_id（跨账号一律 403）
③ token 锁抢合并锁 → 抢不到返回 409（并发 complete 各拼一份会产生两个 URL）
   → 后台每 1/3 租约续期，避免大文件合并超过 10min 后锁被接管
④ 加锁后重新读结果和会话（不用加锁前的旧快照；另一个并发可能刚好完成）
⑤ reconcileBits 对账后判满（顺手清掉坏位）→ 不满返回 400 + missing_chunks 完整清单
⑥ 抢全局合并名额（容量 4，最多等 5s，超时 503）→ 限流保护磁盘 IO
⑦ mergeChunks 全量 Stat 后按序合并，MultiWriter 流式算整文件 MD5
⑧ 整文件 MD5 ≠ init 的 file_hash → 删半成品、作废会话、返回 400 code=file_hash_mismatch
⑨ rename .part → 成品 → 写结果缓存（含 account_id）→ 删 tmp → 删 bits/session → 条件删 hash 映射
```

### 6.2 为什么现在要校验整文件 MD5

原来只校验单片 MD5，有个致命盲区：**客户端自己算的 `chunk_hash` 是它自己声明的**。一个 buggy 或恶意的客户端，只要让它发的错误字节和它声明的 hash 自洽，服务端就照收不误——每片都"对"，拼起来是垃圾。

而 `file_hash` 在 init 时就拿到了，一直躺在会话里没被用过（只当续传索引）。合并时顺手算一遍：

```go
whole := md5.New()
sink := io.MultiWriter(partFile, whole)   // partFile 是最终的 .mp4.part，校验通过后才 rename
for i := 0; i < session.TotalChunks; i++ {
    io.Copy(sink, cf)   // 写盘 + 算 hash 一次 IO 完成
}
```

用 `MultiWriter` 而不是合并完再读一遍文件，是为了**避免 200MB 的二次读盘**。

**校验失败不能只删文件**：早期实现删完半成品就返回 400，但会话、位图、hash 索引都还在。客户端拿着同一个 `upload_id` 重试，还是会对同一份坏数据反复合并，一直卡到 24h TTL。现在的处理是 `invalidateSession`——删 tmp、删 bits、删 session，并且**条件删除** hash 映射（只在映射仍指向本会话时才删，避免误删并发 re-init 建的新映射）。前端收到 `code=file_hash_mismatch` 后重新 `init`、完整重传一次（最多一次），把「确定失败」变成一条能走通的恢复路径（`VideoView.vue:152-155,284-290`）。

### 6.3 清理顺序：rename → 写结果 → 删临时分片 → 删会话

```
rename .part → 成品
  → 写 chunk_upload_result:{id}（含 account_id）
  → 删 tmp 目录
  → 删 bits / session
  → CompareAndDelete hash 映射（仅当仍指向本会话）
```

顺序不能随便换：

- **结果必须早于删会话**：反过来会出现「会话没了但结果没写进去」，客户端重试收到 404，而文件其实已经合并好了。
- **结果也必须早于删 tmp**：如果先删 tmp 再写结果，进程崩在中间就是「位图说全齐、分片已经没了、结果也没有」——既不能回放，也不能续传，只能全量重传。
- **hash 映射要条件删除**：并发 `init` 可能已经把 `(uid, hash)` 指向新会话，无条件 `DEL` 会删掉新会话的索引。用 Lua 做「GET 相等才 DEL」（`CompareAndDelete`）。

即使某一步 Redis 删除失败，留下的也只是带 TTL 的 key，不会产生「假完成」的脏会话。

### 6.4 并发 complete：token 锁 + 心跳 + 全局限流

两个请求同时 complete（用户双击、代理重放、前端重试），都通过判满检查，就会各写一份文件、各返回一个 URL——两个文件都在磁盘上，后返回的那个赢。虽然不致命，但会留下孤儿文件。

锁的设计有四层，缺一层都会在某个时序下失效：

1. **token 锁**：`SETNX` 写入随机 token，释放时用 Lua「GET 相等才 DEL」。只删自己的锁，不会因为租约到期被接管后误删别人的锁。
2. **心跳续期**：合并 200MB 可能超过 10min 租约。后台每 `mergeLockTTL/3` 执行一次「GET 相等才 PEXPIRE」，仍然持有锁才续期（`RefreshLock`）。没有心跳，大文件合并到一半锁就过期，第二个请求会进来重复合并。
3. **锁内二次检查**：拿到锁后**重新读结果缓存和会话**。另一个并发请求可能已经在等锁期间完成并清理了会话——这时应该回放结果，而不是 404。
4. **全局限流**：per-upload_id 锁只防同一会话重复合并；不同会话之间再用容量 4 的信号量限制同时合并数，等 5s 拿不到名额返回 503。没有它，突发流量会同时占满磁盘 IO，把整个进程拖慢。

这里的锁是**必要**的：合并是对多个资源的复合操作，不像置位那样能靠单命令原子性解决——正好和 §3 形成对照。

## 七、为什么会话放 Redis，不放 MySQL

| 特征 | 结论 |
|---|---|
| 临时性 | 24h 后无论完成与否都该清 → Redis TTL 天然契合，MySQL 要写定时任务扫 |
| 高频写 | 每片一次写 → MySQL 行级写 + 事务日志，代价高一个数量级 |
| 非业务数据 | 丢了最大代价是「重新传」，不影响业务一致性 |
| 结构 | 位图 / SETNX 锁 / 结果缓存都是 Redis 原生能力 |

**代价（已知取舍）**：Redis 不可用时整个分片上传 503。这是项目「API 对 Redis 降级」的唯一例外——分片传输本身就没有 Redis 无法工作。降级路径是单次上传接口 `/video/uploadVideo` 仍可用（限 200MB）。

实现上，`cmd/main.go` 在 Redis ping 失败时把 `cache` 置为 `nil`，四个接口开头统一：

```go
if h.cache == nil {
    c.JSON(503, gin.H{"error": "chunk upload requires redis"})
    return
}
```

**快速失败优于产生脏会话**：宁可告诉用户「现在传不了」，也不要在状态不可靠的情况下收下一半字节。

## 八、前端：断点续传是怎么"接上"的

### 8.1 核心机制：位图的空洞可以任意补

```js
const done = new Set(initRes.uploaded_chunks)   // ① init 返回已传下标
const pending = gaps(totalChunks, done)          // ② 缺口 = 未传的下标，顺序无关
await runPool(pending)                           // ③ 并发 3 补传
```

**位图不是水位线**。水位线（`uploadedCount = 11`）意味着「0~10 连续传完」，中间一旦有洞就永久卡住；位图允许 `10=true, 11=false, 12=true` 这种任意中间态，补传顺序完全无关。

### 8.2 合并前核对一次

并发和重试会造成一类特殊状态：**服务端写成功了，但响应在回程丢了**。客户端看到的是「失败」，会重试；重试时服务端位图已置位 → 短路 200 → 进度照常推进。看起来没问题。

但极端情况下（比如 401 刷新 token 后重放、多标签页），仍可能有片没到位。所以在 complete 前加了一轮核对：

```js
for (let round = 0; round < 3; round++) {
    const st = await videoApi.chunkStatus(uploadId)
    const gaps = missingChunks(st.uploaded_chunks)
    if (gaps.length === 0) break
    await runPool(gaps)     // 只补传缺口，不重传全部
}
```

这让 `chunk/status` 这个原本没人调用的接口真正派上用场——**以服务端为准**（单一事实来源），而不是信任客户端自己的记账。

> **注意前提**：这轮核对成立的前提是 `status` 说实话。而服务端早期版本里 `status` 直接回位图，「位图有、磁盘没有」的片会被当成已传，前端自然会漏过它。所以后端侧必须有 §5.5 的 `reconcileBits`——**核对的依据本身必须是可信的**。

最后一道防线是合并失败时的自动补传：服务端发现缺片会回 `missing_chunks: [0, 3]`，前端把这几片从本地记账里删掉立刻重传，再重试合并，而不是把错误抛给用户。

```js
const missing = missingChunkIndices(e)      // 从 ApiError.payload 里取
if (missing.length > 0) {
  missing.forEach((i) => done.delete(i))    // 本地记账也要跟着退回去
  syncProgress()
  await runPool(missing)
  continue                                  // 下一轮重新 complete
}
```

### 8.3 整文件校验失败：服务端作废会话，前端重来一次

`file_hash_mismatch` 和缺片是两类错误，恢复方式不同：

- **缺片**：会话仍然有效，补传缺的片再合并即可。
- **整文件哈希不符**：说明已落盘的分片里有坏字节，**这个会话的数据已经不可信**——补哪一片都无法确定。服务端必须 `invalidateSession`，否则客户端会对着同一份坏数据反复 complete。

前端据此做一次有界的「整轮重来」：

```ts
if (isFileHashMismatch(e)) {          // payload.code === 'file_hash_mismatch'
  if (restartRound >= 1) throw e      // 只重来一次，避免无限循环
  stage.value = '文件校验失败，重新上传'
  return uploadVideoChunked(file, restartRound + 1)  // 重新 init → 重新切片上传
}
```

重来一次是合理的：坏字节通常来自偶发的传输/写盘问题；如果第二次还算出不同的整文件哈希，说明文件本身或客户端计算有问题，继续重试没有意义——直接把错误暴露给用户。

### 8.4 重试要有退避，也要会放弃

```js
for (let attempt = 0; attempt < MAX_RETRIES; attempt++) {
    try { await uploadChunk(...); return }
    catch (e) {
        if (isFatal(e)) break                                  // 4xx 请求本身不对，重试无意义
        await sleep(300 * 2 ** attempt + Math.random() * 200)  // 指数退避 + jitter
    }
}
```

两个要点：

- **指数退避**：服务端抖动时，立即重试等于第二次冲击
- **jitter**（随机抖动）：没有它，一批同时失败的分片会在同一毫秒一起重试，形成同步的尖峰
- **4xx 不重试**：`400 hash mismatch`、`403 forbidden`、`404 session not found` 重试一万次也一样

### 8.5 请求必须有超时

`fetch` 默认没有超时。弱网下 5MB 的请求可能永远挂着，前端永远等不到失败，也就**永远触发不了重试和续传**——断点续传整个机制形同虚设。

`client.ts` 加了 `timeoutMs` 选项（`AbortController` + `AbortSignal`），分片上传单片 120s，超时转成 `ApiError('请求超时', 408)`，被当作可重试错误进入退避循环。

### 8.6 已知未做的部分（诚实清单）

| 缺口 | 影响 | 修法方向 |
|---|---|---|
| 整文件 MD5 在主线程同步算 | 200MB 约几秒无响应 | Web Worker / 抽样 hash（首尾片 + 长度） |
| 刷新页面后要重新选文件 | 靠 `file_hash` 命中旧会话，但要手动重选 | localStorage 存 `fileHash → uploadId` |
| 没有取消/暂停按钮 | 用户只能等 | AbortController 暴露给 UI |
| 会话与账号绑定，换账号不可续 | 符合预期 | — |
| 合并成功但用户从未 publish | 成品 `.mp4` 没有「主人」，不会被自动清理 | assets 表（pending/committed）+ 年龄巡检（见 Q8） |

## 九、易混淆对照

| 概念 | 区别 |
|---|---|
| `upload_id` vs `file_hash` | 前者=**这次上传行为**的 ID（每次新会话不同）；后者=**文件内容**的 ID（同文件永远相同）。续传靠 file_hash 找回 upload_id |
| 位图 vs 水位线 | 位图允许任意空洞、补传顺序无关；水位线一旦有洞就永久卡死 |
| `chunk_hash` vs `file_hash` | 前者校验**单片**传输完整性；后者标识**整文件**身份 + 合并后终检 |
| `SETBIT` vs 分布式锁 | 单 bit 状态变更用 SETBIT（原子、无锁）；复合操作（合并）才需要 SETNX |
| 409 vs 400（complete） | 409=**正在合并**，退避后重试；400=**缺片/哈希不符**——缺片按 `missing_chunks` 补传，`code=file_hash_mismatch` 则必须重新 init 整轮重传 |
| 503 的两种来源 | Redis 不可用=整个功能下线；`too many concurrent merges`=合并名额已满，退避重试即可 |
| 503 vs 404（会话） | 503=Redis 不可用，整个功能下线；404=会话不存在/已过期/已合并完 |
| 幂等 vs 归属校验 | 结果缓存保证「同一请求重复执行结果一致」；`account_id` 校验保证「别人拿着你的 upload_id 也回放不到你的结果」 |

## 十一、一句话总结

**业务路径**：算指纹 → 建会话 → 并发传片（单片 MD5 + 长度校验 + 唯一临时名原子落盘 + SETBIT 置位）→ 核对补传 → token 锁 + 心跳合并（流式整文件 MD5）→ 写结果、删临时分片、清会话。

**核心技术**：
1. 分片把「不可靠的大传输」拆成「可独立重试的小传输」
2. **Redis 位图 + SETBIT 原子置位**：并发写进度不覆盖（换数据结构解决并发，而不是加锁）；置位与续期用 Lua 保证一起生效
3. **位图的空洞可任意补**：续传只补缺口，与顺序无关
4. **两级 MD5**：单片防传输坏字节，整文件防「每片都对、拼起来不对」；整文件不符则作废会话并让前端整轮重来一次
5. **先落盘后置位 / 唯一临时名 + 原子 rename**：消除「假完成」「读到半片」「并发写者互删」
6. **结果缓存 + token 锁 + 心跳 + 全局信号量**：complete 幂等、并发不重复合并、结果不越权回放、磁盘 IO 有上限
7. **快速失败**：Redis 不可用直接 503，不产生脏会话
8. **位图必须由磁盘对账**：`init` / `status` / `complete` 统一走 `reconcileBits`，位是 1 但字节不在的当场清位；缺片一次性以 `missing_chunks` 报回，前端自动补传再重试——**会话不会卡死到 TTL 过期**
9. **TTL 之外还要补偿清理**：Redis 过期只回收 key，`chunk_cleaner` 按「超龄 + 无活会话」回收 tmp、按超龄回收 `.mp4.part`，成品留给业务对账

## 十二、面试追问 Q&A

> 每条三段：**问题 → 简答（考场上先答这一句）→ 完整回答（被追问时展开）**。
> 顺序按「最容易被问穿」排列，Q1 和 Q3 是本模块最危险的两处。

---

### Q1：`UploadedBits []bool` 不也是位图吗？为什么非要换成 Redis 位图？

**简答**：它在**逻辑语义**上是位图，但在**存储实现**上不是——Go 的 `bool` 占 1 字节，JSON 序列化后每片 5~6 字节，Redis 眼里就是一坨普通 String，没法按 bit 寻址。真正的差别是「改一位要付多大代价」：JSON 必须整段读-改-写（并发必然互相覆盖），而 `SETBIT` 只写一个 bit，天然原子。

**完整回答**：
先澄清一个常见误解：**Redis 的 BITMAP 不是独立数据类型，底层还是 String（SDS）**。所以新旧方案的差别不在「存了什么」，而在「Redis 能不能按 offset 直接寻址到某一个 bit」。

三层距离：
1. Go 的 `[]bool` 里每个元素占 **1 字节**，不是 1 bit（真正的 Go 位图要 `[]uint64` + 位运算）；
2. JSON 序列化成 `[true,false,...]`，每片 **5~6 字节 ≈ 40~48 bit**；
3. 存进 Redis 后是普通 String，`SETBIT`/`GETBIT`/`BITCOUNT` 对它一个都用不了——改一位只能整段读回来。

于是并发就出问题了：

```
请求A(片5): GET → bits[5]=true ─────────────┐ 写回整个 JSON
请求B(片6): ── GET → bits[6]=true ──────────┼─ 写回，覆盖 A
请求C(片7): ──── GET → bits[7]=true ────────┴─ 写回，覆盖 B
```

写单元是「整个会话」，多个请求读到同一个旧值各自算新值，**最后写的人赢**。换成 `SETBIT` 后写单元变成「一个 bit」，三个请求写三个 offset，物理上不冲突。

**为什么不加锁而要换掉它**：加锁能用，但每片多 2 次 Redis 往返、并发 3 退化成串行（吞吐掉到 1/3），还要处理锁 TTL、误删、死锁一整套问题。为 1 个 bit 的写入引入分布式锁是把问题想重了。

**加分点**：空间不是主要动机（200 字节无所谓），**并发正确性才是**。注意 `complete` 那里反而**用了锁**——两处正好是这个问题的两面（见 Q2）。

---

### Q2：那 `complete` 为什么又用锁？同样是改状态，为什么这里不用原子命令？

**简答**：因为 `SETBIT` 解决的是「单 bit 状态变更」，而合并是**对多个资源的复合操作**（读 N 个分片 + 创建成品 + 写 Redis + 删会话），没有单条命令能把它做成原子的，所以才需要带 token 的 `SETNX` 锁；而且锁要配心跳和全局限流才完整。

**完整回答**：
判断标准很简单——**能不能用一条 Redis 命令表达这个状态变更**：

| 操作 | 能否单命令原子 | 方案 |
|---|---|---|
| 「第 5 片已传」 | 能（`SETBIT key 5 1`） | 位图，不用锁 |
| 「把 40 个分片拼成一个文件并登记结果」 | 不能 | token 合并锁 + 结果缓存 + 全局限流 |

```583:650:backend/internal/video/chunk_handler.go
	token, acquired, err := h.cache.Lock(ctx, lockKey, mergeLockTTL) // SETNX 写入随机 token
	if !acquired {
		c.JSON(http.StatusConflict, gin.H{"error": "merge already in progress"})
		return
	}
	defer func() { _ = h.cache.Unlock(context.Background(), lockKey, token) }() // GET 相等才 DEL

	// 后台心跳：仍持有锁才续期，避免大文件合并超过租约被接管
	go func() { /* 每 mergeLockTTL/3 调一次 RefreshLock */ }()

	// ……拿到锁后重新读结果/会话、reconcileBits 判满……
	if !h.acquireMergeSlot(ctx) { // 全局容量 4，等 5s
		c.JSON(http.StatusServiceUnavailable, gin.H{"error": "too many concurrent merges, retry later"})
		return
	}
```

**加分点**：五个容易漏的细节——① 锁必须**带 token**，释放时用 Lua「GET 相等才 DEL」，租约到期被接管后不会误删对方的锁；② **心跳续期**，否则 10min 租约撑不完大文件合并；③ 抢到锁后**重新读结果和会话**，否则用的是加锁前的旧快照，锁白加；④ 会话读不到时**再查一次结果缓存**（可能是另一个并发 complete 已经合并完并把会话删了），直接回放 URL 而不是返回 404；⑤ 再加一层**全局信号量**限制不同会话的并发合并数，防止磁盘 IO 被打满。

### Q3：Redis 挂了怎么办？你项目不是说「Redis 可降级、不中断服务」吗？

**简答**：分片上传是这条原则的**唯一例外**，四个接口统一返回 503。因为上传会话本身就是状态机，没有 Redis 就无从工作；宁可告诉用户「现在传不了」，也不在状态不可靠的情况下收下一半字节产生脏会话。降级路径是单次上传接口 `/video/uploadVideo`（限 200MB）仍然可用。

**完整回答**：

```231,313,491,539:backend/internal/video/chunk_handler.go

		c.JSON(http.StatusServiceUnavailable, gin.H{"error": errChunkCacheUnavailable.Error()})
```

`cmd/main.go` 在 Redis ping 失败时把 `cache` 置为 `nil`，所以这个判断是可靠的（不是靠 error 猜的）。

为什么这里不能像 Feed 那样「降级直查 MySQL」？因为其它模块的 Redis 只是**加速器**（没有就回源 MySQL，慢但正确），而分片上传的 Redis 是**唯一的状态存储**——换成 MySQL 写入就要扛住「每片一次写」，而且还要自己做 TTL 清理和位图。所以这属于「功能下线」而不是「性能降级」。

**加分点**：这个取舍要**主动说**，否则面试官抓到「你开头说 Redis 可降级，这里又说 503」会直接质疑一致性。我的简历里也把例外写进去了。

### Q4：单片都已经校验 MD5 了，合并完再算一次整文件 MD5 不是多余吗？

**简答**：不多余。单片 MD5 防的是「传输过程中坏了」，整文件 MD5 防的是「每片都对、拼起来不对」——而且单片的 `chunk_hash` 是**客户端自己声明的**，客户端只要让错误字节和它声明的哈希自洽，服务端就照收。

**完整回答**：
两级 MD5 覆盖的是不同的信任边界：

| 级别 | 校验什么 | 防什么 |
|---|---|---|
| 单片 `chunk_hash` | 服务端重算该片字节 vs 客户端声明 | 网络传输损坏、写了半片 |
| 整文件 `file_hash` | 合并后整体重算 vs init 时声明 | 客户端伪造自洽的单片哈希、分片错位/重复、合并逻辑 bug |

`file_hash` 在 init 时就写进会话了，之前只当续传索引用，合并时正好拿它做终检。实现上用 `io.MultiWriter(文件, md5)`，**一次 IO 同时写盘和算哈希**，不会为了校验再读一遍 200MB。

**加分点**：校验失败不是「删文件就完事」。半成品删掉后，必须**同时作废会话、位图、hash 索引**（`invalidateSession`），否则客户端会拿着同一个 `upload_id` 对着同一份坏数据反复 complete，一直卡到 24h TTL。hash 索引要用「值仍指向本会话才删」的条件删除，避免误删并发 re-init 建的新映射。前端收到 `code=file_hash_mismatch` 后重新 init、整轮重传一次——`TestFileHashMismatchInvalidatesSession` 锁住了这个行为。

### Q5：断点续传为什么用 `file_hash` 找回会话，而不是把 `upload_id` 存起来？

**简答**：`upload_id` 是**行为 ID**（刷新页面、换个浏览器就没了，而且每次新会话都不同）；`file_hash` 是**内容 ID**（同一个文件永远算得出同一个值）。检索键是 `(accountID, fileHash)`，用户刷新后只要重新选同一个文件就能命中旧会话。

**完整回答**：
Redis 里专门有一个反查键 `chunk_upload_hash:{accountID}:{fileHash} → uploadID`，init 时先查它。命中就读出位图，把已传下标返回给前端，前端跳过这些片。

顺带三个设计细节：
- **必须比对参数**：同一文件换了分片大小再选一次，`(uid, fileHash)` 仍会命中，但 `chunk_size` 对不上 → 前端按新大小切片、服务端按旧大小校验长度，全部 400。所以用 `session.Matches(req)`，不一致就当陈旧会话重建。
- **续传要刷新 TTL**：24h 是从最后一次活动开始算的，不然大文件传一半会话过期了。而且 session / bits / hash 索引必须**一起续**（`touchSession` 用一次 `PExpireMany`），否则会出现「位图还在、会话先过期」或「会话还在、hash 索引先过期」的错位。
- **`file_hash` 一物三用**：续传索引 + 合并后的验收标准 + 跨会话的文件身份。

**加分点**：现在只做到「同账号重传可续」，没做**秒传**（服务端已有该文件就直接返回 URL）。要扩展的话，加一个全局 `file_hash → video` 映射即可——但要先想清楚「同文件不同账号」的版权/隐私语义，本项目刻意没做。

### Q6：位图说「第 3 片传了」，但磁盘上没有这个文件，会怎样？

**简答**：这就是「位图 ≠ 磁盘」的坑。老实现会**死锁**：重传被幂等短路掉，`complete` 报 500，会话 24h 内永远完不成。现在的修法是**把对账收敛成一个函数** `reconcileBits`——任何对外表达进度的出口（`init` / `status` / `complete`）都先拿位图和磁盘对一遍，位是 1 但字节不在的当场**清位**退回「未上传」；`complete` 还会一次性返回**全部**缺失片下标，前端据此自动补传再重试。三个入口都能自愈。

**完整回答**：

```155:175:backend/internal/video/chunk_handler.go
func (h *ChunkUploadHandler) reconcileBits(ctx context.Context, s *ChunkUploadSession) ([]bool, error) {
	bits, err := h.cache.GetBits(ctx, h.bitsKey(s.UploadID), s.TotalChunks)
	if err != nil {
		return nil, err
	}
	if len(bits) != s.TotalChunks {
		return nil, fmt.Errorf("invalid session data")
	}
	for i, uploaded := range bits {
		if !uploaded {
			continue
		}
		fi, statErr := os.Stat(h.chunkPath(s.UploadID, i))
		if statErr == nil && fi.Size() == s.ExpectedChunkSize(i) {
			continue
		}
		bits[i] = false
		_ = h.cache.SetBitWithTTL(ctx, h.bitsKey(s.UploadID), int64(i), 0, sessionTTL)
	}
	return bits, nil
}
```

三步走：

| 步骤 | 位置 | 作用 |
|---|---|---|
| ① 单片即时核对 | `UploadChunk` 幂等短路前 `os.Stat` | 客户端重试这一片时立刻修复 |
| ② 出口统一对账 | `reconcileBits`，`init` / `status` / `complete` 全走它 | 刷新重传这类入口也能发现坏片 |
| ③ 合并失败给全清单 | `mergeChunks` 先全量 Stat 再动手 | 客户端一轮补完，不用逐片试 |

写入侧配套的顺序是「先写 `.part` → `rename` 落盘 → 最后 `SETBIT` 置位」：反过来崩在中间就会留下死锁态，现在最多是「文件在、位是 0」，重传一片即可。

> 一句话原则：**宁可让客户端重传一片，绝不出现「假完成」。**

**加分点**（这题真正的深度在根因）：位图在 Redis（多实例共享），分片在本地磁盘（每实例私有）——**两份生命周期完全不同的东西被当成同一份状态在用**。所以多实例 + 轮询负载均衡下这不是偶发而是必然：`upload` 落到实例 B 的磁盘，`complete` 打到实例 A，A 的 `tmp` 是空的，而 Redis 位图说全齐了。对账能让它**自愈**，但要**根除**得让分片离开本地磁盘：直传对象存储（OSS/S3），或至少共享存储 / 会话粘滞。

### Q7：分片大小 5MB 是怎么定的？能不能更大或更小？

**简答**：5MB 是「单片重传代价」和「请求数放大」的折中——太小则请求数和 Redis 写次数放大（1MB 的话 200MB 要 200 次），太大则单片失败重传的代价太高、内存峰值也高。后端用 `ChunkSize = 5<<20` 常量做上限兜底，防止前后端契约漂移。

**完整回答**：
- **不能太大**：单片失败要整片重传，10MB 在弱网下重传一次就是好几秒；同时服务端要在内存里缓冲整个分片（Gin 超大分片还会落到临时文件再读一遍）。
- **不能太小**：请求数、Redis `SETBIT` 次数、前端 MD5 计算次数全部按 1/分片大小放大；200MB / 1MB = 200 次请求，服务端 QPS 直接翻几十倍。
- **后端必须校验**：原来 `ChunkSize` 常量定义了却没人用，前后端各写一份 5MB，改了一边就会漂移。现在 init 强制 `chunk_size ≤ 5MB`，同时校验 `total_chunks == ceil(file_size/chunk_size)`。

**加分点**：`total_chunks` 还有个 4096 的上限，防止恶意客户端声明天文数字的片数，让 `status`/`complete` 的循环和位图读写被放大。另外 `file_size` 上限 200MB，和单次上传接口保持一致。

### Q8：上传会话为什么放 Redis，不放 MySQL？

**简答**：三个特征都指向 Redis——**临时**（24h 后该消失，TTL 天然契合，MySQL 要写定时任务扫）、**高频写**（每片一次，MySQL 行级写 + 事务日志代价高一个数量级）、**非业务数据**（丢了最多重传，不影响业务一致性）。而且位图、SETNX 锁、结果缓存都是 Redis 原生能力。

**完整回答**：
会话是典型的「有 TTL 的过程状态」而不是业务实体。放 MySQL 要额外付出：定时清理任务、每片一次事务写、`SETBIT` 换成行更新（还得处理并发覆盖）。

代价就是 §7 说的——**Redis 不可用时整个功能 503**。这是本项目「API 对 Redis 降级」的唯一例外，因为分片传输本身就没有 Redis 无从工作。

**加分点**：清理已经补上了——`chunk_cleaner` 每小时扫一次，只删「mtime 超过 24h **且** Redis 里没有对应会话」的 tmp 目录，以及超龄的 `.mp4.part`；成品 `.mp4` 不凭磁盘状态删（可能已被 publish 引用）。仍然没做的是**孤儿成品的业务对账**：合并成功但用户从未 publish 的文件没有「主人」，正确做法是 assets 表记录 `pending/committed` 状态 + 年龄巡检，这是「文件系统与数据库一致性」问题，和「删了 DB 行、文件还在」是同一类。另外 cleaner 只清本实例磁盘，多实例共享存储时要靠分布式协调或对象存储 lifecycle。

### Q9：整文件 MD5 在前端主线程算，大文件不卡吗？为什么不改？

**简答**：会卡，200MB 大约 1~2 秒无响应，这是**已知的、有意识的取舍**。已做的缓解是先设 `stage='计算文件指纹'` 并 `await sleep(0)` 让浏览器先把提示画出来再算。没上 Web Worker 是因为它会让上传流程变成异步消息交互，复杂度上升；真要做我更倾向**抽样哈希**（首尾片 + 长度 + 采样若干片），把 O(n) 降到 O(1)。

**完整回答**：
`computeFileMD5` 是按 2MB 切片**流式**喂给 SparkMD5 的，所以不是「把 200MB 读进内存」——真正的代价是 SparkMD5 的 `append` 是同步 CPU 计算，占住主线程。

可选的三条路：
1. **Web Worker**：彻底不卡主线程，但上传流程要改成消息交互，错误处理、取消都要跨线程传递；
2. **抽样哈希**：只算首尾各一片 + 中间采样几片 + 文件长度，碰撞概率极低（对象存储的秒传常用这招），O(1) 完成；
3. **服务端算**：前端不算指纹，但这样就拿不到「跨会话的文件身份」，断点续传的入口没了——代价太大。

**加分点**：如果面试官追问「那断点续传的 file_hash 不就不准了」，答案是：抽样哈希只用于**校验**（弱校验足够），续传入口可以另外用「文件名 + 大小 + 首片哈希」组合键，把「身份」和「校验」两个职责拆开。

### Q10：你最初的实现有什么问题？是怎么发现的？

**简答**：P0 是并发传片丢进度——「读整个 session JSON → 改一位 → 写回」的 read-modify-write 竞态，前端 3 并发时后写覆盖前写，结果是「片都传成功了，complete 报缺 2 片」。是**代码审查**发现的，不是测试发现的，因为测试里 `uploadChunk` 是串行调用的，永远复现不出来。

**完整回答**：
发现路径：读 `UploadChunk` 时注意到它是 `getSession → 改 UploadedBits[i] → saveSession` 三步，而前端 `MAX_CONCURRENT = 3`；单元测试里每个分片都是 `await` 完再传下一个，天然串行，所以**这类 bug 属于「测试覆盖率 100% 也照样溜到生产」**的类型。

修完补了一条并发回归测试 `TestConcurrentChunkUploadKeepsAllBits`：8 个 goroutine 同时传 8 片，结束后断言 `uploaded_chunks` 长度 == 8。这是验证修复最直接的方式。

同一轮还修了：参数不自洽（能造出永远完不成的会话）、complete 不校验整文件 MD5、并发 complete 会合并出两份文件、`.part` 半片窗口、`bit` 与磁盘不一致的死锁、`randHex` 错误被忽略。

第二轮专门补「并发与故障时序」的洞，每个都配了回归测试：

| 修复 | 测试 |
|---|---|
| 同片并发写互相覆盖/互删（唯一临时名 + 有界 rename） | `TestConcurrentSameChunkUploadIsSafe`、`TestRenameReplaceKeepsDestinationWhenSourceMissing` |
| 结果缓存回放前校验账号归属（否则知道 upload_id 就能拿别人 URL） | `TestCompleteReplayChecksOwnership` |
| 整文件哈希不符后作废会话（否则卡到 TTL） | `TestFileHashMismatchInvalidatesSession` |

**加分点**：这个模块给我最大的体会是——**并发问题优先想「能不能换一个本身就原子的数据结构和命令」，而不是「怎么给非原子操作加锁」**。`SETBIT`/`INCR`/`HINCRBY`/`SETNX`/Lua 都是这个思路的工具；只有当操作是「多资源复合」时才真的需要锁。第二层体会是：**「原子」和「清理」要分开想**——`SETBIT` 保证状态不丢，但文件系统、结果缓存、会话是三个独立资源，崩溃时序和清理顺序必须单独设计。
