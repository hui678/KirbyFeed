## 0. 先背这条链路（30 秒总述）

被问「讲讲你的分片上传」时，先给这一条，再按追问展开：

```
前端选文件 → 2MB 切片流式算 file_hash（SparkMD5 增量）
  → POST /video/chunk/init
      → (accountID, file_hash) 命中旧会话？参数 Matches？
          → 命中：reconcileBits 对账 → 返回已传下标 → 续传
          → 未命中/参数变了：crypto/rand 生成 upload_id，写 session + hash 索引
  → 只传缺口，最多 3 片并发：POST /video/chunk/upload
      → 会话存在 → 归属校验 → 下标范围 → 精确长度 → 单片 MD5
      → 写 {idx}.{rand}.part → rename 成 {idx} → SETBIT 置位 → 三把 key 续期
  → 合并前最多 3 轮 POST /video/chunk/status，按服务端位图补缺
  → POST /video/chunk/complete
      → 账号归属 → 结果缓存回放（校验归属）→ Lock 抢合并锁 + 心跳续期
      → reconcileBits 判满 → 全局合并信号量（4 路，等 5s）
      → 全量 Stat → 0..N-1 合并到 {rand}.mp4.part
      → MultiWriter 写盘同时算整文件 MD5 → 比对 init 的 file_hash
      → 通过则 rename 成 .mp4；失败则清 tmp + 作废会话（客户端重新 init）
      → 写 result(1h) → 删 tmp → 删 bits/session/hash
  → 返回 URL；随后 /video/publish 才写 videos 表
```

**三句话内核：**

1. 分片把「一次可能失败的大传输」拆成「N 次可独立重试的小传输」，失败粒度从 O(file) 降到 O(chunk)。
2. 进度用「单 bit 原子写（`SETBIT`）+ 磁盘对账（`os.Stat`）」维护，而不是「读整个会话 JSON → 改一位 → 写回」。
3. `complete` 用「结果缓存 + 带 token 的合并锁 + 心跳续期」做幂等，用「两级 MD5 + 先落盘后置位 + 成品 `.part` 原子 rename」挡住「假完成」和「半片」。

**三层幂等（被问「重复了怎么办」时按这个顺序答）：**

| 层 | 机制 | 防什么 | 位置 |

# 第一层：基础原理

## 1. 为什么需要分片上传？与一次性上传相比，优势和额外成本分别是什么？

**一句话：** 分片把「一条可能失败的大传输」拆成 N 条可独立重试的小传输，换来可恢复性、并行度和更细的进度；代价是把无状态的文件上传变成了**有状态的分布式会话**。

**展开（一次性上传绕不过去的四个坑）：**

| 坑 | 后果 |
|---|---|
| 单连接单流 | 传到 90% 断网 → 200MB 全部重来 |
| 服务端无进度记忆 | 无法断点续传，刷新即从头 |
| 中间层 body size 限制 | 大请求容易被 Nginx / 网关 / Gin 限制砍掉 |
| 单 TCP 连接的拥塞控制 | 高 RTT 下跑不满带宽 |

分片带来的直接收益：

- **失败粒度**：重传一片 5MB，而不是整个 200MB；
- **并行度**：前端 3 片并发，多个连接同时跑；
- **小请求**：单请求 5MB，更容易穿过代理和超时限制；
- **可观测**：进度按「已传片数 / 总片数」，天然支持百分比和续传；
- **早失败**：单片 MD5 不匹配立即 400，不用等整文件传完；
- **服务端可治理**：可以按片做限流、配额、审计。

额外成本（也是这个模块 80% 的代码量）：

| 成本 | 具体表现 |
|---|---|
| 状态管理 | 会话 JSON、位图、hash 索引、TTL、合并锁、结果缓存 |
| 合并开销 | 200MB 读 + 200MB 写 + 整文件 MD5，CPU 和磁盘 IO 都翻倍 |
| 临时存储 | 分片和成品同时存在，峰值约 2× 文件大小 |
| 请求放大 | 40 次请求 vs 1 次，鉴权、日志、监控、连接开销都放大 |
| 一致性 | 位图 vs 磁盘、会话 vs 分片、文件 vs 数据库，三对事实要收敛 |
| 客户端复杂度 | 切片、并发池、指数退避、超时、续传、缺失补传 |
| 垃圾清理 | 放弃的上传、崩溃的半成品、过期的 tmp 目录 |

**边界：**

- 分片不一定更快。小文件（十几 MB 以内）分片后请求开销占比高，反而不如单次上传；本项目的单次接口 `/video/uploadVideo` 就保留着，既是小文件路径，也是 Redis 不可用时的降级路径。
- 「可恢复」依赖会话状态可靠。Redis 一旦丢失，续传能力就没了；所以分片上传是本项目「Redis 可降级」原则的唯一例外（见学习文档 Q3 与 `chunk_handler.go:38,230`）。
- 分片只解决「传输可靠性」，不解决「文件与业务记录的一致性」；后者是 Q18。

**加分：** 分片上传的难点不在「切片」，而在「切片之后多出来的状态」。面试时可以先说「分片本身很简单，真正的工作量在会话、幂等、对账和清理」，把话题引到你真正做过的地方。

## 2. 为什么选择 5MB 作为分片大小？如果改成 1MB 或 20MB，会有什么影响？

**一句话：** 5MB 是「单片重传代价 × 请求数放大 × 内存/超时」的折中，同时也刚好是 S3/OSS multipart 的最小分片惯例（最后一片除外）。

**展开（以 200MB 文件为例）：**

| 分片大小 | 片数 | 单片重传代价 | 请求 / SETBIT 次数 | 服务端内存峰值 | 主要问题 |
|---|---|---|---|---|---|
| 1MB | 200 | 1MB | 200 | ~1MB | 请求、鉴权、日志、连接开销放大；迁移对象存储时违反 5MiB 最小分片 |
| **5MB** | **40** | **5MB** | **40** | **~5MB** | **折中；与 S3/OSS 最小分片对齐** |
| 20MB | 10 | 20MB | 10 | ~20MB | 单片失败重传贵、超时窗口大、前端算 MD5 卡顿；本项目会直接 400 |

具体约束：

- **不能太大**：单片失败要整片重传，20MB 在弱网下重传一次就是好几秒；服务端 Gin 默认把 32MB 以内的 multipart 先缓存在内存里，20MB × 并发数会显著抬高内存；单片超时（120s）也更容易被触发。
- **不能太小**：请求数、`SETBIT` 次数、前端单片 MD5 次数都按 1/分片大小放大；1MB × 200 片意味着 200 次鉴权、200 次日志、200 次 Redis 写，QPS 直接翻五倍。
- **后端是上限不是固定值**：`ChunkSize = 5 << 20` 是拒绝阈值，`Validate` 要求 `chunk_size <= 5MB`，同时要求 `total_chunks == ceil(file_size / chunk_size)`（`chunk_entity.go:73-96`）。
- **前后端必须一致**：前端 `CHUNK_SIZE` 写死 5MB（`VideoView.vue:122`）。只改前端不改后端，init 直接 400；只改后端不改前端，切片大小对不上，upload 全部长度校验失败。
- **对象存储约束**：S3 系 multipart 规定除最后一片外，每片至少 5MiB、最多 5GiB，最多 10000 片。1MB 分片在本地磁盘能跑，但迁到 OSS/S3 会不合法——这也是 5MB 的一个隐性好处。

**边界：**

- 最后一片通常小于 5MB，`ExpectedChunkSize` 会按 `file_size - index * chunk_size` 算精确长度（`chunk_entity.go:36-48`），不会要求补齐。
- 本项目 200MB 上限决定最多 40 片；`MaxTotalChunks = 4096` 是防恶意声明超大位图，不是常规业务规模。
- 分片大小是契约，不是纯客户端参数；服务端必须兜底，否则客户端可以造出自相矛盾的会话（Q7）。

**加分：** 如果面试官问「能不能动态分片」，可以答：能，按网络 RTT/丢包做 1~8MB 自适应，或者按文件大小分档；但动态分片会让 `chunk_size` 成为会话的一部分，续传时必须严格 `Matches`，复杂度上升，200MB 以内固定 5MB 足够。

## 3. 前端流式计算 MD5 是如何实现的？为什么不直接把整个文件读进内存？

**一句话：** 用 2MB 切片 + `SparkMD5.ArrayBuffer` 增量 `append`，MD5 的内部状态是固定大小，所以峰值内存只有一个切片；整文件读进内存会额外占 200MB 且移动端容易 OOM。

**展开：**

```ts
// VideoView.vue:103-112
const chunkSize = 2 << 20
const spark = new SparkMD5.ArrayBuffer()
for (let offset = 0; offset < file.size; offset += chunkSize) {
  const buf = await file.slice(offset, end).arrayBuffer()
  spark.append(buf)
}
return spark.end()
```

三个关键点：

1. **`file.slice()` 是惰性的**：返回的是 Blob 视图，不会立刻读盘；真正读数据发生在 `arrayBuffer()`，每次只读 2MB。
2. **MD5 是增量算法**：Merkle–Damgård 结构按 64 字节块处理，内部状态只有 128 bit + 一个 64 字节缓冲，跟文件总大小无关。所以「分多次 append」和「一次性算」结果完全相同。
3. **内存峰值 ≈ 2MB + Spark 内部缓冲**，不是 200MB。代价是 CPU：`spark.append` 是同步 JS 计算，200MB 大约占用主线程 1~2 秒，页面会掉帧/短暂无响应。

为什么不用 `file.arrayBuffer()` 一次读完：

- 200MB 的 `ArrayBuffer` 直接进内存，再加上 Spark 的拷贝/视图，移动端很可能 OOM；
- 大块分配会造成明显 GC 峰值；
- 浏览器对单个 ArrayBuffer 也有实际上限，不同设备差异很大。

工程上的缓解：

- 计算前先设 `stage='计算文件指纹'` 并 `await sleep(0)`，让浏览器先把提示画出来（`VideoView.vue:157-160`）；
- 每读 2MB 有一次 `await`，事件循环能插入渲染，但 `append` 本身仍是同步的，所以只能减轻、不能消除卡顿。

**边界：**

- 这是**已知的、有意识的取舍**，不是「流式就不会卡」。真要彻底解决，需要 Web Worker、WASM，或者抽样哈希（首尾片 + 采样片 + 文件长度）。
- Web Crypto 的 `crypto.subtle.digest` 是异步的，但**没有流式 API**，必须把完整数据交给它，反而不适合 200MB。
- 2MB 是 IO 粒度，和 5MB 分片大小无关；用 2MB 是为了降低峰值内存、增加让出事件循环的次数。

**加分：** 如果面试官追问「那 `file_hash` 算得慢，能不能不算」，可以答：`file_hash` 一物三用——续传索引、合并终检、跨会话文件身份。不算就失去了断点续传的入口；折中方案是抽样哈希，但要接受极低概率的误判，并且要把「身份」和「校验」两个职责拆开。

## 4. Redis 位图如何记录已经上传的分片？分片索引与 bit offset 如何对应？

**一句话：** 第 `i` 片的 offset 就是 `i`，`SETBIT chunk_upload_bits:{upload_id} i 1` 单 bit 原子置位；40 片只占 5 字节，而且允许任意空洞，补传顺序完全无关。

**展开：**

- **一一对应**：`offset = chunk_index`，不额外编码、不做哈希。`TotalChunks` 决定逻辑长度，实际 key 长度由最高置位 bit 决定。
- **基本命令**：

| 命令 | 用途 |
|---|---|
| `SETBIT key i 1` | 标记第 i 片已传，单命令原子 |
| `SETBIT key i 0` | 对账发现「位是 1 但字节不在」时清位 |
| `GETBIT key i` | 幂等短路时查单片 |
| `GETBIT` pipeline | 一次往返读 N 位，`cache.go:166-176` |
| `BITCOUNT key` | 统计已传片数（本项目判满不再直接用它） |

- **底层类型**：Redis 的 BITMAP 不是独立数据类型，底层就是 String（SDS）。所以它天然支持 `GETRANGE`、`STRLEN`，也受 String 最大 512MB 限制；`SETBIT` 的 offset 上限是 2^32-1。
- **bit 顺序**：Redis 把 offset 0 定义为第一个字节的最高位（MSB），不是最低位。这不影响「i ↔ i」的语义，但如果自己用 `GETRANGE` 解包，顺序要对。
- **空间**：40 片 → 40 bit → 5 字节；4096 片 → 512 字节。相比每个会话一份几百字节的 JSON，空间不是重点，**并发正确性才是**。
- **为什么不用 `[]bool` 存 JSON**：Go 的 `bool` 占 1 字节，JSON 序列化后每片 5~6 字节，而且改一位必须整段读-改-写，3 个并发请求会互相覆盖（这正是原来的 P0 bug）。
- **TTL 配套**：`SetBitWithTTL` 用 Lua 把 `SETBIT` 和 `PEXPIRE` 合成一次原子执行（`cache.go:99-106`），避免「置位成功但续期失败」留下永不过期的 key。

**边界：**

- `GetBits` 是 N 条 `GETBIT` 的 pipeline，不是一次范围读。40 片没问题；4096 片就是 4096 条命令，虽然数据只有 512 字节，但命令开销不可忽略。更优的是 `GETRANGE` 一次取 512 字节自己解包，或 `BITFIELD key GET u4096 0`。
- **原子性边界**：单 key 的「置位 + 续期」已经用 Lua 闭合；但会话、位图、hash 索引是三个 key，跨 key 仍不是原子的。并发 re-init 可能让三者短暂指向不同会话，因此清理 hash 索引用 compare-and-delete，而不是无条件 `DEL`。
- 位图只记录「我认为传了」，不代表「字节真的在」；后者必须靠磁盘对账（Q10）。

**加分：** 能把「位图 vs 水位线」讲清楚很加分：水位线（`uploadedCount=11`）意味着 0~10 连续传完，中间有洞就永久卡住；位图允许 `10=1, 11=0, 12=1` 这种任意中间态，所以续传只补缺口、与顺序无关。这是选择位图而不是计数器的根本原因。

## 5. MD5 可以证明什么？它是否能够保证文件来源可信，或者彻底避免碰撞？

**一句话：** MD5 只能证明「收到的字节与某个声明值一致」，防的是意外损坏和传输错误；它不证明来源可信，也不是抗碰撞的安全边界。

**展开（本项目的两级 MD5）：**

| 级别 | 谁声明 | 谁校验 | 防什么 |
|---|---|---|---|
| 单片 `chunk_hash` | 客户端 | 服务端对该片字节重算 | 网络损坏、写入半片、截断 |
| 整文件 `file_hash` | 客户端（init 时） | 服务端合并后对整体重算 | 分片错位/重复、客户端自洽的坏片、合并逻辑 bug |

它能证明的：

- 传输过程中字节没有发生意外变化；
- 服务端收到的内容和客户端声明的摘要一致；
- 合并后的整体和 init 时声明的摘要一致。

它不能证明的：

- **来源可信**：MD5 没有密钥，任何人都能对任意内容算出 MD5；它不提供身份认证。来源可信靠 TLS、JWT、签名，不靠 MD5。
- **抗碰撞**：MD5 的碰撞攻击早已实用化，chosen-prefix collision 可以构造两个不同文件同 MD5。用来做安全校验（比如「同 MD5 即同文件」的秒传）是不合格的。
- **内容安全**：MD5 不检查文件是不是视频、有没有恶意载荷；需要 magic bytes / ffprobe / 病毒扫描。
- **客户端诚实**：`chunk_hash` 是客户端自己声明的。一个 buggy 或恶意客户端，只要让错误字节和它声明的 hash 自洽，服务端每片都会「校验通过」。所以整文件终检也只能保证「和客户端自己声明的 file_hash 一致」，不能证明这个文件就是用户以为的文件。

**边界：**

- 本项目的威胁模型是「防传输/存储损坏」，不是「防恶意客户端伪造」。在这个模型下 MD5 足够且便宜（200MB 在浏览器里算 MD5 比 SHA-256 快）。
- 如果要做秒传/去重，MD5 会带来碰撞投毒和跨账号隐私问题；应升级到 SHA-256 + 文件长度 + 抽样哈希，并且想清楚「同文件不同账号」的语义。
- **分片 MD5 不能拼接出整文件 MD5**。MD5 是链式结构，`md5(A) + md5(B)` 和 `md5(A||B)` 没有可组合关系；整文件必须对拼接后的字节重新流式计算（Q12）。

**加分：** 更好的方案是 Merkle 树：init 时客户端提交分片哈希组成的 Merkle root，服务端逐片校验「这一片属于这个文件」，还能定位是哪一片坏了。代价是 init 请求多传 N 个哈希（40 片 × 32B ≈ 1.3KB），以及客户端要多算一层。这是「整文件 MD5 只能告诉你坏了、不能告诉你哪片坏了」的正解。

# 第二层：实现细节

## 6. 上传任务如何创建？后端如何生成唯一的 `upload_id`，并将用户、文件标识、总分片数关联起来？

**一句话：** `(accountID, file_hash)` 是断点续传的检索键，命中且参数一致就复用旧会话；否则用 `crypto/rand` 生成 128-bit 随机串拼上纳秒时间戳作为 `upload_id`，把用户、文件元数据、分片数写进 session JSON，并建立 hash 反查索引。

**展开：**

`InitChunkUpload`（`chunk_handler.go:230-310`）的顺序：

1. **Redis 可用性**：`h.cache == nil` 直接 503（分片上传是 Redis 降级的唯一例外，见学习文档 Q3）。
2. **绑定 + 参数自洽**：`req.Validate()`（`chunk_entity.go:73-96`）检查文件大小、分片大小、片数、`total_chunks == ceil(file_size/chunk_size)`、`file_hash` 是 32 位 hex、文件名的路径分隔符。
3. **取账号**：`jwt.GetAccountID(c)`。
4. **续传命中**：`chunk_upload_hash:{accountID}:{fileHash}` → 旧 `upload_id`；读出 session，`session.Matches(req)` 比对 `file_size / chunk_size / total_chunks / file_hash` 四项。
   - 一致：`reconcileBits` 对账 → `touchSession` 同时续期 session / bits / hash 索引 → 返回 `uploaded_chunks`。
   - 不一致（例如换了分片大小）：当作陈旧会话，走新建；hash 索引会被新 `upload_id` 覆盖，旧 key 靠 TTL 自然过期。
5. **新建**：`randHex(16)`（`crypto/rand`，32 个 hex 字符）+ `UnixNano()`；写入 `chunk_upload:{upload_id}` 的 session JSON，再写 `chunk_upload_hash:{uid}:{hash}` 反向索引。

session JSON 字段（`chunk_entity.go:24-34`）：

| 字段 | 作用 |
|---|---|
| `upload_id` | 本次上传行为的 ID |
| `account_id` | 归属校验，防越权 |
| `filename` | 元数据（不参与磁盘路径） |
| `file_size` | 最后一片长度、总大小校验 |
| `chunk_size` | 每片期望长度 |
| `total_chunks` | 位图逻辑长度、判满依据 |
| `file_hash` | 续传索引 + 合并终检 |

**为什么不用数据库自增 ID：** 自增 ID 可枚举、不能天然过期、每片一次写库代价高；`upload_id` 是临时过程的 ID，放 Redis 最合适（见学习文档 Q8）。

**边界：**

- `upload_id` 是**随机但非秘密**的：它不是鉴权凭证，`upload` / `status` / `complete` 都会用 `session.AccountID` 校验归属；结果缓存里也带 `account_id`，回放同样校验（Q17）。秒传/共享场景如果要把 ID 给别人，需要额外的 scoped token。
- 同一账号、同一文件重复 init 会复用同一个会话；同一文件换账号会得到不同会话，避免跨账号续传/泄露。
- 旧会话被新会话覆盖 hash 索引后，旧 session/bits/tmp 仍会存在到 TTL 到期；`chunk_cleaner` 会在目录超过 24h 且无活会话时回收（Q14）。
- `upload_id` 里的时间戳不承担排序职责，只是额外区分和便于排查。

**加分：** 讲清楚「`upload_id` 是行为 ID，`file_hash` 是内容 ID」：前者每次新会话都不同，后者同一文件永远相同。断点续传的本质是「用内容 ID 找回行为 ID」，这也是为什么刷新页面后必须重新选同一个文件——浏览器不持有 `upload_id`（当前没有用 localStorage 记住它）。

## 7. 用户上传第 3 个分片时，后端如何校验分片编号、文件大小、MD5 和任务归属？

**一句话：** 五道门依次过：会话存在 → 账号归属 → 下标范围 → 精确长度 → 单片 MD5；全过了才写 `.part`、rename、置位。

**展开（`UploadChunk`，`chunk_handler.go:312-431`）：**

| 顺序 | 校验 | 失败返回 | 说明 |
|---|---|---|---|
| 1 | 绑定 multipart 表单 | 400 | `upload_id`、`chunk_index`、`chunk_hash` 必填，`chunk_index >= 0` |
| 2 | `getSession(upload_id)` | 404 | 会话不存在/已过期/已合并 |
| 3 | JWT 取 `accountID` | 400/401 | 路由层已过 JWT 中间件；无 token 时 401，解析失败时 400 |
| 4 | `session.AccountID == accountID` | 403 | 防别人拿到 `upload_id` 越权写 |
| 5 | `0 <= chunk_index < TotalChunks` | 400 | 防越界位图/越界文件名 |
| 6 | `ExpectedChunkSize(index) >= 0` | 400 | 防参数非法算出负数长度 |
| 7 | 位图 + `os.Stat` 幂等短路 | 200 | 已传且磁盘大小对，直接返回 |
| 8 | `c.FormFile("file")` | 400 | 缺文件 |
| 9 | `f.Size == expected` | 400 | **精确**长度，最后一片可短 |
| 10 | 服务端重算该片 MD5 vs `chunk_hash` | 400 | 返回 `expected` / `actual` |
| 11 | 写 `{idx}.{rand}.part` → rename | 500 | 原子落盘；临时名按请求唯一 |
| 12 | `SETBIT` 置位 + 三把 key 续期 | 500 | 先落盘后置位（Lua 原子置位+TTL） |

几个容易漏的点：

- **归属校验在写盘之前**：不是先收字节再判断，避免未授权请求占用磁盘和带宽。
- **长度是「精确」不是「不超过」**：`f.Size != expected` 直接拒绝。否则客户端可以把第 0 片传成 1 字节，合并时按错误偏移拼接。
- **文件名不参与路径**：临时路径是 `tmp/{upload_id}/{index}`，成品是 `videos/{uid}/{date}/{rand}.mp4`；`filename` 只做元数据，init 时还额外拒绝了 `/`、`\`、`..`。
- **单片 MD5 是流式算的**：`io.Copy(hash, chunkFile)` 后 `Seek(0)` 再写盘，不把 5MB 读成一个 `[]byte`。
- **`GETBIT` 短路也要 `Stat`**：位图说传了但磁盘没有时，先清位再重收（Q10）。

**边界：**

- `chunk_hash` 是客户端声明的，服务端只能保证「收到的字节和这个声明一致」，不能保证「这一片属于 init 时那个整文件」。真正的归属由合并后的整文件 MD5 兜底（Q12、Q19）。
- 没有校验 content-type / magic bytes：任何 5MB 以内的字节都能被接收，最终只是被命名为 `.mp4`。生产环境应加 ffprobe / 文件头校验 / 病毒扫描。
- 没有 per-user 上传 QPS 限制，恶意用户可以反复 init/upload 制造磁盘和 Redis 压力（Q20）。

**加分：** 把校验顺序讲成「越便宜、越靠前」：会话和归属是 Redis/JWT 级，长度是 header 级，MD5 要读完整片，写盘最贵。这样即使被刷，也能在最便宜的环节挡掉大部分无效请求。

## 8. 两个请求同时上传同一个分片，如何处理？先检查位图再写文件会不会出现竞态？

**一句话：** 位图这一层是安全的（`SETBIT` 单 bit 原子、幂等）；「检查位图 → 写文件」确实是 check-then-act，但文件层现在用**请求唯一的临时名 + 安全 rename**，两个 writer 各有自己的 inode，最后完成者覆盖，不会再互相删文件。

**展开：**

先分清两层：

| 层 | 操作 | 是否原子 | 并发后果 |
|---|---|---|---|
| 状态层 | `SETBIT key i 1` | 是，单命令原子 | 两个请求都置 1，结果一致 |
| 文件层 | 写 `{i}.{rand}.part` → rename → `{i}` | rename 原子，临时名互不相干 | 最后完成者覆盖目标，内容一致时无害 |

关键修复（`chunk_handler.go:435-488`）：

1. **临时名带请求唯一后缀**：`{idx}.{16位随机}.part`。两个并发 writer 不再共享同一个 inode，谁先 rename 都不会把对方正在写的文件搬走。
2. **`renameReplace` 的安全回退**：Windows 的 rename 不能覆盖已存在文件。回退前先 `Stat(src)`，源不存在就**直接返回错误，绝不删目标**；源存在才在有限重试里删目标再 rename。旧实现「rename 失败就删目标」在源已被另一个请求搬走时，会把唯一的好文件删掉。
3. **状态最终仍由位图收敛**：两个请求都成功 rename 后都置位；即使其中一个请求失败，只要另一个成功，`reconcileBits` + `GETBIT + Stat` 也会把状态拉回一致。

典型时序（两请求都还没置位）：

```
A: GETBIT=0 → 校验 → Create("{i}.A.part") → 写 5MB ─┐
B: GETBIT=0 → 校验 → Create("{i}.B.part") → 写 5MB ─┼→ 两个独立 inode
A: close → rename("{i}.A.part" → "{i}") ───────────┘
B: close → rename("{i}.B.part" → "{i}") → Windows 需要先删目标
   → Stat(src) 成功 + Stat(dst) 成功 → 删目标 → rename 成功
   → 最终文件是 B 的字节；同下标同内容，结果一致
```

**边界：**

- 没有对同一 index 加短锁：并发同片仍是「最后完成者赢」。对同一文件来说每片字节相同，所以无害；如果客户端真的对同一 `upload_id` 传了**不同内容**，整文件 MD5 会在 complete 拦下（Q19）。
- 清理逻辑只删「无活会话且超过 24h」的 tmp 目录，不会在写入过程中删当前会话的 `.part`；请求唯一的临时文件如果在极端崩溃下残留，会随目录一起被回收。
- 状态层不需要锁：这正是「单 bit 状态变更用原子命令，复合操作才用锁」的分界（Q11）。

**回归测试：** `TestConcurrentSameChunkUploadIsSafe`（8 个 goroutine 同时传同一片，断言全部 200、无 `.part` 残留、合并结果字节正确）、`TestRenameReplaceKeepsDestinationWhenSourceMissing`（源不存在时目标必须保留）。

**加分：** 面试官问「先检查再写有没有竞态」，不要只答「有」或「没有」。正确答法是分层：**状态层的竞态被 `SETBIT` 消除了；文件层的竞态靠「唯一临时名 + 原子 rename」从『互相破坏』降级为『最后写入者覆盖』；内容正确性最终由整文件 MD5 兜底**。

## 9. 分片内容保存在哪里？如果直接保存在本地磁盘，多个 API 实例如何共享分片？如果保存在对象存储，架构又有什么不同？

**一句话：** 现在存在 API 本地磁盘 `.run/uploads/tmp/{upload_id}/{index}`，单机正确、多实例必然分叉；对象存储把「收片、合并、清理」交给 OSS/S3 的 multipart API，API 只保管会话映射。

**展开（当前本地磁盘布局）：**

```
.run/uploads/
├── tmp/{uploadID}/
│   ├── 0  1  2 ...                    ← 已确认的完整分片
│   └── 3.a1b2c3d4e5f60718.part        ← 正在写的分片（请求唯一临时名）
└── videos/{uid}/{date}/{rand}.mp4     ← 合并后的成品（合并中先写 .mp4.part）
```

静态文件由 `r.Static("/static", "./.run/uploads")` 直接暴露（`router.go:31`）。

**多实例下会发生什么：**

- 上传请求落到实例 A，分片写在 A 的本地盘；
- complete 落到实例 B，B 的 `tmp/{upload_id}` 是空的；
- `reconcileBits` 把 B 看到的「位图有、磁盘没有」全部清位，返回完整缺失清单；
- 客户端补传，可能又落到 A 或 C；complete 再换一台，系统进入「补传—丢失—再补传」的循环。

对账能**自愈**，但无法**根除**。三种缓解：

| 方案 | 代价 |
|---|---|
| 会话粘滞（按 `upload_id` 或用户路由到同一实例） | 负载不均；实例故障后分片仍丢 |
| 共享存储（NFS / CephFS / 分布式文件系统） | 运维复杂；rename 原子性和锁语义要确认 |
| 对象存储（推荐） | 改造客户端和鉴权；有存储/请求成本 |

**对象存储架构：**

```
init：后端创建 multipart upload（或对每个 part 预签名）
  → 返回 upload_id + 每个 part 的预签名 URL（短 TTL、限定 key + partNumber）
upload：客户端直接 PUT 到 OSS，拿到每片 ETag
status：后端 ListParts（服务端事实）或客户端上报 ETag
complete：后端调 CompleteMultipartUpload(parts=[{PartNumber, ETag}...])
  → OSS 在服务端拼接，不复制 200MB 数据
  → 返回对象 URL（可接 CDN）
abort：超时/取消时 AbortMultipartUpload；生命周期规则自动清理未完成的分片
```

对比：

| 维度 | 本地磁盘 | 对象存储 |
|---|---|---|
| 多实例 | 需要粘滞/共享存储 | 天然共享 |
| 合并开销 | 读 200MB + 写 200MB + MD5 | 元数据操作，几乎不搬数据 |
| 带宽 | 全走 API 服务器 | 客户端直传，API 只传控制流 |
| 持久性 | 单机盘，实例挂了就没了 | 多副本/多 AZ |
| 清理 | 自己写 GC | 生命周期规则 |
| 完整性校验 | 服务端能重算整文件 MD5 | 直传时服务端看不到字节，需 checksum/回调/异步校验 |
| 安全 | JWT + 归属校验 | 预签名 URL 是能力凭证，必须短 TTL、最小 scope |
| 限制 | 磁盘/inode | 最小 5MiB（最后一片除外）、最多 10000 片、ETag 语义因厂商而异 |

**边界：**

- 直传对象存储会削弱「服务端重算整文件 MD5」这一层：如果完全信任客户端声明的哈希，就失去 Q12 的终检。需要让 OSS 做 checksum（如 `x-amz-checksum-sha256`）、或后端异步下载抽检、或客户端上传后回调服务端做 HEAD + 抽样。
- 预签名 URL 泄露等于把某个 part 的写权限给了别人；TTL 要短，key 和 partNumber 要绑死。
- S3 的 ETag 不保证是 MD5（分片上传、加密、某些厂商实现都会变），不能直接拿 ETag 当整文件 MD5 用。

**加分：** 对象存储最大的价值不是「省磁盘」，而是把「合并」从「200MB 数据搬运」变成「一次元数据提交」，同时用 `AbortMultipartUpload + lifecycle` 从根上解决 Q14 的孤儿分片。这是「自愈」和「根除」的区别。

## 10. Redis 位图记录某个分片已上传，但实际文件内容丢失了，如何检测并恢复？

**一句话：** 不信任位图，所有对外表达进度的出口（`init` / `status` / `complete`）都先走 `reconcileBits`：bit=1 就 `Stat` 并比对精确大小，不合格当场清位；合并前再全量 `Stat` 一次，缺片一次性返回完整清单。

**展开（三层防线）：**

| 层 | 位置 | 作用 |
|---|---|---|
| ① 单片即时核对 | `UploadChunk` 的幂等短路前 | 客户端重试这一片时立刻修复 |
| ② 出口统一对账 | `reconcileBits`，`init` / `status` / `complete` 全走它 | 刷新、续传、合并都能发现坏片 |
| ③ 合并失败给全清单 | `mergeChunks` 先全量 `Stat` 再动手 | 客户端一轮补完，不用逐片猜 |

```go
// chunk_handler.go:155-175
for i, uploaded := range bits {
    if !uploaded { continue }
    fi, statErr := os.Stat(h.chunkPath(s.UploadID, i))
    if statErr == nil && fi.Size() == s.ExpectedChunkSize(i) { continue }
    bits[i] = false
    _ = h.cache.SetBitWithTTL(ctx, h.bitsKey(s.UploadID), int64(i), 0, sessionTTL)
}
```

**为什么必须核对：** 位图和磁盘是两份独立的事实。只信位图的话：

- 客户端重传 → 被幂等短路，不重建文件；
- `complete` → `chunk i missing` → 500；
- 会话 24h 内永远完不成，客户端还不知道是哪一片坏了。

**写入顺序是配套的**：`写 .part → rename → SETBIT`。如果反过来，进程崩在中间就会留下「位是 1、磁盘没有」的死锁态；现在这个顺序下崩溃最多留下「文件在、位是 0」，客户端重传一片即可。原则是：**宁可重传一片，绝不假完成。**

**恢复路径：**

- 客户端刷新后重选文件 → `init` 命中旧会话 → `reconcileBits` 返回真实进度；
- 前端 `status` 最多 3 轮核对，按缺口补传；
- `complete` 返回 `missing_chunks: [0, 3]`，前端删掉本地记账、补传、重试合并；
- 相关测试：`TestStatusRepairsBitsWhenChunkFileLost`、`TestInitResumptionReportsTruthfulProgress`、`TestCompleteReportsAllMissingChunksAndRecovers`。

**边界：**

- `Stat` 只能发现「不存在 / 大小不对」，发现不了**同大小的字节损坏**（bit 翻转、内容被替换）。后者由合并时的整文件 MD5 兜底（Q12）。
- 对账是**惰性**的：只在有人访问时发生。`chunk_cleaner` 只回收「已无会话且超过 24h」的目录，不会主动替活会话修坏片；如果会话永远没人再访问，坏片会一直挂到 TTL。
- 多实例本地盘下，「位图有、磁盘没有」不是偶发而是必然（Q9）；对账让它自愈，但根除要靠共享存储/对象存储。
- 每次对账 N 次 `os.Stat`；40 片是微秒级，4096 片会到毫秒级，仍可接受，但要知道成本。

**加分：** 用一句话总结这题：**「位图是索引/缓存，磁盘才是权威。」** 把位图当缓存看，就不会问「为什么不信 Redis」；缓存和权威分叉时，永远以权威为准并回写缓存，这是所有缓存一致性的通用套路。

## 11. 为什么合并前需要加锁？锁的粒度是整个上传任务，还是某个文件？如何防止重复合并？

**一句话：** 合并是「读 N 片 + 建成品 + 写 Redis + 删会话」的复合操作，没有单条命令能原子完成，所以用 **per-upload_id 的 token 锁**把并发 complete 串行化；锁内重读会话，长合并靠心跳续租，结果缓存兜最终幂等。

**展开：**

```go
// chunk_handler.go:583-618（简化）
token, acquired, err := h.cache.Lock(ctx, lockKey, mergeLockTTL)
if !acquired {
    c.JSON(http.StatusConflict, gin.H{"error": "merge already in progress"})
    return
}
defer func() { _ = h.cache.Unlock(context.Background(), lockKey, token) }()

// 心跳：只在自己仍持有锁时 PEXPIRE，锁被别人接管后不会续上对方的锁
go func() { /* 每 mergeLockTTL/3 调一次 RefreshLock(ctx, key, token, ttl) */ }()
```

为什么必须加：

- 两个 complete 同时通过判满 → 各自 `os.Create` 一个随机文件名 → 各写一份 → 两个 URL，后返回的赢，留下孤儿文件；
- 用户双击、代理重放、前端超时重试，都会制造并发 complete。

锁的粒度：

| 粒度 | 结果 |
|---|---|
| 全局一把锁 | 所有用户的上传串行，吞吐灾难 |
| per-file_hash | 同文件不同账号会互相阻塞，语义也不对 |
| **per-upload_id** | **一个会话一把锁，互不干扰，最细的正确粒度** |
| per-chunk | 合并不止一个片，锁不住整个复合操作 |

四个容易漏的细节：

1. **抢到锁后重新读结果和会话**（`chunk_handler.go:610-623`）：加锁前的 session 可能是旧快照；另一个并发 complete 也可能刚好完成。
2. **锁带 token，释放用 compare-and-delete**：`Unlock` 是 Lua「GET 相等才 DEL」。租约到期、锁被别人接管后，旧持有者的 `defer` 不会误删新锁。
3. **心跳续租**：合并最长可能超过 10min（慢盘 + 200MB + MD5），后台每 1/3 租约调 `RefreshLock`（Lua compare-and-PEXPIRE）。只有仍持锁才续期，不留「给别人的锁续命」的窗口。
4. **全局限流**：per-upload_id 锁只防同一会话重复合并；不同会话之间再用容量 4 的信号量限流，等 5s 拿不到名额返回 503，避免突发流量把磁盘 IO 打满（`chunk_handler.go:742-746（`acquireMergeSlot`）`）。

结果缓存是最终幂等（`chunk_handler.go:560-568`）：complete 成功写 `chunk_upload_result:{id}`（1h，内含 `account_id`），之后任何重复 complete 都先校验归属、再直接回放 URL，连锁都不用抢。

**边界：**

- **进程崩溃后锁要等 10min 才释放**，而前端 complete 只重试 3 次、总退避约 6s，全部会收到 409。用户体感是「合并一直失败」，实际要等锁过期（Q13）。要彻底解决需要把「合并中」持久化，而不是靠锁 TTL 猜。
- **没有 fencing token**：锁只能保证「同一时刻最多一个持有者」，不能阻止一个已被判定过期、但仍在写的旧进程最终写出文件。极端慢盘下仍可能需要内容寻址/唯一成品名来保证物理唯一。
- 这里的锁不是为了保证「数据正确」，而是为了避免「重复资源」；真正的幂等靠结果缓存。

**加分：** 和 Q8 形成对照：**单 bit 状态变更用原子命令，复合操作才用锁**。判断标准是「能不能用一条 Redis 命令表达这个状态变更」。`SETBIT` 能，所以不加锁；「拼 40 片 + 登记结果 + 删会话」不能，所以加锁。

## 12. 合并时如何避免把错误顺序的分片拼接起来？如何校验最终文件大小和 MD5？

**一句话：** 分片文件名就是下标，`mergeChunks` 按 `0..N-1` 顺序打开，每片先校验精确长度；整文件 MD5 在写盘的同一次 IO 里用 `io.MultiWriter` 流式计算，最后与 init 的 `file_hash` 比对。

**展开：**

```go
// chunk_handler.go:779-827（简化）
for i := 0; i < session.TotalChunks; i++ {
    fi, err := os.Stat(path(i))
    if err != nil || fi.Size() != session.ExpectedChunkSize(i) {
        missing = append(missing, i)
    }
}
if len(missing) > 0 { return "", missing, nil }   // 不写半成品

whole := md5.New()
sink := io.MultiWriter(finalFile, whole)
for i := 0; i < session.TotalChunks; i++ {
    cf, _ := os.Open(path(i))
    io.Copy(sink, cf)   // 写盘 + 算 hash 一次 IO 完成
}
finalFile.Sync()        // 先刷盘，再交给上层 rename
```

- **顺序不会错**：文件名由服务端生成，`{index}` 与字节内容一一对应；合并循环显式按 0..N-1，不依赖目录遍历顺序，也不排序。
- **重复不会混入**：一个下标只有一个文件；`Stat` 按精确长度校验，缺片/短片都进 `missing`。
- **大小校验是隐式的**：`Validate` 保证 `total_chunks == ceil(file_size/chunk_size)`，每片长度又精确匹配，所以拼接后的总大小必然等于 `file_size`。再加一次 `Stat(finalPath)` 比对是廉价防御。
- **整文件 MD5**：`io.MultiWriter(文件, md5)` 在拷贝的同时算哈希，避免合并完再读一遍 200MB。
- **单片 MD5 不能拼出整文件 MD5**：MD5 是链式的，必须对拼接后的完整字节流重新算，这也是为什么要在合并时算。
- **成品先写 `.mp4.part`**：合并、`Sync`、hash 校验全通过后才 `rename` 成 `.mp4`。崩溃最多留下 `.mp4.part`（由 cleaner 回收），不会留下「名字是成品、内容缺尾」的文件。
- **失败处理**：整文件 MD5 不匹配 → 删临时文件 → `invalidateSession`（删 tmp/bits/session，compare-and-delete hash 索引）→ 返回 400 `code=file_hash_mismatch`。会话必须作废，否则客户端会对同一份坏数据重试到 TTL 过期。

**边界：**

- 全量 `Stat` 和 `os.Open` 之间存在 TOCTOU：如果中间有并发清理删掉某片，`Open` 失败会退化成「缺这一片」，返回 `missing=[i]`，上层清位并让客户端补传。
- 同大小内容被替换，`Stat` 发现不了，只有整文件 MD5 能发现。
- **整文件 MD5 能告诉你「坏了」，但不能告诉你「哪片坏了」**：当前恢复路径是「作废会话 → 客户端重新 init → 全量重传」。正确但昂贵；更细的定位需要 init 时提交分片哈希清单（Merkle root），逐片定位。当前实现选择的是「正确性优先、恢复路径明确」，不是「最小重传」。
- 合并是在 API 进程内同步做的，不是后台 Worker；"Worker 宕机"要换成「API 进程崩溃」（Q13）。

**加分：** 如果面试官问「为什么不合并完再算 MD5」，答两点：① 200MB 二次读盘是纯浪费，`MultiWriter` 让写和算共用一次 IO；② 合并时算还能顺带发现「分片在合并期间被替换」的问题。再补一句 Merkle 树能把「整体坏了」细化到「哪片坏了」，就是加分项。

## 13. 如果合并过程执行到一半，Worker 宕机了，用户重试后如何恢复？是否需要临时文件、状态机和原子重命名？

**一句话：** 本项目没有独立合并 Worker，合并在 API 请求内同步执行；崩溃恢复靠「成品先写 `.mp4.part`、校验后 rename + 结果先于清理落盘 + 锁 TTL 到期」，重试能收敛且不会触发全量重传；但还没有持久化的合并状态机，也没有「成品文件 vs DB 引用」的对账。

**展开（先纠正前提）：** `CompleteChunkUpload` 直接在 Gin Handler 里做合并（`chunk_handler.go:538-739`），没有把合并丢给 Worker。所以「Worker 宕机」应表述为「API 进程崩溃/被 kill」。这本身是一个设计点：合并是重 IO 操作，放在请求内会占用连接和内存，规模大时应改成异步任务 + 状态查询。

按崩溃点拆（当前实现）：

| 崩溃点 | 磁盘 | Redis | 重试结果 |
|---|---|---|---|
| 合并写 `.mp4.part` 中途 | 临时半成品残留，tmp 完整 | 锁残留至 TTL，session/bits 完整 | 锁过期后重试重新合并；`.mp4.part` 由 cleaner 24h 后回收 |
| `.mp4.part` 写完、rename 前 | 临时半成品完整，tmp 完整 | 同上 | 同上，不会出现「名字是成品」的坏文件 |
| rename 完成、result 未写 | final 完整，tmp 仍在 | session/bits 完整 | 重新合并出第二份成品（孤儿 +1），但 URL 幂等仍成立 |
| **result 已写、tmp 未删** | tmp 完整，final 完整 | result 在，session/bits 在 | 命中 result 回放 URL；残留 key 由 cleaner 回收 |
| result 已写、session 未删 | tmp 已删，final 完整 | result 在，session/bits 仍在 | 命中 result 回放；残留 key 到 TTL/cleaner |
| hash 校验失败 | `.mp4.part` 删除 | 会话被 `invalidateSession` 作废 | 重复 complete 404；客户端收到 `file_hash_mismatch` 后重新 init |

关键顺序（`chunk_handler.go:723-733`）：**rename 成品 → 写 result → 删 tmp → 删 bits/session/hash**。旧实现先删 tmp 再写 result，崩在中间会造成「位图说全齐、分片已没」，只能全量重传；现在只要 result 写成功，重试永远命中回放。

恢复机制：

- **锁 TTL 10min + 心跳续租** 是崩溃检测：进程死了，心跳停止，锁靠过期释放；正常慢合并则持续续租，不会被第二个 complete 抢走。
- **前端 complete 只重试 3 次**，退避 1s/2s/3s，约 6s 内全部 409。所以崩溃后用户立即重试会一直看到「合并中」，要等 10min。
- **结果缓存**保证「至少合并一次、URL 幂等」，但不保证「物理文件只有一份」。

已经补上的东西：

1. **成品原子写**：`.mp4.part` → `fsync`（`mergeChunks` 内的 `Sync`）→ 校验整文件 MD5 → `rename` 成最终名。
2. **锁租约续期**：后台心跳用 compare-and-expire 只给自己续租；释放用 compare-and-delete。
3. **清理顺序**：result → tmp → session/bits/hash；hash 索引用 compare-and-delete，避免误删并发 re-init 的新映射。
4. **残留回收**：`chunk_cleaner` 每小时扫一次，回收超过 24h 且无活会话的 tmp 目录，以及崩溃留下的 `.mp4.part`。

仍未做（属于架构/下一阶段）：

1. **合并状态机**：session 增加 `status: uploading | merging | done` + `lease_until`，用 CAS 抢占；崩溃后可被其它实例接管，而不是干等锁 TTL。
2. **fencing token**：防止租约过期后旧进程仍写出成品；当前靠唯一成品名避免覆盖，但会多一份文件。
3. **孤儿成品清理**：`videos/` 下没有被 DB 引用的文件，需要 assets 表/发布状态才能安全巡检（Q18）。
4. **异步化**：合并提交到任务队列，接口立即返回 `merging`，前端轮询 status；这也能避免长请求占住连接。

**边界：**

- 当前方案是 **at-least-once 合并 + URL 幂等**，不是「物理文件恰好一份」。进程在 rename 之后、result 之前崩溃，会多一份孤儿成品；要接受极端情况下的这一份冗余。
- 没有持久化的「合并中」状态，无法区分「正在合并」和「已经崩了」，只能靠锁 TTL 猜。
- 进程被 kill 时 `defer` 不执行；`.mp4.part` 会留在磁盘，由 cleaner 按年龄回收。

**加分：** 如果迁到对象存储，`CompleteMultipartUpload` 本身是服务端原子操作，重试幂等，这类崩溃恢复问题基本消失。这是「自建合并」和「托管 multipart」最大的工程差异之一。

## 14. Redis 位图如何设置 TTL？如果上传任务过期，但磁盘上的分片没有清理，会造成什么问题？

**一句话：** 位图/会话/hash 索引都是 24h，结果是 1h，锁是 10min；三者用同一个 `touchSession` 一起续期，临时文件由 `chunk_cleaner` 按「无活会话 + 超过 24h」回收，但 `videos/` 下未被 DB 引用的成品仍需要业务侧对账。

**展开（当前 TTL 与续期时机）：**

| key | TTL | 续期时机 |
|---|---|---|
| `chunk_upload:{id}`（session） | 24h | init 命中/新建；每个分片上传成功；status 查询 |
| `chunk_upload_bits:{id}` | 24h | 每次 `SetBitWithTTL`（Lua 原子置位+续期）；`touchSession` |
| `chunk_upload_hash:{uid}:{hash}` | 24h | init 续传命中；每个分片上传成功；status 查询 |
| `chunk_upload_result:{id}` | 1h | complete 成功时写 |
| `chunk_upload_lock:{id}` | 10min | complete 抢锁；心跳每 1/3 租约 compare-and-expire |

两个实现细节：

- `SetBitWithTTL` 用 Lua 把 `SETBIT` 和 `PEXPIRE` 合成一次原子执行（`cache.go:99-106`），不存在「置位成功、续期失败」的中间态。
- **TTL 续期统一**：`touchSession` 用一个 pipeline 同时续 session / bits / hash 索引（`chunk_handler.go:123-134`）。三者的寿命必须一致，否则会出现「位图还在、session 已过期」（upload 404）或「session 还在、hash 索引已过期」（同一文件被当成新上传）。

TTL 到期后的孤儿来源与处理：

| 场景 | 残留 | 现在怎么处理 |
|---|---|---|
| 用户传到一半放弃 | `tmp/{upload_id}` 的分片 | 24h 后无活会话 → cleaner 删除 |
| 会话过期 | 同上，且 Redis 已无记录 | cleaner 删除 |
| 同文件换分片大小重新 init | 旧会话的 tmp + 旧 Redis key | Redis 到 TTL；tmp 由 cleaner 回收 |
| 合并中途崩溃 | 半成品 `.mp4.part` | cleaner 按 mtime 删除 |
| 合并成功但用户从未 publish | `videos/{uid}/{date}/{rand}.mp4` | **仍无自动清理**（需要 assets 表，Q18） |
| hash mismatch | tmp + bits | 服务端立即 `invalidateSession`，不再等 TTL |

**已落地的清理任务**（`chunk_cleaner.go:22-89`，`main.go` 在 Redis 可用时启动）：

- 每小时扫一次 `tmp/`：目录 mtime 超过 24h **且** Redis 里没有对应 session 才删；Redis 不可用时跳过，宁可不动也不毁掉活会话。
- 扫 `videos/`：只删 mtime 超过 24h 的 `*.mp4.part`。成品 `.mp4` 不凭磁盘状态删——它可能已被 publish 引用。
- 启动时立即执行一次，之后按 ticker 周期执行。

剩下的边界：

1. **孤儿成品仍需业务对账**：`complete` 不写 DB，用户没 publish 的文件没有「主人」。正确做法是 assets 表（`pending/committed`）+ 年龄阈值巡检（Q18）。
2. **多实例本地盘**：cleaner 只清理本实例磁盘；共享存储下需要分布式协调或按实例分目录。
3. **结果 TTL 与业务对齐**：1h 内重复 complete 能回放；1h 后 session 已删，只能 404。如果前端有「隔很久再点重试」的场景，要相应延长。
4. **对象存储**：用 `AbortMultipartUpload` + lifecycle 规则自动清理未完成分片，是比自建 cleaner 更彻底的方案（Q9）。
5. **TTL 不是垃圾回收器**：它只回收 Redis 内存，不回收磁盘；清理任务必须用「mtime + 会话存在性 + 年龄阈值」三重条件，删太早会破坏活上传，删太晚磁盘会满。
6. **24h 是体验和成本的折中**：太短，用户隔天回来无法续传；太长，孤儿占盘更久。

**加分：** 把「TTL 过期」和「资源泄漏」分开讲：Redis 侧的过期是自动的、正确的；泄漏发生在 Redis 之外的磁盘/对象存储。这是分布式系统里常见的「有状态引用」问题，和「数据库删了行、文件还在」是同一类（Q18）。

# 第三层：故障与反问

## 15. 上传 100 个分片，前 99 个成功、最后一个失败，客户端如何准确找出缺失分片并续传？

**一句话：** 以服务端为准：`init` / `status` 返回对账后的已传下标，前端算差集只补缺口；`complete` 失败时返回完整 `missing_chunks`，前端删本地记账、补传、再合并。

**展开（前端闭环，`VideoView.vue:162-303`）：**

1. **单片失败先自己重试**：`uploadOne` 最多 3 次尝试，指数退避 + jitter；4xx（除 401/408/409）视为 fatal，不重试。
2. **整轮失败后不丢进度**：服务端位图和分片已经落盘，失败只影响这一次请求；用户重新选同一个文件 → 重算 `file_hash`（同一文件结果相同）→ `init` 命中旧会话。
3. **`init` 返回可信进度**：服务端先 `reconcileBits`，再返回 `uploaded_chunks`；前端 `missingChunks()` 用 `0..N-1` 减去已传集合，只传缺口。
4. **合并前再核对最多 3 轮**：`chunkStatus` 以服务端位图为准，补上「服务端成功但响应丢了」的片；本地 `done` 只是 UI 记账，不是事实来源。
5. **合并失败兜底**：`complete` 返回 `missing_chunks: [0, 3]` 时，前端把这几个下标从 `done` 删掉、立即补传、`continue` 重试合并；409（正在合并）则退避 1s/2s/3s。

```
init → uploaded_chunks = [0..98]（假设 99 已传）
  → gaps = [99]
  → 只传 99
  → status 核对 → gaps 为空
  → complete
```

为什么不能只信本地 `done`：

| 本地记账的盲区 | 服务端为什么知道 |
|---|---|
| 请求成功但响应丢失，客户端以为失败 | 位图已置位，`status` 会返回 |
| 多标签页/重试并发 | 位图是共享状态 |
| 页面刷新，内存状态清零 | 会话 + 位图在 Redis |
| 位图有、磁盘没有 | `reconcileBits` 清位并报缺 |

**边界：**

- 「100 片」在当前配置下超出上限：200MB / 5MB = 40 片。要 100 片，要么分片改成 2MB（200MB / 2MB = 100），要么提高 `MaxFileSize`；`MaxTotalChunks = 4096` 本身支持。
- 如果失败原因是 fatal 4xx（`chunk hash mismatch`、403、404 会话不存在），前端不会重试，必须用户重新 init/重新选文件；这时「准确找出缺失」不等于「能自动恢复」。
- `status` 本身可能 503（Redis 不可用），这时整个续传链路不可用，只能等 Redis 恢复。
- 每轮 `status` 是 `GETBITS` pipeline，O(N) 次命令 + N 次 `Stat`；40 片很轻，4096 片要评估耗时。

**加分：** 这题的本质是「进度的事实来源」：客户端记账只是缓存，服务端对账后的位图才是权威。把这句话讲出来，比背「我用了 status 接口」高一个层次。

## 16. 如果前端上传成功但网络断开，客户端没有收到响应，再次上传同一分片会发生什么？

**一句话：** 重传会命中服务端的幂等短路（位图=1 且磁盘大小正确）直接 200；如果崩在置位之前，则重写覆盖；两种顺序都收敛到「一片一份」，因为分片状态是布尔值而不是计数器。

**展开（两个窗口）：**

| 服务端实际状态 | 客户端看到的 | 重传时发生什么 |
|---|---|---|
| 已 rename + 已 `SETBIT` | 失败（响应丢了） | `GETBIT=1` + `Stat` 大小对 → 200 短路，不重写 |
| 已 rename，未 `SETBIT`（崩在中间） | 失败 | `GETBIT=0` → 重新写 `.part` → rename 覆盖 → 置位 |
| 写了 `.part`，未 rename | 失败 | 没有完整分片、位也是 0 → 重新写；旧的唯一临时文件最多残留一份，由 cleaner 回收 |
| `SETBIT` 成功但磁盘文件丢了 | 成功（客户端以为完成） | 重传时 `Stat` 失败 → 清位 → 重新收（Q10） |

关键点：

- **状态是幂等的**：`SETBIT i 1` 重复执行结果一样；`rename` 覆盖同一下标结果一样；不像 `INCR` 那样重复就多算一次。
- **响应丢失不等于操作丢失**：客户端应以服务端查询为准；`status` 会把「其实成功了」的片补回本地记账。
- **顺序保证**：先落盘后置位，所以「客户端收到 200」一定意味着字节已经 rename 到位（不考虑 fsync/断电的极端情况）；反过来「没收到 200」只意味着不确定，重传是安全的。
- **complete 的响应丢失**：结果缓存（1h）让重复 complete 回放同一个 URL，不会二次合并。

**边界：**

- 同片并发写不再互相破坏：临时名按请求唯一，rename 是「最后完成者覆盖」（Q8）。如果重传和原请求在时间上重叠，最终文件可能是任一请求的字节；同一文件同一片内容相同，所以无害。
- 多实例本地盘：位图共享、文件不共享；重传落到另一台时 `Stat` 失败 → 清位 → 重传，能自愈，但说明部署形态有问题（Q9）。
- Redis 与磁盘的持久化不同步：极端断电后可能出现「位图在、文件没了」或反过来，前者靠对账，后者最多重传一片。

**加分：** 和点赞/热度对比：点赞如果直接 `INCR`，响应丢失后重试会重复加；解决办法是幂等键 + 去重表，或者把「加一」改成「置为某状态」。分片上传天然选了后者——**把副作用设计成幂等的，比事后去重便宜得多**。

## 17. 如果同一个 `upload_id` 被两个客户端同时使用，如何防止分片串文件或者覆盖？

**一句话：** 跨账号由 `session.AccountID` 校验挡住（403），结果缓存回放也校验 `result.AccountID`；同账号多标签页不会串文件（路径按 index 固定、参数绑在会话里），但会出现「一边 complete 删会话、另一边还在传」，以及同片并发写的最后写入者覆盖。

**展开：**

**跨账号：**

- `upload` / `status` / `complete` 都会读 session 并比对 `AccountID`，不一致返回 403（`chunk_handler.go:335,513,575`）。
- `complete` 的结果回放发生在读 session 之前，但结果对象里存了 `account_id`，回放前同样校验（`chunk_handler.go:562,612`）。
- `upload_id` 是 128-bit 随机 + 纳秒，不可枚举；但它是**能力凭证**，不是鉴权凭证，真正的权限仍靠 JWT + 归属校验。

**同账号、两个标签页：**

| 操作 | 结果 |
|---|---|
| 传不同的 index | 安全：不同文件路径，`SETBIT` 各自原子 |
| 同时传同一个 index | 文件层临时名唯一，最后完成者覆盖；状态最终收敛（Q8） |
| A 已 complete，B 还在传 | A 删了 session/bits/tmp；B 的 upload 收到 404，`isFatal` 判定不重试，B 报错 |
| A 已 complete，B 再调 complete | result 缓存命中（1h 内）→ 回放同一个 URL；超过 1h → 404 |

**防止串文件：**

- 临时路径由 `upload_id + index` 决定，客户端不能指定文件名/路径；
- `init` 校验 `filename` 不含 `/`、`\`、`..`，成品名是随机 hex，扩展名服务端固定 `.mp4`；
- 会话绑定 `file_size / chunk_size / total_chunks / file_hash`；换文件重新 init 会得到新会话，旧 `upload_id` 的 `chunk_size` 对不上会 400；
- 同大小但不同内容：单片 MD5 是客户端自证的，能过；但合并后的整文件 MD5 对不上 `session.FileHash`，会被 400 拦下（Q19）。

**边界与改进：**

- 没有「单写者租约」：同一账号可以有多个标签页同时传同一个会话。要彻底避免，可以给 init 返回一个 `writer_token`，upload/complete 必须带；或者用 `localStorage + BroadcastChannel` 让同一浏览器的标签页选出一个 leader。
- 没有「已完成」墓碑：complete 删会话后，迟到的 upload 只能 404。可以在 upload 开头先查 result 缓存，命中则返回 409 `already completed` + URL，语义更清楚。
- 不同账号共享同一个文件（秒传）当前不支持，也不应该直接复用 `upload_id`；要共享应该走全局 `file_hash → object` 映射 + 权限模型。

**加分：** 把 `upload_id` 类比成「上传会话的句柄」：句柄可以传递，但每次使用都要校验持有者权限。只靠「ID 猜不到」不是安全模型，`crypto/rand` 只是降低了被猜中的概率。

## 18. 文件合并成功，但数据库中的视频记录创建失败，如何避免出现孤儿文件？反过来，数据库记录成功但文件不存在又怎么办？

**一句话：** 本项目的 `complete` 只产出文件和 URL，`videos` 记录是后续 `/video/publish` 才写的，两者没有事务关系；所以「有文件没记录」是常态风险，「有记录没文件」只能靠存储可靠性和巡检。

**展开（先厘清链路）：**

```
chunk/complete → 写 videos/{uid}/{date}/{rand}.mp4 → 返回 play_url
  → 前端拿 play_url 调 /video/publish
  → VideoService.Publish 在同一事务里写 videos + outbox_msgs
```

`complete` 不碰数据库，`publish` 不碰文件系统。中间任何一步失败：

| 失败点 | 结果 | 现状 |
|---|---|---|
| 合并成功，用户没点发布 / 发布失败 | 磁盘有文件，DB 无记录 | **孤儿文件**，无自动清理 |
| 合并成功，发布成功，文件后来被删/丢 | DB 有 `play_url`，静态 404 | 播放失败，无自动检测 |
| 合并中途崩溃 | `.mp4.part` 半成品 | cleaner 24h 后回收（Q13/Q14） |
| 合并成功但删 tmp 失败 | tmp 残留 | 无活会话且超 24h → cleaner 回收（Q14） |

**为什么不能靠事务：** 文件系统不是事务资源，MySQL 事务回滚不会删文件；反过来文件删除也不会回滚 DB。硬要跨系统原子，只能上分布式事务/2PC，代价远大于收益。正确方向是**幂等 + 对账 + 补偿**。

**减少孤儿文件：**

1. **内容寻址**：成品直接命名为 `videos/{uid}/{date}/{file_hash}.mp4`。重试合并覆盖同一路径，天然幂等；同文件可去重（跨账号去重要先想清楚隐私/版权）。
2. **上传记录表**：`complete` 时写一条 `upload_assets(upload_id, account_id, path, file_hash, status=pending)`；`publish` 成功后在同一个事务里把状态改成 `committed`。清理任务只删 `pending` 且超过 TTL 的文件，不会误删正在发布流程中的文件。
3. **定期巡检**：扫 `videos/` 下 mtime 超过 24h 的文件，比对 DB 的 `play_url`（或 assets 表），无引用才删。**必须有年龄阈值**，否则会删掉「刚合并、马上要发布」的文件。
4. **Outbox/事件驱动**：`complete` 后发一个「资产已就绪」事件，发布消费它；失败进入重试/死信，至少失败可见。
5. **对象存储生命周期**：未完成 multipart 自动 abort；成品加版本控制/软删除，降低误删风险。

**减少「有记录没文件」：**

- 读取时校验存在性：静态 404 时返回占位/告警，而不是静默黑屏；
- 存储层用多副本/版本控制，禁止绕过应用直接删文件；
- 删除视频走软删除 + 延迟物理删除，给恢复留窗口；
- 定期对 `play_url` 做抽样 HEAD，发现缺失告警。

**边界：**

- 清理孤儿是危险操作：DB 写入可能正在进行，文件暂时「无引用」不等于「永久无引用」。年龄阈值 + `pending/committed` 状态是最低要求，不能裸 `find -delete`。
- 当前项目没有 assets 表，也没有巡检任务；`play_url` 是绝对 URL，迁移域名后旧记录也会指向旧 host。这些都应主动承认，而不是等面试官挖。
- 静态目录 `r.Static("/static", "./.run/uploads")` 直接暴露文件；文件名 128-bit 随机，不可枚举，但拿到 URL 即可访问。视频本身是公开内容，这个模型可接受；私有视频需要签名 URL。

**加分：** 一句话收尾：**「文件系统不是事务资源，别用事务思维解决它；用幂等写入 + 状态标记 + 对账清理。」** 这和 Outbox 的思路是相通的：把「跨系统原子」降级成「本地状态 + 可重试 + 可观测」。

## 19. 用户上传过程中修改了本地文件内容，但仍使用原来的 `upload_id`，后端如何识别这种情况？

**一句话：** 单片 MD5 是客户端自证的，改过的片也能过；真正的识别点在 `complete` 的整文件 MD5——它会和 init 时声明的 `file_hash` 对不上，服务端删半成品、作废会话，前端收到 `file_hash_mismatch` 后重新 init 完整上传一次。

**展开（分情况）：**

| 客户端行为 | 服务端看到什么 | 结果 |
|---|---|---|
| 改文件后重新 init | 新 `file_hash`，与旧 `(uid, hash)` 不匹配 | 新会话；旧会话/tmp 变孤儿到 TTL |
| 改文件后继续用旧 `upload_id` 传改过的片 | 单片 `chunk_hash` 与内容自洽，校验通过 | 未改的片复用，改过的片覆盖；合并时整文件 MD5 ≠ `session.FileHash` → 400 |
| 只改一个字节（大小不变） | 同上，`Stat` 也发现不了 | 同上，只有整文件 MD5 能发现 |
| 文件变大/变小但仍用旧会话 | 下标越界或长度不匹配 | upload 400；或 complete 缺片 |
| 改文件且伪造新的 `file_hash` 重新 init | 新 hash 与新内容一致 | 这是一次「新文件」上传，旧分片浪费，但不构成混淆 |

为什么单片校验挡不住：

- `chunk_hash` 是客户端算的、客户端传的，服务端只验证「收到的字节 = 声明的 hash」；
- 服务端在 init 时只有整文件 hash，没有每片的期望 hash，所以无法判断「这一片是否属于 init 时那个文件」；
- 只有把所有片拼起来重算，才能知道整体是不是原来的文件。

**检测之后怎么办：**

- 当前：`complete` 返回 400，body 带 `code: "file_hash_mismatch"` 与 expected/actual；服务端删除合并临时文件并 `invalidateSession`（删 tmp/bits/session，compare-and-delete hash 索引）。
- 前端 `isFileHashMismatch` 识别到该 code 后重新调用 `uploadVideoChunked(file, 1)`：重新算整文件 MD5、重新 init（旧映射已删，必然是新会话）、重传全部分片。最多重试 1 次，避免客户端指纹本身算错时无限循环。
- 为什么必须作废会话：保留会话等于让客户端对着同一份确定失败的数据反复 complete，一直卡到 24h TTL。作废后至少给出一条明确、能走通的恢复路径。
- 这条路径的代价是**全量重传**。想做到「只补坏片」需要 init 时提交分片哈希清单（Merkle root），让服务端能判断「这一片属于这个文件」并定位坏片。

**根因与改进：**

- 根因是**服务端没有「分片 → 整文件」的绑定承诺**。init 只拿到一个整体 hash，无法验证单片归属。
- 正解是 **Merkle 树 / 分片哈希清单**：init 时客户端提交每片的 hash（或 Merkle root），服务端逐片校验「这一片属于这个文件」，还能直接定位坏片；合并时再校验 root。代价是 init 多传 N 个 hash（40 × 32B ≈ 1.3KB），完全可接受。
- 另一个方向是内容定义分块（CDC）+ 服务端重算，适合秒传/去重场景，但复杂度更高。

**边界：**

- 如果客户端是恶意的，它可以让内容和声明的 `file_hash` 完全自洽——这不算「识别失败」，只是它上传了另一个文件。MD5 不是身份认证（Q5）。
- 同一文件被修改后如果所有分片都重新传且新的整文件 hash 恰好等于旧值，只可能是 MD5 碰撞；在非对抗场景可以忽略，对抗场景应换 SHA-256。
- 浏览器里 `File` 对象通常是对磁盘文件的引用，上传过程中被外部程序修改的行为因浏览器而异；工程上不能依赖「File 是不可变快照」，服务端终检才是可靠边界。

**加分：** 这题最能体现「校验层次」：单片 MD5 解决「传输完整性」，整文件 MD5 解决「整体一致性」，Merkle root 才能解决「分片归属 + 坏片定位」。三层各管一件事，不要指望一层包打天下。

## 20. 大量用户同时上传文件时，如何控制带宽、磁盘 I/O、临时文件数量和合并任务并发？

**一句话：** 分四层限：客户端并发/超时/退避，接入层 body 限制与限流，服务端 per-user 在途数与全局合并信号量，存储层流式 IO 与临时文件 GC。

**展开：**

| 层 | 可控手段 | 本项目现状 | 缺口 |
|---|---|---|---|
| 客户端 | 并发数、单片超时、指数退避 + jitter、暂停/取消、自适应并发 | 并发 3、3 次尝试、120s、jitter | 无自适应、无暂停/取消、MD5 占主线程 |
| 接入层 | `client_max_body_size`、proxy 读写超时、按 IP/用户限流、请求体落盘策略 | 部署时需确认 ≥5MB、超时 >120s | 仓库内没有显式限流配置 |
| 服务层 | 文件/片数上限、per-user 在途上传数、全局合并并发、请求超时、独立部署 | 200MB/4096 片；全局合并信号量 4 路（等 5s → 503） | 无 per-user 配额/在途上传数 |
| 存储层 | 流式拷贝、磁盘余量预检、tmp 分片数、GC、对象存储卸载 | `io.Copy` 流式；`chunk_cleaner` 每小时回收无主 tmp 与 `.mp4.part` | 单机盘、无磁盘余量预检 |
| Redis | 按 `upload_id` 分片 key、`SETBIT` O(1)、`GETBITS` O(N) | key 天然分散，无全局热 key | 4096 片时 `GETBITS` 命令数偏多 |

具体分析：

- **带宽**：API 服务器同时承担上行和下行；分片上传的 5MB 请求会占用连接和 worker。最有效的卸载是**客户端直传对象存储**，API 只处理控制流（Q9）。其次是接入层按用户限速、限制单用户并发连接。
- **磁盘 I/O**：合并是 200MB 读 + 200MB 写，且和正常静态文件读取共享磁盘。已经用容量 4 的全局信号量限制同时合并数（`chunk_handler.go:742-746（`acquireMergeSlot`）`、`acquireMergeSlot`），等 5s 拿不到名额返回 503；超过这个量级应改成独立 merge worker 或任务队列。
- **临时文件数量**：一个 200MB 上传 40 个片，1000 个并发用户就是 4 万个文件；目录已按 `upload_id` 分片，但 inode 和目录项仍是压力。`chunk_cleaner` 按「无活会话 + 24h」回收，仍需磁盘余量告警。
- **合并并发**：per-upload_id 锁防同一会话重复合并；全局信号量防不同会话同时打满磁盘。拿不到名额返回 503（而不是无限排队），让客户端退避重试；更彻底的方案是异步化后排队。
- **内存**：Gin 默认 `MaxMultipartMemory = 32MB`，5MB 的分片会先缓存在内存；并发 100 个上传就是约 500MB 峰值。可以调低该值让大分片落临时文件，或改用流式读取。
- **服务隔离**：合并是重 IO/CPU 操作，和 Feed、点赞共用一个进程会互相影响。规模上来后应拆成独立的 merge worker，API 只负责收片和控制。

**边界：**

- 单机本地磁盘天然无法水平扩展：加实例只会让「上传在 A、合并在 B」更频繁（Q9）。真正的扩容前提是共享存储/对象存储。
- 没有 per-user 配额时，一个用户可以用多个账号/多个文件打满磁盘；需要账号级并发和日配额。
- 限流要考虑「正常的大文件上传」和「恶意刷」的区分：按在途字节数/并发片数限，比按 QPS 限更贴近资源消耗。
- 用 Little's Law 估算：并发 = 吞吐 × 延迟。3 并发 × 每片 2s ≈ 1.5 片/s/用户；瓶颈通常在磁盘/出口带宽/合并 CPU，而不是 Redis（`SETBIT` 是 O(1)，key 也按会话分散）。

**加分：** 监控指标要能定位瓶颈：活跃会话数、在途分片数、tmp 目录字节数、合并耗时 P95/P99、合并队列长度、磁盘剩余、5xx/409/503 比例、单片上传 P95。没有这些指标，「扩容消费者」就是拍脑袋。

# 附：口径、速查与收尾

## A. 这个模块能承诺什么、不能承诺什么

| 可以说 | 不要说 |
|---|---|
| 分片可独立重试，失败粒度是 5MB | 「分片一定比单次上传快」——小文件反而更慢 |
| `SETBIT` 单 bit 原子，并发传不同片不会互相覆盖 | 「并发传同一片字节完全确定」——临时名唯一后不会互相破坏，但仍是最后完成者覆盖 |
| 进度以服务端 `reconcileBits` 对账结果为准 | 「位图就是磁盘事实」——位图只是索引 |
| `complete` 幂等：结果缓存（带归属）+ token 锁 + 心跳 | 「合并绝对不会产生两份文件」——锁 TTL/进程崩溃仍有窗口 |
| 两级 MD5：单片防传输损坏，整文件防拼接/自洽坏片 | 「MD5 能证明文件来源可信」——它不提供认证，也不抗碰撞 |
| 先落盘后置位，正常崩溃不会「假完成」 | 「断电也绝对不丢」——取决于 fsync/Redis 持久化配置 |
| Redis 不可用时快速失败 503，不产生脏会话 | 「Redis 挂了也能传」——分片上传是唯一例外 |
| 多实例本地盘靠对账自愈 | 「多实例本地盘没问题」——能自愈但会反复补传，根除要靠共享存储/对象存储 |
| 文件与 DB 通过发布流程衔接 | 「文件和数据库强一致」——没有事务，只有最终对账 |

## B. 五个最容易被问穿的追问（一句话口径）

| 题 | 一句话口径 |
|---|---|
| **Q8 同片并发** | 状态层 `SETBIT` 原子；文件层用请求唯一临时名 + 安全 rename，不会互相删文件，最后完成者覆盖。内容正确性由整文件 MD5 兜底；回归测试 `TestConcurrentSameChunkUploadIsSafe`。 |
| **Q10 位图有、磁盘没有** | 位图是索引不是事实。`init` / `status` / `complete` 统一走 `reconcileBits`，`Stat` + 精确大小不合格就清位；合并前全量 `Stat`，缺片一次性返回完整清单。 |
| **Q11 合并为什么加锁** | 合并是「读 N 片 + 建成品 + 写 Redis + 删会话」的复合操作，没有单命令能原子完成；per-upload_id 的 token 锁串行化并发 complete，心跳续租防慢合并超时，结果缓存兜最终幂等。 |
| **Q13 合并崩溃** | 没有 Worker，合并在 API 请求内。成品先写 `.mp4.part` + `fsync` + 校验后 rename；清理顺序是 result → tmp → session；崩溃最多留 `.mp4.part` 或一份孤儿成品，重试能回放，不会全量重传。仍缺持久化合并状态机。 |
| **Q18 文件与 DB** | `complete` 不写 DB，`publish` 才写，两者没有事务。孤儿文件靠「内容寻址 + assets 状态表 + 年龄阈值巡检」；记录有、文件无靠存储可靠性和读取时校验。 |

**四个接口的语义：**

| 接口 | 幂等性 | 关键失败码 |
|---|---|---|
| `/chunk/init` | 同账号同文件 → 同一 `upload_id` | 400 参数不自洽；503 Redis 不可用 |
| `/chunk/upload` | 同片重复 → 200 短路 | 403 非本人；400 长度/MD5；404 会话不存在 |
| `/chunk/status` | 只读 | 403；404；503 |
| `/chunk/complete` | 结果缓存回放（校验归属） | 409 正在合并；503 合并名额已满；400 缺片/`file_hash_mismatch`；403 非本人；404 |

## D. 一句话收尾

> 这个模块的核心不是「会切片」，而是三件事：**用原子数据结构消灭并发覆盖**（`SETBIT` 而不是读改写 JSON）、**用磁盘对账消灭假完成**（`reconcileBits` + 先落盘后置位）、**用结果缓存 + token 锁 + 心跳消灭重复合并**。并发写盘、合并崩溃、hash 不符卡死、结果回放越权、清理缺失这些工程缺口已经补上；剩下的两条是真正的架构边界：**多实例共享存储**与**文件/数据库一致性**。
