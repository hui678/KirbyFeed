### F1. 视频实体被缓存成两份副本

**Q｜面试官会怎么问**
> 「同一个视频，你为什么缓存成了两个 key？」
> 「说说你做过的一次重构 / 你觉得哪里设计得不好？」

**回答要点**（30 秒版）
- **现象**：`video:entity:<id>`（Feed 用）和 `video:detail:id=<id>`（详情页用）存的是**同一个 `video.Video` 结构体的同一行数据**，序列化结果逐字段完全相同
- **三个症状**：① 双份 Redis 内存 ② 失效必须删两次，漏一个就「Feed 显示 101 赞、详情显示 100 赞」 ③ TTL 不一致（1h vs 5min）
- **根因**：`FeedService` 和 `VideoService` 各自实现了一套缓存逻辑，没有收敛
- **修法**：抽出 `internal/video/video_cache.go`，统一 `VideoEntityKey` / `VideoEntityTTL` / `InvalidateVideoEntity`
- **原则**：**同一份数据，只允许有一个 cache key 构造入口**

**完整回答**（逐字练）
> 「同一份视频数据在两条读路径上被缓存成了两个 key，TTL 还不一致 —— Feed 是 1 小时、详情是 5 分钟。根因是两个 Service 各自实现了一套缓存逻辑。我也发现了一个具体后果：删除视频时只删了详情那个 key，没删 Feed 那个，导致**视频删掉了还能从 Feed 刷出来，最长 1 小时**。
> 修法是把 key 构造、TTL、失效统一收到一个共享模块里，改成单一入口，以后写路径只会调用一个失效函数。原则就是：**同一份数据，只允许有一个 cache key 构造入口**。」

### F2. 删除视频后缓存没失效

**Q｜面试官会怎么问**
> 「你们删数据的时候缓存怎么处理？」
> 「漏删除会怎么样？」

**回答要点**（30 秒版）
- **现象**：`VideoService.Delete` 原先只删 `video:detail:id=%d`，没删 `video:entity:%d`
- **后果**：视频删了还能从 Feed 刷出来，最长 1 小时
- **根因**：失效逻辑散落在各处手写，漏一处就露馅
- **修法**：统一走 `InvalidateVideoEntity()`（`video_service.go:105`）
- **原则**：失效必须有**唯一入口**，不能靠「记得每个 key 都删一遍」

**完整回答**
> 「这个是我上面那轮收敛的副产品。原来失效逻辑散落各处手写，删视频时只删了详情那个 key、漏了 Feed 那个 —— 结果视频删掉了还能从 Feed 刷出来最长 1 小时。收敛之后失效只剩一个入口，写路径不可能再漏。」

### F3. TTL 不一致（5min vs 1h）

**Q｜面试官会怎么问**
> 「你这个实体缓存 TTL 是怎么定的？为什么不能给详情页单独设一个短 TTL？」

**回答要点**（30 秒版）
- **现象**：详情页 5min、Feed 1h，同一个字段在两个接口上过期时间不同
- **问题本质**：不是「不同 TTL 本身有错」，而是**同一份数据出现了两个不一致的真相来源**
- **修法**：统一为 `VideoEntityTTL = 1h`，`NewVideoService` 直接用常量（`video_service.go:27-28`）
- **诚实补充**：如果详情页确实需要更高新鲜度，正确做法不是给它换 TTL，而是把高频变字段（点赞数）从实体缓存里拆出去单独查

**完整回答**
> 「统一成同一个常量了。其实问题不在 5 分钟还是 1 小时，而在于**同一份数据出现了两个不一致的真相来源**。如果详情页真的要更高新鲜度，正确做法不是给它换一个 TTL，而是把高频变的字段（比如点赞数）从实体缓存里拆出去单独查。」

### F4. 关注流的 context 超时预算被跨步骤复用 ⭐ **主推这条**

**Q｜面试官会怎么问**
> 「你觉得这个项目哪里做得不好？」
> 「你踩过什么坑？」
> 「这个分布式锁真的生效了吗？」← 最毒的一问

**回答要点**（30 秒版）
- **位置**：`feed/service.go` 的 `ListByFollowing`（修复前第 369-395 行）
- **现象**：一个 50ms 的 `cacheCtx` 被 `GET → SETNX → 双重检查 GET → SetBytes` **四个步骤串起来共用**
- **根因**：带 timeout 的 context 的**额度会被串联在上面的操作连续消耗**
- **后果链**：DB 一慢 → `SetBytes` 超时 → 错误被 `_ =` 丢弃 → **缓存永远写不进去** → 等待方轮询永远落空 → 白等 100ms → 全部兜底查库 → **锁退化成串行查库**
- **为什么难发现**：本地低负载 DB 几毫秒返回，回填成功；**只有压力上去、DB 变慢才暴露**
- **修法**：抽出 `singleRedisOpTimeout` 常量，每个 Redis 操作各自申请独立预算；顺带修两处偷懒 —— `lockErr` 不再被 `_` 丢弃、轮询从 `time.Sleep` 改成 `select` 响应取消
- **原则**：**带 timeout 的 context 不能跨多个 IO 步骤复用**

**完整回答**（建议逐字练）
> 「关注流那个分布式锁分支，我把一个 50ms 的 context 复用到了加锁、双重检查和回填上。带 timeout 的 context 的额度是被串联在上面的操作**连续消耗**的，本地测不出来，DB 一慢回填就超时、错误还被 `_ =` 吞了，结果缓存永远写不进去，锁实际退化成串行查库。
> 修法是每一步 Redis 操作用独立的超时预算。这件事让我记住一个原则：**带 timeout 的 context 不能跨多个 IO 步骤复用。**」

### F5. 同一份数据的「并联双机制」收敛 ⭐ **适合讲「架构复盘」**

**Q｜面试官会怎么问**
> 「视频这块你用了几种防击穿手段？」
> 「同一个视频，详情页和 Feed 列表会不会各查一次库？」
> 「为什么详情页用锁、Feed 用 singleflight？」← **陷阱题，但陷阱已经拆了**：改造前确实是这样，现在**只剩一种**了

**回答要点**（30 秒版）
- **现象**：删掉冗余 `video:detail` 之后，`GetVideoByIDs`(singleflight) 和 `GetDetail`(SETNX) 开始命中**同一个** `video:entity:<id>`
- **关键判断**：这两层是**并联**，不是串联 —— 两条回源路径**互不感知**
- **后果**：同一瞬间同一视频仍有 **P+1** 次回源（SETNX 持锁者 1 + 每 Pod 的 singleflight leader P），**防护完全不叠加**
- **根因**：只合并了 key，**没合并回源路径**
- **修法**：`video_cache.go` 新增共享的 `EntityLoadGroup` + `EntitySingleflightKey`；详情页删掉 SETNX 改用同一 Group（并补 `safeCopy`）；Feed 侧从自身 `requestGroup` 切到共享 Group
- **三重收益**：① 一份数据一套机制 ② 回源 P+1 → **P** ③ 意外的收获 —— 详情页请求与 Feed 列表请求现在能真正合并成一次查库
- **判据**：**两条回源路径感知不到对方，就不叫两层防护**

**完整回答**（逐字练）
> 「删掉冗余 key 之后我才发现，两条读路径上各自有一套锁在保护同一份数据 —— 它们是**并联**的，彼此看不见，防护根本不叠加：SETNX 的持锁者不知道还有 P 个 singleflight leader 正在查同一个视频。
> 所以我收敛了：把回源收进一个共享的 singleflight Group。判据是 —— **两条回源路径感知不到对方，就不叫两层防护。** 收敛之后回源从 P+1 降到 P，而且详情页请求和 Feed 列表请求能真正合并，这是并联状态下做不到的。」

### F6. 热榜漏走实体缓存 ⭐ 适合接在「三级缓存用在哪」之后讲

**Q｜面试官会怎么问**
> 「热榜这个接口缓存怎么做的？」
> 「为什么热榜用实体缓存，关注流却缓存一整页 ID？」← 选型对比题，很能拉开差距

**回答要点**（30 秒版）
- **原来的问题**：`ListByPopularity` 直接 `repo.GetByIDs` 查库，**没走三级缓存** —— 热门视频在最新流里已经缓存成 `video:entity:<id>` 了，热榜还要再查一次库
- **为什么算遗漏**：热榜的结构其实是「ZSET 快照给 ID 顺序 → 按 ID 装配内容」，和最新流**一模一样**，天然该走实体缓存
- **修法**：改用 `f.GetVideoByIDs(ctx, ids)`，删掉手工重排那段（`GetVideoByIDs` 内部 `buildOrderedResult` 已按入参顺序返回并跳过缺失，语义等价）
- **收益**：热门视频在最新流、热榜、关注流 hydrate、详情页四条路径上**共用同一份 `video:entity:<id>`**，命中率叠加
- **为什么热榜不缓存整页**：① 翻页参数五个（`offset`/`asOf`/`latestPopularity`/`latestBefore`/`latestIDBefore`），组合爆炸命中率极低 ② ID 列表已被 ZSET 快照缓存过，再缓存整页是重复 ③ 内容装配是主键批量查询，本来就不贵 ④ 整页会把点赞数/删除状态冻住
- **关注流缓存的是「ID 页 + 游标」**，不是渲染结果 —— 成员因人而异，内容仍是全站共享的

**完整回答**
> 「热榜原来是漏的 —— 它直接查库，可热门视频在最新流里早就缓存成 `video:entity:<id>` 了，等于同一个视频缓存了一份又查了一次库。它的结构其实是『ZSET 快照给 ID 顺序、内容另外装配』，和最新流完全一样，所以直接换成走实体三级缓存就行。
> 至于为什么不用整页缓存：热榜翻页参数有五个，组合爆炸命中率极低；而且 ID 列表已经被快照缓存过了，再缓存整页是重复。关注流缓存的是**成员 ID 页 + 游标**，不是渲染结果 —— 它的成员查询贵且因人而异，但视频内容本身仍是全站共享的，所以内容也走实体缓存。**判据是『什么是全局共享的、什么是因人而异的』。**」

> 💡 **这题的价值**：它考的不是「你会不会背三级缓存」，而是「你能不能根据接口形态判断该用哪种缓存粒度」。能答出「关注流只缓存成员 ID、内容仍然共享实体」，说明是真理解了，不是背的。

### F7. 热度更新有两份实现，修了一处漏了另一处 ⭐ 讲的是「修复要顺着调用链查副本」

**Q｜面试官会怎么问**

**回答要点**（30 秒版）

- **后果**：我在第一份里把共用的 context 拆开了，但第二份还留着 `50ms` 同时给 `ZincrBy` 和 `Expire` —— **以为修完了，其实只修了一半**

- **修法**：内联块改为直接调用 `UpdatePopularityCache`（`video_service.go:246`），重复实现删掉（顺带移除随之悬空的 `strconv` import）

**完整回答**

### F8. Redis 宕机时没有任何雪崩防护 ⭐⭐ 适合接在「缓存自愈」之后讲

**Q｜面试官会怎么问**
> 「Redis 挂了，所有请求都打到 MySQL，你怎么避免数据库雪崩？」
> 「加 TTL 随机抖动是不是就行了？」← 陷阱题，**抖动对这种雪崩无效**

**回答要点**（30 秒版）
- **先拆两个成因**：(a) 大量 key **同时过期** → TTL 抖动有效；(b) 缓存层**整体不可用** → **抖动完全无效**，得靠熔断/限流
- **原来的问题**：Redis 整体挂掉时，`GetVideoByIDs` 走全量降级、`ListByFollowing` 直接兜底查库（SETNX 此时已失效）；singleflight 只能把 N 收敛到 **P（Pod 数）**，压力毫无衰减地压到 MySQL
- **修法**：补**两道闸门** —— 驱动层 `sqlDB.SetMaxOpenConns`（原来 GORM 默认**无上限**，会一路建连接打满 MySQL 的 `max_connections`，让**所有**查询一起失败）；应用层统一 `dbguard` 回源并发闸门，容量自动取连接池一半（默认 32），**非阻塞**获取，拿不到直接 503
- **覆盖面**：Feed 的每个 DB 入口都过 `dbguard`（`GetVideoByIDs`、最新流冷尾/重建、热榜兜底、关注流 JOIN、`ListTags`、`ListByTag`、liked 查询）+ 详情页 `GetDetail`
- **为什么不排队**：排队只是把堆积从数据库搬到应用内存，压力最终还是会落到库上
- **为什么回 503 不是 500**：包装 `apierror.ErrServiceOverloaded` → `ClassifyHTTPStatus` 映射 503。这是**主动限流降级**不是服务故障，客户端收到 503 才知道该退避重试
- **hydrate 失败不再静默丢条**：一页 20 条里 1 条被闸门拒绝，整页聚合报错（503/500），不返回「19 条 + 200」的短页 —— 短页会被客户端读成「到底了」，热榜还会按 member 数推进 offset、永久跳过缺失项
- **还差什么**：熔断、全局限流、指标、Redis 高可用（哨兵/集群）还没做；`dbguard` 是**进程级**的，P 个 Pod 的总回源上限是 P×32

**完整回答**
> 「先说 TTL 随机抖动：对这种雪崩完全无效。它防的是『大量 key 同时过期』，而这里是『缓存层整体不可用』—— Redis 已经不响应了，key 过没过期根本不重要。
> Redis 全挂时我们是全量降级，这时候 singleflight 只能把 N 个请求收敛到 Pod 数，压力还是会压到库上。我补了两道闸门：驱动层给连接池设上限（原来 GORM 默认无上限，会一路建连接把 MySQL 的 `max_connections` 打满，那会让**所有**查询一起失败，连本来能成功的也跟着挂）；应用层统一 `dbguard`，容量自动取连接池的一半，拿不到配额就直接放弃这次回源，**不排队**，因为排队只是把堆积从数据库搬到应用内存。
> 降级表现统一是 503，不再返回短页：一页里只要有一条回源失败，整页就报错。因为『少几条但 200』会被客户端当成到底了，热榜还会据此推进 offset，把缺失内容永久跳过。
> 还差的是熔断、全局限流和指标，而且闸门是进程级的 —— 我有意识地没做：没有真实流量校准不了阈值，**宁可写进生产化清单，也不硬做一个参数拍脑袋的实现**（详见三级缓存文档 §8.4）。」

> 💡 **这题的价值**：绝大多数候选人只会答「加 TTL 随机抖动」。能**区分两种雪崩成因**并指出抖动对其中一种无效，再给出限流的落地方式和 503 的语义，是明显的高一档。
> 顺带能接住追问：**singleflight 为什么管不了跨实例** —— 因为它的状态是进程内的 map，不同 Pod 内存完全隔离，所以只能 N→P；而实体缓存**故意**不用 SETNX，正是因为 Redis 宕机时 singleflight 是唯一还活着的防线。

### F9. 缓存穿透：不存在的 ID 每次都打 MySQL ⭐⭐ 必问题

**Q｜面试官会怎么问**
> 「你怎么防缓存穿透？」
> 「加布隆过滤器了吗？」← 陷阱题

**回答要点**（30 秒版）
- **现象（修复前）**：`len(videoList)==0` 直接 return，**没有缓存「不存在」这个事实**；详情页 `GetDetail` 拿到 `gorm.ErrRecordNotFound` 也一样 → 同一个不存在的 ID **每次都查库**
- **为什么容易被忽略**：自测时你总是拿真实视频测，不存在的 ID 几乎不会出现；但 videoID 是自增 uint，**可以轻易枚举**
- **修复**：空值占位 —— 写哨兵 `__null__`，TTL **60s**；L2 在 `json.Unmarshal` **之前**识别哨兵 → 跳过回源。**两条读路径都接上**（共用同一个 key，只改一边等于没改）：Feed 走 `ScheduleEntityWrite` 有界异步写，详情页在 `ErrRecordNotFound` 分支同步写
- **坑 1**：哨兵**不能**用 JSON 的 `"null"` —— `json.Unmarshal([]byte("null"), &v)` **不报错**，只会给你留一个 `ID=0` 的零值实体
- **坑 2**：**只写不识别等于没做** —— 哨兵是非法 JSON，不先识别会 `Unmarshal` 失败 → 掉进 `missedL2` → 照样查库
- **为什么不用布隆过滤器**：新发布的视频没同步进过滤器 → **被误判成不存在、直接 404**（功能错误，不是性能问题，且演示时极难发现）；再者它不支持删除、多实例要各自同步、误判率还要调参

**完整回答**
> 「原来查不到什么都不记，同一个不存在的 ID 每次都打一次库 —— 这是穿透。我用空值占位：查不到就写一个 60 秒的哨兵，L2 读到哨兵直接跳过回源。
> 没用布隆过滤器，因为它有个致命问题：**新发布的视频没同步进过滤器，会被误判成不存在、直接 404** —— 这是功能错误不是性能问题，而且演示时极难发现。再加上它不支持删除、多实例要各自同步、误判率还要调参，这个量级下不划算。
> 还有个坑：哨兵不能用 JSON 的 `null`，因为 `json.Unmarshal("null", &v)` 不报错、会给你留一个零值实体出来。我取的 `__null__`，并且在解析前显式识别 —— **只写不识别等于没做**，哨兵是非法 JSON，不识别就会退化成普通 miss。」

> 💡 **这题的价值**：绝大多数人只会背「布隆过滤器防穿透」。能说出**具体场景下为什么不用它**（新发布视频会被误判 404），再讲清哨兵为什么不能是 JSON 的 `null`，说明是真写过、不是背的。

### F10. 关注流整页缓存把动态字段冻了 24 小时 → 改成只存 ID ⭐⭐ 主推的「结构性问题」故事

**Q｜面试官会怎么问**
> 「列表缓存你存了什么？存整页结果有什么问题？」
> 「作者改了标题 / 删了视频，别人的关注流什么时候能更新？」

**回答要点**（30 秒版）
- **现象（修复前）**：关注流把 `[]FeedVideoItem` 整页缓存 24h —— 标题、封面、`LikesCount`、`IsLiked` 全冻在里面，只有关注/取关会失效
- **后果**：作者改标题/删视频，别人的关注流**脏到 24h**；点赞数不更新；`IsLiked` 甚至是这个用户上一次看到的状态
- **为什么不能「补失效」**：视频一变就 `DelByPattern` 扫所有用户的关注流，失效粒度是**全站**，写放大和用户数成正比
- **修法**：列表缓存改成 `CachedFollowingPage{VideoIDs, HasMore, NextTime, NextIDBefore}`，命中后仍走 `GetVideoByIDs` 重新装配内容
- **收益**：视频改名/点赞/删除只失效**单个实体**；列表只在关注/取关时失效
- **代价（诚实说）**：每页多一次实体 MGET + liked 查询；列表**成员**仍有回填竞态（见下文 B5）
- **原则**：**把「因人而异的成员关系」和「全站共享的内容」分开缓存**

**完整回答**
> 「原来我把关注流的整页渲染结果直接缓存 24 小时。问题是标题、点赞数、删除状态、甚至 is_liked 都被冻住了 —— 作者改了标题，别人的关注流要等一天才更新；更糟的是 is_liked 是『这个用户上一次看到时的状态』。
> 想靠补失效解决也不行：视频一变就扫掉所有用户的关注流，失效粒度是全站，写放大会和用户数成正比。所以我把结构改了：列表只存 ID 和游标，内容每次命中后重新走实体缓存装配。这样视频变更只失效单个 `video:entity:<id>`，精确得多。代价是每页多一次 MGET，这个我认。」

### F11. 删除缓存后旧值迟到回填 → 版本号 CAS ⭐⭐ 缓存一致性必问

**Q｜面试官会怎么问**
> 「先删缓存还是先更新数据库？」
> 「删除缓存之后，一个读请求把旧值写回来怎么办？」

**回答要点**（30 秒版）
- **竞态**：读请求 A 查库拿到旧值 → 写请求更新库并 `DEL` 缓存 → A 把**旧值**写回缓存 → 旧数据一直留到下次失效
- **常见但不够好的解法**：延迟双删（靠 sleep 赌时序）、先更新库再删缓存（仍有窗口）
- **本项目解法**：每个视频一个版本号 `video:entity:ver:<id>`
  - 失效：Lua 原子执行「`INCR` 版本 + `PEXPIRE` + `DEL` 实体」
  - 读路径：**查库前**批量 `MGET` 版本号；回写时 Lua 比较，版本变了就放弃
  - 版本读不到（Redis 故障）：本次只查库、不回写，因为比较基准不可信
- **为什么版本 TTL 是 25h**：必须明显长于实体 1h。版本号比实体先过期，一次迟到的旧回写就会重新通过校验
- **原则**：**异步回写必须可判别「我读到的还是不是当前版本」**

**完整回答**
> 「单纯删缓存有个经典竞态：读请求在删除之前就查了库，拿到旧值，删除之后它才把旧值写回去 —— 旧数据又占住缓存了。延迟双删是靠 sleep 赌时序，我不想那么做。
> 我给每个视频加了版本号：失效的时候原子地把版本 +1 再删实体；读请求在查库之前记下版本，回写时用 Lua 比较，版本变了就丢弃这次回写。这样迟到的旧值永远写不进去。版本号 TTL 我设了 25 小时，必须比实体 1 小时长 —— 否则版本先过期，旧回写又能通过校验。」

### F12. 改名只改 `accounts`，历史视频永久显示旧名字 ⭐ 细节题

**Q｜面试官会怎么问**
> 「用户改名之后，历史内容上的作者名怎么更新？」
> 「你们有没有做反范式冗余？怎么保证一致？」

**回答要点**（30 秒版）
- **背景**：Feed 装配直接读 `videos.username`（反范式冗余），避免每次都 join `accounts`
- **现象（修复前）**：改名只 `UPDATE accounts` → 用户主页是新名字，但历史视频卡片**永久显示旧名字**，只有重新发布才恢复
- **修法**：一个事务里更新 `accounts.username` + token + `videos.username WHERE author_id`，并 `Pluck` 出受影响视频 ID；**提交后**逐个 `videocache.Invalidate`
- **为什么失效放提交后**：事务回滚却删了缓存只会多一次 miss；事务内删、未提交时读请求会把未提交旧值填回去
- **残留窗口**：其他实例的 L1 本地缓存最坏 5 秒（L1 无跨实例失效的既定代价）

**完整回答**
> 「Feed 为了免 join 在 videos 表冗余了 username。只改 accounts 会出现一个很隐蔽的问题：用户主页是新名字，但他所有历史视频的卡片永远显示旧名字，只有重新发布才恢复。
> 修法是一个事务里同时更新 accounts 和 videos.username，并返回受影响的视频 ID；事务提交后再逐个失效实体缓存。失效不能放在事务里——事务没提交时读请求会把未提交的旧值重新填进缓存。剩下的窗口是其他实例的 L1，最坏 5 秒，这是本地缓存没有跨实例失效的既定代价。」

### A 级：真 bug（当前无未修复项）

#### ~~A1. 热榜 `ListByPopularity` 的 `opCtx` 被 4 步共用~~ → ✅ 已修复（2026-10-27）

**Q｜面试官会怎么问**
> 「还有别的地方犯同样的错吗？」← 讲完 F4 后**极大概率**被这样追问
> 「热榜这块你的超时是怎么设计的？」

**回答要点**（30 秒版）
- **原问题**：一个 80ms 的 `opCtx` 串起 `Exists` + `ZUnionStore`（合并 60 个分钟桶，最贵）+ `Expire` + `ZRevRange`
- **本质**：F4 的同卵兄弟，而且中间那步是全链路最贵的 Redis 操作
- **修法**：① `ZUnionStore` 用专用 `hotMergeTimeout = 500ms`，基于 `Background()`（快照是共享结果，不能跟着某个请求取消）；② 读路径 `ZRevRange` 单独 50ms；③ `hotKeyExists` 每次独立 50ms；④ **快照改为后台预生成**（`StartHotSnapshotBuilder`），读路径只剩一次 `EXISTS` + 一次 `ZREVRANGE`，on-demand 合并只作兜底
- **原则**：**带 timeout 的 context 不能跨多个 IO 步骤复用**；贵操作必须单独给预算

**完整回答**
> 「有，热榜那条路径上原来也有同样的问题，而且更严重 —— 那个 context 上串了四个操作，中间那个 `ZUnionStore` 要合并 60 个分钟桶，是全链路最贵的一步。
> 我后来把它彻底拆了：`ZUnionStore` 用独立的 500 毫秒预算，读路径的 `ZRevRange` 自己 50 毫秒，`EXISTS` 也独立；再进一步把快照生成搬到后台定时预生成，读路径只剩一次 `EXISTS` 和一次 `ZREVRANGE`，按需合并只作为兜底。这样既修了 context 复用，也把最贵的阻塞命令从请求路径上拿走了。」

> 💡 **策略**：讲完 F4 之后主动说「同类问题我在热榜也找到了，并且已经修掉」，比被问出来更好。

### B 级：设计缺口 / 架构债

#### B2. singleflight 用 `Do` 不用 `DoChan`

**Q｜面试官会怎么问**
> 「singleflight 有什么坑？」
> 「leader 卡住了会怎么样？」

**回答要点**（30 秒版）
- **位置**：`feed/service.go` 的 `requestGroup.Do` 4 处（`sf:fallback` / `sf:cold` / `sf:stitch` / `sf:hot:merge`）+ 共享的 `EntityLoadGroup.Do`
- **现象**：`Group.Do` **不接受 context**，无法超时、无法响应取消
- **后果**：leader 那次 DB 查询卡住 → **所有 follower 永久阻塞** → goroutine 堆积直到打满
- **这正是 singleflight 相对 SETNX 的真实倒退**：SETNX 有 100ms 轮询上界，`Do` 没有上界
- **修法**：换 `DoChan` + `select { <-ctx.Done(); <-time.After(...) }` + 超时后自己兜底查库

**完整回答**
> 「有坑。我用的 `Do` 不接受 context，所以 leader 一旦卡住，所有等待者会永久阻塞。对比分布式锁那边 —— 它有 100 毫秒的轮询上界，反而更安全。正确写法是用 `DoChan` 配合 select，给一个超时兜底查库。」

#### ~~B3. Redis 整体挂掉无熔断 / 限流兜底~~ → ✅ 已补闸门，仍未做熔断

**Q｜面试官会怎么问**
> 「Redis 挂了你的 DB 扛得住吗？」

**回答要点**（30 秒版）
- **现状**：Redis 不可用时整批沉到 MySQL，但回源统一过 `dbguard`（容量 = 连接池一半，默认 32，**非阻塞**），驱动层 `MaxOpenConns` 兜底；过载返回 503，不再静默短页
- **覆盖面**：Feed 所有 DB 入口 + `GetDetail` + liked 查询
- **仍然没有**：熔断、全局限流、指标；`dbguard` 是进程级，P 个 Pod 的总上限是 P×32
- **定性**：这是「先保住数据库」的最小闭环，不是完整的生产级保护
- **如果要继续改**：接 `sony/gobreaker`，用压测数据定阈值；网关层做全局限流；先补 `/metrics` 的闸门拒绝计数

**完整回答**
> 「Redis 挂掉时我们不返回错误，而是整批降级到 MySQL。现在降级态不是裸奔了：所有回源都过 `dbguard`，容量自动取连接池的一半，拿不到配额直接 503；连接池本身也有上限，不会无限建连接把 MySQL 打满。
> 但我不把它说成完整方案：熔断、全局限流、指标都还没有，闸门也是进程级的。这是『先保住数据库』的最小闭环，剩下的写进了生产化清单。」

#### B5. 关注流列表成员回填竞态 & `IsLiked` 静默降级

**Q｜面试官会怎么问**
> 「关注流缓存改成只存 ID 之后，一致性还有问题吗？」
> 「为什么只有部分接口在失败时返回 503？」

**回答要点**（30 秒版）
- **成员竞态**：取关/关注触发的 `DelByPattern` 如果撞上一个已经在查库的请求，后者随后 `setCached` 会把旧 ID 页写回 → 成员集合多/少一个，直到 TTL 到期。内容会重新装配，所以是「成员短暂过期」而不是「整页脏」
- **修法方向**：列表回写也加版本 CAS（与实体同一套），或把成员变更做成可比较的 epoch
- **`IsLiked` 降级**：`buildFeedVideos` 的 liked 查询在闸门满/查询失败时，日志后把所有 `is_liked` 置 false —— 用户会看到点赞状态丢了
- **为什么保留**：`is_liked` 是辅助字段，不该为了它再给已过载的库加压；点赞写入有唯一索引兜底
- **一致性缺口**：`GetVideoByIDs` 已经做到「一条失败整页报错」，但 liked 查询仍静默降级，两者语义不统一

**完整回答**
> 「改成只存 ID 之后，内容不会冻住了，但**成员**还有一个回填竞态：取关触发的 pattern 删除，如果撞上一个已经在查库的请求，它随后把旧 ID 页写回去，成员就会短暂过期到 TTL。这个我暂时接受，因为内容每次都会重新装配；要修的话，列表回写也得加一套版本号。
> 另一个不一致是 `is_liked`：hydrate 失败已经会整页报错，但 liked 查询失败还是静默置 false。这是有意的——辅助字段不值得再压库，不过我会在响应里加 degraded 标记，避免客户端误读。」

### C 级：风格 / 不一致

#### C1. L1 默认 TTL 3s，实际写入却是 5s

**Q｜面试官会怎么问**

**完整回答**
> 「实际是 5 秒。构造函数的两个参数分别是默认 TTL 和后台清理间隔，5 秒是清理间隔不是 TTL；真正决定 TTL 的是写入时显式传的参数，两处都传了 5 秒。所以那个 3 秒的默认值没被用上 —— 这是代码里的一个不一致，不影响运行，但读的时候容易误导。」

#### C2. singleflight 的 key 被加了 Redis 前缀

**Q｜面试官会怎么问**
> 「你这几个 singleflight 的 key 是怎么定的？」

**回答要点**（30 秒版）
- **位置**：`feed/service.go` 的 `requestGroup.Do` 4 处（`sf:fallback` / `sf:cold` / `sf:stitch` / `sf:hot:merge`，第 328 / 393 / 449 / 881 行）
- **现象**：用 `f.rediscache.Key("sf:xxx")` 构造，会拼出 `v1:sf:xxx`
- **问题**：这个 key **只活在进程内存的 map 里，永远不会进 Redis**，给它加 Redis 版本前缀是概念混淆
- **对比**：视频实体那条已经修好了 —— 改用 `video.EntitySingleflightKey()`（`fmt.Sprintf`，不加前缀）
- **原则**：**只有真正要写入 Redis 的 key 才需要版本前缀**

**完整回答**
> 「这四条用的是 Redis 的 key 构造函数，会拼上版本前缀，但 singleflight 的 key 只活在进程内存里、永远不写 Redis，给它们加前缀是概念混淆。视频实体那条我统一的时候改成普通字符串拼接了。原则很简单：**只有真正要落 Redis 的 key 才需要版本前缀。**」

#### C3. 锁 key 前缀错位

**Q｜面试官会怎么问**
> 「你的锁 key 是怎么拼的？」

**回答要点**（30 秒版）
- **位置**：`feed/service.go` 第 736 行（`ListByFollowing`）
- **现象**：`lockKey := "lock:" + cacheKey`，而 `cacheKey` 已经是 `v1:feed:listByFollowing:v2:...`
- **结果**：拼出来是 `lock:v1:feed:listByFollowing:v2:...` —— **前缀跑到中间去了**
- **影响**：功能完全正常（只要全局一致）
- **问题**：一旦以后要按 prefix 做 SCAN 清理或监控，这个 key 就扫不到
- **对比**：`GetDetail` 那条已经随 F5 的 SETNX 删除一起消失了

**完整回答**
> 「这条我不太满意：`lockKey` 是拿已经带完整前缀的 cacheKey 再拼一个 `lock:`，结果前缀跑到中间去了。功能没影响，但以后如果要按前缀做批量清理或者加监控，这个 key 就扫不到。这个也是一次性杂活，暂时搁着。」
