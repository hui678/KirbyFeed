## 0. 先回答一个问题：为什么热榜不能只读一个「累计热度 key」

热榜要回答的是「**最近这段时间**什么最火」。先看三种做法：

| 做法 | 问题 |
|---|---|
| 一个 `hot:video:total` ZSET，`ZINCRBY` 累加 | 存的是**历史累计值**：3 个月前爆过的视频永远压在新视频头上（马太效应），且**无法自然淘汰**、无法表达时间窗口 |
| 定时任务跑批算热度分，写进一个 ZSET | 榜单延迟 = 跑批周期（分钟~小时级），还要额外维护调度与补偿 |
| **分钟分桶 + 读时合并** | ✅ 本项目采用 |

**核心洞察**：热度是**带时间维度的聚合量**，所以必须把时间维度编码进 key。一旦按分钟切开：

- 「最近一小时」= 取最近 60 个桶 `SUM`——窗口语义**天然成立**；
- 窗口随时间前移，滑出窗口的旧桶不再参与合并，由 TTL 回收——**不需要任何清理任务**；
- 时间已经过去的桶**不再被写入**（封桶）——这是稳定分页能成立的地基（见 §5）。

## 3. 写侧：分钟桶

```go
// backend/internal/video/popularity_cache.go:60-94（节选）
func UpdatePopularityCache(ctx context.Context, cache *rediscache.Client, id uint, change int64, eventID string) error {
	if cache == nil || id == 0 || change == 0 {
		return nil
	}
	InvalidateVideoEntity(ctx, cache, id)

	now := time.Now().UTC().Truncate(time.Minute)
	windowKey := cache.Key("hot:video:1m:%s", now.Format("200601021504"))
	member := strconv.FormatUint(uint64(id), 10)

	// 有 eventID 时走 Lua：SET dedup NX EX + ZINCRBY + EXPIRE 原子执行
	if eventID != "" {
		incrCtx, incrCancel := context.WithTimeout(ctx, singleRedisOpTimeout)
		defer incrCancel()
		_, err := cache.Eval(incrCtx, hotIncrOnceScript,
			[]string{cache.Key("hot:dedup:%s", eventID), windowKey},
			member, change,
			int64(hotDedupTTL/time.Second), int64(hotWindowTTL/time.Second))
		return err
	}
	// 无 eventID 的历史调用退化：直接 ZINCRBY + EXPIRE（不保证幂等）
}
```

### 3.1 为什么是 `ZINCRBY` 而不是 `ZADD`

这是**全项目最值得记住的一组对照**，面试官很爱问：

| ZSET | score 存什么 | 写命令 | 幂等吗 |
|---|---|---|---|
| 时间线 `feed:global_timeline` | `create_time`（**不可变**） | `ZADD` | ✅ 重复写结果相同 |
| 热榜 `hot:video:1m:<分钟>` | 窗口内热度增量（**累加**） | `ZINCRBY` | ❌ 天生不幂等 → **需 Lua 原子去重**（§3.2.1） |

> 「为什么用 `create_time`？因为它不可变——重复 `ZADD` 不会让 score 漂移。
> 热榜的 `popularity` 是累加的，所以只能 `ZINCRBY`，它天生不幂等，需要另一套保护
> —— 也就是 §3.2.1 的 `event_id` + Lua 原子去重。」

### 3.2 三个容易被忽略的细节

1. **`Truncate(time.Minute)` + `UTC`**：key 精确到分钟，多实例、多时区写入落到同一个桶上，不会因为机器时钟格式差异产生两个桶。
2. **`ZINCRBY` 是 O(log N) 且无读改写**：不需要「取出来 → 加一 → 写回去」，天然无并发竞争，不需要锁。
3. **TTL 2h vs 窗口 60min**：窗口是 60 个桶，但 `as_of` 最多回溯 59 分钟，最早一份快照的最旧输入桶是 `latest-118min`（相对当前时刻约 119 分钟前）——2h 刚好覆盖，只留一两分钟余量，不是「2 倍冗余」。真正的淘汰靠「窗口不取它」，TTL 只是防止 key 无限堆积。

### 3.2.1 ⭐ 消费端「先处理再 ACK、崩溃重投」怎么避免热度重复加？

这是被追问频率最高的一题，因为它同时考了 MQ 语义和 Redis 用法。

**先说 MySQL 侧为什么天然幂等。** 热度的 MySQL 落点是 `videos.popularity`，
它由落库 Worker 在**业务行的事务里**累加：

```36:51:backend/internal/video/like_repo.go
		res := tx.Clauses(clause.Insert{Modifier: "IGNORE"}).Create(&Like{...})
		if res.Error != nil {
			return res.Error
		}
		if res.RowsAffected == 0 {
			return nil                      // ← 重复投递：直接返回，计数绝不加第二次
		}
		if err := bumpVideoColumn(tx, videoID, "likes_count", 1); err != nil {
```

**幂等键不是计数本身，而是业务行的唯一索引** `idx_like_video_account`：
同一条点赞事件重投两次，第二次 `INSERT IGNORE` 的 `RowsAffected=0`，函数在
「加计数之前就返回了」。计数只是业务行的副作用，**放在同一个事务、且在幂等判断之后**，
就被唯一索引顺带保护住了。

> 这条原则值得单独记：**不要用「计数」做幂等，用「产生这个计数的业务行」做幂等。**
> 计数是 Number，看不出是不是加过；业务行有唯一索引，天然能回答「有没有发生过」。

**再说 Redis 侧为什么必须额外处理。** `ZINCRBY` 是累加，重投一次就多加一次：

```
消费端：ZINCRBY +1 → 还没 ACK → 连接断 → broker 重投 → ZINCRBY +1 → 热榜 +2
而 MySQL 侧被唯一索引挡住只 +1 —— 两个存储直接对不上。
```

修复方式是用 **Lua 把「去重判断」和「累加」合成一个原子操作**：

```lua
-- KEYS[1]=幂等标记  KEYS[2]=分钟桶
if redis.call('SET', KEYS[1], '1', 'NX', 'EX', ARGV[3]) == false then
  return 0                                    -- 这个事件处理过，跳过
end
redis.call('ZINCRBY', KEYS[2], ARGV[2], ARGV[1])
redis.call('EXPIRE', KEYS[2], ARGV[4])
return 1
```

**为什么不能用两条命令（`SETNX` 再 `ZINCRBY`）**——这是本题的题眼：
两条命令之间进程崩溃，会留下「已标记为处理过、但累加没执行」的状态，
后续所有重试都被去重挡住，**这次热度永久丢失**。Redis 执行 Lua 是单线程原子的，
要么三步全做、要么全不做，不存在这个中间态。

> 对照上一节：时间线靠「`ZADD` 覆盖语义」把幂等下沉到存储操作，热榜靠
> 「Lua 原子去重」。**什么时候用哪种？**
> 副作用本身幂等（覆盖写、删除）→ 下沉，不加额外状态；
> 副作用是累加 → 必须引入幂等键，且**幂等判断与副作用必须原子**。

**幂等键从哪来？必须是「发布前生成、两条路径共用」。**
`PopularityMQ.Update` 改成**接收**外部 `eventID`，而不是内部生成：

```go
popEventID, _ := rabbitmq.NewEventID()
if err := s.popularityMQ.Update(ctx, like.VideoID, 1, popEventID); err == nil {
	redisEnqueued = true
}
...
if !redisEnqueued {
	UpdatePopularityCache(ctx, s.cache, like.VideoID, 1, popEventID)   // 同一个 ID
}
```

因为存在「publish 成功但 confirm 超时」这个无法消除的窗口：消息其实已经在队列里，
消费端迟早会处理；而服务层以为发布失败，又走降级直写一次。**两条路径共用同一个
`event_id`，Lua 去重才能保证只生效一次。** 如果 `event_id` 在 `Publish` 里才生成，
降级路径根本拿不到它，这个洞就补不上。

### 3.3 ⚠️ 纠偏：分钟桶**不是**「把写热点分散到 60 个 key」

这是一个**说出来就会被面试官抓住**的错误表述。看 key 的生成：同一时刻的**所有**写入都落在 `now.Truncate(time.Minute)` 这**一个**桶上。60 个 key 是**读侧**的窗口，不是写侧分片。

分钟分桶的真实价值只有三条（见 §0）：窗口语义成立、旧桶自动退出、封桶后不可变。

> 如果真要分散写热点，做法是**按 videoID 哈希分片**（`hot:video:1m:<分钟>:<shard>`），读侧合并时每个桶要拼 N 倍 key——那是另一种设计，本项目没做。别把两件事混为一谈。

### 3.4 封桶：不可变性从哪来

写入永远用「当前分钟」做 key。时间越过 T 分钟进入 T+1，写侧就转向 `...:T+1`，**`...:T` 从此不再被写入，成为一个只读的定稿数据块**。

这个性质是整个稳定分页方案的地基（§5.3）。

## 4. 读侧：`ZUNIONSTORE` 生成快照

```go
// backend/internal/feed/service.go:787-825（buildHotSnapshot）
keys := f.hotWindowKeys(asOf)                 // [asOf-59min, asOf] 共 60 个桶
dest := f.hotSnapshotKey(asOf)                // hot:video:merge:1m:<as_of>

unionCtx, cancel := context.WithTimeout(context.Background(), hotMergeTimeout) // 500ms
if err := f.rediscache.ZUnionStore(unionCtx, dest, keys, "SUM"); err != nil {
    cancel()
    return err
}
cancel()

// 裁到 Top-5000，把结果集 M 和快照内存压成常数
if err := f.rediscache.ZRemRangeByRank(trimCtx, dest, 0, -(hotSnapshotCap + 1)); err != nil {
    return err
}
if card, err := f.rediscache.ZCard(cardCtx, dest); err != nil {
    return err
}
if card == 0 {
    // 空窗口也要留标记，否则 EXISTS 永远 miss、每请求重合并
    if err := f.rediscache.SetBytes(emptyCtx, f.hotSnapshotEmptyKey(asOf), []byte("1"), hotSnapshotTTL); err != nil {
        return err
    }
} else {
    if err := f.rediscache.Expire(expireCtx, dest, hotSnapshotTTL); err != nil {
        return err
    }
}

// 读：ZREVRANGE 按 rank 取页，O(log N + M)
members, err := f.rediscache.ZRevRange(readCtx, dest, int64(offset), int64(offset+limit-1))
```

> `asOf` 由 `hotLatestSealedMinute(now)` 给出：`now.Truncate(minute) - 1min`。窗口里没有任何一个桶还在被写。

### 4.1 快照 key 的设计

`dest` 用 `as_of` 命名，含义是「**截至 as_of 这一刻的榜单定格**」。因此：

- 同一个 `as_of` 的所有翻页请求，读的是**同一份**快照；
- 不同分钟的 `as_of` 互不干扰，快照 key 天然按分钟分散，**不存在大批 key 同时失效**的雪崩风险（见 `start-learn/缓存体系.md`）。

### 4.2 成本与摊薄（面试必问）

`ZUNIONSTORE` 的复杂度是 **O(N) + O(M·log M)**（N = 所有输入桶元素总数，M = 结果集大小），而且是**阻塞命令**，跑在 Redis 单线程上。

摊薄手段就是 `EXISTS` + 2 分钟 TTL：

| | 聚合次数 |
|---|---|
| 无快照 | 每个请求 1 次（= QPS 次/秒） |
| 有快照 | 每个 `as_of` 1 次 ≈ **1 次/分钟** |

**这就是简历里那句「聚合从每请求一次摊薄为每分钟一次」的出处**，是可以从代码直接推导的硬指标，不需要压测数据。

### 4.3 为什么这里敢用 `offset`（而不是游标）

`ZREVRANGE` 按 **rank** 取元素，复杂度是 **O(log N + M)**，不是 `OFFSET` 那种「扫过前 k 行再丢弃」。所以深分页不会劣化——第 1 页和第 100 页代价一样。

> 对比：`ListLatest` 用游标是为了避开 MySQL 的 `OFFSET` 深分页；热榜用 `offset` 是因为 ZSET 的 rank 访问本来就是 O(log N)。两个场景的判据不同，别背混了。

### 4.4 百万视频规模下：为什么这个合并必须搬出读路径

**先看复杂度。** `ZUNIONSTORE dest 60keys AGGREGATE SUM` 的官方复杂度是 **O(N) + O(M·log M)**，其中 N = 所有输入桶的元素总数，M = 结果集大小。

按百万视频粗算（假设每分钟约 5 万个视频产生热度事件）：

| 项 | 量级 |
|---|---|
| N（60 个桶的输入总量） | 60 × 5 万 ≈ **300 万** |
| M（去重后的结果集） | 最多 **100 万** |
| O(M·log M) | 100 万 × 20 ≈ **2000 万次比较** |

Redis 单线程处理命令，**这一步会阻塞同实例上的所有其它命令**，单次耗时通常在 **1~10 秒**量级。

**原实现在这个规模下会同时踩三个坑**：

| # | 问题 | 后果 |
|---|---|---|
| 1 | 合并放在读请求路径上 | 快照过期的瞬间，至少有一个请求被钉住数秒，并阻塞整个 Redis 实例 |
| 2 | `ZUNIONSTORE` 与 `Exists`/`Expire`/`ZRevRange` **共用 80ms 预算**，且错误被 `_ =` 吞掉 | 必然超时 → 快照永远写不进去；而 `ZREVRANGE` 对不存在的 key **返回空且不报错** → 热榜**静默地**整体降级到 MySQL，没人能发现 |
| 3 | 快照没有容量上限 | M 可达百万：内存上百 MB，排序成本无法收敛 |

**已做的三处修改**：

1. **后台预生成（治本）**：`StartHotSnapshotBuilder` 每分钟预生成**最后封桶分钟**的快照（不是当前分钟），读路径只剩 `EXISTS` + `ZREVRANGE`（O(log N + M)）。把 O(N) 阻塞命令彻底移出请求路径。
2. **独立超时 + 不再吞错**：`hotMergeTimeout`（500ms）单独给 `ZUNIONSTORE`；失败时 `log.Printf` 留痕。
3. **快照裁剪到 Top-N**（`hotSnapshotCap = 5000`）：`ZREMRANGEBYRANK dest 0 -(cap+1)` 把 M 压成常数。代价是榜单深度被截断到 Top-5000，对只展示头部的入口可接受。

> 面试话术：「百万视频下这个合并是 O(N)+O(M·log M)，跑在 Redis 单线程上要数秒——它根本不该出现在读请求路径上。我改成后台每分钟预生成，读路径只剩一次 ZREVRANGE；另外把超时预算拆开、错误不再静默吞掉，否则规模一大它会『看起来正常』地整体降级到 MySQL。快照还加了 Top-N 裁剪，把 M 从『一小时活跃视频数』压成常数。」

## 5. 稳定分页：这个模块真正的核心

### 5.1 问题：实时榜上 `offset` 翻页必然出错

热度每秒都在累加。用户翻到第 2 页时，榜单已经变了：

- 某个视频涨到第 1 页的位置 → 第 2 页**重复**出现它；
- 某个视频从第 2 页掉出去 → 它**永远不会被看到**（漏项）。

本质原因：**排序键在翻页期间是可变的**。

### 5.2 解法：把「算榜」和「取页」解耦

两层保障：

**第一层 —— 快照复用。** 翻页期间读的是同一个 `dest` 快照（`Exists` 命中即复用），排序键被冻结。

**第二层 —— `as_of` 锁定窗口集合。** 即使快照 TTL 到期要重建，`as_of` 固定了「哪 60 个桶」，窗口不会漂。

**singleflight 的定位变了（修完封桶语义之后）。**

旧实现 `Exists` 未命中就各自 `ZUNIONSTORE`，而 `as_of` 取当前分钟（桶还在写），并发合并会得到不同结果、后完成的覆盖先完成的——排序键在翻页期间变了，这是**正确性问题**。

现在 `as_of` 只取已封桶分钟，60 个输入桶全部只读，所以并发重复合并是**幂等**的：即使不收敛，最终写进快照的也是同一个结果。`singleflight`（`service.go:852`）因此**主要**是性能保护——避免快照过期瞬间 N 个并发请求各自跑一次 O(N)+O(M·log M) 的阻塞命令，把 Redis 实例钉住；同时它仍保证「同一 `as_of` 只合并一次、翻页期间所有请求读同一份快照」这一正确性收益（见 `service.go:832-835` 注释）。

> 面试时把这一点讲清楚会加分：**「singleflight 在封桶修对后不再是正确性地基（那由『窗口里没有可写桶』保证），但它仍兜住『同一 as_of 读同一份快照』的翻页一致性，并挡住过期瞬间的重复合并。」** 正确性的地基是「窗口里没有可写桶」，不是锁。

### 5.3 ⭐ 封桶论证：为什么过期重建的结果与首份逐位一致

这是本模块**最漂亮、也最容易被讲错**的一段推演，建议背下来。

**旧论证（已废弃）**：`as_of` 取当前分钟，靠「TTL 2min > 1min，过期重建时 `as_of` 桶已封桶」来保证一致。

它有两个问题：

1. 正确性被押在一个可配置数字上——有人把 TTL 改短、缓存提前逐出、手工删 key，重建就会读到还在写的桶；
2. 首份快照本身就只包含当前分钟的**前半段**。即使重建发生在封桶之后，重建结果（整分钟）也**必然与首份不同**——翻页会重复或漏项。

**现在的论证**：`as_of` 只取**最后一个已封桶的分钟**（`hotLatestSealedMinute`，`service.go:62`）。

| 时刻 | 事件 |
|---|---|
| 10:00:59 | 写侧仍写 `...:10:00` |
| 10:01:00 | 写侧转向 `...:10:01`；`...:10:00` **封桶定稿** |
| 10:01:xx | 后台/读路径生成 `as_of = 10:00`，窗口是 `[09:01, 10:00]`，60 个桶全部只读 |
| 任意时刻重建 | 同样 60 个只读桶 → 同一个 `ZUNIONSTORE` 输入 → **逐位一致** |

关键：一致性来自**「窗口里没有任何一个可写桶」**，而不是「等 TTL 过期」。重建是同一个纯函数的第二次求值，与 TTL 长短、重建频率、谁触发都无关。

> 代价：当前分钟事件不参与任何快照，要等该分钟结束才可见（刷新粒度约 1 分钟）。这是用「1 分钟新鲜度」换「重建确定一致」。
>
> 如果哪天要支持事件时间（`OccurredAt`），就必须允许回写已封桶——那会直接推翻这段论证，需要 watermark + 迟到补偿 + 重算，而不是改一行 `Truncate`。

## 6. 排序与内容分离：为什么走实体三级缓存

```1082:1092:backend/internal/feed/service.go
		// 热榜的「排序」与「内容」是分离的：ZSET 快照只给出 ID 顺序，
		// 内容按 ID 走实体三级缓存装配 —— 与最新流、详情页共用同一份
		// video:entity:<id>，热门视频在三条路径上只需缓存一份。
		// GetVideoByIDs 已按入参顺序返回并跳过缺失项，等价于原先的手工重排。
		videos, err := f.GetVideoByIDs(ctx, ids)
```

**为什么不用整页缓存**（关注流缓存的是**成员 ID 页 + 游标**，不是渲染结果）：

| 判据 | 热榜 | 关注流 |
|---|---|---|
| 翻页参数个数 | 5 个（`offset`/`asOf`/`latestPopularity`/`latestBefore`/`latestIDBefore`）→ 组合爆炸，命中率极低 | 只有 `limit` + 游标 + 账号，组合少，命中率高 |
| ID 列表从哪来 | ✅ 快照已经缓存了 ID 顺序，再缓存整页是重复 | ❌ 没有索引层，成员查询贵，必须缓存 ID 页 |
| 单次查询成本 | 主键批量查询，便宜 | 子查询 + 排序，昂贵 |
| 因人而异 | 否 | **是** |
| 缓存粒度 | 只缓存内容（实体共享） | 缓存 ID 页 + 游标；**内容仍走实体缓存**，不缓存渲染结果 |

> 一句话：**热榜有索引层（快照 ZSET），所以只缓存内容；关注流没有索引层，必须缓存「哪些视频在这一页」。但两者都不缓存渲染结果** —— 点赞数、`IsLiked`、改名、删除都在装配时重新算，这是动态字段不会被冻住的原因。

`buildFeedVideos` 最后补上 `is_liked` 个性化字段——这也是实体缓存能被三条路径共享的前提：**缓存里不含个性化字段和排名**。

排序 `popularity DESC, create_time DESC, id DESC` 命中 `idx_videos_popularity_time_id`（见 `video_entity.go`），是标准的**复合游标**（keyset pagination），不会随翻页深度劣化。

### 7.1 ⚠️ P0（已修）：降级翻页曾经是坏的——触发条件要说准

> **状态：已修复。** 面试讲法：先说清原缺陷和触发条件，再说改法——这是「发现问题 → 定位 → 修掉」的完整素材，比只讲设计更值钱。

原缺陷是「Redis 不可用时加载更多会重复第一页」，方向对，但**触发条件要讲准**，否则会被追问打穿：

| 情况 | 行为 |
|---|---|
| `f.rediscache == nil`（启动时 Redis 就不通） | 整个 Redis 分支跳过 → 落 MySQL，响应 `degraded=true` |
| `ensureHotSnapshot` 返回 false（EXISTS 失败 / 合并失败） | 落 MySQL，响应 `degraded=true` 并打日志 |
| 快照存在但窗口确实为空 | **返回空列表**，`degraded=false`，不落 MySQL |
| `force_db=true`（前端已处于降级会话） | 直接走 MySQL，不再探测 Redis |

前两种情况才是「重复第一页」的来源——**旧前端只传 `limit/as_of/offset`，从不传 `latest_popularity/latest_before/latest_id_before`**，DB 分支拿不到游标，只能从头再来。现在这个前提已经不成立（见下面改法 1）。

**已实施的改法（三层）**：

1. **前端回传游标**（治本）。服务端两种路径都会返回 `next_latest_popularity / next_latest_before / next_latest_id_before`，前端原来丢了。现在 `HotRankPanel.vue` 存下这三元组，之后**每次翻页都带上**——不只降级态带，因为 Redis 也可能在翻页中途挂掉。

   ```ts
   // frontend/src/components/HotRankPanel.vue:44
   const hasCursor = !reset && state.nextLatestIDBefore > 0 && state.nextLatestBefore !== ''
   ```

   `feed.ts` 里 `latest_before` 与 `latest_id_before` 这对游标必须**同时**出现才写入 body，否则后端 `handler.go:122-126` 会判为「部分提供」直接 400；`latest_popularity` 是独立字段，缺失时只当作 0 带入游标过滤，并不触发 400。

2. **后端兜底**（防止旧客户端）。降级路径新增保护，`offset > 0` 却拿不到游标时返回空页，绝不带着空游标从头查：

   ```go
   // backend/internal/feed/service.go:1095-1100
   if offset > 0 && (latestBefore.IsZero() || latestIDBefore == 0) {
       return ListByPopularityResponse{
           VideoList: []FeedVideoItem{},
           Degraded:  true,
       }, nil
   }
   ```

3. **降级会话钉住排序**（防止混榜）。响应带 `degraded=true`，前端后续请求带 `force_db=true`，服务端直接跳过 Redis 分支。这样 Redis 中途恢复也不会把累计榜和窗口榜拼进同一个会话；只有用户主动刷新（`as_of=0`、`force_db=false`）才开启新会话。

> 面试话术：「降级翻页我原来写坏了——前端没回传 DB 游标，Redis 一挂『加载更多』就重复第一页。修法是三层：前端把服务端返回的复合游标回传（不只降级态带，因为 Redis 可能在翻页中途挂）；后端拿不到游标就返回空而不是从头查；降级后用 `degraded` + `force_db` 把会话钉在 DB 榜上，避免 Redis 恢复时混榜。
> 这里有个判据：**降级态宁可少给数据，也不能给错位的数据**——重复第一页比返回空页更糟，因为它看起来是『正常工作的』。」

### 8.2 Worker 侧：吞错后 Ack（✅ 已修）

改前：

```go
func (w *PopularityWorker) process(ctx context.Context, body []byte) error {
	...
	video.UpdatePopularityCache(ctx, w.cache, evt.VideoID, evt.Change)
	return nil        // ← 永远返回 nil
}
```

两个结论：

1. **`process` 永远返回 `nil`**（`UpdatePopularityCache` 没有返回值，内部 `_ = cache.ZincrBy(...)` 把错误吞了）→ 「指数退避重试 3 次」**是死代码，永远不触发**，消息一律立即 Ack。
2. **Redis 故障期间热度事件静默丢失**，且因为已 Ack 无法重投 → 热榜**不会最终一致**。

**修复**：`UpdatePopularityCache` 改为返回 `error`，Worker 用统一 `Consumer` 骨架
（进程内退避 → TTL 重试队列 → 死信队列告警），并顺带补上幂等（§3.2.1）：

```go
return video.UpdatePopularityCache(ctx, w.cache, evt.VideoID, evt.Change, evt.EventID)
```

> 面试话术（讲「发现 → 修复 → 又发现新洞」的完整链路）：
> 「这块原来有个死角——Worker 吞掉了 Redis 错误仍然 Ack，Redis 故障期间的热度事件
> 全丢，热榜根本谈不上最终一致。我让 `UpdatePopularityCache` 返回 error 并接上
> 统一重试骨架。**但接上重试之后立刻暴露出第二个洞**：`ZINCRBY` 是累加的、不幂等，
> 重试一次热榜就多加一分，而 MySQL 侧的 popularity 有唯一索引保护只加一遍——
> 两边会直接对不上。所以又补了 Lua 原子去重，并把 `event_id` 改成发布前生成、
> 让降级直写和 MQ 消费共用同一个键。」

**残留**：死信队列目前只打日志，还缺按 `event_id` 重投的管理接口。

## 9. 已知问题清单

### A 级（会被追问，建议主动承认）

**A1 ✅已修｜读路径 `ZUNIONSTORE` 没有并发保护、且错误被静默吞掉**

原现象：快照过期的那一瞬，N 个并发请求同时 `Exists` 未命中 → **全部各自跑一次 60 桶合并**，无锁、无 singleflight；`_ = ZUnionStore(...)` 把错误吞掉，规模一大就静默降级（详见 §4.4）。

它比"性能问题"更严重——**在旧的「`as_of` = 当前分钟」语义下**，并发首访写入的两次快照内容不同，会破坏翻页一致性（详见 §5.2）。

已修：`ensureHotSnapshot` 用 singleflight 按 `as_of` 去重 + `StartHotSnapshotBuilder` 后台预生成 + 独立超时预算 + 失败打日志。另外 `as_of` 改成只取已封桶分钟后，并发合并本身已幂等，singleflight 进一步退化为纯成本保护。

**A2 ✅已修｜`as_of` 完全由客户端控制，无校验、无上限**

- 原问题：`reqAsOf` 直接 `time.Unix(reqAsOf, 0)`，任意值都会生成一个独立快照 key + 一次 60 桶合并。低成本变换 `as_of` 就能打满 Redis CPU。
- 现在：`as_of` 必须落在 `[latest-59min, latest]`（`latest` = 最后封桶分钟）。越界时**首页**收敛到最新榜，**翻页**返回 `expired=true`；负数在 `handler.go:99-103` 直接 400。
- 附带修掉：空窗口写 `:empty` 标记（TTL 2min），不会因为「快照为空 → EXISTS 永远 miss」而每请求重合并；空窗口返回空列表，不再静默降级成累计榜。

### 11.2 参考答案要点

**Q1｜为什么不用累计热度 key**

历史累计 → 老视频永久霸榜，无法表达「最近一小时」，无法自然淘汰。热度是带时间维度的聚合量，所以要把时间编码进 key。

**Q3｜读侧合并 60 个桶性能受得了吗**

`ZUNIONSTORE` 是 O(N)+O(M·log M) 的阻塞命令，确实贵。所以用 `as_of` 级快照 + 2 分钟 TTL 摊薄：**从每请求一次降到每分钟一次**；后台预生成 + singleflight 再兜住过期瞬间。`as_of` 只取已封桶分钟后，并发合并本身已幂等，singleflight 进一步保证「同一 `as_of` 只合并一次、翻页期间所有请求读同一份快照」；正确性的地基是封桶，singleflight 额外兜住翻页一致性。

**Q5｜`as_of` 桶还在写，凭什么一致**

现在窗口里没有任何桶还在写：`as_of = 最后封桶的分钟`，窗口 `[as_of-59, as_of]` 全部只读。首份快照与过期重建是同一个纯函数的两次求值，结果逐位一致。singleflight 防的是并发重复计算，不是一致性。

**Q6｜TTL 为什么 2 分钟**

它现在只控制两件事：同一 `as_of` 多久重建一次、榜单最多滞后多久。**它不再承担一致性职责**——封桶语义保证重建必然一致。改成 30 秒只会让重建更频繁、成本更高，不会破坏翻页一致性（这是旧文档的错误结论）。
下界仍是「别让同一个快照撑太久」的工程折中，上界是 Redis 内存与合并频率。

**Q7｜`offset` 不会劣化吗**

ZSET 按 rank 访问是 O(log N + M)，不是 MySQL `OFFSET` 那种扫过前 k 行。所以敢用 `offset`。

**Q10｜热度是实时的吗**

准实时，三层延迟：
1. **写入延迟**：点赞 → MQ → Worker → `ZINCRBY`，常态秒级；
2. **封桶延迟**：写侧只写当前分钟桶，而当前分钟不参与快照。事件最晚要等这一分钟结束（≤60s）才可见；
3. **会话冻结**：一旦开始翻页，同一 `as_of` 的快照在 2 分钟 TTL 内保持不变，这是刻意为之。

所以「榜头的新鲜度」约 1 分钟，「同一会话的冻结」是 2 分钟——别混成一句「2 分钟」。

## 12. 一句话总结（被要求收尾时）

> 「热榜的核心不是『分桶』，而是**把算榜和取页拆开**：分钟桶让『最近一小时』这个窗口语义成立并提供封桶后的不可变性，`as_of` 锁定窗口集合并只取**已封桶的分钟**，快照把排序键冻结 2 分钟，翻页只在同一份快照上按 offset 切片。
> 重建的一致性是**结构性的**，不靠 TTL 这种可配置数字；空窗口、过期会话、Redis 降级都有显式信号（空列表 / `expired` / `degraded` + `force_db`），不再静默换榜。
> 代价我认：窗口新鲜度约 1 分钟，负向事件跨桶失真，Redis 丢数据只能近似重建。」
