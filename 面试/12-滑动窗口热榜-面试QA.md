## 0. 一页速览（面试前 5 分钟只看这一节）

### 0.1 链路图

```
点赞 / 评论 / 删除评论
  ├─ 落库消息 → LikeWorker / CommentWorker → MySQL（唯一索引幂等，videos.popularity 累计值）
  └─ 热度消息 → PopularityWorker
                 └─ Lua：SET dedup NX EX 24h → ZINCRBY hot:video:1m:<yyyyMMddHHmm> → EXPIRE 2h

后台 StartHotSnapshotBuilder（每 1 分钟）
  └─ ensureHotSnapshot(as_of = 最后封桶的分钟 = 上一分钟)
       └─ ZUNIONSTORE 60 个桶 SUM → hot:video:merge:1m:<as_of>
            ├─ ZREMRANGEBYRANK 裁到 Top-5000
            ├─ 空窗口 → 写 hot:video:merge:1m:<as_of>:empty（TTL 2min）
            └─ 非空   → EXPIRE 2min

读：POST /feed/listByPopularity(as_of, offset, limit, force_db)
  ├─ as_of=0 → 最后封桶分钟；as_of 越界 → 首页换新榜 / 翻页返回 expired
  ├─ 快照或空标记 EXISTS 命中即复用；缺失走 singleflight 按 as_of 合并
  ├─ ZREVRANGE(as_of 快照, offset, offset+limit-1) → ID 顺序
  ├─ GetVideoByIDs → 实体三级缓存装配内容（与最新流/详情共用）
  ├─ buildFeedVideos → 补 is_liked
  └─ Redis 失败 → MySQL 累计榜 + degraded=true；force_db 让该会话留在降级态
```

> 关键变化：`as_of` 不再是「当前分钟」，而是**最后一个已经封桶的分钟**。所以 60 个输入桶在快照生成的那一刻全部定稿，重建结果必然与首份一致；代价是当前分钟的新热度要等这一分钟结束才可见（刷新粒度约 1 分钟）。

### 0.2 数字速查

| 常量 | 值 | 位置 | 它决定了什么 |
|---|---|---|---|
| 窗口长度 | 60 个分钟桶 | `backend/internal/feed/service.go:33` | 「最近一小时」的语义；也决定合并成本 N 的量级 |
| `as_of` 可回溯 | 59 分钟（窗口共 60 个桶） | `backend/internal/feed/service.go:48` | 分页会话寿命约 60 分钟；越界翻页返回 `expired` |
| 快照 TTL | 2 分钟 | `backend/internal/feed/service.go:54` | 同一 `as_of` 多久重建一次、同一会话最长冻结多久（榜头新鲜度由 1 分钟封桶决定）；**一致性不再依赖 TTL > 1min** |
| 快照深度 | Top-5000 | `backend/internal/feed/service.go:71` | 把 M（结果集）压成常数，代价是翻不到 5000 名之后 |
| 合并超时 | 500ms | `backend/internal/feed/service.go:77` | 单独给 `ZUNIONSTORE`，不与读命令共享预算 |
| 单 Redis 操作超时 | 50ms | `backend/internal/feed/service.go:28` | `EXISTS`/`EXPIRE`/`ZREVRANGE` 各自独立预算 |
| 分钟桶 TTL | 2 小时 | `backend/internal/video/popularity_cache.go:15` | 覆盖「窗口 60 桶 + `as_of` 回溯 59min」的最旧输入桶；只防 key 堆积，不负责淘汰 |
| 事件去重标记 TTL | 24 小时 | `backend/internal/video/popularity_cache.go:18` | 必须大于「一条消息最长可能重投多久」 |
| 预生成间隔 | 1 分钟 | `backend/internal/http/router.go:191` | 排名刷新粒度；读路径通常只花一次 `EXISTS` |
| 消费重试 | 进程内 1+3 次 → 重试队列 30s×3 轮 → 死信 | `backend/internal/worker/retry.go`、`backend/internal/middleware/rabbitmq/retry.go` | 决定去重标记 TTL 的下界 |

### 0.3 五句核心结论

1. 热度是**带时间维度的聚合量**，所以时间必须编码进 key——这是分桶存在的唯一理由。
2. 分钟桶不是「写热点分散到 60 个 key」；同一时刻所有写入落在**同一个**桶。60 个 key 是**读侧窗口**（精读 §3.3）。
3. 快照解决的**不是性能，是正确性**：翻页期间排序键不能变。摊薄成「每分钟一次」只是副产品。
4. `as_of` 有两个身份：**快照 ID** 和 **窗口集合的版本号**。客户端回传它，「加载更多」才落在同一份榜上。它的取值必须是**最后封桶的分钟**，否则重建结果会漂移。
5. 所有「零抖动 / 无重复无漏项」都只在 `as_of` 在有效区间 + 快照存活 + 未截断 + 未降级 的边界内成立。越过边界时服务端现在会**显式返回 `expired` 或 `degraded`**，而不是静默换榜。

## 第一层：基础原理（Q1–Q5）

### Q1｜为什么不能直接按视频累计点赞数排序？累计热度会产生什么问题？

**30 秒版**
累计点赞是**单调不减**的量：三个月前爆过的视频永久占据头部，新视频永远上不来（马太效应）；而且它无法表达「最近一小时」，没有时间窗口，也无法自然淘汰。热度是「最近这段时间什么最火」，必须带时间维度。

**展开**

| 用累计值排序 | 后果 |
|---|---|
| 排序键只增不减 | 老内容霸榜，新内容没有曝光机会 |
| 没有时间语义 | 无法回答「最近一小时」；只能回答「历史总量」 |
| 无法淘汰 | 榜单尾部永远是死数据，TTL/清理都无从谈起 |
| 分不清「总量大」和「现在火」 | 一个 100 万赞但没人互动的视频会压住一个 10 分钟涨 1 万赞的视频 |

**入口已统一（原陷阱已消除）**
首页的「热」tab 就是 `HotRankPanel` 调 `listByPopularity`，和推荐/关注/话题并列；原按 `likes_count` 排序的 `ListLikesCount` 已前后端整体删除，不存在「点错入口」的问题了。

**追问：按「点赞速率」排序行不行？**
速率也需要窗口定义（最近 5 分钟？1 小时？），本质还是滑动窗口；而且瞬时速率噪声大，单个爆点会主导榜单。分桶聚合就是在做「窗口内的净增量」。

---

### Q2｜什么是滑动窗口？为什么选择最近 60 分钟，而不是最近 24 小时？

**30 秒版**
滑动窗口 = 只统计「当前时刻往前一段固定长度」内的事件，窗口随时间前移。60 分钟是**产品语义 + 成本**的折中：窗口越长，桶数越多（24h = 1440 个桶），合并的输入规模、快照内存、排名钝化都线性变差；而且长窗口会让几小时前的内容继续压着新内容。

**展开**

| 维度 | 60 分钟 | 24 小时 |
|---|---|---|
| 桶数 | 60 | 1440 |
| 合并输入 N | 60 × 每分钟活跃视频数 | 1440 × 每分钟活跃视频数（约 24 倍） |
| 快照内存 | 可接受，还能裁 Top-N | 结果集更大，裁剪压力更大 |
| 榜单新鲜度 | 一小时前的爆点会自然滑出 | 一天前的爆点还在，发现新内容的能力变差 |
| 对事件延迟的容忍 | 窗口远大于延迟，迟到影响小 | 同理，但代价更高 |

60 不是物理常数，是**可配置的产品决策**：短视频场景里「一小时」符合用户对「现在什么火」的直觉。窗口太短（如 5 分钟）会噪声主导、头部深度不够；太长就退化成累计榜。

**追问：窗口前移时旧数据怎么清理？**
不需要清理任务：滑出窗口的桶不再参与合并，由 TTL（2 小时）回收。TTL 是「防堆积」，不是「定义窗口」（精读 §3.2）。这也是分桶方案比「定时跑批」优雅的地方。

---

### Q3｜为什么要按分钟分桶？相比每次查询都统计最近 60 分钟的原始事件，有什么优势？

**30 秒版**
原始事件方案要在查询时扫描 O(事件数)，而事件数远大于视频数；分桶把它预聚合成 O(桶内 distinct 视频数)。更重要的是分桶带来两个性质：**旧桶自动退出窗口**、**封桶后不可变**——后者是稳定分页的地基。

**展开**

| 方案 | 查询成本 | 存储 | 能否稳定分页 |
|---|---|---|---|
| 每次扫原始事件 | O(事件数)，每次请求都重算 | 要保留全部原始事件 | 不能：任何新事件都会改排序 |
| 分钟桶预聚合 | O(桶内成员数)，且只算一次 | 每桶一个 ZSET，TTL 自动回收 | 能：`as_of` 之后桶不再变 |

**分桶额外买到的东西**

1. **窗口语义天然成立**：最近一小时 = 取最近 60 个桶求和。
2. **封桶不可变**：写入永远用「当前分钟」，越过整点后 `...:T` 不再被写，成为只读数据块（精读 §3.4）。
3. **TTL 即淘汰**：不需要清理任务。

**代价（要主动说）**

- 精度只到分钟；
- 权重/算法变更无法回溯重算（除非另存原始事件）；
- 迟到事件会落到错误的时间桶（Q15）。

**别说错**：「按分钟分桶是为了把写热点分散到 60 个 key」——错。同一时刻所有写入都落在 `now.Truncate(time.Minute)` 这**一个**桶上（`backend/internal/video/popularity_cache.go:67`）。真要分散写热点，得按 videoID 哈希再分片，那是另一种设计。

### Q4｜Redis ZSET 如何实现排行榜？分数相同的成员如何排序？

**30 秒版**
ZSET = 字典（member→score）+ 跳表（按 score 排序）。`ZINCRBY` 是 O(log N) 的原地加分，`ZREVRANGE` 按 rank 取是 O(log N + M)。同分时按 **member 的字典序**排，`ZREVRANGE` 会把 score 和 member 都反向。

**展开**

| 操作 | 复杂度 | 说明 |
|---|---|---|
| `ZINCRBY` | O(log N) | 无读改写，不需要锁，天然抗并发 |
| `ZREVRANGE key start stop` | O(log N + M) | 按 rank 访问，不是「扫过前 k 个再丢弃」 |
| `ZUNIONSTORE` | O(N) + O(M·log M) | 合并 60 桶，阻塞命令 |
| `ZREMRANGEBYRANK` | O(log N + M) | 裁 Top-N |

**同分排序的坑**
ZSET 的 tie-break 是 member 的**字典序**，不是数值序。本项目 member 是十进制 `video_id` 字符串：

```
同分时："9" > "10" > "100"   （字典序）
期望：  100  > 10  > 9       （数值序）
```

这是**确定但不符合直觉**的顺序。它不影响「翻页不重复」（快照冻结后顺序固定），但会影响「同分视频谁在前」。若要数值序，member 需零填充成定宽（如 20 位），或在应用层重排。

另外，MySQL 降级路径的 tie-break 是 `create_time DESC, id DESC`（`backend/internal/feed/repo.go:73-92`），与 Redis 的字典序规则**不一致**——降级切换时同分视频的相对顺序会变（Q19）。

### Q5｜为什么还需要分钟级快照？直接对实时榜单使用 `ZREVRANGE` 分页不行吗？

**30 秒版**
两个原因，缺一不可：
1. **正确性**：热度每秒都在涨，实时榜的排序键在翻页期间是可变的，`offset` 翻页必然重复或漏项；
2. **成本**：60 个桶必须先合并才能排序，而 `ZUNIONSTORE` 是 O(N)+O(M·log M) 的阻塞命令，不能每请求跑一次。

快照 = 把「算榜」和「取页」拆开：排序键冻结 2 分钟，合并摊薄成每分钟一次。

**展开**

| 不加快照 | 后果 |
|---|---|
| 第 1 页取完，某视频涨到第 1 页位置 | 第 2 页重复出现它 |
| 某视频从第 2 页掉出去 | 它永远不会被看到（漏项） |
| 每个请求都合并 60 桶 | Redis 单线程被阻塞，QPS 直接塌 |

**追问：能不能用 `ZREVRANGEBYSCORE` 在 60 个桶上逐页取？**
那等于在应用层做 60 路归并：每页要读 60 个有序集合、维护堆、还要处理跨桶同分；而且它仍然是「实时」的，排序键照样会变。本质上是自己实现一个**非原子**的 `ZUNIONSTORE`，更慢也更难保证一致。

**一句话收口**：快照不是为了「更快」，是为了「翻页时榜单不动」；快只是顺带。

## 第二层：实现细节（Q6–Q13）

### Q6｜分钟桶用什么数据结构？ZSET、Hash 还是其他？各自怎么存热度？

**30 秒版**
每个分钟一个 ZSET：`member = video_id`，`score = 该分钟内的净热度增量`，写入用 `ZINCRBY`。选 ZSET 是因为读侧既要做 60 桶合并（`ZUNIONSTORE`）又要直接按分数排序（`ZREVRANGE`），这两个都是原生命令；Hash 省内存但无序，合并和排序都要搬到应用层。

**展开**

| 结构 | 写入 | 合并 60 桶 | 排序 | 备注 |
|---|---|---|---|---|
| **ZSET（本项目）** | `ZINCRBY` O(log N) | `ZUNIONSTORE SUM` 一条命令 | `ZREVRANGE` 原生 | 每个 member 有跳表开销，内存偏大 |
| Hash | `HINCRBY` O(1)，更省内存 | 只能 `HGETALL` 60 次（或 pipeline），应用层累加 | 应用层排序 O(k log k) | 合并要把「每桶全量」搬到客户端，M×60 中间态 |
| 一个 Hash 存所有分钟 | `HINCRBY video:minute` | 要扫整个 Hash | 应用层排序 | 无法按桶 TTL，淘汰困难 |
| MySQL 索引表 | UPDATE 行 | GROUP BY 聚合 | ORDER BY | 每分钟几十万行更新，写放大严重 |

**代码锚点**
- key 生成：`backend/internal/video/popularity_cache.go:68`
- 累加：Lua 脚本 `:36-43`（`ZINCRBY` 在 `:40`）；调用点 `:76-80`
- TTL：`backend/internal/video/popularity_cache.go:91`

**追问：为什么不用 String 存 JSON？**
每次都要读出来、反序列化、改、写回，是典型的读改写竞态，需要锁；`ZINCRBY` 是服务端原地操作，天然无竞争。

### Q7｜一个点赞事件到达后如何更新分钟桶？消费者重复处理同一条消息，会不会重复加热度？

**30 秒版**
不会。更新走一段 **Lua 脚本**：先用 `SET dedup:<event_id> NX EX 24h` 抢幂等标记，抢不到直接返回；抢到才 `ZINCRBY` 并给桶续 TTL。三步在 Redis 单线程里原子执行。MySQL 侧靠业务行唯一索引 + `INSERT IGNORE` 幂等，两边共用**发布前生成**的同一个 `event_id`。

**展开**

```lua
-- backend/internal/video/popularity_cache.go:36-43
if redis.call('SET', KEYS[1], '1', 'NX', 'EX', ARGV[3]) == false then
  return 0                    -- 这个事件处理过，跳过
end
redis.call('ZINCRBY', KEYS[2], ARGV[2], ARGV[1])
redis.call('EXPIRE', KEYS[2], ARGV[4])
return 1
```

**为什么不能用两条命令（`SETNX` 再 `ZINCRBY`）**
两条命令之间进程崩溃，会留下「已标记处理过、但累加没执行」的状态：后续所有重试都被去重挡住，**这次热度永久丢失**。Lua 要么全做、要么全不做，没有中间态。

**为什么幂等键必须在发布前生成**
存在「publish 成功但 confirm 超时」的窗口：消息已经在队列里，消费端迟早处理；服务层却以为失败，又走了降级直写。两条路径必须共用同一个 `event_id`，Lua 去重才能保证只生效一次。代码：`backend/internal/video/like_service.go:48-49`（生成）、`:62`（MQ 携带）、`:85`（降级携带；取消点赞对称在 `:113-114`、`:124`、`:142`）。

**MySQL 侧为什么天然幂等**
`idx_like_video_account` 唯一索引 + `INSERT IGNORE`；`RowsAffected == 0` 时在「加计数之前」就返回（`backend/internal/video/like_repo.go:46-56`）。原则是：**用「产生计数的业务行」做幂等，不要用计数本身做幂等**（精读 §3.2.1）。

**追问：`INSERT IGNORE` 够不够？**
不够。它只保证 MySQL 侧那一次插入幂等；Redis 侧是 `ZINCRBY`（累加、天生不幂等），必须有自己的幂等键。两边用同一个 `event_id`，才能保证「两个存储都只生效一次」。

### Q8｜当前分钟桶如何与之前 59 个桶合并？每分钟全量扫描所有视频，还是只聚合活跃视频？

**30 秒版**
只聚合**桶里出现过的视频**，不扫任何全量数据。`ZUNIONSTORE dest 60keys AGGREGATE SUM` 把 60 个桶按 member 去重、score 相加，复杂度 O(N)+O(M·log M)。生成时机是后台每分钟一次，预生成的是**最后封桶的分钟**（上一分钟），不是当前分钟；读路径通常只做 `EXISTS` + `ZREVRANGE`。

**展开**

- 输入 key：`[as_of-59min, as_of]` 共 60 个（`backend/internal/feed/service.go:773-779`）。
- 合并：`buildHotSnapshot`（`backend/internal/feed/service.go:787`）。
- 谁触发：
  1. 后台 `StartHotSnapshotBuilder` 每分钟预生成 `hotLatestSealedMinute(now)`（`service.go:892`、`:900`，`router.go:191` 注册）；
  2. 读路径兜底：`ensureHotSnapshot`（`:865`），预生成没跟上或客户端传了历史 `as_of` 时按需合并；
  3. 两者共用 `singleflight`（`:880`），同一个 `as_of` 只合并一次。

**为什么必须是「已封桶的分钟」**
如果 `as_of` 取当前分钟，生成时这个桶只装了前半分钟的事件；TTL 到期后重建，桶里又多出后半段，**同一个 `as_of` 的榜就变了**，翻页会重复/漏项。取上一分钟，60 个输入桶在生成瞬间全部定稿，重建才真的与首份逐位一致（详见 Q12、Q18）。

**「活跃视频」口径**
N 不是「全站视频数」，而是「60 个桶里出现过的 (视频, 分钟) 条目数」。没有热度事件的视频根本不在 ZSET 里，所以合并成本与**事件活跃度**成正比，而不是与视频表规模成正比。

**刷新粒度**
写侧永远落「当前分钟」桶，而当前分钟不参与任何快照。所以一条点赞事件最快在**下一分钟开始**进入榜单，排名刷新粒度约 1 分钟（`StartHotSnapshotBuilder` 的 tick 对齐）。这不是缺陷，是用「1 分钟新鲜度」换「重建确定一致」。

### Q9｜如果视频数量达到百万级，每分钟遍历全部视频重新聚合，成本是多少？如何优化？

**30 秒版**
先纠正前提：不存在「遍历全部视频」，只遍历 60 个桶里的成员。但百万规模下这一步仍然很贵：N ≈ 300 万、M 可达 100 万、排序约 2000 万次比较，Redis 单线程上要**秒级**，会阻塞同实例所有命令。所以做了四件事：挪出读路径、裁 Top-5000、singleflight、独立超时并留痕。再往上还有增量滚动、分片、两阶段 Top-K。

**展开**

按「每分钟约 5 万个视频产生热度事件」粗算（精读 §4.4 同口径）：

| 项 | 量级 |
|---|---|
| N（60 桶输入总量） | 60 × 5 万 ≈ **300 万** |
| M（去重后结果集） | 最多 **100 万** |
| O(M·log M) | 100 万 × 20 ≈ **2000 万次比较** |
| 单次耗时 | **1~10 秒**（阻塞整个 Redis 实例） |

**优化阶梯（按项目已做 → 可继续做）**

| # | 手段 | 解决什么 | 状态 |
|---|---|---|---|
| 1 | 后台预生成，移出读路径 | 快照过期瞬间不再钉住请求 | 已做 |
| 2 | `ZREMRANGEBYRANK` 裁 Top-5000 | 把 M 从「活跃视频数」压成常数 | 已做 |
| 3 | `singleflight` 按 `as_of` 去重 | 并发首访不再重复合并 | 已做 |
| 4 | `hotMergeTimeout` 独立 500ms + 失败打日志 | 不再「永远超时、静默降级」 | 已做 |
| 5 | 增量滚动窗口：`dest + 新桶 - 最旧桶`（权重 +1/-1） | 每 tick 只处理 2 个桶，O(桶大小) | 未做 |
| 6 | 按桶哈希分片到多个 Redis 实例 | 把单实例阻塞拆成 N 份 | 未做 |
| 7 | 两阶段 Top-K：先粗筛候选集再精确排序 | 进一步压缩 M | 未做 |

**面试话术（要落到「阻塞」而不是「CPU 时间」）**
「百万视频下这个合并是 O(N)+O(M·log M)，跑在 Redis 单线程上要数秒——它根本不该出现在读请求路径上。我改成后台每分钟预生成，读路径只剩一次 `ZREVRANGE`；把超时预算拆开、错误不再静默吞掉；快照再加 Top-N 裁剪。真正的问题不是算力，是**阻塞**：一条命令钉住实例，所有业务的 Redis 请求一起排队。」

**追问：增量滚动为什么不直接做？**
`dest` 是 ZSET，减去最旧桶要用 `ZUNIONSTORE` 的 `WEIGHTS 1 -1`，会产生**负分条目**，而且和「封桶后才允许重建」的论证要重新对齐；另外桶一旦丢失，增量结果无法自愈。属于「能做，但正确性成本高」，要先有对账/重建机制再上。

### Q10｜热榜快照具体保存什么？完整排名，还是视频 ID、分数和排名版本？

**30 秒版**
只存一个 ZSET：`member = video_id`，`score = 窗口内 SUM 热度`，**排名是隐含的**（rank 就是逆序位置），不存任何内容字段。版本信息不额外存字段，而是编码在 key 里：`hot:video:merge:1m:<as_of>`。内容按 ID 走实体三级缓存，个性化字段（`is_liked`）在最后装配。

**展开**

| 存什么 | 不存什么 | 原因 |
|---|---|---|
| video_id（member） | 标题、封面、作者 | 内容走 `video:entity:<id>`，与最新流/详情页共用一份 |
| SUM 热度（score） | `is_liked` | 因人而异，必须最后补（`buildFeedVideos`） |
| 隐含 rank | 显式 rank 字段 | rank 是 O(log N) 可算的，物化反而要随插入更新全表 |
| `as_of`（在 key 里） | 独立的版本号字段 | key 本身就是一个版本，不同分钟互不干扰 |

**为什么这样设计**
「排序」与「内容」分离（精读 §6）：

- 快照只给**顺序**，`GetVideoByIDs` 按 ID 批量装配内容；
- 热门视频在热榜、最新流、详情页三条路径上**只缓存一份**；
- 快照因此与用户无关，可以被所有用户共享。

**追问：那排名会不会因为 hydration 失败而错位？**
会「有洞」但不会「错位」，而且要区分两种「洞」：
- **回源失败**（DB 过载 / 闸门拒绝 / 查询报错）：`GetVideoByIDs` 现在**聚合错误直接返回**，整页 503/500，不再返回「19 条 + 200」的短页 —— 短页会被客户端读成「到底了」，热榜还会按 member 数推进 offset、把缺失项永久跳过。
- **视频确实已删除**：这是合法缺失，`GetVideoByIDs` 跳过该 ID，返回条数可能少于 `limit`；`NextOffset` 按 `len(members)` 推进而不是按 `len(items)`（`backend/internal/feed/service.go:1074`），所以下一页不会重复（Q19）。

**追问：Top-5000 之后怎么办？**
翻不到。这是明确的取舍：榜单入口只展示头部。要做完整榜单，得换增量滚动窗口方案，或者不裁剪、但要接受 M 不可控。

### Q11｜用户请求第一页时生成快照，下一页如何继续用同一份快照？快照 ID 怎么传给客户端？

**30 秒版**
首屏 `as_of = 0`，服务端取**最后封桶的分钟**并返回真实 `as_of`；下一页客户端把 `as_of` 和 `next_offset` 原样带回。服务端 `EXISTS` 命中就直接复用同一份快照——`offset` 是在冻结的榜上切片，所以不会重复/漏项。快照 ID 就是 `as_of`（分钟级 Unix 秒）。服务端还会校验区间：`as_of` 超出可翻页范围时，首页换新榜，翻页则返回 `expired=true` 让客户端刷新。

**展开**

**服务端**
```go
// backend/internal/feed/service.go:1012-1030
latest := hotLatestSealedMinute(time.Now())   // 上一分钟（已封桶）
earliest := latest.Add(-hotAsOfLookback)      // latest - 59min

asOf := latest
if reqAsOf > 0 {
    asOf = time.Unix(reqAsOf, 0).UTC().Truncate(time.Minute)
    if asOf.After(latest) || asOf.Before(earliest) {
        // 越界：首页换新榜；offset>0 必须终止，不能把两套窗口拼在一起
        if offset > 0 {
            return ListByPopularityResponse{VideoList: []FeedVideoItem{}, Expired: true}, nil
        }
        asOf = latest
    }
}
```

- `ensureHotSnapshot(asOf)` 保证快照存在（`EXISTS` → `singleflight` → `ZUNIONSTORE`，`service.go:836`）；
- `ZRevRange(dest, offset, offset+limit-1)`（`:1068`）；
- 响应带 `as_of`、`next_offset`、`has_more`，异常时带 `expired` / `degraded`。

**客户端**
```ts
// frontend/src/components/HotRankPanel.vue:44-53
const res = await feedApi.listByPopularity({
  limit: state.limit,
  as_of: reset ? 0 : state.asOf,
  offset: reset ? 0 : state.nextOffset,
  force_db: !reset && state.degraded,
  // DB 复合游标：只要上一页给过就一直带
})
```
「加载更多」回传 `as_of`/`offset`；「刷新」传 `as_of = 0` 主动换新榜（这是设计意图，不是 bug）。收到 `expired` 时清空会话并重新拉第一页。

**为什么这里敢用 `offset`**
`ZREVRANGE` 按 rank 访问是 O(log N + M)，不是 MySQL `OFFSET` 那种「扫过前 k 行再丢弃」。第 1 页和第 100 页代价一样，所以不怕深分页。

**边界（已落地）**

1. `as_of` 现在有区间校验：只允许 `[latest-59min, latest]`。客户端伪造任意值不会再生成新快照；负数直接 400（`handler.go:99-105`）。这修掉了「低成本变换打满 Redis CPU」的洞。
2. 分页会话寿命约 60 分钟：`as_of` 滑出区间后，翻页返回 `expired=true`，由前端重新加载首页。
3. 降级到 MySQL 后 `offset` 失效，必须靠响应里的 `(next_latest_popularity, next_latest_before, next_latest_id_before)` 三元组；前端每页都带，后端对「`offset > 0` 但无游标」直接返回空页（fail-closed）。
4. 一旦降级，前端后续请求带 `force_db=true`，服务端跳过 Redis 分支——Redis 中途恢复也不会把两套榜单拼进同一会话。

### Q12｜如果快照只保留 5 分钟，用户 10 分钟后才请求下一页，应该返回什么？

**30 秒版**
快照没了就**用同一个 `as_of` 重建**，这是安全的：`as_of` 只取**已经封桶的分钟**，60 个桶在生成首份快照时就已经定稿，重建结果必然与首份逐位一致。所以 10 分钟后回来仍然能接着翻。真正会坏的是「`as_of` 滑出可翻页区间」：超出 `[latest-59min, latest]` 后，翻页返回 `expired=true`，明确让客户端刷新，而不是返回错位数据。

**展开**

| 时间点 | 发生什么 | 翻页结果 |
|---|---|---|
| `t0`（`as_of` 封桶之后） | 首次生成快照，TTL 2min | 第 1 页 |
| `t0+2min` | 快照过期，下次请求重建 | 桶已封桶 → 与首份一致 |
| `t0+10min` | 同上（本项目 TTL 是 2min，不是 5min） | 仍一致，只要 `as_of` 还在区间内 |
| `t0+约 60min` | `as_of` 滑出 `[latest-59min, latest]` | `offset>0` → `expired=true`；首页 → 换最新榜 |
| 客户端伪造未来/过老 `as_of` | 越界 | 首页收敛到最新；翻页返回 `expired=true`，不再新建快照 |

**为什么一致性不再依赖 TTL**
旧实现让 `as_of = 当前分钟`，靠「TTL 2min > 1min，重建时该桶已封桶」来论证一致。这个论证有两个问题：它把正确性押在一个可配置数字上，而且只要有人在同一分钟内重建（TTL 被改短、缓存被逐出、手工删 key），结果就会漂移。
现在的做法是把 `as_of` 直接定义成**最后一个已封桶的分钟**（`hotLatestSealedMinute`，`service.go:62`）：60 个输入桶在**生成瞬间**就全部只读。重建是同一个纯函数的第二次求值，与 TTL 多长、什么时候重建都无关。TTL 只剩「新鲜度」和「重建频率」两个职责。

**空窗口与过期**
- 60 个桶确实为空时，`buildHotSnapshot` 会写一个 `hot:video:merge:1m:<as_of>:empty` 标记（TTL 2min，`service.go:768`、`:848`）。`ensureHotSnapshot` 认这个标记，因此**不会每请求重跑一次 `ZUNIONSTORE`**，也不会把空窗口误判成「Redis 坏了」而去降级。
- 空窗口的第一页返回**空列表**（`degraded=false`），这是正确语义：最近一小时确实没有热度，不应该偷偷换成 MySQL 的累计榜。
- `as_of` 越界时由区间校验处理（Q11），与空窗口是两件事。

**一个不可区分的边界（要主动说）**
如果 Redis 被整体清空，60 个桶全没了，从数据上无法区分「窗口本来为空」和「桶丢了」。此时会先写入空标记，榜单最多空 2 分钟，等新事件重新积累。要消除这个盲区，需要「窗口基线」或事件日志（见 Q16）。

### Q13｜热度依赖点赞、评论、播放等多个事件时，权重怎么定？撤销点赞、删除评论等负向事件怎么处理？

**30 秒版**
现状是 `popularity = 点赞 +1 + 评论 +1`，权重都是 1，**没有播放事件**；`videos.popularity` 是 MySQL 侧的累计权威值，Redis 只存窗口增量。权重应在**发布事件时**按类型算好放进 `change`，消费端只做加法。负向事件现在覆盖了「取消点赞 -1」和「删除评论 -1」，都由 MQ 事件驱动、有稳定幂等键；但它们都落在**当前分钟桶**而不是当初 +1 的桶，跨桶抵消失真这一点要主动承认。

**展开**

| 事件 | MySQL 侧 | Redis 分钟桶 | 是否严格正确 |
|---|---|---|---|
| 点赞 | `popularity +1`（`like_repo.go:61`） | `change +1` | 是 |
| 取消点赞 | `popularity -1`（`like_repo.go:90`） | `change -1`（`like_service.go:124`） | **否**：-1 落在取消时刻的桶 |
| 评论 | `popularity +1`（`comment_repo.go:54`） | `change +1` | 是 |
| 删除评论 | `popularity -1`（`comment_repo.go:82`，同一事务） | `change -1`（`comment_service.go:124`） | **否**：同样落在删除时刻的桶 |
| 删除视频 | 无热度事件 | 无 | 快照里仍有它，装配时被跳过 |
| 播放 | 不统计 | 无 | 未实现 |

**删除评论是怎么修的**
旧实现只删 `comments` 行，`videos.popularity` 和窗口热度都不动，等于「+1 永久生效」。现在 `CommentService.Delete`（`comment_service.go:100`）会：
1. 生成稳定幂等键 `comment-del:<commentID>`（`:114`），而不是随机 ID；
2. 发布评论删除 MQ + 热度 `-1` MQ（`:124`）；
3. MQ 不可用时降级直写：`ApplyDelete` + `UpdatePopularityCache(..., -1, popEventID)`（`:134-141`）。

`CommentRepository.ApplyDelete`（`comment_repo.go:60-82`）在**同一事务**里先取 `video_id`、删行、`RowsAffected>0` 才 `popularity -1`。删除天生幂等：行已经不在就不减，避免重复投递把计数减穿。用评论 ID 做幂等键而不是随机事件 ID，是因为「删除同一条评论」无论重投多少次都只应生效一次。

**权重怎么设计**
不要在消费端查权重表（多一次 IO，且改权重会回溯影响历史事件）。正确做法是**发布时定价**：`change = weight(event_type)`，事件体里直接携带带符号增量。这样权重调整只影响新事件，语义清晰。

**负向事件的三个真实问题**

1. **跨桶抵消失真**：10:00 点赞 +1 落在 10:00 桶；11:30 取消 -1 落在 11:30 桶。如果 10:00 已滑出窗口，窗口 SUM 会比「真实净点赞」少 1（把不该扣的扣了）。删除评论同理。
2. **桶分数可能为负**：`ZINCRBY -1` 可以把某个桶的分数减到负数；SUM 数学上仍对，但榜单尾部会出现负热度视频（Top-5000 裁剪会先裁掉它们）。
3. **删除视频不降温**：视频删除没有热度负事件，它的分数只在滑出窗口后自然消失；在此之前快照里仍有它，靠装配阶段过滤，表现为「有洞」而不是「错位」。

**还有一个窄竞态（已知限制）**
两个并发的「取消点赞」请求会各自生成一个 `popEventID` 并各自发 `-1`：MySQL 侧唯一索引/RowsAffected 只减一次，Redis 侧却可能减两次。窗口只有 24 小时，偏差会随窗口滑出自行消失。彻底修需要让热度事件携带「业务行是否真的发生变化」，或把去重键下推到 (video, account, 动作)——但那样会误伤「点赞→取消→再点赞→再取消」的合法序列，所以现阶段选择记录为已知限制。

**要严格正确怎么办**
需要「事件日志 + 事件时间 + 定期重算」：所有正负事件按 `(event_id, occurred_at, video_id, change)` 持久化，窗口查询时按时间范围聚合，或用「事件时间桶 + 允许迟到窗口」重算。成本远高于当前方案。小型项目里更务实的选择是：**明确声明这是「近似窗口热度」**，并在产品上避免展示绝对数值。

**面试话术**
「我的热度是点赞 + 评论各记 1 分，权重在发布时确定。负向事件我做了取消点赞和删除评论的 -1，删除评论走同一事务并带稳定幂等键 `comment-del:<id>`。但它们都记在负向动作发生的那一分钟——如果正向事件已经滑出窗口，窗口 SUM 会和真实净点赞有偏差。这是已知的近似，不是精确值。要做精确，需要事件日志加事件时间重算，我评估过成本，现阶段选择近似。」

## 第三层：故障与反问（Q14–Q19）

### Q14｜「聚合开销摊薄为每分钟一次」，如果每分钟仍需扫描全部视频，复杂度真的可接受吗？

**30 秒版**
先纠正：不扫描全部视频，只合并 60 个桶里出现过的成员。但在百万规模下这一步仍要秒级、且阻塞 Redis 单线程，**留在读路径上不可接受**。所以摊薄只是第一步，真正的解法是把它挪出读路径 + 裁剪结果集。现在每个 `as_of` 只合并一次（约每分钟一次），读路径只剩 `EXISTS` + `ZREVRANGE`。

**展开**

| 说法 | 准确性 |
|---|---|
| 「每分钟遍历全部视频」 | 错。没有全表扫描，只有桶内成员聚合 |
| 「每分钟合并 60 个桶」 | 对，但 N 取决于每分钟活跃视频数，不是视频总数 |
| 「摊薄为每分钟一次」 | 对，可从代码推导：`EXISTS` + 2min TTL，每个 `as_of` 一次 |
| 「每分钟一次就一定便宜」 | 错。百万规模下一次仍可能秒级阻塞 |

**为什么「一分钟一次」还不够**
Redis 是单线程：一条 1~10 秒的 `ZUNIONSTORE` 会让**同实例上所有业务命令**排队。这不是「平均值可接受」的问题，是尾延迟直接爆掉。所以设计目标应该是「**不在共享实例上跑大命令**」，而不只是「降低频率」。

**已落地的四层防护**
1. 后台预生成（`service.go:892`，生成的是上一分钟，不是当前分钟）；
2. Top-5000 裁剪（`service.go:799-804`）；
3. `singleflight` 按 `as_of`（`service.go:852`）；
4. `hotMergeTimeout` 独立预算 + 失败 `log.Printf`（`service.go:836-875`）。

**再往上**
增量滚动窗口（每 tick 只加 1 个桶、减 1 个桶）能把单次成本从 O(60 桶) 降到 O(2 桶)，但要处理负分和桶丢失自愈；分片则把阻塞拆到多个实例。这两条没做，但能讲清取舍。

### Q15｜热度事件延迟 3 分钟才被消费，应计入事件发生时间还是消费时间？各有什么影响？

**30 秒版**
现状是**消费时间**：`time.Now().UTC().Truncate(time.Minute)`（`popularity_cache.go:67`），消息里的 `OccurredAt` 字段存在但没用。这是一个明确的选择：处理时间窗口单调、不会写已封桶；代价是榜单反映「何时处理」而不是「何时发生」。如果改成事件时间，就必须允许写已封桶，那会破坏稳定分页的地基。

**展开**

| 口径 | 语义 | 优点 | 代价 |
|---|---|---|---|
| 消费时间（现状） | 「最近一小时被处理的事件」 | 单调、永不回写旧桶、封桶不可变成立 | 延迟会把热度推迟计入；故障恢复后事件集中涌入会「补涨」 |
| 事件时间 | 「最近一小时发生的事件」 | 语义正确，跨延迟可比 | 会写已封桶 → 已生成快照与重建结果可能不一致；需要 watermark + 迟到窗口 + 重算 |

**3 分钟延迟的实际影响（消费时间口径）**

1. 事件落到 `T+3` 的桶，而不是 `T`；
2. 对当前 `as_of` 来说，只是「晚 3 分钟出现」，不会丢；
3. 如果这 3 分钟恰好跨了窗口边界，原本该滑出的事件被多算了一会儿；
4. 已冻结的 `as_of` 快照不会包含它——用户看到的榜单要等刷新。

**为什么不能简单改成 `OccurredAt`**
写 `T` 桶意味着 `T` 桶在封桶后仍被修改：同一 `as_of` 的「首份快照」和「过期后重建」就可能不一致，直接推翻 Q12/Q18 的一致性基础。现在的 `as_of` 只取已封桶分钟，整个稳定性论证都建立在「封桶后桶不可变」上；一旦允许回写旧桶，这个前提就没了。要改必须配套「允许迟到窗口（比如 2 分钟）+ 窗口内才允许写 + 超出则进入补偿重算」，复杂度上一个台阶。

**面试话术**
「我用的是处理时间窗口，`OccurredAt` 只做审计字段。理由是封桶不可变：只要允许按事件时间回写旧桶，快照重建成不了一致。代价是延迟事件会晚计入、故障恢复后会补涨。如果业务要求严格事件时间，我会加 watermark 和迟到补偿，而不是直接改 `Truncate` 的那一行。」

### Q16｜分钟桶因 Redis 故障丢失，排行榜如何恢复？需要持久化事件或从数据库重建吗？

**30 秒版**
Redis 丢失会同时丢掉四样东西：分钟桶、快照、空窗口标记、去重标记。**未 ACK 的消息**能靠三级重试在恢复后重投；**已 ACK 的事件**只能从 MySQL 重建（`likes.created_at`、`comments.created_at` 按窗口聚合）。但取消点赞会物理删行、去重标记也没了，所以重建是**近似**的。另外「窗口本来为空」和「桶全丢了」在数据上不可区分，恢复后的前 2 分钟会先按空窗口处理。结论：正常故障下最终一致，Redis 数据丢失按「缓存丢失」处理——重建 + 对账，不承诺精确恢复。

**展开**

| 丢失内容 | 能否恢复 | 恢复方式 | 精度 |
|---|---|---|---|
| 未 ACK 的热度消息 | 能 | Consumer 进程内退避 → 重试队列 30s×3 → 死信（`worker/retry.go:82-155`） | 精确 |
| 已 ACK 但只写了 Redis 的事件 | 能（近似） | 从 `likes` / `comments` 按 `created_at` 聚合最近 1 小时 | 取消/删除的负向事件不可重建 |
| 分钟桶 | 能（近似） | 用上面的聚合结果重新 `ZINCRBY` | 同上 |
| 去重标记 | 不能 | 标记与业务行无关联（likes 没有 `event_id`） | 重投事件可能被重复累加 |
| 快照 | 能 | 桶恢复后重新 `ZUNIONSTORE` | 取决于桶 |
| 空窗口标记 | 能 | 桶恢复后重新合并；TTL 2min 内会先按「空窗口」返回 | 最多空 2 分钟 |

**去重标记丢失的连锁反应（容易被追问）**
Redis 清空后，一条已经处理过、但 ACK 丢失的消息被重投：MySQL 侧 `INSERT IGNORE` 仍然挡住（业务行还在），Redis 侧 `SET NX` 却成功 → `ZINCRBY` 再加一次。结果就是「Redis 热度 > MySQL 计数」。这不是理论问题，是缓存与业务库不同生命周期导致的必然偏差。

**实践建议（可以讲成改进方案）**
1. 桶和快照定位为**可重建缓存**，故障后跑一次「最近 1 小时重建任务」，以 MySQL 为准；
2. 重建期间把 `as_of` 重置为「最后封桶的分钟」，丢弃旧会话（旧 `as_of` 早已越界，会返回 `expired`）；
3. 加对账任务：抽样比较 `videos.popularity` 与近窗口 SUM 的偏差，超阈值告警；
4. 若要求严格，把事件日志持久化（DB/Stream），桶只做物化视图。

**面试话术**
「Redis 整体挂掉，我承认分钟桶会丢，丢的是最近一小时的窗口史。没 ACK 的消息能重投；已 ACK 的只能从点赞/评论表按 `created_at` 重建，但取消点赞删了行，重建不精确，去重标记也一起没了，重投可能多加一次。所以我的承诺是：**正常消息故障下最终一致；Redis 数据丢失按缓存丢失处理**，重建 + 对账，不吹精确恢复。」

### Q17｜同一个视频在多个桶中都有热度，合并时如何去重并正确累加？

**30 秒版**
`ZUNIONSTORE ... AGGREGATE SUM` 本身就是按 **member 去重、score 相加**：同一 `video_id` 在 60 个桶里各有一条，合并后只剩一条，分数是 60 个桶的和。所以「多桶」不是重复，是分段时间的累加；真正的重复只可能来自「同一个事件被写了两次」，那由 Lua 去重挡住。

**展开**

```
桶 10:00 → {v1: 3, v2: 1}
桶 10:01 → {v1: 2, v3: 5}
ZUNIONSTORE SUM →
{v1: 5, v2: 1, v3: 5}      -- member 去重，score 相加
```

| 情况 | 会不会重复 | 原因 |
|---|---|---|
| 同一视频出现在多个桶 | 不会 | ZSET member 唯一，SUM 聚合 |
| 同一事件被消费两次 | 不会（正常情况） | Lua `SET NX` 去重 |
| 同一事件被写进两个桶 | 不会（现状） | key 取处理时刻，一次处理只写一个桶 |
| Redis 去重标记丢失后重投 | **会** | 见 Q16 |
| 负向事件跨桶 | 不重复，但**失真** | 见 Q13 |

**负分的处理**
`ZINCRBY -1` 可以让桶分数为负，合并后仍可能是负分。负分条目仍会参与排序（排在最后），Top-5000 裁剪时会被优先裁掉。若不想让负分视频出现在榜单，需要在合并后用 `ZREMRANGEBYSCORE dest -inf 0` 清掉——现在没做。

**追问：怎么保证「同一事件只成功一次」跨桶也成立？**
幂等键与桶写入必须在同一个 Lua 里：先抢 `dedup:<event_id>`，成功才 `ZINCRBY`。只要这两步原子，事件无论被投递多少次、落在哪个桶，都只加一次。

### Q18｜快照生成过程中新的热度事件不断写入 Redis，如何保证生成结果内部一致？

**30 秒版**
`ZUNIONSTORE` 是一条命令，Redis 单线程执行，60 个输入在**同一瞬间**被读取，不会读到「一半更新、一半没更新」的撕裂状态。所以「内部一致」由命令原子性保证。真正的风险不是撕裂，而是**同一个 `as_of` 被生成两次、结果不同**——现在由两层挡住：`as_of` 只取已封桶的分钟（60 个输入桶在生成时全部定稿），以及 `EXISTS` + `singleflight` 保证同一份快照只生成一次。

**展开**

| 层级 | 保证 | 手段 |
|---|---|---|
| 单次合并内部 | 60 个桶同一瞬间读取 | Redis 单线程 + 单命令原子性 |
| 同一 `as_of` 只生成一次 | 所有读者看到同一份 | `EXISTS` 复用 + `singleflight`（`service.go:836-876`） |
| 过期重建与首份一致 | 输入桶在生成时已全部封桶 | `hotLatestSealedMinute`（`service.go:62`），与 TTL 长短无关 |
| 空窗口不反复合并 | 空结果也有「已生成」标记 | `:empty` 标记（`service.go:768, 848`） |
| 生成过程不受请求取消影响 | leader 取消不拖垮等待者 | 用 `context.Background()`（`service.go:800-822`） |
| 生成失败可观测 | 不静默降级 | `log.Printf`（`service.go:875`） |

**为什么「生成时桶还在写」不再是问题**
写侧永远写当前分钟桶，而当前分钟**不在**任何快照的 60 个输入里（`as_of` 是上一分钟，窗口是 `[as_of-59, as_of]`）。所以生成时没有任何一个输入桶在被写；快照是真正的「定稿切片」，不是「这一分钟的临时值」。这是比「单命令原子性」更强的保证：重建是可重复的纯函数求值。

**并发写不会覆盖快照**
旧实现的问题是并发首访各自 `ZUNIONSTORE`，后完成的覆盖先完成的，而两次之间桶还在变 → 翻页中途换榜。现在 `singleflight` 按 `as_of` 收敛，只有一个 leader 写。

### Q19｜「翻页零抖动」是否意味着快照内排名完全不变？视频被删除或设为私密怎么办？

**30 秒版**
「零抖动」指的是：**同一 `as_of`、快照命中、未降级**时，排名序列冻结——不是内容不变，也不是永久不变。视频被删除后，装配阶段会跳过它，这一页条数变少，但 `NextOffset` 按「从快照里取走了几个 member」推进，所以下一页不会重复。当前没有「私密」字段；如果加，只能在装配时过滤，效果同样是「有洞」。

**展开**

| 场景 | 排名 | 本页条数 | 下一页 | 是否重复 |
|---|---|---|---|---|
| 正常 | 冻结 | = limit | `offset + len(members)` | 否 |
| 视频被删除 | 冻结（快照里还在） | < limit（hydration 跳过） | 按 `len(members)` 推进 | 否 |
| 视频设为私密 | 冻结 | < limit（若装配时过滤） | 同上 | 否 |
| 快照被裁到 Top-5000 | 冻结 | — | 5000 之后翻不到 | — |
| Redis 挂 → 降级 MySQL | **变成累计 popularity 排序** | — | 靠 DB 三元组游标 | 会话内不重复 |
| 降级后 Redis 恢复 | **仍留在 MySQL 榜**（前端带 `force_db`） | — | 继续 DB 游标 | 否 |
| 会话刷新 | 回到窗口榜第一页 | — | 新一轮会话 | 否 |
| `as_of` 越界 | — | 0 | 返回 `expired=true`，前端刷新 | — |

**删除为什么不会导致重复**
如果把推进量写成 `offset + len(items)`，视频删除后 `len(items) < len(members)`，推进不足，下一页会把本页最后一条再返回一次。代码已改为 `offset + len(members)`（`service.go:1103`），并有注释说明。这是精读 §9 B1 记录过的修复。

**「零抖动」的边界（要主动说）**

1. **降级切换**：MySQL 按 `popularity DESC`（累计值）排，Redis 按窗口 SUM 排，是两套榜单；中途切换顺序必然变。这是语义不同，不是 bug。
2. **降级态不自愈**：DB 响应返回 `degraded=true`，前端把后续请求标记 `force_db=true`，服务端跳过 Redis 分支。所以 Redis 恢复后**不会**悄悄切回窗口榜，会话要么继续走 DB，要么由用户刷新开始新会话。这修掉了「降级恢复后把两套榜拼在一起」的洞。
3. **空快照不降级**：窗口确实为空时返回空列表（`degraded=false`），不会再静默换成累计榜。
4. **越界显式终止**：`as_of` 滑出 `[latest-59min, latest]` 后，翻页返回 `expired=true`，前端清空会话重新拉第一页。

**面试话术**
「我说的零抖动有明确边界：同一个 `as_of`、快照还在、没降级。删除视频只会让这一页少几条，不会让下一页重复，因为推进量按快照里取走的 member 数算。降级是另一套排序，切过去顺序一定变——但我会用 `degraded` 告诉前端，并用 `force_db` 把这个会话钉在 DB 榜上，不会中途又切回窗口榜。空窗口就返回空榜，不冒充累计榜；`as_of` 过期就返回 `expired` 让用户刷新。」

## 高频 5 题：30 秒话术卡

> 设计文档点名最可能追问：Q8、Q9、Q11、Q14、Q15。

**Q8｜当前桶怎么和 59 个桶合并？全量扫视频吗？**
「不扫视频，只合并 60 个桶里出现过的成员，`ZUNIONSTORE SUM` 按 member 去重、分数相加。生成是后台每分钟预生成**最后封桶的分钟**（上一分钟），读路径通常只做 `EXISTS` 和 `ZREVRANGE`；预生成没跟上时按需合并，用 `singleflight` 按 `as_of` 收敛。取上一分钟而不是当前分钟，是为了让 60 个输入桶在生成时全部定稿，重建结果与首份完全一致。」

**Q9｜百万视频下成本多少？**
「N 是 60 个桶的成员总数，不是视频总数。按每分钟 5 万活跃视频算，N≈300 万、结果集最多 100 万，排序约 2000 万次比较，Redis 单线程要秒级并阻塞全实例。所以我把它挪出读路径、裁到 Top-5000、加 singleflight、拆超时并留痕。再往上做增量滚动或分片。」

**Q11｜第一页生成快照，下一页怎么复用？**
「`as_of` 就是快照 ID。首屏传 0 让服务端取最后封桶的分钟，响应带回 `as_of` 和 `next_offset`；下一页原样带回，服务端 `EXISTS` 命中就复用，`ZREVRANGE` 在冻结的榜上按 offset 切片。ZSET 按 rank 访问是 O(log N + M)，所以这里用 offset 不怕深分页。`as_of` 有区间校验，越界翻页会返回 `expired`，前端重新拉第一页。」

**Q14｜每分钟一次就够了？**
「频率降低不等于成本可接受。百万规模下单次合并仍然秒级阻塞，目标是让大命令不出现在共享实例的读路径上。现在读路径只剩 `EXISTS` + `ZREVRANGE`，合并由后台每分钟做一次；再进一步是增量滚动和分片，我评估过但暂未做。」

**Q15｜迟到 3 分钟计哪个桶？**
「计消费时间，`OccurredAt` 只是审计字段。处理时间窗口单调、永不回写已封桶，这是稳定分页能成立的前提；代价是延迟事件晚计入、恢复后补涨。改成事件时间需要 watermark 和迟到补偿，否则会破坏封桶不可变。」

| 8 | 降级后恢复混榜 | Redis 中途恢复 | 旧实现会把累计榜和窗口榜拼进同一会话 | 响应 `degraded=true`，前端带 `force_db` 钉住 DB 榜 | ✅ 已修 |
| 9 | 空快照持续 miss / 静默降级 | 60 桶全空或 `as_of` 太老 | 旧实现每请求重合并，首屏静默换成累计榜 | `:empty` 标记 + 空窗口返回空列表（`degraded=false`） | ✅ 已修 |
| 10 | 当前分钟热度不立即可见 | 当前分钟内产生的事件 | 要等该分钟封桶（约 1 分钟）才进榜 | 设计取舍；改用事件时间会破坏封桶不可变 | 设计取舍 |
| 11 | 并发双取消可能多减一次 Redis | 同一用户并发两次取消点赞 | MySQL 只减一次，Redis 可能减两次；窗口滑出后自愈 | 需让事件携带「业务行是否真的变化」，或 (video, account) 维度去重但会误伤合法序列 | 已知限制 |
| 12 | 空窗口与桶丢失不可区分 | Redis 整体清空 | 恢复后最多 2 分钟按空窗口返回 | 事件日志 / 窗口基线 | 已知限制 |

**千万不要说的四句话**

1. 「分钟分桶是为了把写热点分散到 60 个 key」——错，同一时刻写同一个桶。
2. 「每分钟遍历全部视频重新聚合」——错，只聚合桶内成员。
3. 「`ZINCRBY` 是幂等的」——错，它是累加；幂等来自 Lua 去重。
4. 「翻页绝对无重复无漏项」——错，只在 `as_of` + 快照 + 未降级边界内成立。

## 19 题一句话答案（考前速览）

| # | 问题 | 一句话 |
|---|---|---|
| 1 | 为什么不能按累计点赞排 | 单调不减 → 老内容霸榜、无时间语义、无法淘汰 |
| 2 | 为什么 60 分钟 | 产品语义 + 成本折中；24h 桶数和合并规模约 24 倍 |
| 3 | 为什么按分钟分桶 | 预聚合降查询成本；旧桶自动退出；封桶不可变 |
| 4 | ZSET 怎么排序 | 字典 + 跳表；同分按 member 字典序，`ZREVRANGE` 反向 |
| 5 | 为什么要快照 | 冻结排序键（正确性）+ 摊薄合并（成本） |
| 6 | 桶用什么结构 | 每分钟一个 ZSET，member=video_id、score=分钟增量 |
| 7 | 重复消费会不会多加 | 不会，Lua `SET NX` 去重 + `ZINCRBY` 原子；MySQL 靠唯一索引 |
| 8 | 怎么合并 60 桶 | `ZUNIONSTORE SUM`，只聚合活跃成员；后台每分钟预生成上一分钟（已封桶） |
| 9 | 百万级成本 | N≈300 万、M≤100 万、秒级阻塞 → 移出读路径 + Top-5000 |
| 10 | 快照存什么 | ZSET（ID + 分数 + 隐含 rank）；版本就是 key 里的 `as_of` |
| 11 | 下一页怎么复用 | 回传 `as_of` + `offset`，`EXISTS` 命中同一份快照；越界返回 `expired` |
| 12 | 10 分钟后翻页 | 同一 `as_of` 重建，封桶后结果一致；滑出区间则明确报过期 |
| 13 | 权重与负向事件 | 发布时定价；取消点赞/删除评论都发 -1，但跨桶失真（已知近似） |
| 14 | 每分钟一次够吗 | 频率不等于成本；关键是别让大命令跑在共享实例读路径 |
| 15 | 迟到计哪个桶 | 消费时间；事件时间需 watermark，否则破坏封桶 |
| 16 | Redis 丢了怎么恢复 | 未 ACK 重投 + MySQL 重建；去重标记丢失 → 近似，需对账 |
| 17 | 多桶同视频怎么合并 | `SUM` 按 member 去重、分数相加；重复只来自重复事件 |
| 18 | 生成时还在写怎么办 | 窗口只含已封桶分钟；单命令原子读 60 桶 + 同一 `as_of` 只生成一次 |
| 19 | 零抖动意味着什么 | 排序冻结、内容可缺；删除留洞不重复；降级/过期有显式标记 |

## 附：演示与口径提醒

1. 首页「热」tab 就是滑动热榜（`HotRankPanel` → `listByPopularity`），与推荐/关注/话题并列；点赞榜接口已删除。
2. 不要照着 `question.md` 第四节的三条错误讲（精读 §10）：快照重建用的是**同一个 `as_of`**、快照有 `EXISTS` 复用、MySQL 降级按 `popularity` 而不是点赞数排序。补充一句：旧实现 `as_of` 取当前分钟时，重建确实会漂移；现在改成「最后封桶的分钟」后，同一个 `as_of` 重建才真正逐位一致。
3. 讲「热度实时性」时区分四个时间：写入延迟（秒级）、封桶延迟（当前分钟内的事件要等该分钟结束，≤1 分钟）、排名刷新粒度（1 分钟 tick）、同一会话冻结（快照 TTL 2 分钟）。别混成一句「2 分钟」。
4. 所有性能数字标明来源：复杂度可以从代码/Redis 文档推导；1~10 秒和 N/M 是**规模假设下的估算**，不是压测数据。被追问压测就直说「这是估算，没有真实压测」。
