## 1. 三十秒总览（先背这一页）

### 1.1 一条数据流

```
发布视频
  └─ 同库事务：videos + outbox_msgs
       └─ poller（1s）→ RabbitMQ（publisher confirm）
            └─ consumer：Lua 原子执行
                          ZADD feed:global_timeline score=create_time(ms) member=video_id
                          ZREMRANGEBYRANK 0 -(TimelineCapacity+1)   ← 只留最近 1000 条
删除视频
  └─ 删库 + 失效实体缓存 + ZREM 热时间线 member（尽力而为）

读 Feed
  ├─ watermark = ZSET 最小 score（ZRANGE 0 0）
  ├─ 游标 > watermark  → 热区：ZREVRANGEBYSCORE 取 ID → 应用层按 (score,id) 重排
  ├─ 游标 ≤ watermark  → 冷区：MySQL 复合游标查询
  ├─ 热区不足 limit+1  → 用最后一条的 (create_time,id) 去 MySQL 向下补齐（不回写 ZSET）
  ├─ has_more = 是否取到 limit+1 条（不是「本页满没满」）
  └─ 无论冷热，内容都走 GetVideoByIDs（实体三级缓存）+ BatchGetLiked

后台
  └─ 每 5 分钟：MySQL 最新 1000 条 vs ZSET，补齐缺失 member（只补不删）
```

### 1.2 关键参数

| 项 | 值 | 说明 |
|---|---|---|
| Redis key | `feed:global_timeline` | 全局唯一，不是每个用户一份；常量在 `video/timeline.go` |
| ZSET score | `videos.create_time.UnixMilli()` | 不可变字段，幂等的前提 |
| ZSET member | `video_id` 的十进制字符串 | 天然去重，重复 `ZADD` 只覆盖 score |
| 容量上限 | `video.TimelineCapacity = 1000` | 写入裁剪、空 ZSET 重建、后台对账三处共用同一常量 |
| 写入原子性 | 一段 Lua：`ZADD` + `ZREMRANGEBYRANK` + `ZCARD` | 不存在「写进去但没裁」的中间态 |
| 热区水位线 | ZSET 最小 score | 动态计算，不维护额外元数据 |
| 排序键 | `(create_time DESC, id DESC)` | MySQL ORDER BY / Redis 应用层重排 / 游标比较三处必须一致 |
| 游标字段 | `latest_time`(ms) + `latest_id_before` | 必须成对；响应里是 `next_time` + `next_id_before` |
| 单页探测 | 取 `limit+1` 条，返回前 `limit` 条 | `has_more = len > limit`，删除过滤不会让它提前为 false |
| 冷区单页上限 | `limit`（handler 限制 1..50） | 超出按 10 处理 |
| 空 ZSET 重建 | singleflight + 从 MySQL 取最新 1000 条 | `EMPTY_DB` 哨兵防递归 |
| 部分缺失修复 | 每 5 分钟对账，只补缺失 member | 不删「多余」，避免误伤对账期间新发布的视频 |
| 关注流缓存 | 首页 30s、后续页 24h | 新视频只影响首页，后续页游标锚定在旧数据上 |

### 1.3 三句话结论（被要求总结时用）

1. **排序键是 `(create_time DESC, id DESC)`**，Redis 只负责给候选集，最终顺序在应用层重建，和 MySQL 的 `ORDER BY` 严格对齐。
2. **热区是 MySQL 的前缀子集，冷区是 MySQL 的范围查询**，所以「热接冷」只需要沿着游标向下补，不需要跨库去重（前提见 Q11）。
3. **「不重不漏」的承诺建立在「排序键不变 + 只在头部追加」上**；删除、取消关注会让页变短，但不会让同一页出现两次，`has_more` 也仍然准确（见 Q14）。

# 一、第一层：基础原理

## Q1. 为什么 Feed 不直接使用 MySQL 的 `LIMIT offset, size`？深分页的性能瓶颈是什么？

**一句话要点**
`OFFSET` 是「先取出前 N 行再丢掉」，代价随页码线性增长；更重要的是每条 Feed 请求都要打 MySQL。本项目用「Redis 接住头部 + MySQL 只做游标范围查询」把这两个问题一起解决。

**展开**

1. **执行代价**：`LIMIT 10 OFFSET 100000` 的真实过程是「定位并跳过 10 万条索引项 → 回表 10 万次（取决于覆盖索引）→ 丢弃 → 返回 10 条」。翻到第 1 万页时，数据库做的是十万行量级的无用功。
2. **页码分页天然不稳定**：第 1 页看完后有 3 条新视频插入，第 2 页整体后移 3 位，页首会**重复**上一页末尾的 3 条；反过来删 3 条就会**漏** 3 条。这是 offset 语义决定的，不是慢查询问题。
3. **无法缓存**：`page=N` 的缓存每次有新视频就整体失效；而 Feed 的访问又高度集中在前几屏，正是最该缓存的部分。
4. **本项目的两层解法**：
   - 头部 1000 条放 Redis ZSET，绝大多数请求不出 Redis；
   - 尾部走 MySQL，但条件是 `(create_time, id) < 游标`，是**索引范围查询**，第 1 页和第 1000 页代价相同。
5. **如果非要用 offset 优化**：延迟关联（先用覆盖索引取 ID 再回表）能减少回表次数，但仍然是 O(offset) 的索引扫描，治标不治本；而且解决不了翻页错乱。

**代码依据**
- 冷区：`feed/repo.go:29`，`WHERE (create_time < ?) OR (create_time = ? AND id < ?)` + `ORDER BY create_time DESC, id DESC`。
- 热区：`feed/service.go:510`，`ZREVRANGEBYSCORE`。
- Redis 不可用时的纯 DB 降级：`feed/service.go:312`、`:321`。

**可能的追问**
> 「那你们 Feed 到底查不查 MySQL？」
> 查。热区不查 MySQL 做**排序**，但视频内容装配和点赞状态仍可能回源；冷区整页查 MySQL。准确说法是「排序读路径热区不落库」，不是「Feed 不查库」。

## Q2. 为什么热时间线使用 Redis ZSET，而不是 List、普通 Set 或 MySQL 索引表？

**一句话要点**
ZSET 同时提供了「按 score 有序」「按 member 去重」「O(log N) 插入」「按 score 范围取一页」「按排名裁剪」这五件事，其他结构至少缺一件。

**展开**

| 结构 | 有序性 | 按时间范围翻页 | 去重 | 裁剪最旧 | 主要问题 |
|---|---|---|---|---|---|
| Redis List | 按**入队顺序** | ❌ 只能按下标 | ❌ 重复投递会产生重复元素 | `LTRIM` 可以 | 消息重投/乱序/重建后，顺序 ≠ `create_time` 顺序；无法按时间游标查 |
| Redis Set | ❌ 无序 | ❌ | ✅ | ❌ | `SMEMBERS` 全量 O(N)，无法分页 |
| MySQL 索引表 | ✅ | ✅ | ✅ | 需 DELETE | 每次读都落库；高 QPS 下就是 Q1 说的问题 |
| **Redis ZSET** | ✅ 按 score | ✅ `ZREVRANGEBYSCORE` | ✅ member 唯一 | ✅ `ZREMRANGEBYRANK` | 内存成本；score 是 float64（见 Q3） |

关键点是 **List 的顺序是「到达顺序」，不是「业务时间顺序」**。本项目的消息会重投（at-least-once）、会被重建、会退避延迟，到达顺序和 `create_time` 顺序并不一致；只有「score 排序」才能把「投递顺序」这个难保证的性质替换成「按业务字段排序」这个容易保证的性质。

**代码依据**
- 写入：`worker/outboxworker.go:317-321`（Lua：`ZADD` + `ZREMRANGEBYRANK`）。
- 读取：`feed/service.go:510`。
- 设计动机：`outboxworker.go:297` 的注释「重复 ZADD 是幂等覆盖」。

**可能的追问**
> 「为什么不用 `ZINCRBY`？」
> 时间线是「覆盖」语义（同一条视频只有固定发布时间），`ZADD` 幂等；热榜才是累加语义，用 `ZINCRBY` 并且要额外做去重（见 `滑动窗口热榜与快照分页.md`）。**用错语义，重复投递就会让排序漂移。**

## Q3. ZSET 的 score 和 member 分别存什么？多个视频发布时间相同，如何保证排序稳定？

**一句话要点**
`score = create_time 的 Unix 毫秒`，`member = video_id`。同分时 Redis 按 member **字典序**排（`"10" < "9"`，不是数值序），所以**不能直接信 Redis 的顺序**；我们把 ZSET 当候选集，取回后在应用层按 `(score DESC, id DESC)` 重排。

**展开**

1. **为什么 score 用 `create_time`**：它不可变。幂等的前提是「重复执行结果一致」；如果 score 是会变的字段（点赞数、热度），重投会让同一条视频的排序漂移，「重复无害」就不成立。
2. **为什么用毫秒不用秒**：
   - 秒级精度下同秒碰撞极多，而 ZSET 同分按字典序 → 顺序直接错；
   - 秒级游标 `score < reqTime` 会把同秒的其余视频全部排除 → 翻页漏数据。
3. **毫秒也不够，仍然会同分**：高发布量下同一毫秒多条是常态。所以排序键升级为 `(create_time, id)`：
   - MySQL 侧：`ORDER BY create_time DESC, id DESC`；
   - Redis 侧：取出后应用层排序，见 `feed/service.go:543`；
   - 游标侧：`(t, id)` 复合比较。
4. **为什么不把 id 编进 score**（例如 `ms * 1000 + id % 1000`）：ZSET 的 score 是 IEEE 754 double，53 位有效位约 `9.007e15`；毫秒时间戳 ~`1.7e12`，乘 1000 后到达微秒量级 ~`1.7e15`，已接近精度临界，再留位给 id 就更不安全；而且取模会碰撞。把 tie-break 放在应用层更简单、更可控。
5. **float64 精度边界**：秒 ~1.7e9 ✅；毫秒 ~1.7e12 ✅（约 5000 倍余量，到公元 2286 年）；微秒 ~1.7e15 ⚠️；纳秒 ~1.7e18 ❌。

**代码依据**
- 写 score：`rabbitmq/timelineMQ.go:111`（`CreateTime.UnixMilli()`）。
- 应用层重排：`feed/service.go:543`。
- 复合游标定义与理由：`feed/entity.go:29`。

**可能的追问**
> 「`id` 是自增的，和发布时间不完全一致，用它做次级键合理吗？」
> 合理。我们不需要 id 和时间的先后一致，只需要**一个稳定的全序**：同一毫秒内按 id 降序是任意但确定的约定，Redis 和 MySQL 都遵守同一条约定，翻页就不会错位。id 由数据库生成、唯一且不变，正好满足。

## Q4. 什么是游标分页？它与传统页码分页有什么区别？

**一句话要点**
页码分页传的是「第几页」（位置），游标分页传的是「上一页最后一条的排序键」（值）。前者在数据插入时会漂移，后者锚定在数据上；前者能跳页，后者只能顺序翻。

**展开**

| 维度 | 页码 / OFFSET | 游标 / Keyset |
|---|---|---|
| 传什么 | `page=3&size=10` | `latest_time=...&latest_id_before=...` |
| 数据库动作 | 扫描并丢弃 `offset` 行 | 索引 seek 到游标位置 |
| 代价 | O(offset + limit) | O(log N + limit) |
| 插入新数据 | 页整体后移 → 重复 | 新数据在游标之前 → 不影响后续页 |
| 能否跳页 | ✅ | ❌（只能顺序翻） |
| 能否给总数 | ✅ | 需要单独 count |
| 缓存 | 页 key 频繁失效 | 游标是值，命中率更稳定 |

本项目的实现细节：

- 请求字段 `latest_time`（毫秒）+ `latest_id_before`，**必须成对**，只给一个直接 400（`feed/handler.go:31`）。
- 响应字段 `next_time` + `next_id_before`，取自**过滤后实际返回的最后一条**，不是「请求的最后一条」。
- 游标是不透明的：客户端不应解析或构造。生产环境建议签名/加密，防止伪造；本项目是公开 Feed，伪造游标最多看到公开数据，所以没做签名。

**可能的追问**
> 「用户想直接跳到第 100 页怎么办？」
> 这个接口不支持，产品上也没有这个入口。短视频 Feed 是无限下滑，不存在「跳页」；排行榜用 `as_of + offset` 是为了稳定翻页，不是给用户跳页。**选择游标就等于放弃了随机访问**，这是明确的取舍。

## Q5. 为什么只保留最近 1000 条热数据？这个阈值如何确定？

**一句话要点**
1000 是按「内存 + 覆盖率 + 重建成本」三者取的折中；它必须按**发布速率**换算成时间窗口来看，而不是一个拍脑袋的条数。

**展开**

1. **内存**：member 是数字 ID 字符串，1000 条在几十 KB 量级；即使将来按频道/标签拆多个 ZSET 也不心疼。
2. **覆盖率**：绝大多数用户刷 Feed 不会翻过前几屏。1000 条覆盖了绝大部分真实请求。
3. **越界代价可接受**：翻出热区走 MySQL 索引游标，是 O(limit) 的范围查询，不会因为「深」而劣化（见 Q18）。
4. **真正的变量是发布速率**：
   - 10 条/秒 → 1000 条 ≈ 100 秒的窗口；
   - 100 条/秒 → 只有 10 秒。
   所以判断标准应该是「**热区要覆盖多长的会话窗口**」：例如 `容量 ≥ 峰值发布 QPS × 期望覆盖秒数`。
5. **怎么验证选得对不对**：看两个指标——热区命中率（热区请求数 / 总请求数）、冷区 QPS。如果冷区 QPS 持续偏高，说明容量不够或发布太快。
6. **实现约束**：容量已经提成 `video.TimelineCapacity = 1000`（`video/timeline.go:8`），写入裁剪、空 ZSET 重建、后台对账三处共用，不会再出现「重建完立刻被裁」的常量漂移。剩余不足是它仍然**静态**：不会按发布速率自动调整；真正产品化时要把它做成配置，并按「峰值发布 QPS × 期望覆盖秒数」推导。

**代码依据**
- 常量：`video/timeline.go:8`。
- 写入裁剪（Lua 内引用该常量）：`worker/outboxworker.go:310`、`:327`。
- 空 ZSET 重建同样取该常量：`feed/service.go:315-360`。
- 后台对账同样取该常量：`feed/service.go:973`。
- 注意：`ListLatest` 的单页上限 50 是接口层限制，与热区容量无关，不要混为一谈。

**可能的追问**
> 「为什么不按时间裁剪，比如只留最近 1 小时？」
> 按时间裁剪更符合直觉，但边界不稳定：发布低谷时 1 小时可能只有几十条，热区太小；发布高峰时 1 小时可能是几十万条，内存不可控。**按条数封顶保证内存上界，按时间封顶保证覆盖语义**，两者只能选一个作为硬约束。本项目选内存可控，把时间覆盖当作结果而不是承诺。

# 二、第二层：实现细节

## Q6. Redis 里保存的是用户自己的 Feed，还是所有关注作者发布的视频？写扩散和读扩散各有什么优缺点？

**一句话要点**
本项目的 `feed:global_timeline` 是**全局公共时间线**（所有作者的最新视频），既不是用户级写扩散，也不是关注流合并；关注流 `ListByFollowing` 走的是 MySQL 的**读扩散**。

**展开**

先分清三条 Feed：

| Feed | 数据来源 | 扩散方式 |
|---|---|---|
| 最新（广场）`ListLatest` | Redis 全局 ZSET + MySQL 冷区 | 单份全局列表，写一次所有人共用 |
| 关注 `ListByFollowing` | MySQL JOIN 关注表 | 读扩散（查询时合并） |
| 热门 `ListByPopularity` | 分钟桶 + 快照 | 与关注关系无关 |

**写扩散（fan-out on write）**：发布时把视频 ID 写进每个粉丝的时间线 ZSET。

- 优点：读极快，一次 `ZRANGE` 就够；读路径不需要 JOIN。
- 缺点：
  - 写放大：100 万粉丝就是 100 万次 `ZADD`；
  - 存储放大：每个用户一份 1000 条，N 个用户 N 份；
  - 僵尸用户浪费：不登录的用户也维护时间线；
  - 关注/取关要回填或删除历史：取关还要知道「该作者的哪些视频在列表里」，通常要把 member 设计成 `authorID:videoID` 或按作者分 key；
  - 大 V 问题：粉丝数决定写成本，必须给大 V 单独降级为拉模式。

**读扩散（fan-out on read）**：查询时把关注的作者内容合并。

- 优点：写便宜、无存储放大、关注关系变更立即生效、不会给僵尸用户维护数据。
- 缺点：
  - 读成本与关注数成正比：5000 个关注就是 5000 路数据源；
  - 分页要做 k 路归并，每路都要各自游标，合并后再取一页；
  - 深度翻页时每路都要 seek，代价高。
- 本项目的实现：MySQL `author_id IN (子查询)` + `(create_time,id)` 游标（`feed/repo.go:49-71`），并对**这一页的 ID 列表 + 游标**做 Redis 缓存（按完整游标做 key，不缓存渲染结果），命中后重新走 `GetVideoByIDs` 装配内容。

**结论**：本项目的「最新」是第三种形态——**单份全局列表**，既没有写扩散放大，也没有读扩散合并，代价是它不是个性化 Feed。关注流才是个性化的，选择了读扩散，因此 5000 关注的场景是它的弱项（见 Q17）。

**可能的追问**
> 「那你的热时间线算写扩散吗？」
> 不算。写扩散的定义是「一条内容写进 N 个用户的收件箱」；这里是一条内容写进**一个全局列表**。它的成本与粉丝数无关，收益是所有人都能读。

## Q7. 热时间线超过 1000 条后，如何原子地淘汰旧数据？并发写入时如何保证数量符合预期？

**一句话要点**
写入和裁剪合并成一段 **Lua 脚本**，一次 `EVAL` 在 Redis 内单线程执行完 `ZADD + ZREMRANGEBYRANK + ZCARD`：不存在「刚加完还没裁」的 1001 条窗口，并发写入也会被串行化，最终基数严格 ≤ 1000。

**展开**

1. **当前写法**（`worker/outboxworker.go:310`、脚本在 `:327`）：

   ```lua
   redis.call('ZADD', KEYS[1], ARGV[1], ARGV[2])
   redis.call('ZREMRANGEBYRANK', KEYS[1], 0, -(tonumber(ARGV[3]) + 1))
   return redis.call('ZCARD', KEYS[1])
   ```

   `ARGV` 是 `[score, member, capacity]`，容量来自 `video.TimelineCapacity`。`ZREMRANGEBYRANK 0 -(N+1)` 的意思是「删掉排名 0 到倒数第 N+1 名」，即保留 score 最高的 N 条。

2. **为什么这样就原子**：
   - Redis 执行脚本期间不会插入其他客户端的命令，`ZADD` 和裁剪对外是一个动作；
   - 不再有「写入成功、裁剪失败」的独立失败点（旧实现里裁剪失败只打日志）；
   - 并发消费者无论怎么交错，结果都等价于按某个顺序逐条执行「加一条 + 裁到 N 条」，最终 ≤ 1000。

3. **仍然要诚实说明的边界**：Lua 保证**不被穿插**，但**不回滚运行时错误**。如果脚本执行到一半遇到类型错误（例如 key 被别的类型占用），已经执行的 `ZADD` 不会撤销。这里的命令都非常简单、类型固定，正常路径不会出现；真出现时靠 5 分钟对账任务的裁剪兜底，而不是假设 Redis 事务有 rollback。

4. **并发/故障下会发生什么**：

   | 场景 | 结果 |
   |---|---|
   | 两个消费者同时写 | 脚本串行执行，最终 ≤1000，没有超量窗口 |
   | 写入后进程崩溃 | 脚本没有「加了没裁」的独立失败点；运行时错误不回滚，按上一条兜底 |
   | 迟到的旧视频事件 | 写入后立刻处于最小 score，被同一次脚本裁掉 —— 这是**期望行为** |
   | 脚本本身报错 | 极少数情况（类型/内存），日志可见，对账任务下一轮把基数裁回上限 |

5. **为什么「收敛」而不是「漂移」**：裁剪不是「删掉我刚加的那条」，而是「保留当前最高的 1000 条」。它不依赖客户端的旧视图，所以并发执行不会丢更新，结果由集合本身决定。
6. **其他可选做法**：
   - **`MULTI/EXEC`**（go-redis 的 `TxPipeline`）：同样能保证不穿插，但要多一次 RTT 和事务开销；
   - **定时裁剪**：接受短暂超量，用后台任务兜底，换取写路径更短。本项目已经有 5 分钟对账，但它只补不删，不能替代写入侧裁剪。
7. **顺序不能反**：先 `ZADD` 再裁。新成员的 score 是当前最大的，裁剪尾部不会误删它；反过来先裁再加，结果会稳定多出一条。

**代码依据**
- Lua 写入 + 裁剪：`worker/outboxworker.go:310`（`Eval`）、`:327`（脚本）。
- 容量常量：`video/timeline.go:8`。
- 对账侧只补不删：`feed/service.go:973`。

**可能的追问**
> 「为什么不用 `ZREMRANGEBYSCORE -inf watermark`？」
> 那需要先算出「第 1000 名的 score」，多一次查询且有竞态；按 rank 裁剪一步到位。代价是**同分组合会被切断**，这正是冷热边界必须回 MySQL 的原因（见 Q10）。

> 「Lua 是不是就没有任何风险了？」
> 不是。Lua 解决的是「原子可见性」，不是「业务回滚」。脚本里不要写「先占位、失败再撤销」这种依赖回滚的逻辑；这里只做幂等写 + 幂等裁，天然适合脚本。

## Q8. 用户第一次请求 Feed 时返回哪些字段作为下一页游标？只用时间戳是否足够？

**一句话要点**
返回 `next_time`（毫秒）+ `next_id_before`（视频 ID），**必须成对使用**。只给时间戳不够：同一毫秒可能有多条视频，纯时间游标会把它们当成一个不可分的整体。

**展开**

1. **响应**（`feed/entity.go:42-43`）：

   ```json
   {
     "video_list": [...],
     "next_time": 1761300005123,
     "next_id_before": 987,
     "has_more": true
   }
   ```

2. **请求**：`latest_time` + `latest_id_before`。handler 会校验：只传一个、或 id 为 0、或 time ≤ 0，直接 400，避免「半个游标」被当成首页处理，导致重复拉第一页。
3. **只给时间戳的两种坏结果**：
   - **漏**：`WHERE create_time < ?` 会把游标那一毫秒的其余视频全部排除；
   - **重/乱**：MySQL 对相同 `create_time` 的行没有稳定顺序，两次查询的相对次序可能变化，相邻页边界就会重复或跳过。
4. **为什么是毫秒**：减少同分概率，但**不能消除**；所以毫秒只是「降低碰撞」，id 才是「消除歧义」。两者缺一不可。
5. **游标取哪一条**：必须是本页**实际返回**的最后一条。如果先按 ZSET 取 10 条、再因为视频被删过滤成 8 条，游标仍要取第 8 条，否则第 9、10 条会被跳过。删除路径现在会 `ZREM` 热时间线，但并发窗口内仍可能过滤，所以这条规则不能省。
6. **`has_more`**：统一用**多取一条**判断——查 `limit+1` 条，`len > limit` 才是还有下一页，返回前截断到 `limit`。热段因删除而不足时，缝合会用冷段按缺口补；补不到只可能是真的到底，所以 `has_more` 不会因为「热区少了几条」提前变成 false。`ListLatest`、纯 DB 降级、关注流三处一致。

**代码依据**
- 游标解析与成对校验：`feed/handler.go:31-39`。
- `limit+1` 探测与截断：`feed/service.go:384`、`:469-472`。
- 响应赋值：`feed/service.go:474-480`。
- 纯 DB 降级同样返回复合游标：`feed/service.go:561-585`。
- 关注流同样的探测方式：`feed/service.go:648-675`。

**可能的追问**
> 「`latest_time` 是秒还是毫秒？接口之间统一吗？」
> 统一毫秒。历史上 `ListByFollowing` 用过秒、`ListLatest` 用毫秒，是契约缺陷，现在两处都统一为毫秒（`feed/service.go:594` 的注释明确写了这一点）。这类「同名字段不同单位」的坑，比逻辑 bug 更难排查。

## Q9 ⭐. 用户翻页过程中插入新视频，为什么 offset 分页会重复或漏项？游标算法如何避免？

**一句话要点**
offset 是「位置」，插入会让所有后续位置整体后移，于是上一页末尾被重新看到；游标是「值」，新视频的排序键在游标之前，天然被 `WHERE ... < 游标` 排除。但游标只对**在头部追加**的数据成立，回填到游标之后的数据仍会漏（见 Q14）。

**展开**

1. **offset 的重复**：用户看完第 1 页（最新 10 条）后，又发布了 3 条。第 2 页 `OFFSET 10` 取到的是「新的第 11~20 条」，而原来的第 8~10 条被挤到了第 11~13 位 → 页首重复 3 条。
2. **offset 的漏项**：如果这期间删了 3 条，整体前移，原来的第 11~13 条变成第 8~10 条，第 2 页从第 14 条开始 → 漏 3 条。
3. **游标的做法**：

   ```sql
   WHERE (create_time < :t) OR (create_time = :t AND id < :id)
   ORDER BY create_time DESC, id DESC
   LIMIT :limit
   ```

   新视频的 `(create_time, id)` 大于游标，不满足条件，**不参与后续分页**；已看过的最后一条也被严格排除（同毫秒用 id 区分）。
4. **热区同样**：`ZREVRANGEBYSCORE` 的 `maxScore = reqTime`（含），然后在应用层丢掉 `score == reqTime && id >= cursor.ID` 的成员（`feed/service.go:533-536`）。这样既不会漏掉同毫秒中 id 更小的，也不会重复 id 更大的。
5. **仍然会破坏承诺的三种情况**：
   - 新数据被**回填到游标之后**（典型：多实例时钟回拨、手工导入历史数据、修改 `create_time`）；
   - 排序键本身被更新（本项目 `create_time` 不可变，规避了）；
   - 客户端不原样回传游标，或者自己构造页码。

**代码依据**
- MySQL 复合条件：`feed/repo.go:36`。
- Redis 侧过滤：`feed/service.go:533-536`。
- 排序对齐：`feed/service.go:543`。

**可能的追问**
> 「那你能保证绝对不重不漏吗？」
> 不能无条件保证。准确表述是：**排序键不可变、数据只在头部追加时，同一游标序列不重复、不遗漏当时已存在的数据**。删除、取消关注、历史回填都会让「不遗漏」失效，但不会造成重复。这个边界在 Q14 展开。

## Q10 ⭐. 游标到达热冷分界点时，如何分别从 Redis 和 MySQL 查询？

**一句话要点**
先取 ZSET 最小 score 当 watermark；`游标 > watermark` 走热区 Redis，`游标 ≤ watermark` 走冷区 MySQL；热区不足一页时，用最后一条的 `(create_time,id)` 去 MySQL 向下补齐，**不回写 ZSET**。这里取的是 `limit+1` 条，多出的一条只用于判断 `has_more`。

**展开**

1. **取水位线**：`ZRANGE key 0 0 WITHSCORES` 拿最小 score（ZSET 按 score 升序，下标 0 就是最小）。
2. **判断**（`feed/service.go:373-388`）：

   ```
   cursor == nil        → 首页，必在热区
   reqTime > watermark  → 热区：ZREVRANGEBYSCORE
   reqTime <= watermark → 冷区：repo.ListLatest（整页 MySQL）
   ```

3. **为什么 `==` 要走冷区**（这是最容易答错的一点）：

   - `ZREMRANGEBYRANK 0 -(TimelineCapacity+1)` 是**按排名**裁剪，可能在最小 score 的同分组合内部切断，导致热区最老那一毫秒的记录**不完整**；
   - 如果游标正好落在 watermark，用 ZSET 继续翻，就会漏掉被裁掉的那部分；
   - 游标一旦 `> watermark`，该 score 组必然完整：如果某分数组有成员被裁，说明它排在第 1000 名之后，那它的 score 只会**≤** watermark，不可能大于 watermark（反证法）。

4. **热区查询**（`feed/service.go:499`）：

   ```
   maxScore = reqTime（含）
   count    = want + ZCOUNT(key, reqTime, reqTime)   ← 补上同毫秒的兄弟，避免它们占满名额
   ZREVRANGEBYSCORE key maxScore -inf LIMIT 0 count
   → 过滤掉 score==reqTime && id>=cursor.ID
   → 按 (score DESC, id DESC) 排序
   → 截断到 want（= limit + 1）
   ```

5. **缝合**（`feed/service.go:424-464`）：热区凑不满 `want` 时，取**最后一条实际装配成功的视频**的 `(CreateTime, ID)` 作为冷游标，`remainLimit = want - len(baseVideos)`，去 MySQL 补。两个容易漏的细节：
   - 热区为空时（边界页的头部视频被删光），回退用入参游标，避免 nil；
   - 冷区查询失败**直接返回错误**，不能返回短页——否则客户端会把「数据库故障」误认为「没有更多了」。
6. **为什么冷数据不回写 ZSET**：一旦回填，用户多翻几页就能把历史数据灌进只保留 1000 条的热池，把真正的新视频挤出去——「冷数据污染热点池」，热区命中率会归零。
7. **准确性提醒**：热区「不查 MySQL」只指**排序**；拿到 ID 后仍要 `GetVideoByIDs` 装配实体、`BatchGetLiked` 查点赞，这两步可能回源 MySQL。

**代码依据**
- 水位线：`feed/service.go:315`、`:373`。
- 分支：`feed/service.go:388`。
- 热区：`feed/service.go:499`。
- 缝合：`feed/service.go:424-464`。

**可能的追问**
> 「如果 watermark 那一刻刚好有 500 条同分视频，会被裁掉一部分吗？」
> 会。裁剪按排名，不按分数组完整性。这正是「边界走冷区」的原因；也是为什么不能简单用 `score <= watermark` 在 Redis 里补齐——那一段本来就不可信。

## Q11. 热数据和冷数据存在时间戳相同的记录，如何去重并维持严格排序？

**一句话要点**
用 `(create_time, id)` 做全序：冷区查询是 `(t,id)` **严格小于**游标；热区在应用层丢掉 `score==t && id>=cursor.ID` 的成员；最终两段都按 `(score DESC, id DESC)` 排。同一视频在 ZSET 里只会有一个 member，不存在「同一条视频重复出现」。

**展开**

1. **「重复」其实有两个来源**，要分开答：
   - **同一条视频在 ZSET 内重复**：不可能。ZSET 的 member 唯一，重复 `ZADD` 只覆盖 score。
   - **同一条视频在热区页和冷区补页里各出现一次**：由游标语义排除。冷区从「热区最后一条」的 `(t,id)` 之后开始，严格不含它。
2. **同毫秒的多条视频**：
   - 冷区：`create_time = t AND id < cursor.ID`；
   - 热区：`score == t` 的成员里，只保留 `id < cursor.ID` 的；
   - 两侧对「同毫秒内的顺序」使用同一约定（id 降序），所以合并后不会出现「A 在热区排前、在冷区排后」的错位。
3. **为什么要应用层重排**：Redis 对同 score 的 member 按字典序（`"100" < "99"`），和数值序不一致。`feed/service.go:543` 按数值 id 重排后，才和 MySQL 的 `ORDER BY id DESC` 对齐。
4. **唯一的破绽**：如果同一条视频在 MySQL 和事件里的 `create_time` 不一致（比如发布后修改了时间），两边对它的排序位置认知不同，就可能错位。本项目的 `create_time` 是 `autoCreateTime` 且不提供修改入口，规避了这一点。
5. **如果真出现异常重复**（例如数据修复导致）：按 ID 去重、保留首次出现，再用最后一条游标补足；但这是兜底，不是常态路径。

**代码依据**
- 热区同分过滤：`feed/service.go:533-536`。
- 应用层排序：`feed/service.go:543`。
- 冷区复合比较：`feed/repo.go:36`。
- ZSET member 幂等：`worker/outboxworker.go:319`。

**可能的追问**
> 「为什么不直接在 score 里编入 id，让 Redis 自己排好？」
> 精度不够（double 53 位，毫秒乘 1000 已接近边界），而且会引入取模碰撞。应用层只对「一页量级」的候选排序，成本 O(k log k)，k ≤ limit + 同毫秒条数，完全可接受。

## Q12 ⭐. 冷数据返回 20 条，但与热数据合并后有 5 条重复，如何补足一页？需要循环回源吗？

**一句话要点**
按现在的游标语义，这种重复**不应该发生**：冷区从「最后一条实际装配成功的 `(t,id)`」之后开始，和热区天然不相交。热区不足时补**一次**冷区就够，不需要循环回源——因为 MySQL 是 ZSET 的超集，且冷区查询没有任何后置过滤。当前实现的 `has_more` 用 `limit+1` 探测，短页也不会误报「到底了」。

**展开**

1. **为什么设计上不会重复**：
   - 热区给出的是 ID 列表，补页游标取的是「最后一条**成功装配**的视频」的 `(create_time, id)`；
   - MySQL 条件是 `(create_time,id) < 游标`，严格不含游标本身；
   - 所以冷区返回的每一条都排在热区最后一条之后，集合不相交。
2. **什么情况下热区不足**（高频追问）：
   - 跨过冷热边界：ZSET 里只剩 6 条，本页还要 10 条；
   - 热区里有视频被删除：`GetVideoByIDs` 装配时被过滤；
   - 删除路径现在会 `ZREM` 热时间线，但「删除」和「读」之间仍有并发窗口，过滤逻辑不能省。
3. **为什么补一次就够**：
   - 冷区查询直接返回 MySQL 行，**没有后置过滤**（不做权限、屏蔽、删除判断，删除的视频在库里已经不存在）；
   - 因此「冷区返回条数 < `remainLimit`」只可能意味着**真的到底了**，再查一次也是空；
   - 反过来，如果将来给冷区加了后置过滤（屏蔽作者、私密视频），这个前提就破了，那时才需要「带上限的循环」。
4. **`has_more` 现在是准的**：查询时取 `limit+1` 条，`len > limit` 才是还有下一页，返回前截断。即使热段因为删除被过滤掉 2 条，也会用冷段按 `want - len` 补回；补不到只可能是库里也没了，此时 `has_more` 才会变成 false，客户端不会提前停止。
5. **删除视频的清理**：`VideoService.Delete` 删库后会按 `video_id` `ZREM` 热时间线（100ms 预算，失败只记日志）。这样删除的视频不再白占名额，减少「热区取 10 条、装配只剩 8 条」的概率；失败残留由读路径过滤 + 对账任务兜底。
6. **「5 条重复 → 补 5 条」这个问法本身是个陷阱**：重复说明游标契约被破坏，正确做法是修根因；如果真去重后补 5 条，补回来的数据可能又和已返回的重复。不是「补数量」，而是「从新游标继续取」。

**代码依据**
- 单次缝合：`feed/service.go:424-464`。
- 游标取最后一条装配成功的视频：`feed/service.go:431-439`。
- `has_more` 计算与截断：`feed/service.go:469-472`。
- 删除时 `ZREM`：`video/video_service.go:107-116`。
- 冷区无后置过滤：`feed/repo.go:29-46`。

**可能的追问**
> 「那你的接口返回 9 条，前端会认为没有更多了吗？」
> 不会了。`has_more` 是独立探测出来的，不是用「本页满没满」推断的：服务端实际查了 `limit+1` 条，只是把多出来的一条丢掉。这是本轮修掉的缺口，旧实现确实是 `len == limit`。

> 「如果冷区查出来正好 0 条，但热区又被过滤成 5 条，会不会死循环？」
> 不会，因为根本不循环。补一次拿到 0 条就说明库里也没有了，直接返回短页并令 `has_more=false`。

## Q13. 热时间线只留 1000 条，如果用户一次跳过很多条，或者冷数据时间范围与热数据重叠，算法如何工作？

**一句话要点**
这个接口没有「跳过 N 条」的能力——游标是值不是下标。用户想跳得远，只能拿一个很老的游标，那时游标早已低于 watermark，直接走冷区 MySQL 索引 seek，与跳多远无关。冷区时间范围与热区重叠是常态，但一页最多是「热段 + 一次冷段补尾」，两段用不重叠的复合游标衔接，不会重复。

**展开**

1. **「跳过很多」在游标语义下是什么**：客户端保存了上次的 `(t,id)`，隔了很久再来请求。`t` 通常远小于 watermark → 冷区整页查 MySQL，O(log N + limit)。
2. **如果跳过后的游标仍大于 watermark**：说明这期间发布量不大，热区还覆盖得到，走 Redis，同样正确。
3. **冷热时间范围重叠**：热区本来就是冷区（MySQL）的一个前缀，重叠是设计的一部分。关键在于：
   - 冷区请求整页只查 MySQL，不会回头再读热区；
   - 只有热区路径才会向下补冷，且补的起点严格在热段最后一条之后。
   所以不会出现「同一页里热一段、冷一段又重复」。
4. **边界情况**：
   - `cursor == nil`：首页，一定热区；
   - ZSET 为空：触发 singleflight 重建，重建后递归一次（`EMPTY_DB` 防死循环）；
   - ZSET 只有 1 条：watermark = 该条 score，请求游标若 ≤ 它就走冷区；
   - 游标在未来（时钟错乱）：热区会把当前所有数据都当作「游标之前」，返回最新一页；这是可接受的降级，不会越界。
5. **这套设计换来的约束**：不支持随机跳页、不支持「第 N 页」。如果产品要「回到上次看到的位置」，客户端保存游标即可，比保存页码可靠。

**代码依据**
- 冷区整页：`feed/service.go:388-408`。
- 热区整页：`feed/service.go:410-422`。
- 空 ZSET 重建：`feed/service.go:310-370`。

**可能的追问**
> 「客户端传了一个伪造的游标，会怎样？」
> 最坏是查到一页公开数据，或者空页。没有越权风险；如果要防刷/防爬，应该在上层做签名和限流，而不是靠游标保密。

## Q14 ⭐. 你声称「翻页无重复无漏项」，这个结论的前提是什么？删除视频、取消关注、关注关系变化后还成立吗？

**一句话要点**
成立的前提是：**排序键不可变、数据只在头部追加、MySQL 是完整超集、客户端原样回传游标**。删除和关注变更只保证「不重复」，不保证「补齐」；跨页也不提供快照一致性。

**展开**

1. **必须同时成立的前提**（少一条就会破）：

   | # | 前提 | 破坏后的表现 |
   |---|---|---|
   | 1 | `create_time` 不被修改 | 排序位置漂移 → 可能重复或跳过 |
   | 2 | `id` 稳定且唯一 | 同毫秒内无全序 → 边界重复/漏项 |
   | 3 | 新数据只会在头部追加 | 回填到游标之后 → 漏项 |
   | 4 | MySQL 是完整数据源，ZSET 只是前缀 | 热区缺失且不补 → 漏项 |
   | 5 | 客户端原样回传 `(next_time,next_id)` | 传错/自己算页码 → 重复 |
   | 6 | 热段与冷段用不重叠的复合游标衔接 | 冷段从热段末尾重新开始 → 重复 |
   | 7 | `limit` 不被中途改变 | 游标语义仍成立，但页大小不稳定 |

2. **删除视频**：已返回的页不受影响；后续页不会再有它。不重复 ✅，但「页变短」是必然的——这不是漏项，是数据没了。删除路径现在会先删库、失效实体缓存，再按 `video_id` `ZREM` 热时间线（`video/video_service.go:107-116`），所以它不会再白占热区名额；并发窗口内残留的 member 仍由 `GetVideoByIDs` 过滤。`has_more` 因为用 `limit+1` 探测，不会因为页短而误报到底。
3. **取消关注**：关注流按**当前**关注集合查询，取关后该作者内容立即不再出现；`social` 服务在关注/取关时会按 `accountID` 清掉该账号所有关注流页缓存（`social/service.go:98` 的 `DelByPattern("feed:listByFollowing:*:accountID=%d:*")`），所以不会读到旧的关注关系。但「不重复」仍成立，「补齐」不成立。
4. **新关注一个人**：他过去的视频排序键在游标之后，本次会话不会补进来；刷新/重新从首页开始才能看到。这是游标语义的自然结果，不是 bug。
5. **关注流缓存的新鲜度**（本轮已修）：
   - 缓存内容改成**只存 ID 列表 + 游标**，命中后重新走 `GetVideoByIDs` 装配，`IsLiked`、点赞数、是否已删除等动态字段不再被冻结；
   - **首页 30s、后续页 24h**：新视频只会插在第一页之前，后续页的游标锚定在旧数据上，发布不会影响它们；
   - 所以「发布后最长一天刷不到新视频」已经不成立，最坏是首页 30s 的延迟；
   - 仍然存在的取舍：发布不会主动扇出失效所有粉丝的首页缓存，靠短 TTL 收敛（`feed/service.go:43`、`:654-657`）。
6. **应该怎么表述简历**：
   - ❌「翻页绝对无重复无漏项」；
   - ✅「在单向前插的数据集上，基于 `(create_time,id)` 的游标翻页不重复、不遗漏；删除与关注变更场景只保证不重复，`has_more` 由 `limit+1` 独立探测」。

**代码依据**
- 游标严格比较：`feed/repo.go:79-85`。
- 删除视频：`video/video_service.go:107-116`；装配兜底过滤：`feed/service.go:123`（`GetVideoByIDs`）。
- 关注流缓存失效：`social/service.go:98`（按 `accountID` 的 `DelByPattern`）。
- 关注流缓存结构（只存 ID）：`feed/service.go:101-111`、`:626-638`。
- 关注流缓存 TTL：`feed/service.go:43`、`:654-657`。

**可能的追问**
> 「面试官说：那你这个『无漏项』是假的？」
> 不要硬扛。回答：「『不漏』限定在查询时刻已存在且未被删除的数据；删除、取关、历史回填都会让这一页少东西，但不会让同一页出现两次。工程上我把这个边界写进了文档，没有把它包装成绝对保证。」这比坚持绝对结论得分高。

## Q15. MySQL 冷数据排序使用什么索引？`user_id`、`created_at`、`id` 的索引怎么设计？

**一句话要点**
项目里是全局时间线，没有 `user_id` 过滤，排序键是 `(create_time DESC, id DESC)`；`idx_videos_create_time` 加上 InnoDB 二级索引隐含的主键，逻辑上等价 `(create_time, id)`，理论上可以支撑反向索引扫描。但 `OR` 条件是否真的走索引必须用 `EXPLAIN` 验证。关注流如果要走同一套游标，应该补 `(author_id, create_time, id)`。

**展开**

1. **全局时间线**（`ListLatest`）：
   - 索引：`idx_videos_create_time (create_time DESC)`；InnoDB 二级索引叶子节点带主键 → 逻辑上等价 `(create_time, id)`；
   - `ORDER BY create_time DESC, id DESC` **理想情况下**可以沿索引反向扫描，不需要 filesort；
   - `WHERE (create_time < ?) OR (create_time = ? AND id < ?)` 是同一索引上的两段范围。优化器**可能**合并成一次 range，也可能选择 index merge 或回退到扫描 + filesort，**必须用 `EXPLAIN` 实测**，不能因为「索引里有这两个列」就断言没有 filesort。
2. **如果优化器不买账**：改写成行构造器比较：

   ```sql
   WHERE (create_time, id) < (?, ?)
   ```

   语义完全等价，更容易被识别成单段范围扫描（MySQL 8 支持行构造器走索引）。这是低成本的兜底；本轮**没有改 schema**，因为是否真的走索引要以线上 `EXPLAIN` 为准，不能凭空加索引。
3. **为什么不能只建 `(create_time)` 然后靠主键排序**：二级索引里的主键是「附带」的，`ORDER BY create_time, id` 能利用；但如果查询里还有别的过滤/连接，优化器可能选择别的执行计划，仍然要 `EXPLAIN` 确认。
4. **关注流**（`ListByFollowing`）：
   - 当前是 `author_id IN (子查询)` + `ORDER BY create_time DESC, id DESC`，`videos.author_id` 只有单列索引；
   - 5000 个作者时，优化器可能选择「扫全局 create_time 索引 + 过滤 author_id」，扫描量不可控；
   - 更合适的索引是 `(author_id, create_time DESC, id DESC)`：每个作者内部天然有序，可以做 k 路归并；但 MySQL 对 `IN + ORDER BY` 仍可能排序，需要实测。
5. **通用原则**：**索引顺序 = 等值列 → 排序列 → tie-break 列**。等值条件在前，范围/排序在后；tie-break 放最后，保证分页边界稳定。

**代码依据**
- 索引定义：`video/video_entity.go:16`。
- 查询与注释：`feed/repo.go:20-46`。
- 关注流查询：`feed/repo.go:49-71`。

**可能的追问**
> 「为什么不用覆盖索引把整行都带上？」
> 页面只需要 10~50 行，回表成本可以接受；把 `title/play_url/cover_url` 都塞进索引会让索引膨胀、写入变慢。真正需要优化时，用「延迟关联」（先取 ID 再回表）比宽覆盖索引更划算。

## Q16. 如果 Redis 热数据因为淘汰、故障或重建而缺失，如何恢复时间线？

**一句话要点**
分三种情况：**整体不可用** → 直接降级 MySQL；**ZSET 为空** → singleflight 从 MySQL 取最新 1000 条重建；**部分缺失** → 每 5 分钟对账一次，用 MySQL 最新 1000 条补齐缺失 member（只补不删）。

**展开**

1. **Redis 整体不可用**：`ListLatest` 开头判断 `rediscache == nil` 或 `ZRANGE` 报错，直接走 `listLatestFromDB`（`feed/service.go:311-322`）。可用性优先，延迟上升。
2. **ZSET 为空**（冷启动、被清空、key 过期）：
   - 用全局 singleflight key 收敛并发，只有一个请求去 MySQL 取最新 1000 条；
   - `ZADD` 批量重建，再裁到容量上限；
   - MySQL 也为空时返回 `EMPTY_DB` 哨兵，**切断「空 → 重建 → 还是空 → 再重建」的递归**；
   - 重建完成后让等待的请求重新查一遍（递归一次）。
3. **为什么 singleflight key 是全局的，不是按游标**：重建结果与游标无关，都是「最新 1000 条」。按游标做 key 会让 N 个用户触发 N 次重建，正好在 Redis 故障恢复时把 MySQL 打爆。
4. **部分缺失：5 分钟对账**（`feed/service.go:951`、`:973`）：
   - 每 5 分钟读 MySQL 最新 1000 条、读 ZSET 全部 member，做差集；
   - 只 `ZADD` 缺失的成员，**不删除**「ZSET 里有、MySQL 快照里没有」的成员——对账期间并发发布的新视频可能不在本次 MySQL 快照里，删「多余」会误伤它们；
   - 补完仍按容量裁剪一次，维持上限；
   - 单次成本：1000 行 MySQL 查询 + 1000 个 member 的 `ZRANGE` + 差量 `ZADD`，5 分钟一次，可以忽略；
   - 多实例部署时每个 API 实例都会跑，但操作是幂等的（`ZADD` 覆盖 + 差集为空就直接返回），不会互相破坏。
5. **仍然存在的窗口**：
   - 从丢失到被发现最多 5 分钟，这段时间里相关页可能少内容；
   - 只能修复「最近 1000 条」范围内的空洞；更老的记录本来就不在热区容量内，不需要修；
   - 「ZSET 里有脏 member」不靠对账删除，靠删除路径的 `ZREM` 和读时装配过滤；对账刻意不做双向同步，避免和写入侧抢数据。
6. **重建的成本**：1000 行查询 + 一次批量 `ZADD`，预算 2s（`feed/service.go:343`）；如果发布量很大，重建期间新视频可能已经进来，重建是「追加 + 覆盖」，不会删掉新数据。

**代码依据**
- 空 ZSET 重建：`feed/service.go:310-370`。
- 降级：`feed/service.go:311-322`。
- 重建写入与裁剪：`feed/service.go:342-357`。
- 周期对账：`feed/service.go:951`（启动）、`:973`（实现）。
- 对账周期常量：`feed/service.go:38`。

**可能的追问**
> 「重建时如果 MySQL 也挂了怎么办？」
> 返回错误，接口 5xx/503。此时没有可信数据源，硬撑返回空列表会误导用户。项目里的回源过载保护已经收敛到 `dbguard`（按连接池上限的一半设置闸门），超限返回 `errDBOverloaded`，HTTP 层分类为 503；重建失败则直接报错，让客户端退避重试。

## Q17. 如果用户关注了 5000 个作者，Feed 是查询时合并多个作者的内容，还是提前写入用户时间线？两种方案复杂度分别是什么？

**一句话要点**
本项目关注流是**查询时合并**（读扩散）：MySQL `author_id IN (关注子查询)` + 游标。5000 关注下读成本高且依赖索引；写扩散读快但写放大、存储放大、大 V 问题严重，通常用「普通用户推、大 V 拉」的混合方案。

**展开**

1. **本项目的实际实现**：`ListByFollowing` 直接 JOIN/子查询关注表，按 `(create_time,id)` 游标取一页（`feed/repo.go:49-71`），再加一层按完整游标做 key 的 Redis 页缓存。缓存里**只存 ID 和游标**，命中后重新装配实体与点赞状态，动态字段不会被冻结。
2. **读扩散的复杂度**：
   - 每次读：关注集合大小 F 的过滤 + 按时间取一页，最好情况 O(log N + limit)（走全局时间索引 + 过滤），最坏情况要扫很多行才凑够 limit（关注的人都很久没发）；
   - 分页：单一数据源，游标简单；
   - 关注变更：立即生效，无需回填；
   - 写：发布只写一条，成本与粉丝数无关。
3. **写扩散的复杂度**：
   - 每次发布：粉丝数 F 次 `ZADD` + 裁剪，大 V 发布 100 万粉丝就是 100 万次写；
   - 存储：每个活跃用户 1000 条，总内存 ≈ 活跃用户数 × 1000；
   - 关注/取关：关注要回填该作者最近 1000 条；取关要删除该作者的所有条目，member 里必须能识别作者（`authorID:videoID` 或按作者分 key）；
   - 读：O(log N + limit)，最便宜。
4. **怎么选**：比较 `读 QPS × 读成本` 和 `发布 QPS × 平均粉丝数 × 写成本`。Feed 是读多写少，通常倾向写扩散；但**大 V 的长尾**会破坏这个平均值，所以工业界用混合：粉丝数低于阈值推、高于阈值拉，读时再合并少量大 V。
5. **本项目的取舍**：用户规模小、关注数上限没有硬约束，读扩散实现简单、无存储放大、关注关系实时生效，是合理选择。**5000 关注是它的最坏输入**，需要靠 `(author_id, create_time, id)` 索引和页缓存兜住；如果真要做大，第一步是给关注数设上限或改混合模式。
6. **别忘了缓存新鲜度**（本轮已修）：关注流首页缓存 30s、后续页 24h。新视频只会影响首页，后续页的游标锚定在旧数据上，所以长 TTL 不会让用户「看不到新视频」；最坏是首页 30s 的延迟。这比「发布时扇出失效所有粉丝」便宜得多。
7. **剩下的真实弱项**：读扩散的合并成本没有变——5000 关注仍然是弱项；缓存只能挡住重复读，挡不住首次回源。真要做大，先给关注数设上限或改混合扩散。

**代码依据**
- 读扩散查询：`feed/repo.go:49-71`。
- 页缓存 key 含完整游标：`feed/service.go:669`。
- 缓存只存 ID：`feed/service.go:101-111`、`:626-638`。
- 缓存 TTL（首页 30s / 后续页 24h）：`feed/service.go:43`、`:654-657`。

**可能的追问**
> 「5000 个关注，MySQL 会怎么执行？」
> 取决于优化器：可能先把子查询物化成 5000 个 `author_id`，再扫 `create_time` 索引逐行过滤；也可能走 `author_id` 索引做 index merge。两种都不理想。正确做法是建 `(author_id, create_time, id)` 复合索引，并把 `IN` 改写成 JOIN，让优化器按作者做范围扫描后归并；最终仍要 `EXPLAIN` 验证，不能靠猜。

## Q18 ⭐. 你的方案到底消除了深分页，还是把深分页转化成了基于游标的范围查询？冷数据最坏会扫描多少记录？

**一句话要点**
是**转化**，不是消除：把 O(offset) 的「扫描并丢弃」换成 O(log N + limit) 的索引 seek。代价是失去随机跳页；冷区最坏扫描量约等于「返回行数 + 索引定位」，但如果执行计划没走对索引（OR 条件、关注流 IN 子查询），最坏会退化成大范围扫描 + filesort。

**展开**

1. **消除的是什么**：offset 的**深度相关性**。第 1 页和第 1000 页都是「索引 seek 到游标 → 顺序取 limit+1 行」，代价与页码无关。
2. **没有消除的是什么**：
   - 仍然是分页，只是换成了 keyset；
   - 不支持跳页；
   - 每页仍然要访问存储（Redis 或 MySQL），不是「一次算完」。
3. **冷区成本拆解**（理想执行计划）：
   - 索引定位：B+ 树高度，通常 3~4 次页访问；
   - 顺序扫描 `limit+1` 条索引项（≤ 51，多出的一条只用于 `has_more`）；
   - 回表 `limit+1` 次取整行；
   - 总共 O(log N + limit)，与 offset 无关。
4. **最坏情况**（必须主动说）：
   - `OR` 条件没被优化成单段 range → 可能退化为范围扫描 + filesort；
   - 关注流 `author_id IN (5000 个)` → 扫描量与关注数、作者活跃度相关，可能远大于 limit；
   - 索引选择性差（比如大量同 `create_time`）→ 同毫秒内仍要按 id 过滤，但最多多取一个同分组合；
   - 冷区没有额外过滤条件，所以不会出现「扫很多行才凑够一页」——除非执行计划错了。
5. **热区成本**：
   - `ZRANGE 0 0` 取 watermark：O(log N)；
   - `ZCOUNT` 同分条数：O(log N)；
   - `ZREVRANGEBYSCORE`：O(log N + M)，M = limit + 同毫秒条数；
   - 应用层排序：O(k log k)，k ≤ M；
   - 加上 `GetVideoByIDs` 的 MGET 和点赞批量查询。
6. **一句话收尾**：**深分页的「深度」被消掉了，但「分页」还在；换来的是稳定的单页延迟和翻页一致性，代价是随机访问能力。**

**代码依据**
- 冷区范围查询：`feed/repo.go:29-46`。
- 热区取数：`feed/service.go:499`。
- 水位线：`feed/service.go:373`。
- `has_more` 探测：`feed/service.go:384`、`:469-472`。

**可能的追问**
> 「那你能给一个具体的扫描行数吗？」
> 冷区理想情况下就是 `limit+1` 行（≤ 51，多出的一条只用于判断 `has_more`）+ 索引定位；关注流在 5000 关注下无法给常数上界，必须用 `EXPLAIN ANALYZE` 实测，并靠 `(author_id, create_time, id)` 索引把上界压到「每作者取 limit 行后归并」。**不要编造数字**，说清楚「哪个查询有常数上界、哪个没有」比报一个假数字更可信。

# 附录 C：如果只记 10 句话

1. 热区是**全局最近 1000 条**，不是每个用户一份；容量常量三处共用。
2. score 是 `create_time` 毫秒，member 是 `video_id`，重复写是幂等覆盖。
3. 同分 Redis 按字典序排，**必须应用层按 `(score,id)` 重排**。
4. 游标是 `(时间, id)`，只给时间会漏同毫秒。
5. 写入和裁剪用一段 **Lua 原子执行**；边界判断「游标 ≤ watermark 走冷区」，因为裁剪会切断最小分数组。
6. 热区不足用最后一条的复合游标向下补**一次**；冷区是 MySQL 超集且无后置过滤，所以不用循环。
7. `has_more` 用 **`limit+1` 探测**，不是「本页满没满」；冷区失败直接报错，不伪装成到底。
8. 「不重不漏」的前提是排序键不变 + 只在头部追加；删除/取关只保证不重复。
9. 空 ZSET 用 singleflight 重建 1000 条；非空但少几条靠 **5 分钟对账只补不删**。
10. 关注流是读扩散，5000 关注是它的最坏输入；缓存只存 ID，首页 30s、后续页 24h。
