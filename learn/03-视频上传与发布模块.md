# 视频上传与发布模块

> 对应源码：`backend/internal/video/` 下的 `video_handler.go`、`video_service.go`、`chunk_handler.go`、`chunk_entity.go`、`video_entity.go`、`video_repo.go`
> 前端对应：`frontend/src/views/VideoView.vue`、`frontend/src/api/video.ts`
> 路由注册：`backend/internal/http/router.go` L30、L70-L85

---

## 一、模块解决什么问题

用户要把本地 mp4 发到平台上。看似简单的一句话，拆开后有四个工程问题：

1. 大文件（最大 200MB）通过 HTTP 一次性传输不可靠 —— **需要分片**
2. 传输中途失败不能要求用户从头再来 —— **需要断点续传**
3. 文件传完和用户填完标题简介之间存在时间差 —— **上传和发布必须分离**
4. 发布成功后还要触发 feed 推送等异步动作，且不允许"视频已发但推送丢了" —— **需要 Outbox 模式**

本模块就是这四个问题的完整答案。

## 二、整体架构：7 个接口，两条路径

| # | 路径 | 含义 | 分组 |
|---|------|------|------|
| 1 | `POST /video/chunk/init` | 创建/恢复上传会话 | 分片路径 |
| 2 | `POST /video/chunk/upload` | 上传一个分片 | 分片路径 |
| 3 | `POST /video/chunk/status` | 查询已传分片 | 分片路径 |
| 4 | `POST /video/chunk/complete` | 合并分片，返回 URL | 分片路径 |
| 5 | `POST /video/uploadVideo` | 一次性整体上传（备用） | 单次路径 |
| 6 | `POST /video/uploadCover` | 上传封面图 | 单次路径 |
| 7 | `POST /video/publish` | 写入 videos 表，触发发布 | 发布 |

外加一行静态目录映射：

```go
r.Static("/static", "./.run/uploads")
```

**两组上传路径互斥**：前端实际用分片路径（1-4），单次上传（5）是同限 200MB 的备用方案。

## 三、业务路径：一次上传的完整 6 步

### 步骤 1：前端预处理（无网络请求）

```javascript
const CHUNK_SIZE = 5 << 20                        // 5MB
const totalChunks = Math.ceil(file.size / CHUNK_SIZE)
const fileHash = await computeFileMD5(file)        // SparkMD5 流式算整文件 MD5
```

- `CHUNK_SIZE`：每片固定 5MB，与后端 `chunk_entity.go` 的 `ChunkSize = 5 << 20` 对齐
- `fileHash`：整文件 MD5，作为**文件内容的唯一身份证**，用于秒传和断点续传识别

### 步骤 2：init —— 建会话

请求：

```json
{
  "filename": "cat.mp4",
  "file_size": 12582912,
  "chunk_size": 5242880,
  "total_chunks": 3,
  "file_hash": "a1b2c3..."
}
```

后端 `InitChunkUpload` 逻辑：

```
用 (accountID, fileHash) 查 Redis
├── 命中 → 返回旧 upload_id + 已传分片列表（断点续传入口）
└── 未命中 → 生成新 uploadID，ChunkUploadSession 序列化存 Redis（TTL 24h）
             同时写 hash → uploadID 反向映射
```

**产物**：Redis 里多了一份上传进度表。磁盘上什么都没有。

### 步骤 3：upload × N —— 并发传片

前端对每一片：

```javascript
const blob = file.slice(start, end)   // 切字节，不落盘
const chunkHash = md5(blob)            // 单片单独算 MD5
uploadChunk(upload_id, chunk_index, chunkHash, blob)
```

后端 `UploadChunk` 对每一片做四道处理（顺序关键）：

1. **归属校验**：`session.AccountID == 当前 JWT 用户`，防越权
2. **长度校验**：该下标的期望长度（`ExpectedChunkSize`），最后一片可短，其余必须等于 `chunk_size`
3. **幂等短路**：位图第 idx 位为 1 **且**磁盘分片大小对得上 → 直接 200；位为 1 但文件没了 → 清位重收（自愈）
4. **MD5 校验**：服务端重算字节 MD5 与 `chunkHash` 比对，防传输损坏
5. **落临时目录**：先写 `{idx}.part` 再原子 `rename` 成 `.run/uploads/tmp/{uploadID}/{idx}`，避免合并时读到半片
6. **原子置位**：`SETBIT chunk_upload_bits:{uploadID} idx 1`（与 `PEXPIRE` 同一次 pipeline），并发传片不会互相覆盖

**产物**：临时目录里逐个出现 `0`、`1`、`2`…，Redis 位图逐渐变全 1。

### 步骤 4：complete —— 合并

请求只带 `upload_id`。后端 `CompleteChunkUpload`：

1. 命中 `chunk_upload_result:{uploadID}` → 直接回放上次 URL（重复 complete 幂等）
2. `SETNX` 抢合并锁，抢不到返回 409（防止两个并发 complete 各拼一份）
3. `BITCOUNT` 检查位图全 1，否则 400 报缺几片
4. 创建最终文件 `.run/uploads/videos/{authorID}/{date}/{randHex16}.mp4`
5. **按 0 → N-1 顺序**逐片 `io.Copy` 拼入，同时用 `MultiWriter` 流式算整文件 MD5
6. 任一片缺失/长度不符 → 删半成品文件，返回 500；**整文件 MD5 ≠ init 的 file_hash → 删文件返回 400**
7. 成功后：删临时目录 → 写结果缓存 → 清位图/会话/hash 映射
8. 返回 `play_url = http://{host}/static/videos/{uid}/{date}/{rand}.mp4`

**产物**：完整 mp4 在磁盘上，URL 已可访问。**但 MySQL 里还一行都没有。**

### 步骤 5：用户填元数据

前端展示表单：标题、简介、封面（封面走 `/video/uploadCover` 得到 `cover_url`）。这一步耗时不可控，这正是上传/发布分离的根本原因。

### 步骤 6：publish —— 事务写库

请求：

```json
{
  "title": "猫",
  "description": "",
  "play_url": "http://localhost:8080/static/videos/3/20261021/9e7d.mp4",
  "cover_url": "http://localhost:8080/static/covers/3/20261021/4b2a.jpg"
}
```

后端 `PublishVideo` → `service.Publish`，**一个事务**写三类数据：

```go
tx.Create(video)                                    // ① videos 表主行
tx.Create(&OutboxMsg{EventType: "video_published"}) // ② outbox_msgs 事件
FirstOrCreate(tag) + Create(VideoTag{...})          // ③ tags + video_tags
```

`author_id` 和 `username` **从 JWT 取，不信前端**。

后续 Worker 进程轮询 `outbox_msgs`，把事件推到 RabbitMQ，触发 feed 推送、热度初始化等异步动作。

## 四、文件字节的存储位置（随时间变化）

| 阶段 | 字节位置 | 会话状态位置 |
|------|----------|--------------|
| 上传前 | 用户本地 | 无 |
| init 后 | 用户本地 | Redis（空 bitset） |
| 逐片上传中 | `.run/uploads/tmp/{uploadID}/{idx}` | Redis（部分 bitset） |
| complete 后 | `.run/uploads/videos/{uid}/{date}/{rand}.mp4` | Redis 已清 |
| publish 后 | 同上（**不动文件**） | MySQL `videos.play_url` 只存 URL 字符串 |

目录结构：

```
.run/uploads/
├── tmp/{uploadID}/        ← 半成品区：未完成会话，失败/超时留孤儿，靠 TTL 兜底
├── videos/{uid}/{date}/   ← 成品视频
└── covers/{uid}/{date}/   ← 成品封面
```

**核心原则**：文件存磁盘，数据库存 URL 字符串，二者通过 `r.Static` 映射松耦合。换域名/换 CDN 只需改 URL 字段，文件不用动。

## 五、核心数据结构

### ChunkUploadSession（Redis 内部，不对外暴露）

```go
type ChunkUploadSession struct {
    UploadID    string  // 本次上传行为 ID
    AccountID   uint    // 上传者，越权校验用
    Filename    string  // 原始文件名（合并时未实际使用）
    FileSize    int64   // 总字节数
    ChunkSize   int64   // 单片字节数
    TotalChunks int     // 总片数
    FileHash    string  // 整文件 MD5，续传索引 + 合并后校验
}
```

进度**不在**这个结构体里，而在独立的 Redis 位图（原因见 `04-分片上传与断点续传.md`）。

四个 Redis key：

- `chunk_upload:{upload_id}` → session JSON（元数据，TTL 24h）
- `chunk_upload_bits:{upload_id}` → **进度位图**，bit i = 第 i 片已上传（`SETBIT`/`GETBIT`/`BITCOUNT`）
- `chunk_upload_hash:{accountID}:{fileHash}` → uploadID 字符串（断点续传查找入口）
- `chunk_upload_result:{upload_id}` → 合并结果 URL（TTL 1h，让重复 complete 幂等）
- `chunk_upload_lock:{upload_id}` → 合并互斥锁（SETNX，TTL 10min）

### Video（MySQL 表）

```go
type Video struct {
    ID          uint      // 主键，发布后才存在
    AuthorID    uint      // 从 JWT 取
    Username    string    // 从 JWT 取
    Title       string    // 必填
    Description string    // 选填
    PlayURL     string    // chunk/complete 返回的 URL
    CoverURL    string    // uploadCover 返回的 URL
    CreateTime  time.Time
    LikesCount  int64     // 初始 0，同步精确更新
    Popularity  int64     // 初始 0，异步更新（排序信号）
}
```

### OutboxMsg（MySQL 表，Outbox 模式载体）

```go
type OutboxMsg struct {
    ID         uint
    VideoID    uint
    EventType  string    // "video_published"
    CreateTime time.Time
    Status     string    // "pending" → Worker 消费后改状态
}
```

## 六、六个有价值的技术点

### 1. 为什么必须分片

单次 HTTP 传 200MB 的硬伤：

- 单连接单流，传到 90% 断网 → 全部重来
- 服务端无进度记忆 → 无法断点续传
- 单连接 TCP 拥塞控制 → 带宽利用率低
- 中间层（Nginx/Gin）body size 限制 → 大请求易被砍

**分片本质**：把一个不可靠的大传输拆成 N 个可独立重试的小传输。代价是服务端要维护"已收哪些片"的状态 —— Redis 会话存在的理由。

### 2. 断点续传怎么实现

两个机制叠加：

- `fileHash` 作文件身份证：同一文件 MD5 永远相同，`(accountID, fileHash) → uploadID` 映射让"再选同一文件"直接命中旧会话
- Redis 位图作进度：init 返回已传分片列表，前端跳过已传片（位图允许任意空洞，补传顺序无关）

效果：传到一半刷新、关浏览器、隔天再传（24h 内），都能从断点继续。

### 3. 单片幂等 + 两级 MD5 校验

- **幂等**：位图第 idx 位为 1 且磁盘分片大小正确 → 短路返回 200（位为 1 但文件没了会清位重收）
- **单片校验**：服务端重算字节 MD5 与前端传的 `chunkHash` 比对，防单片坏字节
- **整文件校验**：合并时流式算整文件 MD5，与 init 声明的 `file_hash` 比对，防「每片都对、拼起来不对」

**没有幂等，重试产生脏数据；没有校验，重试可能写入坏字节。** 这两道是"分片可重试"成立的前提。

### 4. 上传/发布两段式分离

```
[请求1] chunk/complete  → 只落盘，返回 URL（数据库零写入）
[请求2] /video/publish  → URL + 元数据一起事务化写库
```

为什么不合一？发布需要 title/cover_url 等业务字段，用户通常在文件传完后才填。合一会导致：

- 用户填表期间文件字节挂内存（不可接受），或
- 接口既要处理字节又要处理表单（语义混乱）

拆开让**文件传输与业务写入解耦**：文件可传多次，发布只发生一次；传完放弃发布，磁盘留孤儿文件，但数据库始终干净。

### 5. 事务 + Outbox 保证一致性

`service.Publish` 用**本地事务**同时写 `videos` 和 `outbox_msgs`：

- 不允许"videos 提交成功但 outbox 写失败"——否则用户能看到视频但 feed 永远推不出去
- 不用"先写库再发 MQ"的分布式方案——RabbitMQ 不可用时发布会失败，违反项目"MQ 故障不影响主流程"的降级硬约束

**本地事务 + Outbox 表 = 用数据库 ACID 替代分布式事务。**

### 6. 会话状态为什么放 Redis 而不是 MySQL

`ChunkUploadSession` 的三个特征：

- **临时性**：24h 后无论完成与否都该清理，Redis TTL 天然契合
- **高频写**：每传一片更新 bitset，MySQL 行级写代价高
- **非业务数据**：丢失最大代价是"重新传"，不影响业务一致性

代价：Redis 不可用时整个分片上传 503。这是项目"API 进程对 Redis 降级"的例外——**分片本身没有 Redis 就无法工作**，降级退化为单次上传接口仍可用。

## 七、易混淆概念对照

| 混淆点 | 区别 |
|--------|------|
| `upload_id` vs `file_hash` | 前者 = **这次上传行为**的 ID（每次新会话不同）；后者 = **文件内容**的 ID（同一文件永远相同）。断点续传靠 file_hash 找回 upload_id |
| `chunk_index` vs `total_chunks` | index 是序号（0 起），total 是总数。index 最大值 = total - 1 |
| `file_size` vs `chunk_size` | 文件总字节 vs 单片字节。关系：`total_chunks = ceil(file_size / chunk_size)` |
| `chunk_hash` vs `file_hash` | 前者校验**单片**传输完整性，后者标识**整个文件**身份。粒度不同 |
| 位图 vs `uploaded_chunks` | 位图是 Redis 里的 `chunk_upload_bits:{id}`（内部，bit i 表示第 i 片），`uploaded_chunks` 是接口返回的 `[]int`（对外），由 `uploadedIndices()` 从位图解码 |
| `url` vs `play_url`/`cover_url` | **同一字符串的两个别名**。`url` 是通用名，`play_url`/`cover_url` 是业务字段名，publish 只认后者 |

## 八、动手验证清单

前置：MySQL（3307）、**Redis 必须启动**（chunk 接口依赖，否则 503）、后端 API（8080）、前端（5173）。

1. 登录 → 上传页选一个 30MB+ 的 mp4（能切出多片）
2. 上传中并行观察：

   | 观察点 | 期望现象 |
   |--------|----------|
   | `.run/uploads/tmp/{uploadID}/` | 逐个出现 `0`、`1`、`2`… 临时分片 |
   | `.run/uploads/videos/{uid}/{date}/` | complete 后出现 `{rand}.mp4`，tmp 目录同时被清空 |
   | MySQL `videos` 表 | **只有 publish 后**才出现新行 |
   | MySQL `outbox_msgs` 表 | 多一行 `event_type=video_published, status=pending` |

3. **断点续传实测**：传到一半刷新页面 → 重选同一文件 → init 命中旧会话，跳过已传片
4. **对比实验**：临时改用 `/video/uploadVideo` 单次上传，断网后整个文件必须重传 —— 反向证明分片的必要性

## 九、一句话总结

**业务路径**：算 hash → 建会话 → 并发传片 → 合并落盘 → 填表发布 → 事务写库。

**核心技术**：分片把大传输变小 + Redis bitset 记进度 + fileHash 支持断点 + 单片幂等校验 + 上传发布两段式 + 事务 Outbox 保证一致性。
